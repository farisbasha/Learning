# 2.6 — Records

> **What this is:** The feature that removed the single most tedious thing about Java.
> **Learn it early; use it constantly.**

---

## Coming from JS/Python/Dart

| Language | Equivalent |
|---|---|
| Python | `@dataclass(frozen=True)` |
| TypeScript | A `readonly` interface / type |
| Dart | A `final` class with an unnamed constructor, or Dart 3 records |

The behaviour is the same idea: *this type is nothing but its data, and it defines
equality by that data.*

## The concepts

### The one-line version

```java
public record Point(int x, int y) { }
```

That single line generates **all** of this:

```java
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public int x() { return x; }
    public int y() { return y; }

    @Override public boolean equals(Object o) { /* compares x and y */ }
    @Override public int hashCode()           { /* Objects.hash(x, y) */ }
    @Override public String toString()        { return "Point[x=" + x + ", y=" + y + "]"; }
}
```

Every one of those is generated **correctly**, which means you cannot get the
`equals`/`hashCode` contract wrong (2.5).

### The shape it replaces

Here's the 2004 version of the same thing, written out in full so you can see what's gone:

```java
public class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public int getX() { return x; }
    public int getY() { return y; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Point point = (Point) o;
        return x == point.x && y == point.y;
    }

    @Override
    public int hashCode() { return Objects.hash(x, y); }

    @Override
    public String toString() { return "Point{x=" + x + ", y=" + y + '}'; }
}
```

**Thirty lines, of which one carries information.** Multiply that across every DTO,
every API response type, every value object in a codebase — that's why "Java is verbose"
became a cliché, and why records changed the feel of the language.

### Accessors are `x()`, not `getX()`

```java
var p = new Point(1, 2);
p.x();          // ✅
p.getX();       // ❌ does not exist
```

This is the modern convention (2.1). Some older frameworks expecting JavaBeans
`getX()` need configuration to work with records — Jackson, for example, handles records
natively since 2.12.

### The three kinds of constructor

**1. Canonical** — generated for you, takes every component. You get it free.

**2. Compact** — validate or normalise, without restating the assignments:

```java
public record Range(int start, int end) {
    public Range {                          // no parameter list, no body braces for assignment
        if (start > end)
            throw new IllegalArgumentException("start must be <= end");
    }
}
```

The compiler appends `this.start = start; this.end = end;` after your code. You can also
**reassign the parameters** to normalise:

```java
public record User(String name, String email) {
    public User {
        Objects.requireNonNull(name);
        email = email.toLowerCase().strip();      // normalise — assigns to the field
    }
}
```

> This is the idiomatic place for validation. A record built this way **cannot exist in
> an invalid state**, anywhere in the program.

**3. Alternative** — extra constructors, which must delegate to the canonical one:

```java
public record Point(int x, int y) {
    public Point(int both) {
        this(both, both);          // must call the canonical constructor
    }
}
```

### Records are implicitly `final`, and their components are `final`

```java
record Point(int x, int y) { }
class Point3D extends Point { }      // ❌ cannot inherit from a record
```

Why: as you saw in 2.5, *you cannot extend an instantiable class with a new value
component and preserve the `equals` contract*. The language removed the possibility.

Records **can** implement interfaces, which is how you compose them:

```java
record Point(int x, int y) implements Comparable<Point> {
    @Override public int compareTo(Point o) { return Integer.compare(x, o.x); }
}
```

### ⚠️ Shallow immutability, and its limit

```java
record Team(String name, List<String> members) { }

var list = new ArrayList<>(List.of("a", "b"));
var team = new Team("Devs", list);

list.add("c");                  // 💥 mutating the original list...
IO.println(team.members());     // [a, b, c] ← ...changed the "immutable" record
```

The **reference** is final. The object it points at is not (same as `final` fields, 2.1).

**Fix — defensively copy in the compact constructor:**

```java
record Team(String name, List<String> members) {
    Team {
        members = List.copyOf(members);     // immutable snapshot
    }
}
```

Now the record is genuinely immutable. `List.copyOf` also rejects `null` elements, and
returns the same instance if the input is already immutable, so it's cheap.

> **Rule: if a record component is a mutable type (`List`, `Map`, `Date`, an array),
> copy it in the compact constructor.** Otherwise your record is immutable in name only.

### Static members, instance methods, interfaces

Records are normal classes. They can have all of this:

```java
public record Money(BigDecimal amount, String currency) implements Comparable<Money> {

    public static final Money ZERO = new Money(BigDecimal.ZERO, "USD");   // static field

    Money {                                                               // validation
        Objects.requireNonNull(currency);
        if (amount.scale() > 2) throw new IllegalArgumentException();
    }

    public static Money usd(String amount) {                              // static factory
        return new Money(new BigDecimal(amount), "USD");
    }

    public Money plus(Money other) {                                      // instance method
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(amount.add(other.amount), currency);             // returns a NEW one
    }

    @Override public int compareTo(Money o) { return amount.compareTo(o.amount); }
}
```

Note `plus()` returns a **new** `Money` rather than mutating — that's how you write
behaviour on an immutable type.

What records **cannot** have: additional instance fields. Only the components declared
in the header.

```java
record Point(int x, int y) {
    private int cached;      // ❌ compile error
    static int counter;      // ✅ static is fine
}
```

### ⭐ When *not* to use a record

| Don't use a record when | Because |
|---|---|
| **Identity matters** | Two users with the same email are still two rows. Records define equality by content |
| **Fields must change** | Records are immutable. A JPA entity, a mutable builder |
| **The class is behaviour, not data** | A `PaymentProcessor` has no meaningful "components" |
| **You need inheritance** | Records are `final` |

```java
// ❌ wrong — an entity with a lifecycle and a database identity
record User(Long id, String name, String email) { }

// ✅ right — a value you pass around
record UserDto(String name, String email) { }
record Coordinates(double lat, double lon) { }
record ApiResponse(int status, String body) { }
```

> **The test is the value-vs-identity question from 2.5:** *if two of these have
> identical fields, are they the same thing?*

### Local records

Declared inside a method — useful for a temporary grouping in a stream pipeline:

```java
void report(List<Order> orders) {
    record OrderSummary(String customer, BigDecimal total) { }   // local to this method

    orders.stream()
        .map(o -> new OrderSummary(o.customer(), o.total()))
        .sorted(Comparator.comparing(OrderSummary::total).reversed())
        .forEach(s -> IO.println(s.customer() + ": " + s.total()));
}
```

Before records, this meant either a throwaway top-level class or an `Object[]`. Local
records make short-lived intermediate types free.

### Records set up Part 07

Records and **record patterns** were designed as one feature. A quick preview:

```java
sealed interface Shape permits Circle, Rectangle { }
record Circle(double radius) implements Shape { }
record Rectangle(double w, double h) implements Shape { }

double area = switch (shape) {
    case Circle(double r)          -> Math.PI * r * r;     // destructures!
    case Rectangle(double w, double h) -> w * h;
};                                                          // exhaustive — no default
```

`case Circle(double r)` pulls the component straight out. Combined with sealed types
(2.8) the compiler proves you covered every case. That combination — **sealed +
records + switch** — is the modern Java style, and it's what Part 07 is about.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `p.getX()` | Accessors are `p.x()` |
| A record with a `List` component is immutable | Only if you `List.copyOf` in the compact constructor |
| Using a record for a JPA entity | Needs a no-arg constructor and mutability. Won't work |
| Expecting to extend a record | They're `final` |
| Adding an instance field | Only components are allowed |

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Hand-written data classes | `record` |
| Lombok `@Data` / `@Value` for value types | `record` — built in, no annotation processor |
| `Object[]` or `Map<String,Object>` as an ad-hoc tuple | A record, possibly a local one |

---

## Recap

| Concept | One line |
|---|---|
| One line | Generates fields, constructor, accessors, `equals`, `hashCode`, `toString` |
| Compact constructor | Where validation and normalisation go |
| Implicitly `final` | Because inheritance + `equals` cannot compose (2.5) |
| Shallow immutability | Copy mutable components with `List.copyOf` |
| Can have | Static members, instance methods, interfaces |
| Cannot have | Extra instance fields, subclasses |
| Not for | Entities, mutable state, behaviour-first classes |
