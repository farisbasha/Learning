# 2.4 — Interfaces, in their modern form

> **What this is:** Interfaces changed substantially in Java 8 and 9. **Most explanations
> you'll find online describe the 2005 version** — "an interface is just method
> signatures with no code" — which has been wrong for over a decade.

---

## Coming from JS/Python/Dart

- TypeScript `interface` — closest, but TS interfaces are erased and structural. Java's
  are **nominal** (you must declare `implements`) and exist at runtime.
- Python ABCs / protocols — similar intent.
- Dart — every class is implicitly an interface; Java requires the keyword.

---

## The concepts

### Interfaces as contracts

```java
public interface Payable {
    double amount();                      // implicitly public abstract
}

public class Invoice implements Payable {
    private final double total;
    Invoice(double total) { this.total = total; }

    @Override public double amount() { return total; }
}
```

A class can **implement many** interfaces (unlike `extends`, which allows one):

```java
class Invoice implements Payable, Comparable<Invoice>, Serializable { }
```

An interface can **extend many** interfaces:

```java
interface ReadWrite extends Readable, Writable { }
```

> This is Java's answer to multiple inheritance: multiple inheritance of **type and
> behaviour**, but never of **state**. Interfaces cannot have instance fields, which is
> what avoids Python's MRO complexity.

### Default methods `Java 8` — and why they exist

```java
public interface Greeter {
    String name();

    default String greet() {              // has a BODY
        return "Hello, " + name();
    }
}
```

**Why they were added:** in Java 8, the JDK team wanted to add `stream()`, `forEach()`
and `removeIf()` to `Collection`. But `Collection` is an interface, and every
implementation in the world — including thousands outside the JDK — would instantly
stop compiling.

Default methods let an interface grow without breaking implementors. `Collection.stream()`
is a default method. So is `Iterable.forEach()`, `List.sort()`, `Comparator.reversed()`,
and `Map.getOrDefault()`.

> **The framing: default methods are an API evolution tool, not a substitute for
> abstract classes.** They still can't hold state.

**The diamond rules** — when two interfaces provide the same default:

```java
interface A { default String hi() { return "A"; } }
interface B { default String hi() { return "B"; } }

class C implements A, B { }              // ❌ compile error — ambiguous
```

You must resolve it explicitly:

```java
class C implements A, B {
    @Override public String hi() {
        return A.super.hi();              // pick one — note the A.super syntax
    }
}
```

The full resolution order, if you ever need it:
1. **A class wins over an interface.** A concrete method in a superclass beats any default.
2. **The most specific interface wins.** If `B extends A`, `B`'s default beats `A`'s.
3. **Otherwise, ambiguous** — you must override.

### Static methods in interfaces `Java 8`

```java
public interface Validator {
    boolean test(String s);

    static Validator notEmpty() {                    // factory, lives on the interface
        return s -> s != null && !s.isEmpty();
    }
}

Validator v = Validator.notEmpty();
```

Before Java 8, these factories had to live in a separate `Validators` companion class —
which is why the JDK has `Collections` next to `Collection` and `Arrays` next to arrays.
Modern interfaces put their factories on themselves: `List.of`, `Comparator.comparing`,
`Map.entry`.

Static interface methods are **not inherited** by implementing classes. `Validator.notEmpty()`
works; `someValidator.notEmpty()` does not.

### Private methods in interfaces `Java 9`

Once defaults could have bodies, those bodies started duplicating code. Java 9 allowed
private helpers:

```java
public interface Report {
    List<Item> items();

    default double total()    { return sum(items()); }
    default double average()  { return sum(items()) / items().size(); }

    private double sum(List<Item> items) {           // shared, not part of the API
        return items.stream().mapToDouble(Item::price).sum();
    }
}
```

### Constant fields, and the "constant interface" anti-pattern

Every field in an interface is implicitly `public static final`:

```java
interface Config {
    int MAX = 100;        // actually: public static final int MAX = 100;
}
```

```java
// 💀 THE CONSTANT INTERFACE ANTI-PATTERN
interface Constants {
    String API_URL = "...";
    int TIMEOUT = 30;
}
class Service implements Constants { }   // now Service "is-a" bag of constants
```

**Why it's wrong:** `implements` is a statement about your *type*, visible in your public
API. Implementing `Constants` tells the world that `Service` is a `Constants`, which is
meaningless. It also leaks those names into every subclass forever.

```java
// ✅ instead
public final class Constants {
    private Constants() { }
    public static final String API_URL = "...";
    public static final int TIMEOUT = 30;
}
```

Or better still, an `enum` (2.7) or a `record` holding configuration.

### Functional interfaces — the bridge into Part 06

An interface with **exactly one abstract method** is a *functional interface*, and can
be written as a lambda.

```java
@FunctionalInterface
interface Transformer {
    String apply(String input);          // exactly ONE abstract method
    // default and static methods don't count
}

Transformer upper = s -> s.toUpperCase();         // lambda
Transformer upper2 = String::toUpperCase;          // method reference
IO.println(upper.apply("hi"));                     // HI
```

`@FunctionalInterface` is optional but useful — it makes the compiler reject the
interface if someone adds a second abstract method.

The JDK ships a catalogue of these — `Function`, `Predicate`, `Supplier`, `Consumer` —
covered in 6.3. `Runnable`, `Comparator` and `Callable` were retro-fitted as functional
interfaces in Java 8, which is why `new Thread(() -> ...)` works.

### ⭐ Interface vs abstract class — the actual decision now

Both can have code now, so the old "interface = no code" rule is useless. The real
criteria:

| Use an **interface** when | Use an **abstract class** when |
|---|---|
| You need **state** ❌ | You need **fields** / constructor logic ✅ |
| Implementors may already extend something | You control the whole hierarchy |
| You want many unrelated types to fit | The subtypes are genuinely one family |
| You want lambdas to work | — |
| You're defining a capability (`Comparable`, `AutoCloseable`) | You're sharing real implementation |

> **Default answer: interface.** Reach for an abstract class only when you need
> **instance state** or **constructor logic** — those are the two things interfaces
> genuinely cannot do.

The JDK often does both: `List` (interface) + `AbstractList` (skeletal implementation
you can extend if you want the boilerplate for free).

### Programming to an interface

```java
// ❌ the field's type is an implementation
private ArrayList<String> names = new ArrayList<>();
public void process(ArrayList<String> input) { }

// ✅ declare the interface, instantiate the implementation
private List<String> names = new ArrayList<>();
public void process(List<String> input) { }
```

> **The rule: your fields, parameters and return types say `List`; your constructors
> say `ArrayList`.**

Why it matters: with `List`, a caller can pass `List.of(...)`, a `LinkedList`, or
`Collections.unmodifiableList(...)`. With `ArrayList`, they can pass exactly one thing,
and you can never change your internal choice without breaking every caller.

Same rule for `Map`/`HashMap`, `Set`/`HashSet`.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "Interfaces have no code" | Wrong since Java 8 |
| Two interfaces, same default | Compile error. Resolve with `A.super.method()` |
| Static interface methods are inherited | They're not |
| Interface fields are variables | They're implicitly `public static final` |
| `implements Constants` | Anti-pattern — pollutes your type |
| Declaring `ArrayList` as a field type | Use `List` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Constant interfaces | A `final` class with a private constructor, or an enum |
| "Interface = signatures only" as a mental model | Interfaces have defaults, statics and privates |
| Companion classes for factories | Static methods on the interface itself |

---

## Recap

| Concept | Version | One line |
|---|---|---|
| Multiple implementation | — | Many interfaces, one superclass |
| `default` methods | `Java 8` | Let interfaces grow without breaking implementors |
| `static` methods | `Java 8` | Factories on the interface itself |
| `private` methods | `Java 9` | Shared helpers for defaults |
| Functional interface | `Java 8` | One abstract method → lambda-compatible |
| Interface vs abstract | — | Abstract class only for **state** and **constructor logic** |
