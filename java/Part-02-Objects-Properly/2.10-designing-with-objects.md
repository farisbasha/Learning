> not a law.

## ⭐ 1. Immutability by default

### How to build a genuinely immutable class

Five requirements:

1. Make the class `final` (or use a `record`) — so nobody subclasses it and adds mutation
2. Make every field `private final`
3. No setters, no methods that change state
4. **Defensively copy mutable inputs** in the constructor
5. **Defensively copy mutable outputs** in getters

```java
// ❌ looks immutable, isn't
public final class Team {
    private final String name;
    private final List<String> members;

    public Team(String name, List<String> members) {
        this.name = name;
        this.members = members;          // ← stores the CALLER'S list
    }
    public List<String> members() { return members; }   // ← hands it back
}

var list = new ArrayList<>(List.of("a"));
var team = new Team("Devs", list);
list.add("b");                    // 💥 changed the team from outside
team.members().add("c");          // 💥 changed it from the getter
```

```java
// ✅ genuinely immutable
public final class Team {
    private final String name;
    private final List<String> members;

    public Team(String name, List<String> members) {
        this.name = name;
        this.members = List.copyOf(members);      // copy IN
    }
    public List<String> members() { return members; }  // already immutable, safe to share
}
```

`List.copyOf` returns an unmodifiable list, so no copy-on-the-way-out is needed. For a
mutable field type you'd need both directions.

**Same thing as a record** (2.6):

```java
public record Team(String name, List<String> members) {
    public Team {
        members = List.copyOf(members);
    }
}
```

**Watch out for these mutable types** hiding inside "immutable" classes:
`List`, `Map`, `Set`, arrays, `Date`, `Calendar`, `StringBuilder`, and any of your own
mutable classes.

```java
// arrays are always mutable — clone them
public int[] scores() { return scores.clone(); }
```

### What it buys

- **Thread safety for free** — no locks, ever (Part 09)
- **Safe as a hash key** (2.5)
- **No defensive copying by callers** — you can hand it to anyone
- **No "who changed this?" debugging**

> **Default: immutable. Make it mutable only when you have a measured reason.**

## ⭐ 2. Composition over inheritance

You saw *why* in 2.3 (the fragile base class problem). Here's the *technique*.

**Delegation** — hold the thing as a field and forward:

```java
public class RateLimitedClient {
    private final HttpClient client;        // HAS-A
    private final RateLimiter limiter;

    public RateLimitedClient(HttpClient client, RateLimiter limiter) {
        this.client = client;
        this.limiter = limiter;
    }

    public Response send(Request r) {
        limiter.acquire();
        return client.send(r);              // delegate
    }
}
```

**The decision test:**

| Ask | If yes |
|---|---|
| Is a X **truly** a Y, for every Y behaviour, forever? | Maybe inherit |
| Do I only want to *reuse* Y's code? | **Compose** |
| Was Y designed for extension (documented hooks, abstract methods)? | Inherit |
| Is Y a concrete JDK class? | **Compose** |

> **When you do use inheritance, prefer a `sealed` hierarchy** (2.8) — you get the
> polymorphism without the open-ended fragility.

## 3. The builder pattern

**When:** a constructor has too many parameters, or many are optional.

```java
// ❌ the telescoping-constructor problem
new Pizza(12, true, false, true, false, true, "thin");
//         ↑ what is any of this?
```

```java
public final class Pizza {
    private final int size;
    private final boolean cheese, pepperoni, mushrooms;

    private Pizza(Builder b) {                       // private constructor
        this.size = b.size;
        this.cheese = b.cheese;
        this.pepperoni = b.pepperoni;
        this.mushrooms = b.mushrooms;
    }

    public static Builder builder(int size) { return new Builder(size); }

    public static final class Builder {
        private final int size;                      // required
        private boolean cheese, pepperoni, mushrooms; // optional, default false

        private Builder(int size) { this.size = size; }

        public Builder cheese()    { this.cheese = true;    return this; }
        public Builder pepperoni() { this.pepperoni = true; return this; }

        public Pizza build() {
            if (size < 6) throw new IllegalArgumentException("too small");
            return new Pizza(this);
        }
    }
}

var pizza = Pizza.builder(12).cheese().pepperoni().build();
```

**When NOT to:** fewer than ~4 parameters, or when all are required. A record or a plain
constructor is clearer. Builders are boilerplate — only pay for them when the
readability wins.

> Record note: records don't have builders built in, and for 3–4 components they don't
> need one. For a record with 10 components, hand-write a builder or reconsider the design.

## ⭐ 4. Make illegal states unrepresentable

The highest-leverage design idea on this page.

```java
// ❌ this class can represent nonsense
public class Order {
    private String status;            // any string at all
    private String trackingNumber;    // null unless shipped — but nothing enforces that
    private String cancelReason;      // null unless cancelled
}

// "shipped" AND a cancelReason AND no tracking number — all representable
```

```java
// ✅ the illegal combinations cannot be constructed
sealed interface OrderState permits Draft, Placed, Shipped, Cancelled { }
record Draft()                       implements OrderState { }
record Placed(Instant at)            implements OrderState { }
record Shipped(String tracking)      implements OrderState { }   // tracking is REQUIRED here
record Cancelled(String reason)      implements OrderState { }   // and only here
```

Three techniques:

**(a) Constructors that validate** — a record's compact constructor (2.6):
```java
record Percentage(int value) {
    Percentage {
        if (value < 0 || value > 100)
            throw new IllegalArgumentException("0..100, got " + value);
    }
}
```

**(b) Types that constrain** — replace primitives with meaning:
```java
// ❌ nothing stops you swapping these
void transfer(String from, String to, double amount)
transfer(amount, from, to);          // compiles fine 💥

// ✅
void transfer(AccountId from, AccountId to, Money amount)
```
This is the "primitive obsession" fix. `record AccountId(String value) { }` costs one line
and makes an entire category of bug impossible.

**(c) Enums and sealed types** instead of strings and flags (2.7, 2.8).

## 5. Null handling strategies

Four rules, in order of value:

**(a) Never return `null` from a method returning a collection.**
```java
// ❌ forces every caller to null-check
List<Order> findOrders(String id) { return null; }

// ✅
List<Order> findOrders(String id) { return List.of(); }
```
An empty collection behaves correctly in a for-each, a stream, and `.size()`. `null` does not.

**(b) `Optional` at API boundaries — return types only.**
```java
Optional<User> findById(String id);            // ✅ "might not be there" is in the signature
```
```java
// ❌ don't do these
private Optional<String> name;                 // never a field
void f(Optional<String> arg);                  // never a parameter — use an overload
Optional<List<User>> findAll();                // never wrap a collection — return empty
```
Full treatment in 6.7.

**(c) `Objects.requireNonNull` at entry points** — fail fast, at the boundary, with a
useful message:
```java
public Order(Customer customer, List<Item> items) {
    this.customer = Objects.requireNonNull(customer, "customer");
    this.items = List.copyOf(items);           // copyOf also rejects nulls
}
```
An NPE at construction naming the field beats an NPE three hours later in unrelated code.

**(d) Design so `null` never gets in** — immutable objects with validating constructors
mostly achieve this on their own.

## 6. The patterns Java actually uses in its own library

Skip the Gang-of-Four book for now. These six are the ones in the JDK, so you'll meet
them whether you study them or not.

| Pattern | In the JDK | What it is |
|---|---|---|
| **Factory method** | `List.of`, `Optional.of`, `Integer.valueOf` | A named static method instead of `new` (2.2) |
| **Strategy** | `Comparator`, any lambda | Pass behaviour as a parameter |
| **Decorator** | `BufferedReader(new FileReader(f))` | Wrap an object to add behaviour, same interface |
| **Template method** | `AbstractList`, `InputStream` | Base class defines the skeleton, subclass fills the holes |
| **Iterator** | `Iterable`, for-each | Traverse without exposing internals |
| **Observer** | Listeners, `Flow.Subscriber` | Notify interested parties of a change |

Decorator is worth seeing, because it's everywhere in `java.io`:

```java
var reader = new BufferedReader(          // adds buffering
    new InputStreamReader(                 // adds byte→char decoding
        new FileInputStream("data.txt")    // reads bytes
    ));
```

Each wrapper implements the same interface as what it wraps. That's the whole pattern.
(Part 10 covers this stack properly.)

## ⭐ 7. SOLID, honestly

Some of it is load-bearing. Some of it is folklore repeated by people who haven't used it.

| | Verdict |
|---|---|
| **S** — Single Responsibility | ✅ **Load-bearing.** "A class should have one reason to change." The most useful of the five, and the hardest to apply — "responsibility" is genuinely subjective |
| **O** — Open/Closed | ⚠️ **Half.** "Open for extension, closed for modification" was written when inheritance was the only extension mechanism. Today it mostly means "depend on interfaces". Taken literally it produces speculative abstraction |
| **L** — Liskov Substitution | ✅ **Load-bearing, and real.** A subtype must work anywhere its supertype does. Violating it is exactly the `ColorPoint.equals` problem (2.5) and the `CountingList` bug (2.3) |
| **I** — Interface Segregation | ✅ **Mostly true.** Small focused interfaces beat large ones. This is just "don't force implementors to write stubs" |
| **D** — Dependency Inversion | ✅ **Load-bearing.** Depend on abstractions, inject dependencies. This is the thing that makes code testable (2.2) |

**What to actually do:**
- Inject dependencies through the constructor. (D)
- Keep interfaces small. (I)
- Don't break substitutability — prefer composition and `sealed`. (L)
- Split a class when it's genuinely doing two jobs, not because a rule said so. (S)
- **Do not add an interface "in case" there's a second implementation.** YAGNI beats O.

> The most common failure mode isn't ignoring SOLID — it's applying it eagerly and
> producing five interfaces with one implementation each.

## ⭐ 8. Why `Animal extends Dog` taught a generation the wrong instinct

Every Java tutorial opens with:

```java
class Animal { void speak() { } }
class Dog extends Animal { void speak() { IO.println("Woof"); } }
class Cat extends Animal { void speak() { IO.println("Meow"); } }
```

**Why it's a bad first example:**

1. **It's the only situation where inheritance is obviously right** — a real taxonomy
   with no data, no lifecycle, no invariants. Almost no business domain looks like this.
2. **It teaches inheritance as the default tool**, when in real code composition is the
   default and inheritance is the exception.
3. **It has no state**, so it never shows the fragile base class problem, the
   constructor-calls-overridable-method bug, or the `equals` symmetry problem — the three
   things that actually go wrong.
4. **It implies deep hierarchies are natural.** `Animal → Mammal → Dog → Labrador` looks
   tidy in a diagram and is unmaintainable in code.

**What a realistic version looks like:**

```java
// Not "a Dog IS-A Animal" but "a notifier HAS-A channel"
sealed interface Channel permits Email, Sms, Push { }
record Email(String address) implements Channel { }
record Sms(String number)    implements Channel { }
record Push(String deviceId) implements Channel { }

final class Notifier {
    private final Channel channel;                    // composition
    Notifier(Channel channel) { this.channel = channel; }

    void send(String message) {
        switch (channel) {                            // exhaustive (2.8)
            case Email(String addr)  -> sendEmail(addr, message);
            case Sms(String number)  -> sendSms(number, message);
            case Push(String device) -> sendPush(device, message);
        }
    }
}
```

Immutable, composed, exhaustive, no inheritance. That's modern Java, and it looks nothing
like the tutorial.

## The defaults, in one list

1. **Fields `private final`.** Remove `final` only with a reason.
2. **Classes `final`**, or `sealed`. Open them deliberately.
3. **If it's data, make it a `record`.**
4. **If it's a closed set of alternatives, make it `sealed` + records.**
5. **If it's a closed set of values, make it an `enum`.**
6. **Compose. Inherit only when the base class was designed for it.**
7. **Copy mutable inputs and outputs.**
8. **Return empty collections, never `null`. `Optional` for return types only.**
9. **Validate in the constructor. Make illegal states unrepresentable.**
10. **Inject dependencies. No static business logic.**

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "Immutable" class holding a `List` | Copy it in and out |
| Builder for a 3-field class | Boilerplate. Use a record |
| `Optional` as a field or parameter | Only for return types |
| An interface per class "for testability" | YAGNI. Add it when there's a second implementation |
| Applying SOLID as five rules to satisfy | Two are load-bearing, one is half-true |

## Recap

| Principle | One line |
|---|---|
| Immutability | Default. `final` + copy in + copy out |
| Composition | Default. Inheritance is the exception |
| Builder | Only for many/optional parameters |
| Illegal states | Make them unconstructable — validate, and use types |
| Null | Empty collections; `Optional` on returns; `requireNonNull` at entry |
| Patterns | Learn the six the JDK uses |
| SOLID | L and D are real. O is half folklore |
| `Animal/Dog` | Teaches the wrong default |
