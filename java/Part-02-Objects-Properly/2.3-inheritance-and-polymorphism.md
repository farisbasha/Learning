# 2.3 — Inheritance and polymorphism

> **What this is:** The classical mechanism. **Important to understand deeply, and then
> to use sparingly.** Most of this page is about the machinery; the last third is about
> why you should reach for composition instead.

---

## Coming from JS/Python/Dart

- JS has prototypes; Java has real classes with a fixed vtable. Simpler, stricter.
- Python has **multiple** inheritance and MRO. Java has **single** inheritance of
  classes, multiple of interfaces (2.4). Far fewer surprises.
- Dart is closest — `extends` one, `implements` many.

---

## The concepts

### `extends` and `Object`

```java
class Animal { }
class Dog extends Animal { }
```

**One superclass only.** Every class without an explicit `extends` implicitly extends
`Object` — so every object in Java has `toString()`, `equals()`, `hashCode()`,
`getClass()`, `wait()`, `notify()` (2.5).

### `super`

```java
class Dog extends Animal {
    Dog(String name) {
        super(name);              // call the parent constructor — must be first*
    }

    @Override
    void speak() {
        super.speak();            // call the parent's version
        IO.println("Woof");
    }
}
```

\* Relaxed in Java 25 — validation statements may precede it (2.1).

If you don't write `super(...)`, the compiler inserts `super()`. If the parent has no
no-arg constructor, that's a compile error and you must call one explicitly.

### ⭐ Overriding versus overloading

Two mechanisms with confusingly similar names. They are unrelated.

| | **Overriding** | **Overloading** |
|---|---|---|
| Same name | ✅ | ✅ |
| Same parameters | ✅ | ❌ — that's the point |
| Where | Subclass replaces parent's method | Same class, different signature |
| Resolved | **Runtime** (dynamic dispatch) | **Compile time** (1.5) |

```java
class Parent { void f(int x) { } }

class Child extends Parent {
    @Override void f(int x) { }   // OVERRIDE — same signature
    void f(String s) { }          // OVERLOAD — different signature
}
```

**`@Override` is not optional in practice.** It's technically just an annotation, but:

```java
class Parent { void speak() { } }

class Child extends Parent {
    void spaek() { }              // typo — silently creates a NEW method
    @Override void spaek() { }    // ❌ compile error: does not override anything
}
```

It catches typos, and it catches the parent changing its signature out from under you.
**Always write it.**

### ⭐ Dynamic dispatch

```java
Animal a = new Dog();
a.speak();          // "Woof" — Dog's version
```

The variable's **declared** type is `Animal`. The **actual** object is a `Dog`. Java
picks the method based on the actual object, at runtime. That's dynamic dispatch, and
it's the entire point of polymorphism.

**How the JVM does it — the vtable idea:**

Each class has a **virtual method table**: an array of pointers, one slot per method.
A subclass's vtable starts as a copy of its parent's, with overridden slots replaced.

```
Animal vtable:            Dog vtable:
  [0] speak → Animal      [0] speak → Dog        ← replaced
  [1] eat   → Animal      [1] eat   → Animal     ← inherited
                          [2] fetch → Dog        ← added
```

A call becomes: *look at the object's class pointer → read its vtable → jump to slot 0.*
Two memory reads and an indirect jump. Cheap, but not free — and in Part 08 you'll see
the JIT often **devirtualise** this away entirely when only one implementation is loaded.

**What is NOT dispatched dynamically:**

| Kind | Dispatch |
|---|---|
| Instance methods | **Runtime** (dynamic) |
| `static` methods | Compile time — by declared type |
| `private` methods | Compile time — not inherited |
| `final` methods | Compile time — cannot be overridden |
| **Fields** | **Compile time — by declared type** |

That last one catches people:

```java
class Parent { String name = "parent"; }
class Child extends Parent { String name = "child"; }   // HIDES, doesn't override

Parent p = new Child();
IO.println(p.name);          // "parent"  ← field access uses the DECLARED type
IO.println(((Child) p).name); // "child"
```

**Fields are never polymorphic.** Don't shadow fields — it's always a bug.

### Covariant return types

An override may return a **more specific** type:

```java
class Animal {
    Animal reproduce() { return new Animal(); }
}
class Dog extends Animal {
    @Override
    Dog reproduce() { return new Dog(); }    // ✅ Dog IS-A Animal
}
```

Useful for builders and `clone()`.

### You cannot override a static method — you hide it

```java
class Parent { static void f() { IO.println("Parent"); } }
class Child extends Parent { static void f() { IO.println("Child"); } }

Parent p = new Child();
p.f();          // "Parent" ← resolved by DECLARED type. This is "hiding", not overriding
```

`@Override` on a static method is a compile error, which is how you find out.

### `abstract`

```java
abstract class Shape {
    abstract double area();                 // no body — subclasses must implement

    void describe() {                       // concrete method — shared
        IO.println("Area: " + area());
    }
}

class Circle extends Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

new Shape();   // ❌ compile error — cannot instantiate an abstract class
```

An abstract class is a partial implementation: some behaviour shared, some left to
subclasses.

### `final`

```java
final class Money { }                // cannot be extended
class Account {
    final void close() { }           // cannot be overridden
}
```

`final` on a class or method **seals a design deliberately**. `String`, `Integer` and all
the wrappers are final — nobody can subclass `String` and break the assumptions the
entire standard library makes about it.

> **Related but different:** `sealed` (2.8) says "only *these specific* classes may
> extend me", which is a middle ground between open and `final`.

## ⭐ The fragile base class problem

This is why the advice is "use inheritance sparingly".

```java
// A helpful-looking subclass of HashSet
class CountingSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int addCount() { return addCount; }
}

var set = new CountingSet<String>();
set.addAll(List.of("a", "b", "c"));
IO.println(set.addCount());     // 6, not 3  💥
```

**Why:** `HashSet` inherits `addAll()` from `AbstractCollection`, which is implemented by
calling `add()` in a loop. So `addCount` is incremented once by `addAll` (+3) and three
more times by the `add()` calls it triggers (+3).

Now the part that makes this genuinely alarming — **the same subclass of `ArrayList`
gives 3, the correct answer**:

```java
class CountingList<E> extends ArrayList<E> { /* identical code */ }

var list = new CountingList<String>();
list.addAll(List.of("a", "b", "c"));
IO.println(list.addCount());    // 3  ✅
```

`ArrayList.addAll()` doesn't call `add()` — it grows the backing array and uses
`System.arraycopy`. Identical subclass code, two different answers, and **nothing in
either superclass's documentation tells you which**. You have to read the JDK source,
for the exact version you're compiling against.

That's the fragile base class problem: the subclass depends on an **implementation
detail** of the parent that isn't in its contract and can change in any release.
**Inheritance breaks encapsulation** — the subclass and superclass are coupled in ways
neither one declares.

### Composition is usually the better answer

```java
class CountingSet<E> {
    private final Set<E> delegate = new HashSet<>();      // HAS-A, not IS-A
    private int addCount = 0;

    public boolean add(E e)  { addCount++; return delegate.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);
    }
    public int addCount() { return addCount; }            // 3 ✅ — always
}
```

Now `HashSet` is just a field. Its internals cannot leak. You expose exactly the
methods you want, and a JDK update can't break you.

> **The test:** ask *"is a X really a Y, for every possible Y behaviour, forever?"*
> If you hesitate, use composition.

**When inheritance IS right:**
- The superclass was **designed** for it — documented, `protected` hooks, abstract
  methods (`AbstractList`, `InputStream`).
- You control both classes and they ship together.
- It's a genuine type hierarchy, ideally `sealed` (2.8).

### Calling an overridable method from a constructor

Already shown in 2.1, repeated here because it's the same family of bug:

```java
class Parent {
    Parent() { init(); }             // ⚠️
    void init() { }
}
class Child extends Parent {
    private String data = "value";
    @Override void init() { IO.println(data.length()); }   // 💥 NPE — data is still null
}
```

**Never call an overridable method from a constructor.** Make it `private`, `static`,
or `final`.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Omitting `@Override` | Typos silently create new methods |
| Shadowing a field | Fields use the declared type — never polymorphic |
| "Overriding" a static method | It's hiding; resolved at compile time |
| Extending `HashSet`/`ArrayList`/`HashMap` | Fragile base class. Delegate instead |
| Overridable method in a constructor | Subclass fields are still `null` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Deep hierarchies (`Animal→Mammal→Dog→Labrador`) | Composition; 2–3 levels max |
| Extending a concrete JDK collection | Delegation, or `AbstractList` if you must |
| Inheritance for code reuse only | Composition |

---

## Recap

| Concept | One line |
|---|---|
| Single inheritance | One `extends`; everything extends `Object` |
| Overriding vs overloading | Runtime vs compile time. Unrelated mechanisms |
| Dynamic dispatch | Actual object's type wins — via the vtable |
| Fields & statics | **Not** polymorphic — declared type wins |
| `abstract` / `final` | Partial implementation / sealed shut |
| **Fragile base class** | Inheritance breaks encapsulation. Prefer composition |
