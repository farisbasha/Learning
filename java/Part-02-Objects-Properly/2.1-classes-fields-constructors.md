# 2.1 — Classes, fields and constructors

> **What this is:** The mechanics of making one thing. Java's object model is stricter
> and more explicit than JavaScript's or Python's — and modern Java has added several
> ways to say *"this is just data"* that older Java could not express.

---

## Coming from JS/Python/Dart

| | JS/Python | Java |
|---|---|---|
| Add a field later | `obj.newThing = 5` ✅ | ❌ Fields are fixed at compile time |
| Constructor | One (`constructor` / `__init__`) | **Many**, distinguished by parameters |
| `this` | Depends on call site (JS) | Always the current instance. No `bind` needed |
| Field defaults | `undefined` / must set | Automatic: `0`, `false`, `null` |

The `this` difference is a relief — Java's `this` is never ambiguous, so none of the
`const self = this` / `.bind(this)` machinery exists.

## The concepts

### The shape of a class

```java
public class Account {
    // fields (a.k.a. instance variables)
    private final String id;
    private double balance;

    // constructor
    public Account(String id, double balance) {
        this.id = id;
        this.balance = balance;
    }

    // methods
    public void deposit(double amount) {
        this.balance += amount;
    }
}
```

`this` refers to the current instance. It is only *required* when a parameter shadows a
field (as in the constructor above) — otherwise it's optional and usually omitted.

### Constructors

```java
public class User {
    private String name;
    private int age;

    // no-arg
    public User() {
        this("Unknown", 0);       // this(...) chaining — delegate to another constructor
    }

    // full
    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

Rules:
- **`this(...)` must be the very first statement** in a constructor (relaxed in
  Java 25 for `super()` — see below).
- **The default constructor only exists if you write no constructor at all.** The moment
  you add `User(String, int)`, the free `User()` disappears.

```java
class A { }                       // A() exists, generated by the compiler
class B { B(int x) { } }          // B() does NOT exist. new B() is a compile error
```

## ⭐ Initialisation order

Learn the exact order. It explains a whole class of bug.

When you call `new Child()`:

```
1. Child's static init      ── once ever, when the class first loads (2.2)
2. Parent's static init     ── (actually happens first, parent before child)
3. Parent's field initialisers
4. Parent's instance initialiser blocks
5. Parent's constructor body
6. Child's field initialisers      ← note: AFTER the parent constructor body
7. Child's instance initialiser blocks
8. Child's constructor body
```

**The short version: superclass fully constructed first, then this class's fields, then
this class's constructor body.**

```java
class Parent {
    Parent() {
        IO.println("Parent constructor");
        greet();                  // ⚠️ calls the OVERRIDDEN version
    }
    void greet() { IO.println("Parent greet"); }
}

class Child extends Parent {
    private String name = "Basha";      // field initialiser

    Child() {
        super();                         // implicit
        IO.println("Child constructor");
    }

    @Override void greet() { IO.println("Child greet: " + name); }
}

new Child();
```

Output:
```
Parent constructor
Child greet: null          ← 💥 name is null, not "Basha"
Child constructor
```

**Why:** `Parent`'s constructor runs at step 5. `Child`'s field initialiser (`name = "Basha"`)
doesn't run until step 6. So when `greet()` is dispatched to `Child`, `name` is still
at its default `null`.

> **The rule this gives you: never call an overridable method from a constructor.**
> See 2.3. Make it `private`, `static`, or `final` if you must call it.

**Instance initialiser blocks** — a bare `{ }` block in the class body, run before the
constructor. Rare; mostly used when several constructors share setup, though calling a
common private method is clearer.

```java
class Thing {
    private List<String> items;
    { items = new ArrayList<>(); }    // instance initialiser
}
```

### Flexible constructor bodies `Java 25`

Historically `super(...)` or `this(...)` had to be the **first** statement, which made
validating arguments awkward.

```java
// ❌ before Java 25 — illegal
class Positive extends Number {
    Positive(int v) {
        if (v < 0) throw new IllegalArgumentException();   // can't do this first
        super(v);
    }
}
```

```java
// ✅ Java 25 — statements allowed before super(), as long as they don't touch `this`
class Positive extends Number {
    Positive(int v) {
        if (v < 0) throw new IllegalArgumentException("must be positive");
        super(v);
    }
}
```

You still cannot *read* or *assign* instance fields before `super()` — only compute and
validate.

### `final` fields, and why they're the default you want

```java
public class Point {
    private final int x;      // must be assigned exactly once
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
    // no setters — this object can never change
}
```

A `final` field must be assigned either at declaration or in **every** constructor,
exactly once.

Why make it the default:
- **Thread safety for free** — a properly-constructed immutable object is safe to share
  across threads with no locking (Part 09).
- **Safe as a `HashMap` key** — its hash can never change (2.5).
- **No "who changed this?"** — the answer is nobody.

> **The habit: start every field `final`. Remove it only when you have a reason.**
> This is the single highest-value style rule in Java, and it's what makes records
> (2.6) feel natural.

### Encapsulation done honestly

The tutorial version — a getter and setter for every field — is **not encapsulation**.
It's a public field with extra typing.

```java
// ❌ Not encapsulation. Nothing is hidden.
public class Account {
    private double balance;
    public double getBalance()          { return balance; }
    public void setBalance(double b)    { balance = b; }
}

account.setBalance(account.getBalance() - 100);   // caller does the logic
```

```java
// ✅ Expose behaviour, hide state.
public class Account {
    private double balance;

    public void withdraw(double amount) {
        if (amount <= 0)        throw new IllegalArgumentException("positive only");
        if (amount > balance)   throw new InsufficientFundsException(id, amount);
        balance -= amount;
    }

    public double balance() { return balance; }   // read is fine
}

account.withdraw(100);   // the object protects its own invariants
```

> **The test:** can a caller put this object into an invalid state? If yes, it isn't
> encapsulated, however many `private` keywords it has.

Note the getter is named `balance()`, not `getBalance()` — that's the modern convention
(records use it, and the JDK increasingly does too). The `getX`/`setX` convention comes
from the 1997 JavaBeans spec; frameworks still expect it, but for your own code the
short form reads better.

### Object lifetime — there is no destructor

```java
// 💀 finalize() — deprecated since 9, REMOVED. Never use.
protected void finalize() { }
```

`finalize()` was unpredictable (it might never run), slow, and a source of security bugs.

What to use instead, in order of preference:

**1. try-with-resources** — for anything holding a file handle, socket or connection:

```java
try (var reader = Files.newBufferedReader(path)) {
    // use it
}   // close() called automatically, even if an exception is thrown
```

Any class implementing `AutoCloseable` works here. Full details in Part 04.

**2. `Cleaner`** — only if you're wrapping native memory and genuinely need a safety net:

```java
private static final Cleaner CLEANER = Cleaner.create();
CLEANER.register(this, () -> freeNativeMemory(address));
```

Rare. If you think you need it, you probably need try-with-resources.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Calling an overridable method in a constructor | Subclass fields aren't initialised yet → `null` |
| Expecting `new B()` to work after adding `B(int)` | The default constructor disappears |
| `final` on a field holding a `List` | The *reference* is final; the list still mutates |
| `finalize()` | Removed. Use try-with-resources |
| Getters + setters = encapsulation | It's a public field with ceremony |

The `final` one deserves a demo:

```java
private final List<String> items = new ArrayList<>();

items.add("x");                 // ✅ allowed — the list changed
items = new ArrayList<>();      // ❌ compile error — the reference can't
```

`final` locks the arrow, not the object. Real immutability needs `List.copyOf()` (2.10).

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `finalize()` | try-with-resources, `Cleaner` |
| `getX`/`setX` on every field | Behaviour methods; or a `record` if it's genuinely data |
| Non-final fields by default | `final` by default |

---

## Recap

| Concept | One line |
|---|---|
| Constructors | Overloadable; chain with `this(...)`; the free one vanishes if you write your own |
| **Initialisation order** | Parent fully built → this class's fields → this class's constructor body |
| Constructor + overridable method | A real bug. Never do it |
| `final` fields | Default choice. Thread-safe, hash-safe, no surprises |
| Encapsulation | Expose behaviour, hide state — not getters on everything |
| No destructor | try-with-resources |
