# 2.8 — Sealed types

> **What this is:** A way to say *"these are the **only** possible subtypes"* — which
> lets the compiler reason about **completeness**. `Java 17`

---

## Coming from JS/Python/Dart

You already know this idea under other names:

| Language | The same thing |
|---|---|
| **TypeScript** | Discriminated unions — `type Shape = Circle \| Square` |
| **Rust** | `enum Shape { Circle(f64), Square(f64) }` |
| **Dart 3** | `sealed class Shape` |
| **Kotlin** | `sealed class` |
| **Haskell/ML** | Sum types / algebraic data types |

Java calls it sealed types, and combined with records (2.6) it gives you the same thing:
**a closed set of alternatives that the compiler can check you handled.**

---

## The concepts

### The syntax

```java
public sealed interface Shape
        permits Circle, Rectangle, Triangle { }

public record Circle(double radius)            implements Shape { }
public record Rectangle(double w, double h)    implements Shape { }
public record Triangle(double b, double h)     implements Shape { }
```

`permits` lists exactly which types may implement `Shape`. Anything else is a compile
error:

```java
record Pentagon(double side) implements Shape { }
// ❌ error: Pentagon is not allowed in the sealed hierarchy
```

### Every permitted subtype must choose one of three

This is the rule people miss. Each subtype must be declared `final`, `sealed`, or
`non-sealed`:

| Modifier | Means |
|---|---|
| `final` | The hierarchy stops here. **Records are automatically final** ✅ |
| `sealed` | It has its own closed set of subtypes |
| `non-sealed` | **Reopens** the hierarchy — anyone may extend this branch |

```java
public sealed interface Shape permits Circle, Polygon, Blob { }

public record Circle(double r) implements Shape { }        // final (records are)

public sealed interface Polygon extends Shape              // sealed — continues closed
        permits Rectangle, Triangle { }

public non-sealed interface Blob extends Shape { }         // non-sealed — anyone can extend
```

`non-sealed` is an escape hatch. Using it gives up the exhaustiveness benefit for that
branch, so use it rarely.

### Placement rules

The permitted subtypes must be **accessible to the sealed type** at compile time:

- **Same file** — then you can omit `permits` entirely:

```java
// Shape.java — all in one file
public sealed interface Shape { }              // no permits needed
record Circle(double r)          implements Shape { }
record Rectangle(double w, double h) implements Shape { }
```

- **Same package** — list them with `permits`.
- **Same named module** — allowed if you're using modules (11.10).

You cannot seal across unrelated jars, which is the point: the set must be knowable.

## ⭐ Why a closed hierarchy is useful

Without sealing, the compiler can never know you've covered everything:

```java
// ❌ not sealed — the compiler demands a default it cannot check
double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
        default -> throw new IllegalStateException("unknown shape");   // forced
    };
}
```

With sealing, the compiler knows the complete list:

```java
// ✅ sealed — exhaustive, no default
double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
        case Triangle t  -> 0.5 * t.b() * t.h();
    };
}
```

**And here's the payoff.** Add a fourth shape:

```java
public sealed interface Shape permits Circle, Rectangle, Triangle, Square { }
record Square(double side) implements Shape { }
```

```
error: the switch expression does not cover all possible input values
```

**Every switch over `Shape` in the entire codebase stops compiling** until someone
handles `Square`. You cannot forget a case. The compiler is your migration checklist.

> This is exactly the benefit described for enums in 2.7 and switch expressions in 1.2 —
> sealed types extend it from "a fixed set of constants" to "a fixed set of *shapes with
> data*."

### Sealed interfaces + records = Java's sum type

The combination is the whole point:

```java
sealed interface Result<T> permits Ok, Err { }
record Ok<T>(T value)      implements Result<T> { }
record Err<T>(String msg)  implements Result<T> { }

// use it
String describe(Result<Integer> r) {
    return switch (r) {
        case Ok<Integer> ok   -> "got " + ok.value();
        case Err<Integer> err -> "failed: " + err.msg();
    };
}
```

Compare with the TypeScript you'd write:

```typescript
type Result<T> = { kind: "ok"; value: T } | { kind: "err"; msg: string };
```

Same idea, same exhaustiveness checking, same safety.

### Modelling with closed hierarchies

Four patterns worth recognising:

**1. Results** — success or failure, with no exceptions:
```java
sealed interface PaymentResult permits Approved, Declined, Pending { }
record Approved(String txId)          implements PaymentResult { }
record Declined(String reason)        implements PaymentResult { }
record Pending(Instant retryAfter)    implements PaymentResult { }
```

**2. States** — a state machine where illegal states don't exist:
```java
sealed interface OrderState permits Draft, Placed, Shipped, Cancelled { }
record Draft()                          implements OrderState { }
record Placed(Instant at)               implements OrderState { }
record Shipped(String tracking)         implements OrderState { }
record Cancelled(String reason)         implements OrderState { }
```

Note `Shipped` **has** a tracking number and `Draft` does not — the data lives with the
state it belongs to. A single class with nullable `trackingNumber` and `cancelReason`
fields can represent nonsense; this cannot.

**3. Expressions** — the classic interpreter:
```java
sealed interface Expr permits Num, Add, Mul { }
record Num(int value)            implements Expr { }
record Add(Expr left, Expr right) implements Expr { }
record Mul(Expr left, Expr right) implements Expr { }

int eval(Expr e) {
    return switch (e) {
        case Num n -> n.value();
        case Add a -> eval(a.left()) + eval(a.right());
        case Mul m -> eval(m.left()) * eval(m.right());
    };
}
```

**4. Commands** — a closed set of things that can happen:
```java
sealed interface Command permits Create, Update, Delete { }
```

### Sealed vs enum — which one

| Use an **enum** | Use a **sealed hierarchy** |
|---|---|
| A fixed set of **values** | A fixed set of **shapes** |
| All constants have the same fields | Each case carries **different data** |
| `Status.ACTIVE`, `Day.MONDAY` | `Circle(r)` vs `Rectangle(w,h)` |

If every alternative would carry identical data, use an enum. If they carry different
data, use a sealed interface with records.

### Preview of Part 07

Right now you write `case Circle c -> ... c.radius() ...`. With **record patterns**
(7.3) you destructure directly:

```java
double area(Shape s) {
    return switch (s) {
        case Circle(double r)              -> Math.PI * r * r;
        case Rectangle(double w, double h) -> w * h;
        case Triangle(double b, double h)  -> 0.5 * b * h;
    };
}
```

And they nest:

```java
case Add(Num(int a), Num(int b)) -> a + b;      // matches Add of two Nums, pulls both out
```

That's Part 07. **Sealed + records + switch patterns is the modern Java idiom**, and this
page is the middle third of it.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Forgetting `final`/`sealed`/`non-sealed` on a subtype | Compile error — every permitted subtype must choose |
| Adding a `default` to a sealed switch | Defeats the entire point |
| Permitted subtype in a different package | Must be same file, package, or module |
| Using `non-sealed` casually | Gives up exhaustiveness for that branch |
| Sealing when the set genuinely should be open | Plugins and extension points want open interfaces |

---

## Recap

| Concept | One line |
|---|---|
| `sealed ... permits` | Declares the complete set of subtypes |
| Each subtype | Must be `final`, `sealed`, or `non-sealed` |
| Placement | Same file (no `permits` needed), package, or module |
| Payoff | **Exhaustive switch with no `default`** |
| Adding a case | Breaks every switch until handled — a compiler-checked TODO list |
| Sealed + records | Java's discriminated union / sum type |
| vs enum | Enum for values; sealed for shapes carrying different data |
