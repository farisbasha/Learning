# 2.2 — `static`, and what it really means

> **What this is:** *"Belongs to the class, not to any instance."* A simple rule with
> surprisingly wide consequences.

---

## Coming from JS/Python/Dart

Closest analogue: a module-level variable in Python, or a `static` member in Dart.
The important difference is **when** it initialises — Java's answer is "later than you
think", and that timing is a real source of bugs.

---

## The concepts

### Static fields and methods

```java
public class Counter {
    private static int totalCreated = 0;   // ONE copy, shared by all instances
    private int id;                        // one per instance

    public Counter() {
        totalCreated++;
        this.id = totalCreated;
    }

    public static int total() {            // callable without an instance
        return totalCreated;
    }
}

new Counter(); new Counter();
Counter.total();    // 2  — called on the CLASS, not an object
```

A `static` method has no `this`. It cannot touch instance fields, because there's no
instance to touch.

### When static is correct, and when it's a hidden global

**Correct:**
- Pure functions — `Math.max`, `Integer.parseInt`
- Factory methods — `List.of`, `Optional.of` (see below)
- Genuine constants — `Math.PI`

**A hidden global:**
```java
// ❌ mutable static state
public class Config {
    public static String apiUrl;    // anyone can change it, from anywhere, at any time
}
```

This is a global variable. It's untestable (test order now matters), unsafe across
threads (Part 09), and impossible to reason about locally.

> **The rule: `static` + mutable = global variable. `static` + `final` + immutable = fine.**

### Static initialiser blocks, and when a class actually initialises

```java
public class Registry {
    private static final Map<String, String> CODES;

    static {                                   // runs ONCE, when the class initialises
        CODES = new HashMap<>();
        CODES.put("IN", "India");
        CODES.put("US", "United States");
    }
}
```

**When does that run?** Later than you'd guess. A class is initialised on the **first**
of these:

1. An instance is created (`new Registry()`)
2. A static method is called
3. A **non-constant** static field is read or written
4. A subclass is initialised
5. It's the main class

**Not** on these:
- Merely *declaring* a variable of that type
- Reading a `static final` **compile-time constant** (see the next section — this is the
  big one)
- Loading the class via `Class.forName(name, false, loader)`

```java
class Loud {
    static { IO.println("Loud initialised"); }
    static final String NAME = "loud";           // compile-time constant
    static final List<String> ITEMS = List.of(); // NOT a compile-time constant
}

Loud x;                    // nothing printed — declaration doesn't initialise
IO.println(Loud.NAME);     // nothing printed! ← the constant was inlined
IO.println(Loud.ITEMS);    // "Loud initialised" ← now it runs
```

That second line is the surprise, and it leads directly to the next section.

### ⭐ Constant inlining — the surprise that survives recompiles

```java
// Config.java
public class Config {
    public static final int VERSION = 1;
}

// App.java
IO.println(Config.VERSION);
```

The compiler sees that `Config.VERSION` is a `static final` with a **compile-time
constant** value, and **copies the literal `1` directly into `App.class`**. `App` no
longer references `Config` at all for that value.

Now:

```bash
# change VERSION to 2 in Config.java
javac Config.java      # recompile ONLY Config
java App               # prints 1  ← still the old value!
```

You have to recompile **`App`** too. In a big project with partial builds, this produces
genuinely baffling "I changed it and nothing happened" bugs.

**Which fields get inlined:** `static final` of a primitive type or `String`, assigned a
constant expression.

```java
static final int A = 1;                    // inlined ⚠️
static final String B = "hi";              // inlined ⚠️
static final int C = compute();            // NOT inlined — runtime value
static final List<String> D = List.of();   // NOT inlined — not a primitive/String
static final Integer E = 1;                // NOT inlined — boxed type
```

**Naming convention:** constants are `UPPER_SNAKE_CASE`.

### Why `main` was `static`, and why it no longer has to be

```java
public static void main(String[] args)
```

`static` was required because **there is no object yet** — the JVM must call your entry
point before any instance of anything exists.

`Java 25` removed the requirement. The JVM now constructs an instance for you:

```java
// hello.java — Java 25
void main() {
    IO.println("Hello");
}
```

See 0.4 for the full decoding of the old ceremony.

### Static factory methods — usually better than constructors

```java
List.of("a", "b")            // instead of new ArrayList<>() then two adds
Optional.of(value)
Integer.valueOf(5)
LocalDate.of(2026, 9, 19)
Map.entry(k, v)
```

Why the JDK prefers them:

| Advantage | Example |
|---|---|
| **They have names** | `LocalDate.of()` vs `LocalDate.ofEpochDay()` — two constructors couldn't both be `LocalDate(long)` |
| **They can return a cached instance** | `Integer.valueOf(5)` returns a pooled object (1.1) |
| **They can return a subtype** | `List.of()` returns a different class depending on size |
| **They can return nothing** | A constructor must return an instance; a factory can return `Optional.empty()` |

Conventional names: `of`, `valueOf`, `from`, `getInstance`, `newInstance`, `copyOf`.

### Utility classes and why `static` everywhere makes code untestable

```java
public final class StringUtils {      // final — nobody should extend it
    private StringUtils() { }         // private constructor — nobody should instantiate it
    public static String slugify(String s) { ... }
}
```

That's the correct shape for a utility class: `final`, private constructor, all statics.

**But** when business logic goes static, testing dies:

```java
// ❌
public class OrderService {
    public static Order place(Cart cart) {
        var price = PriceApi.fetch(cart);    // static call into a real HTTP client
        ...
    }
}
```

You cannot substitute `PriceApi` in a test. There's no seam — no interface, no
constructor parameter, nothing to swap.

```java
// ✅ instance + injected dependency
public class OrderService {
    private final PriceApi prices;
    public OrderService(PriceApi prices) { this.prices = prices; }

    public Order place(Cart cart) {
        var price = prices.fetch(cart);      // now substitutable in a test
        ...
    }
}
```

> **The rule: `static` for pure functions and factories. Instances for anything with
> dependencies or state.** This is also, in one sentence, what dependency injection
> frameworks exist to automate.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Mutable `public static` field | A global variable. Untestable, unsafe |
| Changing a `static final int` and recompiling one file | Callers keep the old inlined value |
| Assuming a class initialises when declared | It initialises lazily, on first real use |
| `static` business logic | No seam for tests |
| Calling an instance method from `static` | Compile error — there is no `this` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| "Constant interface" — an interface holding only constants | A `final` class with a private constructor (2.4) |
| Mutable static singletons | Injected instances, or an enum singleton (2.7) |

---

## Recap

| Concept | One line |
|---|---|
| `static` | Belongs to the class; no `this` |
| Static init | Runs **lazily**, on first real use of the class |
| Constant inlining | `static final` primitives/Strings get copied into callers |
| Static factories | Named, can cache, can return subtypes — usually better than `new` |
| Utility class | `final` + private constructor + all static |
| Static business logic | Untestable. Use instances |
