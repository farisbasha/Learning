# 2.5 — The Object contract

> **What this is:** Every object inherits five methods that **the entire standard library
> assumes you have implemented correctly**. Get `equals`/`hashCode` wrong and your
> `HashMap` silently loses data. This is one of the highest-consequence pages in Part 02.

---

## Coming from JS/Python/Dart

Python's `__eq__` / `__hash__` is the exact same contract, with the exact same rule that
equal objects must hash equally. JS has no equivalent — `Map` uses reference identity
only, which is why you've probably never hit this class of bug before.

---

## The concepts

### `toString()`

The default is useless:

```java
class Point { int x, y; }
IO.println(new Point());     // Point@1b6d3586   ← class name + identity hash in hex
```

(Same format you decoded for arrays in 1.4.)

```java
@Override
public String toString() {
    return "Point[x=" + x + ", y=" + y + "]";
}
```

**Always override it.** It costs two minutes and pays off in every log line, every
debugger session, and every failed test message for the life of the code.

> ⚠️ **Never put secrets in `toString()`** — passwords, tokens, card numbers. It ends up
> in logs. This is a real and common leak.

## ⭐ `equals()` — the five-part contract

```java
Object o1 = new Point(1, 2);
Object o2 = new Point(1, 2);
o1 == o2          // false — different objects
o1.equals(o2)     // false by default! Object.equals IS ==
```

`Object.equals()` is reference identity. You must override it for value types.

**The contract — five rules, all of which the library relies on:**

| Rule | Means |
|---|---|
| **Reflexive** | `x.equals(x)` is true |
| **Symmetric** | `x.equals(y)` ⟺ `y.equals(x)` |
| **Transitive** | `x.equals(y)` and `y.equals(z)` ⟹ `x.equals(z)` |
| **Consistent** | Repeated calls give the same answer (if nothing changed) |
| **Null-safe** | `x.equals(null)` is **false**, never an exception |

### Writing it correctly

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;                    // 1. fast path
    if (o == null || getClass() != o.getClass())   // 2. type check
        return false;
    Point other = (Point) o;                       // 3. cast
    return x == other.x && y == other.y;           // 4. compare fields
}
```

For reference-typed fields, use `Objects.equals` — it's null-safe:

```java
return Objects.equals(name, other.name)
    && Objects.equals(email, other.email)
    && age == other.age;                 // primitives use ==
```

### `getClass()` vs `instanceof` in `equals`

This is the subtle bit.

```java
if (getClass() != o.getClass()) return false;    // strict — subclass is never equal
if (!(o instanceof Point other))   return false;  // lenient — subclass CAN be equal
```

| | `getClass()` | `instanceof` |
|---|---|---|
| Symmetry | Always preserved | Can break with subclasses |
| Liskov substitution | Technically violated | Preserved |
| Recommendation | **Use this by default** | Only when the class is `final` |

Use `getClass()` unless the class is `final`, in which case `instanceof` (with a pattern,
Part 07) is cleaner:

```java
// Java 16+ pattern form, for a final class
@Override public boolean equals(Object o) {
    return o instanceof Point p && x == p.x && y == p.y;
}
```

## ⭐ `hashCode()` — the contract with `equals`

**The rule:**

> **If `a.equals(b)` is true, then `a.hashCode() == b.hashCode()` must be true.**
>
> The reverse is *not* required — unequal objects may share a hash (a "collision").

```java
@Override
public int hashCode() {
    return Objects.hash(x, y);      // handles nulls, combines properly
}
```

For a single primitive field, avoid the array allocation `Objects.hash` does:
```java
@Override public int hashCode() { return Integer.hashCode(x); }
```

### What breaks when you violate it

This is the part worth internalising.

```java
class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { /* correct */ }
    // ❌ hashCode NOT overridden — inherits Object's identity hash
}

Map<Point, String> map = new HashMap<>();
map.put(new Point(1, 2), "origin-ish");
IO.println(map.get(new Point(1, 2)));     // null  💥
IO.println(map.size());                    // 1, but you can never find the entry
```

**Why.** A `HashMap` is an array of buckets. `put` does:

```
bucket index = hash(key) % numberOfBuckets
```

The two `Point(1,2)` objects have *different* identity hashes, so they land in
**different buckets**. `get` looks in the wrong bucket, finds nothing, returns `null`.
It never even gets to calling `equals`.

```
put(Point(1,2))  → hash 8291  → bucket 3  → [ Point(1,2) → "origin-ish" ]
get(Point(1,2))  → hash 4417  → bucket 9  → empty → null
```

The entry is in the map. You just can't reach it. **Silent data loss, no exception.**

> **The rule: always override `equals` and `hashCode` together.** Your IDE generates
> both at once for exactly this reason. Or — better — use a `record` (2.6), which
> generates both correctly and you cannot get it wrong.

### The mutable-key trap

Even with both implemented correctly:

```java
class MutablePoint { int x, y; /* equals + hashCode on x,y */ }

var p = new MutablePoint(1, 2);
Set<MutablePoint> set = new HashSet<>();
set.add(p);

p.x = 99;                      // mutate the key AFTER inserting

set.contains(p);               // false  💥 — it's in bucket for hash(1,2)
                               //             but now hashes to bucket for hash(99,2)
```

> **Hash keys must be immutable.** This is the practical reason `final` fields are the
> default you want (2.1), and why `String` being immutable (1.3) matters so much.

### Why inheritance and `equals` fundamentally do not compose

```java
class Point { int x, y; }
class ColorPoint extends Point { Color color; }
```

How should `ColorPoint.equals` work?

**Option A — ignore colour:** then `new ColorPoint(1,2,RED).equals(new ColorPoint(1,2,BLUE))`
is true. Wrong.

**Option B — compare colour, and let a `Point` equal a `ColorPoint` if coordinates match:**

```java
Point p = new Point(1, 2);
ColorPoint cp = new ColorPoint(1, 2, RED);

p.equals(cp)    // true  (Point only checks x,y)
cp.equals(p)    // false (ColorPoint also checks color)
```

**Symmetry is broken.** And once it's broken, `List.contains()` gives different answers
depending on argument order, and `HashSet` behaves unpredictably.

**Option C — transitivity breaks instead:**
```java
ColorPoint red   = new ColorPoint(1,2,RED);
Point      plain = new Point(1,2);
ColorPoint blue  = new ColorPoint(1,2,BLUE);

red.equals(plain)   // true
plain.equals(blue)  // true
red.equals(blue)    // FALSE — transitivity violated
```

> **There is no correct answer.** This is a genuine, proven limitation: *you cannot
> extend an instantiable class with a new value component and preserve the `equals`
> contract.*
>
> **The fix is composition** (2.3): give `ColorPoint` a `Point` field instead of
> extending it.

This is also why **records are implicitly `final`** (2.6) — the language removed the
possibility of making this mistake.

### `clone()` and `Cloneable` — understand, then avoid

```java
class Thing implements Cloneable {
    @Override protected Object clone() throws CloneNotSupportedException {
        return super.clone();      // a magic shallow field-copy by the JVM
    }
}
```

Why it's considered a design mistake:
- `Cloneable` is a **marker interface with no methods** — it doesn't declare `clone()`,
  it just changes what `Object.clone()` does. Bizarre.
- `Object.clone()` is `protected`, so you must override it just to make it callable.
- It's **shallow** — nested mutable objects are shared between the original and the copy.
- It bypasses constructors, so `final` fields and invariants aren't enforced.

**Use a copy constructor or static factory instead:**

```java
public Thing(Thing other) {                       // copy constructor
    this.name = other.name;
    this.items = List.copyOf(other.items);        // deep where it matters
}

public static Thing copyOf(Thing other) { ... }   // or a factory
```

### `getClass()` and a first look at `Class`

```java
Object o = "hello";
Class<?> c = o.getClass();
c.getName();          // "java.lang.String"
c.getSimpleName();    // "String"
```

A `Class` object is the JVM's runtime description of a type — its methods, fields,
annotations and superclass. It's the entry point to reflection (11.6), and it's how
frameworks discover your code. One `Class` object exists per class per class-loader (8.2).

### `wait()` / `notify()` / `notifyAll()`

Noted here because they're on `Object`, understood in Part 09. Every object has a
monitor and can be used for thread coordination.

> In modern code you'll use `java.util.concurrent` (9.5–9.10) instead. These are the
> 1996 primitives underneath it.

## ⭐ Value semantics versus identity semantics

The distinction that decides whether a type should be a record.

| | **Value semantics** | **Identity semantics** |
|---|---|---|
| "Same" means | Same contents | Same object |
| Examples | `Point`, `Money`, `LocalDate`, `String` | `Thread`, `Socket`, a DB connection, a `User` **entity** |
| Needs `equals`/`hashCode` | ✅ Yes | ❌ No — inherit `Object`'s |
| Should be | Immutable, often a **record** | A regular class |

```java
// Value — two points with the same coordinates ARE the same point
record Point(int x, int y) { }

// Identity — two connections to the same DB are still two different connections
class DatabaseConnection { }   // don't override equals
```

> **Ask: "if two of these have identical fields, are they the same thing?"**
> Yes → value semantics → make it a record. No → leave `equals` alone.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Overriding `equals` without `hashCode` | Silent data loss in `HashMap`/`HashSet` |
| `public boolean equals(Point p)` | That's an **overload**, not an override. Add `@Override` to catch it |
| Mutating an object used as a hash key | It becomes unreachable in the map |
| `instanceof` in `equals` on a non-final class | Breaks symmetry |
| Overriding `equals` on an entity with an identity | Usually wrong — ask the value/identity question |
| Secrets in `toString()` | Leaks into logs |

That second one is worth seeing:

```java
public boolean equals(Point p) { ... }     // ❌ overload — Object.equals still wins
@Override public boolean equals(Object o)  // ✅ override
```

Without `@Override`, this compiles fine and silently does nothing. `HashMap` calls
`equals(Object)`, never your version.

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `clone()` / `Cloneable` | Copy constructor or static factory |
| Hand-writing `equals`/`hashCode` for a data class | A **`record`** (2.6) |
| `wait`/`notify` in new code | `java.util.concurrent` (Part 09) |

---

## Recap

| Method | Rule |
|---|---|
| `toString()` | Always override. No secrets |
| `equals()` | Reflexive, symmetric, transitive, consistent, null-safe. `getClass()` check |
| `hashCode()` | **Equal ⟹ same hash.** Always override alongside `equals` |
| Keys | Must be immutable |
| Inheritance + `equals` | Cannot compose. Use composition; records are `final` for this reason |
| `clone()` | Avoid. Copy constructor |
| Value vs identity | Decides whether the type should be a record at all |
