# 9.9 — `CompletableFuture`

> **What this is:** Java's promise API. **Powerful, composable, and with a genuinely
> awkward method surface.**

---

## ⭐ Coming from JavaScript

This is the closest mapping in the whole roadmap, so use it:

| JavaScript | Java |
|---|---|
| `Promise.resolve(v)` | `CompletableFuture.completedFuture(v)` |
| `new Promise(...)` | `supplyAsync(() -> ...)` |
| `.then(v => other)` | **`.thenApply`** — value → value |
| `.then(v => promise)` | ⭐ **`.thenCompose`** — value → future (**the flatMap**) |
| `.then(v => {...})` no return | `.thenAccept` |
| `.catch(e => ...)` | `.exceptionally` |
| `.finally(...)` | `.whenComplete` |
| `Promise.all([...])` | `.allOf(...)` ⚠️ **returns `Void`** |
| `Promise.race([...])` | `.anyOf(...)` |
| `await` | `.join()` / `.get()` (⚠️ **blocking**) |

**What does *not* map:**

| | JS | Java |
|---|---|---|
| Thread model | Single-threaded event loop | **Real threads** — continuations run wherever |
| `then` merging values and promises | Auto-flattens both | ⭐ **`thenApply` vs `thenCompose` are separate** |
| `await` | Suspends cheaply | `.join()` **blocks a real thread** |

> ⭐ **The `thenApply`/`thenCompose` split is the #1 source of confusion for JS
> developers.** JS's `.then()` does both; Java makes you pick. Pick wrong and you get
> `CompletableFuture<CompletableFuture<String>>`.

---

## Creating

```java
CompletableFuture.supplyAsync(() -> compute());          // returns a value
CompletableFuture.runAsync(() -> doSomething());         // returns void
CompletableFuture.completedFuture("value");              // already done
CompletableFuture.failedFuture(new RuntimeException());  // Java 9

// manual completion — for adapting callback APIs
var cf = new CompletableFuture<String>();
someCallbackApi.onSuccess(cf::complete);
someCallbackApi.onError(cf::completeExceptionally);
```

> ⚠️ **`supplyAsync` without an executor uses the common `ForkJoinPool`** (9.8, 6.8) —
> shared JVM-wide. **Always pass your own executor** in a server:
> ```java
> CompletableFuture.supplyAsync(() -> compute(), myExecutor);
> ```

## ⭐ Chaining — and the `thenApply` / `thenCompose` split

```java
// thenApply: T → U          (like map, 6.5)
cf.thenApply(String::toUpperCase);                      // CompletableFuture<String>

// thenCompose: T → CompletableFuture<U>   (like flatMap)
cf.thenCompose(id -> fetchUserAsync(id));               // CompletableFuture<User>

// ❌ using thenApply where the function returns a future
cf.thenApply(id -> fetchUserAsync(id));
// → CompletableFuture<CompletableFuture<User>>  😱 nested
```

> **The rule: if your lambda returns a `CompletableFuture`, use `thenCompose`.** Otherwise
> `thenApply`. Exactly the `map`/`flatMap` distinction from 6.5.

```java
cf.thenCombine(other, (a, b) -> a + b);    // combine TWO independent futures
cf.thenAccept(v -> IO.println(v));         // consume, → CompletableFuture<Void>
cf.thenRun(() -> IO.println("done"));      // ignore the value, → Void
```

## ⭐ The `Async` suffix — which thread runs the continuation

**This catches everyone.**

```java
cf.thenApply(f)                    // runs on whichever thread completed cf — OR the caller
cf.thenApplyAsync(f)               // runs on the common ForkJoinPool
cf.thenApplyAsync(f, myExecutor)   // runs on myExecutor
```

**Without `Async`, the continuation runs on *whichever thread happened to complete the
previous stage*** — or, if the stage was already complete when you attached, **on the
thread that called `thenApply`**.

The consequences:

```java
// ⚠️ heavyWork runs on the thread that completed fetchData() —
//    possibly a Netty I/O thread, or the common pool
fetchData().thenApply(data -> heavyWork(data));

// ✅ explicit
fetchData().thenApplyAsync(data -> heavyWork(data), cpuBoundExecutor);
```

> ⭐ **This is a real production hazard.** A CPU-heavy or blocking continuation attached
> without `Async` can end up running on an event-loop thread or the common pool, stalling
> something completely unrelated (6.8, 9.8).
>
> **Rule: use the `Async` variant with an explicit executor whenever the continuation does
> real work.** Use the non-`Async` form only for trivial transformations.

## Combining many

```java
var f1 = fetchUser(1);
var f2 = fetchUser(2);
var f3 = fetchUser(3);

// ⚠️ allOf returns CompletableFuture<Void> — NOT the results
CompletableFuture.allOf(f1, f2, f3)
    .thenApply(v -> Stream.of(f1, f2, f3)
                          .map(CompletableFuture::join)   // safe — all are done
                          .toList());
```

> ⚠️ **`allOf` returns `Void`**, unlike JS's `Promise.all` which gives you the array. You
> have to collect the results yourself from the original futures. This is the single most
> complained-about piece of the API.

A reusable helper is worth writing once:

```java
static <T> CompletableFuture<List<T>> allOf(List<CompletableFuture<T>> futures) {
    return CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new))
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList());
}
```

```java
CompletableFuture.anyOf(f1, f2, f3);       // CompletableFuture<Object> — first to complete
```

## ⭐ Errors

```java
cf.exceptionally(ex -> "fallback");                   // recover — like .catch()
cf.handle((value, ex) -> ex != null ? "fallback" : value);   // both outcomes, transforms
cf.whenComplete((value, ex) -> log(value, ex));       // both, does NOT transform — like .finally()
cf.exceptionallyCompose(ex -> fallbackAsync());       // Java 12 — async recovery
```

| Method | Sees | Can change the result |
|---|---|---|
| `exceptionally` | Exception only | ✅ |
| `handle` | Both | ✅ |
| `whenComplete` | Both | ❌ **passes through** |

**How exceptions propagate:** an exception **skips every subsequent stage** until it hits
a handler — same as a JS promise chain.

```java
fetchUser(id)
    .thenApply(User::name)          // ← skipped if fetchUser failed
    .thenApply(String::toUpperCase) // ← skipped
    .exceptionally(ex -> "unknown") // ← lands here
```

> ⚠️ **Exceptions are wrapped in `CompletionException`.** Unwrap with `ex.getCause()` to
> get the real one (4.3):
> ```java
> .exceptionally(ex -> {
>     Throwable cause = ex instanceof CompletionException ? ex.getCause() : ex;
>     log.error("failed", cause);
>     return fallback;
> })
> ```

> ⚠️ **A `CompletableFuture` with no terminal handler swallows its exception silently** —
> the same failure mode as `submit()` in 9.8. Always end a chain with `exceptionally`,
> `handle`, or `whenComplete`.

## Timeouts `Java 9`

```java
cf.orTimeout(5, TimeUnit.SECONDS);                       // fail with TimeoutException
cf.completeOnTimeout("default", 5, TimeUnit.SECONDS);    // complete with a fallback
```

Before Java 9 this needed a separate scheduled executor. ⚠️ Note neither **cancels** the
underlying work — it only stops *waiting* for it.

## Blocking — `get` vs `join`

```java
cf.get();                    // throws checked ExecutionException + InterruptedException
cf.join();                   // throws unchecked CompletionException
cf.getNow(defaultValue);     // doesn't block — returns the default if incomplete
```

> **`join()` is usually what you want inside a lambda**, because it's unchecked and lambdas
> can't throw checked exceptions (6.1, 4.2). That's why the `allOf` helper above uses it.

## ⭐ Why virtual threads make much of this unnecessary

**This is the most important thing on the page.**

`CompletableFuture` exists because **blocking a platform thread was too expensive** (9.1) —
so instead of blocking, you described a chain of callbacks that hop between threads.

**Virtual threads (9.11) make blocking cheap.** So you can write the straightforward
version again:

```java
// ❌ the CompletableFuture version — async, composable, hard to read and debug
CompletableFuture<Order> f =
    fetchUser(userId)
        .thenComposeAsync(user -> fetchCart(user.id()), executor)
        .thenComposeAsync(cart -> priceCart(cart), executor)
        .thenApplyAsync(priced -> new Order(priced), executor)
        .exceptionally(ex -> Order.failed(ex.getCause()));
```

```java
// ✅ with virtual threads — plain, blocking, sequential code
Order buildOrder(String userId) {
    var user   = fetchUser(userId);     // blocks — and that is now FINE
    var cart   = fetchCart(user.id());
    var priced = priceCart(cart);
    return new Order(priced);
}
```

The second version has a **real stack trace**, works with a **debugger**, works with
**try/catch** (4.3), works with **try-with-resources**, and is obviously correct.

| | `CompletableFuture` | Virtual threads |
|---|---|---|
| Stack traces | Fragments across threads | **Complete and meaningful** |
| Debugging | Step into a callback — good luck | **Ordinary stepping** |
| try/catch | Doesn't work — use `exceptionally` | **Works** |
| Reading it | A pipeline of callbacks | Top to bottom |

> ⭐ **`CompletableFuture` is still right for genuine fan-out** — "call these five services
> in parallel and combine" (or `StructuredTaskScope`, 9.12). It is **no longer necessary
> for sequential I/O**, which is what most people were using it for.
>
> **If you're on Java 21+ and writing a chain to avoid blocking, stop. Just block on a
> virtual thread.**

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `thenApply` with a future-returning lambda | Nested `CF<CF<T>>`. Use `thenCompose` |
| Omitting `Async` | The continuation runs on an unpredictable thread |
| `supplyAsync` with no executor | The **common pool** — shared JVM-wide (6.8) |
| `allOf` gives you the results | It returns **`Void`** |
| Chain with no error handler | The exception **vanishes silently** |
| `ex.getMessage()` in `exceptionally` | It's a `CompletionException` — use `getCause()` |
| `orTimeout` cancels the work | It only stops waiting |
| Using it for sequential I/O on Java 21+ | Just block on a virtual thread |

---

## Recap

| Concept | One line |
|---|---|
| `thenApply` vs **`thenCompose`** | map vs **flatMap**. Lambda returns a future ⟹ `thenCompose` |
| **`Async` suffix** | Controls **which thread** runs the continuation. Pass an executor |
| `allOf` | Returns **`Void`** — collect results yourself |
| Errors | `exceptionally` / `handle` / `whenComplete`; unwrap `CompletionException` |
| Timeouts | `orTimeout`, `completeOnTimeout` `Java 9` — don't cancel |
| `join()` over `get()` | Unchecked — usable in lambdas |
| ⭐ **Virtual threads** | Replace it for **sequential I/O**. Keep it for fan-out |
