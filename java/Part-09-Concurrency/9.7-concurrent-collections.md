# 9.7 — Concurrent collections

> **What this is:** **Almost always the right answer instead of synchronising a plain
> collection yourself.** This is the page where most real concurrent code gets written.

---

## ⭐ `ConcurrentHashMap`

The workhorse. Use it instead of `HashMap` wherever more than one thread is involved.

```java
Map<String, Integer> map = new ConcurrentHashMap<>();
```

### How it works

| Era | Mechanism |
|---|---|
| Java 5–7 | **Lock striping** — 16 segments, each independently locked |
| **Java 8+** | **CAS on empty buckets; `synchronized` on the first node of a non-empty bucket** |

So in the common case (no collision) a write is a single CAS (9.6) with **no lock at
all**. Under collision, the lock is on that one bucket — other buckets are unaffected.

**Reads are entirely lock-free**, always. The internal nodes use `volatile` fields (9.3), so
readers see a consistent view with no synchronisation.

### ⭐ The atomic compound operations

**This is the real reason to use it.** Each of these is **one atomic operation** — fixing
the check-then-act race from 9.2:

```java
map.putIfAbsent(k, v);                        // ✅ atomic
map.computeIfAbsent(k, key -> expensive(key));// ✅ atomic (5.3)
map.computeIfPresent(k, (key, v) -> v + 1);
map.compute(k, (key, v) -> v == null ? 1 : v + 1);
map.merge(k, 1, Integer::sum);                // ✅ the atomic counting idiom
map.remove(k, expectedValue);                 // ✅ atomic conditional remove
map.replace(k, oldValue, newValue);           // ✅ atomic CAS on a key
```

```java
// ❌ a race, even on a ConcurrentHashMap
if (!map.containsKey(k)) map.put(k, v);

// ✅
map.putIfAbsent(k, v);
```

**Measured** — 8 threads racing on 2,000 keys in a `ConcurrentHashMap`, counting how often
`put` overwrote a value that appeared between the check and the put:

```
run 1: 148 overwrites
run 2: 285 overwrites
```

> ⭐ **Both `containsKey` and `put` are individually thread-safe, and the sequence still
> races hundreds of times.** Thread safety does not compose — that's the whole point of
> the atomic compound operations above.

> ⚠️ **The lambda runs while holding that bucket's lock.** So:
> - Keep it **short** — no I/O, no network calls
> - **Never modify the same map inside it** — it can deadlock or corrupt the map
> - It must not block

### ⚠️ Why `size()` is approximate

```java
map.size();      // a best-effort estimate
map.isEmpty();   // same
```

There is **no global lock**, so no single moment when the whole map is quiescent. `size()`
sums per-cell counters that other threads are changing as it reads.

> **You cannot use `size()` for correctness** — only for monitoring. `if (map.size() < MAX)
> map.put(...)` is a race no matter what you wrap it in.

### ⚠️ No nulls

```java
map.put(k, null);     // 💥 NullPointerException
```

Deliberate (5.3): with nulls allowed, `get()` returning `null` would be ambiguous —
"absent" or "present with null"? — and you'd need a second, racy `containsKey` call to
disambiguate. Forbidding nulls makes `get()` unambiguous.

## ⭐ Why `Collections.synchronizedMap` is not equivalent

```java
Map<String,Integer> m = Collections.synchronizedMap(new HashMap<>());
```

This wraps every method in `synchronized`. **It makes each method atomic. It does not make
your sequence atomic.**

```java
// ❌ STILL A RACE — check-then-act (9.2)
if (!m.containsKey(k)) {
    m.put(k, v);              // another thread can put between the two calls
}
```

And iteration requires **manual external locking**, which people forget:

```java
synchronized (m) {                      // ⚠️ mandatory, and easy to miss
    for (var e : m.entrySet()) { ... }
}
```

| | `synchronizedMap` | `ConcurrentHashMap` |
|---|---|---|
| Concurrency | **One lock for everything** — full serialisation | Per-bucket; reads lock-free |
| Compound operations | ❌ You must lock externally | ✅ **Built in and atomic** |
| Iteration | Manual external lock, or `CME` (5.6) | Weakly consistent, no lock |
| Throughput | Poor under contention | Excellent |

> **`Collections.synchronizedMap` is a 1998 compatibility wrapper.** It exists to make a
> `HashMap` minimally safe; it is not a concurrent map. Same for `synchronizedList`,
> `synchronizedSet`. 💀 Don't use them in new code.

## `CopyOnWriteArrayList`

**Every write copies the entire backing array.**

```java
List<Listener> listeners = new CopyOnWriteArrayList<>();
listeners.add(l);            // ⚠️ O(n) — copies the whole array
for (var l : listeners) l.onEvent(e);   // ✅ lock-free, snapshot, no CME
```

| | |
|---|---|
| Reads | **Free** — no locking at all, reads an immutable snapshot |
| Writes | **O(n)** — full array copy under a lock |
| Iteration | A **snapshot** at iterator creation. Never throws `CME` (5.6) |

> **Use it only for read-heavy, write-almost-never collections** — listener registries,
> event handler lists, configuration that changes at startup.
>
> ⚠️ **Never for anything that changes regularly.** Adding 10,000 elements one at a time is
> 10,000 array copies — O(n²).

`CopyOnWriteArraySet` is the set equivalent (backed by the same mechanism).

## Queues

### `ConcurrentLinkedQueue`

Unbounded, **non-blocking**, lock-free (CAS-based, 9.6). `poll()` returns `null` when
empty rather than waiting.

> ⚠️ Unbounded means **no backpressure** — a fast producer can exhaust the heap (8.3).

### ⭐ The `BlockingQueue` family

**The most useful concurrent tool in the JDK**, and the foundation of producer–consumer.

It adds a **third method family** to the two from 5.4:

| Operation | Throws | Returns sentinel | **Blocks** | Times out |
|---|---|---|---|---|
| Insert | `add` | `offer` | **`put`** | `offer(e, t, u)` |
| Remove | `remove` | `poll` | **`take`** | `poll(t, u)` |
| Examine | `element` | `peek` | — | — |

```java
BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);

// producer
queue.put(task);          // BLOCKS if full        ← backpressure

// consumer
Task t = queue.take();    // BLOCKS if empty       ← no busy-waiting
```

**The implementations:**

| Implementation | Bounded | Notes |
|---|---|---|
| **`ArrayBlockingQueue`** | ✅ **Always** | Array-backed, single lock. **The safe default** |
| `LinkedBlockingQueue` | Optional | ⚠️ **Unbounded by default.** Separate put/take locks — higher throughput |
| `SynchronousQueue` | Zero capacity | A direct handoff — `put` waits for a `take`. Used by `newCachedThreadPool` (9.8) |
| `PriorityBlockingQueue` | Unbounded | Ordered by `Comparator` (5.5) |
| `DelayQueue` | Unbounded | Elements available only after their delay expires — scheduling |
| `LinkedTransferQueue` | Unbounded | `transfer()` waits for a consumer to take it |

### ⭐ Producer–consumer, and backpressure as a design concern

```java
BlockingQueue<Task> queue = new ArrayBlockingQueue<>(1000);   // ⭐ BOUNDED

// producer
while (hasWork()) {
    queue.put(nextTask());        // blocks when full — the producer SLOWS DOWN
}

// consumer
while (!Thread.currentThread().isInterrupted()) {
    try {
        process(queue.take());
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();     // 9.1
        break;
    }
}
```

> ⭐ **The bound *is* the backpressure.** An unbounded queue doesn't remove the problem of
> a producer outrunning a consumer — it converts it from "the producer slows down" into
> "the heap fills up and the process dies" (8.3).
>
> **Always bound your queues.** This is the single most common production mistake in this
> area, and it appears again in 9.8 with thread pools.

The queue also replaces hand-rolled `wait`/`notify` (9.4) entirely — no conditions, no
`while` loops, no spurious wakeups to think about.

## `ConcurrentSkipListMap` / `ConcurrentSkipListSet`

**A sorted concurrent map** — the concurrent `TreeMap` (5.3).

```java
NavigableMap<String,Integer> m = new ConcurrentSkipListMap<>();
m.firstKey(); m.headMap("m"); m.ceilingKey("x");    // the full NavigableMap API
```

Uses a **skip list** rather than a tree, because skip lists can be updated lock-free with
CAS while balanced trees can't. O(log n), fully concurrent, sorted.

> There is no `ConcurrentTreeMap` — this is it.

## ⚠️ Weakly consistent iterators

Every concurrent collection here gives **weakly consistent** iteration (5.6):

| | Fail-fast (`HashMap`, `ArrayList`) | Weakly consistent (concurrent) |
|---|---|---|
| Concurrent modification | Throws `CME` (best-effort) | **Never throws** |
| What you see | — | Everything present for the whole iteration, **plus possibly** later changes |

```java
var map = new ConcurrentHashMap<>(Map.of("a",1));
for (var e : map.entrySet()) {
    map.put("b", 2);          // ✅ no exception. Whether you SEE "b" is unspecified
}
```

> ⭐ **"No `ConcurrentModificationException`" is not the same as "a snapshot."** You get
> neither a guaranteed-consistent view nor a loud failure — you get a vague guarantee.
> If you need a true snapshot, copy first: `new ArrayList<>(map.values())`.
>
> (`CopyOnWriteArrayList` is the exception — it genuinely *is* a snapshot.)

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `Collections.synchronizedMap` is a concurrent map | One global lock; compound ops still race |
| `if (!chm.containsKey(k)) chm.put(k,v)` | A race. Use `putIfAbsent` |
| Using `chm.size()` for a decision | **Approximate.** Monitoring only |
| `null` into a `ConcurrentHashMap` | NPE |
| Slow work inside `computeIfAbsent` | Holds the bucket lock |
| `CopyOnWriteArrayList` for a growing list | O(n) per write → O(n²) |
| **Unbounded queues** | No backpressure → `OutOfMemoryError` |
| Weakly consistent = snapshot | It isn't. Copy if you need one |

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Hashtable`, `Vector` (5.1) | `ConcurrentHashMap`, `CopyOnWriteArrayList` |
| `Collections.synchronizedMap/List/Set` | A real concurrent collection |
| Hand-rolled `wait`/`notify` producer-consumer | `BlockingQueue` |
| `synchronized` around a `HashMap` | `ConcurrentHashMap` |

---

## Recap

| Collection | For |
|---|---|
| **`ConcurrentHashMap`** | **The default.** Lock-free reads; **atomic** `merge`/`computeIfAbsent`; `size()` approximate; no nulls |
| `CopyOnWriteArrayList` | Read-heavy, write-almost-never. True snapshot iteration |
| `ConcurrentLinkedQueue` | Unbounded, non-blocking |
| **`ArrayBlockingQueue`** | **Bounded** producer–consumer. **The bound is the backpressure** |
| `SynchronousQueue` | Direct handoff, zero capacity |
| `ConcurrentSkipListMap` | Sorted + concurrent |
| Iterators | **Weakly consistent** — no `CME`, but no snapshot either |
