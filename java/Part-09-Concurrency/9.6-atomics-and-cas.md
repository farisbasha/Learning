# 9.6 — Atomics and compare-and-swap

> **What this is:** **Lock-free programming at the level you will actually use it** —
> which is mostly counters and references, not writing your own lock-free data structures.

---

## ⭐ The CPU instruction underneath

Every atomic in Java is built on one hardware instruction:

> **Compare-and-swap (CAS): atomically — if this memory location currently holds
> `expected`, set it to `newValue` and report success; otherwise report failure and change
> nothing.**

On x86 it's `LOCK CMPXCHG`; on ARM it's a load-linked/store-conditional pair. Either way
it's **a single uninterruptible instruction**, which is what makes it a primitive you can
build on.

### The retry loop pattern

CAS can fail, so lock-free code is always a loop:

```java
// this is essentially what incrementAndGet() does
int increment(AtomicInteger counter) {
    while (true) {
        int current = counter.get();
        int next = current + 1;
        if (counter.compareAndSet(current, next)) {   // succeeded?
            return next;
        }
        // another thread changed it — read again and retry
    }
}
```

**Why this fixes the lost update from 9.2:** the read-modify-write isn't atomic, but the
**write is conditional on nothing having changed**. If another thread interleaved, the CAS
fails and you redo the work with fresh data. No update is ever lost.

| | Lock | CAS |
|---|---|---|
| A thread that stalls | **Blocks everyone** | Others proceed |
| Progress guarantee | None (a holder can be descheduled) | **Lock-free** — someone always progresses |
| Under contention | Context switches | Wasted retries |

## The atomic classes

```java
AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference<V>
AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray<V>
```

```java
var counter = new AtomicInteger(0);

counter.get();                  counter.set(5);
counter.incrementAndGet();      // ++i
counter.getAndIncrement();      // i++
counter.addAndGet(10);
counter.compareAndSet(5, 10);   // CAS — returns boolean

counter.getAndUpdate(x -> x * 2);           // apply a function, return the OLD value
counter.updateAndGet(x -> x * 2);           // ...return the NEW value
counter.accumulateAndGet(5, Integer::sum);  // combine with a value
```

> ⚠️ **The lambda in `updateAndGet` may run several times** — it's inside the retry loop.
> It must be **pure and side-effect free**. This is a real bug source.

```java
// ❌ the counter may be incremented more than once per call
atomic.updateAndGet(x -> { sideEffectCounter++; return x + 1; });
```

**`AtomicReference` for objects:**

```java
var ref = new AtomicReference<Config>(initial);
ref.compareAndSet(old, updated);
ref.updateAndGet(c -> c.withTimeout(30));      // works nicely with immutable objects (2.10)
```

> ⭐ **`AtomicReference` + an immutable object is the cleanest lock-free pattern in Java.**
> Build a new value, CAS it in, retry if someone beat you. No locks, no visibility
> concerns (9.3).

**Atomics also give you `volatile` semantics** — every `get()`/`set()` has the visibility
and ordering guarantees from 9.3.

## ⭐ `LongAdder` and `LongAccumulator`

**Under heavy contention, `AtomicLong` is slow** — every thread CASes the *same* memory
location, so they fight over one cache line and most retries are wasted.

```java
var counter = new LongAdder();
counter.increment();
counter.sum();                 // ⚠️ the total — not atomic with the increments
```

**How it wins: striping.** Instead of one value, `LongAdder` keeps an internal array of
cells. Each thread hashes to its own cell and increments **that**, so different threads
touch different memory. `sum()` adds them up.

```
AtomicLong:   all threads → [ one value ]              ← contention
LongAdder:    thread A → [cell0]  thread B → [cell1]   ← no contention
              sum() = cell0 + cell1 + ...
```

**Measured** — 8 threads × 2M increments each (16M total), OpenJDK 17:

| | Time | |
|---|---|---|
| `AtomicLong` | **628 ms** | retry storms on one cache line |
| **`LongAdder`** | **56 ms** | ⭐ **11× faster** |

Both produced exactly 16,000,000 — the difference is purely throughput.

| | `AtomicLong` | `LongAdder` |
|---|---|---|
| Uncontended | **Faster** | Slightly slower |
| **Heavily contended** | Slow — retry storms | ⭐ **~11× faster (measured)** |
| Exact value at any instant | ✅ | ❌ `sum()` is a snapshot |
| Memory | 1 long | An array of cells |

> **Use `LongAdder` for metrics and statistics** — hit counters, request counts — where you
> want the total occasionally and write constantly.
> **Use `AtomicLong`** when you need the exact current value on every update (e.g. an ID
> generator where `incrementAndGet()` must return a unique number).

`LongAccumulator` generalises it to any associative function (6.5):

```java
var max = new LongAccumulator(Long::max, Long.MIN_VALUE);
max.accumulate(42);
```

> ⚠️ The function must be **associative and side-effect free** — same requirement as
> `reduce` (6.5), for the same reason: the order of combination is unspecified.

## ⭐ The ABA problem

CAS checks **the value**, not whether it changed and changed back.

```
Thread 1: reads A, gets descheduled
Thread 2: changes A → B → A
Thread 1: wakes, CAS(A, C) → SUCCEEDS

           ...but the world is not what Thread 1 thinks it is.
```

For an `AtomicInteger` counter this is harmless — a `5` is a `5`. **It matters for
references**, particularly in lock-free stacks and queues, where "the head is still the
same node" does not mean "nothing happened" — that node may have been popped, reused, and
pushed back, with the rest of the list now completely different.

**The fix — add a version stamp:**

```java
var ref = new AtomicStampedReference<>(node, 0);

int[] stampHolder = new int[1];
Node current = ref.get(stampHolder);
int stamp = stampHolder[0];

ref.compareAndSet(current, newNode, stamp, stamp + 1);   // value AND stamp must match
```

The stamp increments on every change, so A→B→A is detectable.

`AtomicMarkableReference` is the cheaper variant — a reference plus one boolean, for
"logically deleted" flags.

> **You will rarely hit ABA**, because you'll rarely write lock-free data structures — the
> JDK already has them (9.7). Know the name so you recognise it in a code review.

## `VarHandle` `Java 9`

**Typed, safe, low-level memory access with explicit ordering modes** — the supported
replacement for `sun.misc.Unsafe`.

```java
class Counter {
    private volatile int value;
    private static final VarHandle VALUE;

    static {
        try {
            VALUE = MethodHandles.lookup().findVarHandle(Counter.class, "value", int.class);
        } catch (Exception e) { throw new ExceptionInInitializerError(e); }
    }

    void increment() {
        int v;
        do { v = (int) VALUE.getVolatile(this); }
        while (!VALUE.compareAndSet(this, v, v + 1));
    }
}
```

**The access modes** — you choose exactly how much ordering to pay for:

| Mode | Guarantees |
|---|---|
| `getPlain` / `setPlain` | None — like a normal field read |
| `getOpaque` / `setOpaque` | Atomicity, no ordering |
| `getAcquire` / `setRelease` | One-directional ordering — cheaper than volatile |
| `getVolatile` / `setVolatile` | Full volatile semantics (9.3) |

> **Why it exists:** `sun.misc.Unsafe` was never public API, yet half the ecosystem used
> it (Netty, Hazelcast, every serialisation library). `VarHandle` gives the same power with
> type safety and no `Unsafe`. Strong encapsulation of JDK internals (Java 17) made this
> necessary.
>
> **You will use it approximately never.** It's for library authors. Recognise it in JDK
> source.

## ⭐ Why lock-free is not automatically faster

The most important paragraph on this page.

### 1. Contention makes CAS worse, not better

Under heavy contention, threads spin and retry. **Wasted CPU on every failure.** A lock at
least parks the thread and lets the CPU do something else.

```
low contention:   CAS ≫ lock          (no syscall, no context switch)
high contention:  lock may well win   (parking beats spinning)
```

### 2. Cache line bouncing

A CAS requires **exclusive ownership of the cache line**. With N cores hammering one
`AtomicLong`, that line ping-pongs between cores continuously:

```
core 0 takes exclusive ownership → core 1 invalidates it, takes ownership →
core 2 invalidates... ~100 cycles each time
```

That's the entire reason `LongAdder` exists.

### ⭐ 3. False sharing — the invisible one

**Two unrelated variables on the same 64-byte cache line contend as if they were the
same variable.**

```java
class Counters {
    volatile long a;     // these two are adjacent in memory (8.4)
    volatile long b;     // → same 64-byte cache line
}
// Thread 1 only touches `a`. Thread 2 only touches `b`.
// They still destroy each other's cache line.
```

Symptom: performance that collapses for no visible reason, and improves when you add a
field you never use.

**The fix:** `@Contended` (JDK-internal, needs
`-XX:-RestrictContended`) or manual padding. `LongAdder`'s cells are `@Contended` for
exactly this reason.

> **The honest summary: measure.** "Lock-free" describes a *progress guarantee*, not a
> speed guarantee. An uncontended `synchronized` block costs ~20ns (9.4) and the JIT can
> delete it entirely (8.8). **Reach for atomics for counters and reference swaps; don't
> assume they're faster.**

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Lock-free is always faster | Under contention it can be **slower**. Measure |
| Side effects in `updateAndGet` | The lambda may run several times |
| `LongAdder.sum()` is atomic with increments | It's a snapshot |
| CAS detects all changes | **ABA** — use `AtomicStampedReference` for references |
| Two unrelated counters are independent | **False sharing** if they share a cache line |
| `AtomicInteger` for a compound invariant spanning two fields | You need a lock |

That last one matters:

```java
// ❌ each field is atomic; the PAIR is not (9.2 check-then-act)
AtomicInteger low = ..., high = ...;
if (low.get() < high.get()) { ... }     // can be false between the two reads

// ✅ one atomic reference to an immutable pair
record Range(int low, int high) { }
AtomicReference<Range> range = new AtomicReference<>(new Range(0, 10));
```

## Recap

| Concept | One line |
|---|---|
| **CAS** | One CPU instruction: set if unchanged. The basis of everything here |
| Retry loop | CAS can fail ⟹ read again and redo |
| `AtomicInteger`/`Long`/`Reference` | Counters and reference swaps. Also give volatile semantics |
| ⭐ `AtomicReference` + immutable | The cleanest lock-free pattern in Java |
| **`LongAdder`** | **Striped** — much faster under contention. `sum()` is approximate |
| ABA | CAS checks value, not history. `AtomicStampedReference` |
| `VarHandle` | `Unsafe`'s safe replacement. For library authors |
| **Not automatically faster** | Contention, cache line bouncing, **false sharing** |
