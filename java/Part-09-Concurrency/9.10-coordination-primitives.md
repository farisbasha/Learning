# 9.10 — Coordination primitives

> **What this is:** **Small, sharp tools.** Learn what each is for so you **recognise the
> situation** when you meet it — that's the actual value, since you'll write these rarely.

---

## ⭐ At a glance

| Primitive | One line | Reusable |
|---|---|---|
| **`CountDownLatch`** | Wait for **N things to happen, once** | ❌ |
| **`CyclicBarrier`** | **N threads wait for each other**, repeatedly | ✅ |
| **`Semaphore`** | **Bound** the number of concurrent users | ✅ |
| `Phaser` | A flexible, reusable barrier with dynamic parties | ✅ |
| `Exchanger` | A rendezvous where **two threads swap objects** | ✅ |

All are built on AQS (9.5).

---

## `CountDownLatch` — wait for N things, once

```java
var latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    pool.submit(() -> {
        try { doWork(); }
        finally { latch.countDown(); }      // ⭐ ALWAYS in finally
    });
}

latch.await();                               // blocks until the count hits 0
latch.await(10, TimeUnit.SECONDS);           // or times out
IO.println("all three done");
```

> ⚠️ **`countDown()` must be in a `finally`.** If a task throws before counting down, the
> waiter blocks **forever**. This is the most common bug with latches.

**Two classic uses:**

```java
// 1. wait for N workers to finish
var done = new CountDownLatch(workerCount);

// 2. a starting gun — release all threads at once (useful in stress tests, 9.12)
var start = new CountDownLatch(1);
for (...) pool.submit(() -> { start.await(); doWork(); });
start.countDown();                           // everyone goes at the same instant
```

**One-shot.** Once it reaches zero it stays there — `await()` returns immediately forever
after. There is no reset.

## `CyclicBarrier` — N threads wait for each other, repeatedly

```java
var barrier = new CyclicBarrier(3, () -> IO.println("--- phase complete ---"));
//                             ↑ parties     ↑ optional barrier action, runs once per cycle

// in each of 3 threads:
for (int phase = 0; phase < 5; phase++) {
    computePhase(phase);
    barrier.await();          // blocks until ALL THREE arrive, then all proceed
}
```

**Cyclic** — it resets automatically after each release, so it works for iterative
algorithms: simulations, matrix computations, anything with synchronised rounds.

### `CountDownLatch` vs `CyclicBarrier`

| | `CountDownLatch` | `CyclicBarrier` |
|---|---|---|
| Who waits | **One (or more) waiters**, separate from the workers | **The participants themselves** |
| Who counts down | The workers | Arrival *is* the count |
| Reusable | ❌ One-shot | ✅ **Resets** |
| Barrier action | — | ✅ Runs once per cycle |

> **The distinction: a latch is "wait for others". A barrier is "wait for each other".**

> ⚠️ **A barrier is all-or-nothing.** If one participant fails to arrive (throws, is
> interrupted), **every other waiter gets `BrokenBarrierException`** and the barrier is
> permanently broken until `reset()`. That's deliberate — a partial round is meaningless.

## ⭐ `Semaphore` — bound concurrent access

```java
var semaphore = new Semaphore(10);       // 10 permits

semaphore.acquire();                      // blocks if none available
try {
    callRateLimitedApi();
} finally {
    semaphore.release();                  // ⭐ ALWAYS in finally
}
```

```java
semaphore.tryAcquire();                          // don't block
semaphore.tryAcquire(5, TimeUnit.SECONDS);       // with a timeout
semaphore.acquire(3);                            // multiple permits at once
new Semaphore(10, true);                         // fair (9.5 — usually don't)
```

**Uses:**

| Use | |
|---|---|
| **Rate limiting** | At most N concurrent calls to a downstream service |
| **Resource pooling** | N database connections, N file handles |
| **Throttling** | Bound concurrency independently of thread count |

> ⭐ **`Semaphore` is the right tool for bounding concurrency when you have virtual
> threads** (9.11). You have a million threads and want at most 50 hitting the database —
> a semaphore does exactly that, and it's the modern replacement for "size the pool to
> limit concurrency".

```java
// with virtual threads: unlimited threads, bounded downstream pressure
var dbLimit = new Semaphore(50);
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var task : millionTasks) {
        exec.submit(() -> {
            dbLimit.acquire();
            try { return queryDatabase(task); }
            finally { dbLimit.release(); }
        });
    }
}
```

> ⚠️ **A `Semaphore` is not reentrant** (unlike `synchronized`, 9.4). Acquiring twice on
> one thread consumes two permits and can deadlock against yourself.
>
> ⚠️ **Permits are not owned.** Any thread can `release()` — including one that never
> acquired, which silently *increases* the permit count. That's occasionally useful and
> usually a bug.

## `Phaser` — a flexible, reusable barrier

`CyclicBarrier` with **dynamic registration**:

```java
var phaser = new Phaser(1);              // register self

for (var task : tasks) {
    phaser.register();                    // ⭐ parties can JOIN at runtime
    pool.submit(() -> {
        try { doWork(); }
        finally { phaser.arriveAndDeregister(); }   // ⭐ and LEAVE
    });
}

phaser.arriveAndAwaitAdvance();           // wait for this phase
```

| vs `CyclicBarrier` | |
|---|---|
| Party count | **Dynamic** — register/deregister at any time |
| Phases | Numbered, queryable (`getPhase()`) |
| Waiting | Can arrive without waiting (`arrive()`) |
| Hierarchy | Phasers can be tiered for scalability |

> More flexible and more complex. **If `CyclicBarrier` fits, use it.** Reach for `Phaser`
> when the number of participants genuinely changes between phases.

## `Exchanger` — a rendezvous for two threads

```java
var exchanger = new Exchanger<Buffer>();

// thread 1 (producer)
Buffer empty = exchanger.exchange(full);     // hands over `full`, receives `empty`

// thread 2 (consumer)
Buffer full = exchanger.exchange(empty);     // hands over `empty`, receives `full`
```

**Both threads block until both arrive**, then they swap objects.

The classic use is **buffer swapping** in a pipeline — a producer fills a buffer while a
consumer drains another, and they trade when both are ready, with zero allocation.

> **You will almost certainly never use this.** Know the name.

## ⭐ Choosing between them — and noticing when a queue is simpler

**The most useful part of this page.**

| Situation | Reach for |
|---|---|
| "Wait for these N tasks to finish" | `CountDownLatch` |
| "All threads finish round K before anyone starts K+1" | `CyclicBarrier` |
| "At most N at a time" | **`Semaphore`** |
| "Producer hands work to consumer" | ⭐ **`BlockingQueue`** (9.7) |
| "Wait for one async result" | `CompletableFuture` (9.9) |
| "Start all threads at once" | `CountDownLatch(1)` |
| Parties change between rounds | `Phaser` |

### ⭐ The one worth internalising

> **Most producer–consumer coordination people build out of latches, semaphores and
> `wait`/`notify` is a `BlockingQueue` (9.7).**

```java
// ❌ hand-built coordination
var lock = new ReentrantLock();
var notFull = lock.newCondition();
var notEmpty = lock.newCondition();
var buffer = new ArrayDeque<Task>();
// ...30 lines of correct-if-you're-careful code (9.5)

// ✅
var queue = new ArrayBlockingQueue<Task>(100);
queue.put(task);      // producer — blocks when full, giving backpressure
queue.take();         // consumer — blocks when empty
```

The queue gives you mutual exclusion, condition waiting, **and backpressure** (9.7) in two
method calls, with nothing to get wrong.

> **And in modern code, prefer higher-level tools generally:** an `ExecutorService` +
> `invokeAll` often replaces a `CountDownLatch`; `CompletableFuture.allOf` (9.9) or
> `StructuredTaskScope` (9.12) replaces most of the rest.
>
> ```java
> // instead of a CountDownLatch over N tasks:
> List<Future<Result>> results = pool.invokeAll(tasks);   // blocks until all complete
> ```

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `countDown()` not in `finally` | A thrown task blocks the waiter **forever** |
| `release()` not in `finally` | A permanently leaked permit — eventual deadlock |
| Expecting a `CountDownLatch` to reset | One-shot. Use `CyclicBarrier` |
| One participant fails at a barrier | **All** get `BrokenBarrierException` |
| Acquiring a `Semaphore` twice on one thread | Not reentrant — consumes two permits |
| `release()` without `acquire()` | Silently **adds** a permit |
| Building producer–consumer by hand | Use a `BlockingQueue` |
| `await()` with no timeout | An unbounded hang. Prefer the timed forms |

---

## Recap

| Primitive | Use for |
|---|---|
| **`CountDownLatch`** | Wait for N events, **once**. `countDown()` in `finally` |
| **`CyclicBarrier`** | N threads wait for **each other**, repeatedly. All-or-nothing |
| **`Semaphore`** | **Bound concurrency.** The right partner for virtual threads. Not reentrant |
| `Phaser` | Dynamic parties |
| `Exchanger` | Two-thread swap. You won't need it |
| ⭐ **`BlockingQueue`** | **Usually simpler than all of them** for producer–consumer |
