# 9.11 — Virtual threads

> **What this is:** **The biggest change to Java concurrency since 2004**, and the reason
> your services can write plain blocking code again. `Java 21`

---

## ⭐ The problem they solve

A platform thread (9.1) is an OS thread:

| Cost | |
|---|---|
| Stack | **~1 MB reserved** (8.3) |
| Creation | ~1 ms — a syscall |
| Context switch | ~1–10 µs — through the kernel |
| **Practical limit** | **Thousands** |

**So you can have thousands, not millions.** And that one fact generated everything in
9.8 and 9.9:

```
platform threads are expensive
   → you can't have one per request
      → so pool them (9.8)
         → so a blocked thread is a wasted expensive resource
            → so never block: use callbacks and futures (9.9)
               → so your code becomes a pipeline of continuations
                  → so stack traces, debuggers and try/catch stop working
```

**Virtual threads cut the root.** Threads become cheap, so you can have one per task, so
blocking is fine again, so the whole tower of workarounds becomes unnecessary.

---

## ⭐ What a virtual thread is

> **A continuation on the heap, scheduled by the JVM onto a small pool of carrier
> threads.**

```
    millions of virtual threads (heap objects, stacks grow on demand)
              │  │  │  │  │  │  │  │
              ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼
    ┌───────────────────────────────────┐
    │  carrier threads (a ForkJoinPool) │   ← ~one per CPU core
    └───────────────────────────────────┘
              │  │  │  │
              ▼  ▼  ▼  ▼
         real OS threads
```

| | Platform thread | Virtual thread |
|---|---|---|
| Backed by | An OS thread | A **heap object** |
| Stack | ~1 MB, reserved upfront | **Grows and shrinks on the heap** — starts at a few hundred bytes |
| Creation | ~1 ms | **~1 µs** |
| Scheduled by | The OS kernel | **The JVM** |
| Practical count | Thousands | **Millions** |

### ⭐ Mounting and unmounting

**This is the mechanism.**

```
1. A virtual thread MOUNTS on a carrier thread and runs.
2. It hits a blocking call — socket read, file I/O, sleep, lock.
3. The JVM COPIES ITS STACK OFF the carrier onto the heap. It UNMOUNTS.
4. The carrier immediately runs a different virtual thread.
5. When the I/O completes, the virtual thread is rescheduled, its stack is
   copied back, and it MOUNTS again — possibly on a DIFFERENT carrier.
```

> **The blocking call didn't block an OS thread.** It parked a heap object. That's the
> whole trick.
>
> The JDK's I/O and concurrency APIs were rewritten to make this work: `Socket`,
> `InputStream`, `Files`, `BlockingQueue`, `ReentrantLock`, `CompletableFuture.join`,
> `Thread.sleep` — all unmount instead of blocking.

## Creating them

```java
// one-off
Thread.startVirtualThread(() -> doWork());

// with a builder
Thread.ofVirtual().name("worker-", 0).start(() -> doWork());
Thread.ofVirtual().unstarted(() -> doWork());

// ⭐ the one you'll actually use
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var task : tasks) {
        executor.submit(() -> handle(task));      // a NEW virtual thread per task
    }
}   // try-with-resources: waits for all of them (9.8, Java 19)
```

```java
// a million threads — this genuinely works
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 1_000_000).forEach(i ->
        exec.submit(() -> { Thread.sleep(1000); return i; }));
}
```

The same with platform threads needs ~1 TB of stack reservation and dies immediately.

## ⭐ Do not pool them

> **Pooling a virtual thread is a category error.**

```java
// ❌ completely wrong
Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// ✅
Executors.newVirtualThreadPerTaskExecutor();
```

**Pools exist to amortise an expensive resource** (9.8). Virtual threads are cheap —
~1 µs to create, a few hundred bytes. Pooling them adds queueing and contention to solve a
problem that no longer exists.

**And if you need to limit concurrency** — which is a different and legitimate concern —
use a **`Semaphore`** (9.10), not a pool:

```java
var dbLimit = new Semaphore(50);           // bound the DOWNSTREAM pressure
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> {
        dbLimit.acquire();
        try { return query(); } finally { dbLimit.release(); }
    });
}
```

> **Separate the two concerns: threads are free, resources are not.** Bound the resource,
> not the threads.

## ⭐ Pinning

**A pinned virtual thread cannot unmount** — it blocks its carrier thread, defeating the
purpose.

### Historically: inside `synchronized`

```java
synchronized (lock) {
    socket.read();          // ⚠️ pinned on Java 21 — blocks the CARRIER thread
}
```

On Java 21, a virtual thread blocking inside a `synchronized` block held its carrier. With
a small carrier pool, enough pinned threads could **starve the whole application** — all
carriers occupied, no virtual thread able to run.

```java
// ✅ the Java 21 workaround — ReentrantLock unmounts correctly (9.5)
lock.lock();
try { socket.read(); }
finally { lock.unlock(); }
```

### ⭐ How the situation has improved

**JDK 24 (JEP 491) fixed `synchronized`.** Virtual threads can now unmount inside
`synchronized` blocks and methods. The `monitorenter`/`monitorexit` implementation was
reworked so monitors are no longer tied to the carrier.

> **On Java 24+ you no longer need to rewrite `synchronized` into `ReentrantLock` for
> virtual threads.** On Java 21–23, you still do. This is a genuine
> check-your-version issue.

**Still pins, on every version:**

| Cause | Why |
|---|---|
| **Native frames** — JNI, FFM (11.9) | The JVM can't copy a native stack off the carrier |
| Class initialisers that block (8.2) | — |

```bash
-Djdk.tracePinnedThreads=full     # Java 21–23, diagnose pinning
-Xlog:jfr                          # JFR emits VirtualThreadPinned events
```

## ⭐ What they do NOT help

> **Virtual threads are a *throughput* tool for *blocking I/O* only.**

| | Helps? |
|---|---|
| Thousands of concurrent HTTP calls | ✅ **Enormously** |
| Database queries, file I/O, RPC | ✅ |
| A web server handling 100k connections | ✅ |
| **CPU-bound work** | ❌ **No.** You still have N cores |
| Making a single request faster | ❌ **No.** Latency is unchanged |

```java
// ❌ pointless — you have 8 cores; a million virtual threads doesn't change that
IntStream.range(0, 1_000_000).forEach(i ->
    vExec.submit(() -> expensiveMathComputation(i)));
```

For CPU-bound work, use a **fixed platform thread pool sized to your cores** (9.8) or
parallel streams (6.8). Virtual threads add scheduling overhead with no benefit.

> **They improve throughput, not latency.** A request that takes 100ms still takes 100ms.
> You can just serve far more of them at once.

## ⭐ `ThreadLocal` with millions of threads

`ThreadLocal` (9.1) technically works — but:

| Problem | |
|---|---|
| **Memory** | A million threads × per-thread values = a lot of heap (8.3) |
| **Inheritance** | `InheritableThreadLocal` copies to each child — a million copies |
| **The pooling leak is gone** ✅ | Virtual threads aren't reused, so the 9.1 pooled-thread leak doesn't apply |

**This is why scoped values exist** (9.12) — an immutable, inheritable, structurally-scoped
replacement that costs nothing per thread:

```java
// ScopedValue — Java 25
private static final ScopedValue<User> USER = ScopedValue.newInstance();

ScopedValue.where(USER, currentUser).run(() -> {
    handleRequest();          // USER.get() works anywhere inside, no leak possible
});
```

## Observability

**A thread dump with a million threads is not useful**, so `jcmd` gained a new format
(8.9):

```bash
jcmd <pid> Thread.dump_to_file -format=json threads.json
```

JSON, **grouped by the executor/scope that created them**, rather than a flat list of a
million stacks. Virtual threads do **not** appear in a classic `jstack` dump.

> ⚠️ **Name your virtual threads** if you want to find them —
> `Thread.ofVirtual().name("handler-", 0)`. Unnamed virtual threads show as blank, which
> makes a dump much harder to read.

## ⭐ What changes in practice

```java
// ===== before =====
var pool = Executors.newFixedThreadPool(200);       // sized by the I/O formula (9.8)
CompletableFuture
    .supplyAsync(() -> fetchUser(id), pool)
    .thenComposeAsync(u -> fetchOrders(u), pool)
    .thenApplyAsync(this::summarise, pool)
    .exceptionally(ex -> fallback);
```

```java
// ===== after =====
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> {
        var user   = fetchUser(id);       // blocks. Fine.
        var orders = fetchOrders(user);   // blocks. Fine.
        return summarise(orders);
    });
}
```

**What you get back:** real stack traces, working debuggers, `try`/`catch` (4.3),
try-with-resources, and code that reads top to bottom.

**Framework support:** Spring Boot 3.2+ (`spring.threads.virtual.enabled=true`), Tomcat 11,
Jetty 12, Helidon Níma, Quarkus. Mostly a configuration flag.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| **Pooling virtual threads** | A category error. One per task |
| Using them for CPU-bound work | No benefit. You still have N cores |
| Expecting lower latency | **Throughput**, not latency |
| `synchronized` + blocking I/O on Java 21–23 | **Pins** the carrier. Fixed in **24** |
| Native/JNI calls | Still pin, on every version |
| `ThreadLocal` at a million-thread scale | Use **scoped values** (9.12) |
| Expecting `jstack` to show them | Use `Thread.dump_to_file -format=json` |
| Sizing a virtual thread "pool" | Bound the **resource** with a `Semaphore` (9.10) |

## Recap

| Concept | One line |
|---|---|
| **What** | A **continuation on the heap**, scheduled onto carrier threads. `Java 21` |
| Cost | ~1 µs to create, a few hundred bytes — vs ~1 ms and ~1 MB |
| **Mount/unmount** | Blocking copies the stack **off** the carrier; the carrier runs someone else |
| Create | `Executors.newVirtualThreadPerTaskExecutor()` |
| ⭐ **Don't pool** | Bound resources with a **`Semaphore`**, not threads |
| **Pinning** | `synchronized` pinned on 21–23, **fixed in 24**. Native frames always pin |
| **Not for** | **CPU-bound work.** Throughput, not latency |
| Replaces | Most `CompletableFuture` chains for sequential I/O (9.9) |
