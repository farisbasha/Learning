# 9.8 — Executors and thread pools

> **What this is:** **Stop creating threads. Submit tasks instead.**

---

## The interfaces

```java
Executor                 // execute(Runnable) — that's the whole interface
  └─ ExecutorService     // submit(), shutdown(), invokeAll(), Future
       └─ ScheduledExecutorService    // schedule(), scheduleAtFixedRate()
```

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

pool.execute(() -> doWork());                    // fire and forget
Future<String> f = pool.submit(() -> compute()); // returns a Future
```

**Why this beats `new Thread()` (9.1):** threads are reused (creation is ~1ms and ~1MB),
the queue gives you backpressure, and you get lifecycle management, scheduling and results.

---

## ⭐ The `Executors` factory methods — and the hidden risk

```java
Executors.newFixedThreadPool(4);       // ⚠️ UNBOUNDED queue
Executors.newCachedThreadPool();       // ⚠️ UNBOUNDED thread count
Executors.newSingleThreadExecutor();   // ⚠️ UNBOUNDED queue
Executors.newScheduledThreadPool(2);
Executors.newWorkStealingPool();       // a ForkJoinPool
Executors.newVirtualThreadPerTaskExecutor();   // Java 21 — see 9.11
```

**Two of these are memory risks, and the reason is the same each time: an unbounded
something.**

### `newFixedThreadPool` — an unbounded queue

```java
// what it actually constructs
new ThreadPoolExecutor(4, 4, 0L, MILLISECONDS,
    new LinkedBlockingQueue<Runnable>());     // ⭐ UNBOUNDED (9.7)
```

Tasks arriving faster than 4 threads can process them **queue up without limit**. The queue
grows until `OutOfMemoryError: Java heap space` (8.3).

> **Same lesson as 9.7: the bound is the backpressure.** Without it, overload becomes a
> crash instead of a slowdown.

### `newCachedThreadPool` — an unbounded thread count

```java
new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, SECONDS,
    new SynchronousQueue<Runnable>());        // ⭐ zero capacity → always creates a thread
```

A `SynchronousQueue` has no capacity, so every task that can't be handed to an idle thread
**creates a new one**. Under a burst you get thousands of platform threads (~1MB stack
each, 9.1) → `OutOfMemoryError: unable to create native thread`.

> **Never use `newCachedThreadPool` in a server.** It has no upper bound on anything.

## ⭐ Building a `ThreadPoolExecutor` explicitly

```java
var executor = new ThreadPoolExecutor(
    4,                                        // core pool size
    10,                                       // max pool size
    60L, TimeUnit.SECONDS,                    // keep-alive for threads above core
    new ArrayBlockingQueue<>(100),            // ⭐ BOUNDED queue (9.7)
    new ThreadFactoryBuilder().setNameFormat("worker-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy() // ⭐ rejection policy
);
```

### ⚠️ How the parameters actually interact

**This order surprises everyone:**

```
1. threads < core        → create a new thread
2. else                  → QUEUE the task
3. queue full            → create a thread, up to max
4. queue full AND at max → REJECT (rejection policy)
```

> ⭐ **The queue fills up *before* the pool grows past core size.** With an **unbounded**
> queue, step 3 never happens — **`maxPoolSize` is silently ignored** and your pool never
> exceeds `corePoolSize`. This catches everyone once.

### The rejection policies

| Policy | Behaviour |
|---|---|
| `AbortPolicy` (default) | Throws `RejectedExecutionException` |
| ⭐ **`CallerRunsPolicy`** | **The submitting thread runs the task itself** — natural backpressure, because the producer is now busy and stops submitting |
| `DiscardPolicy` | Silently drops it ⚠️ |
| `DiscardOldestPolicy` | Drops the oldest queued task ⚠️ |

> **`CallerRunsPolicy` is usually the right choice for a server.** It throttles the
> producer instead of dropping work or crashing.

### ⭐ Name your threads

```java
new ThreadFactory() {
    private final AtomicInteger n = new AtomicInteger(1);
    public Thread newThread(Runnable r) {
        return new Thread(r, "order-processor-" + n.getAndIncrement());
    }
}
```

A thread dump full of `pool-1-thread-7` tells you nothing (8.9). Named threads make
production debugging dramatically easier. **Always set a thread factory.**

## ⭐ Pool sizing

| Work type | Formula |
|---|---|
| **CPU-bound** | `Runtime.getRuntime().availableProcessors()` (+1) |
| **I/O-bound** | `cores × (1 + waitTime / computeTime)` |

**Why they differ:** a CPU-bound thread uses its core continuously — more threads than
cores just adds context switches. An I/O-bound thread is **blocked most of the time**, so
you need many more to keep the cores busy.

```
a task that waits 90ms and computes 10ms:
   8 cores × (1 + 90/10) = 8 × 10 = 80 threads
```

> ⭐ **And this formula is exactly what virtual threads make obsolete** (9.11). The whole
> reason it exists is that platform threads are too expensive to have one per blocking
> task. With virtual threads you have one per task and stop sizing pools at all.

**Never share one pool between CPU-bound and I/O-bound work** — one slow I/O task starves
the CPU work. Use separate pools. (Same hazard as the common `ForkJoinPool` in 6.8.)

## ⭐ Shutdown done right

```java
pool.shutdown();                                       // no new tasks; finish the queue
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                                // interrupt running tasks (9.1)
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        log.error("pool did not terminate");
    }
}
```

| Method | Does |
|---|---|
| `shutdown()` | Rejects new tasks; **runs everything already queued** |
| `shutdownNow()` | Rejects new; **drops the queue**; **interrupts** running tasks |
| `awaitTermination(t, u)` | Blocks until done or timeout |

> ⚠️ **`shutdownNow()` only interrupts.** A task that swallows `InterruptedException` (9.1)
> ignores it and runs forever. The two-phase pattern above is the correct shape.
>
> ⚠️ **A non-daemon pool thread keeps the JVM alive** (9.1). Forgetting `shutdown()` means
> your program never exits — a very common bug.

### try-with-resources `Java 19`

`ExecutorService` now implements `AutoCloseable` (4.3):

```java
try (var pool = Executors.newFixedThreadPool(4)) {
    pool.submit(task1);
    pool.submit(task2);
}   // close() = shutdown() + awaitTermination(forever)
```

Much harder to get wrong. ⚠️ Note it waits **indefinitely** — fine for a bounded batch,
wrong if a task might hang.

## ⭐ `Future` and its limitations

```java
Future<String> f = pool.submit(() -> compute());

f.get();                       // ⚠️ BLOCKS
f.get(5, TimeUnit.SECONDS);    // with a timeout
f.cancel(true);                // true = interrupt if running
f.isDone();
```

**The limitations that created `CompletableFuture`** (9.9):

| Limitation | |
|---|---|
| **`get()` blocks** | Defeats the point of async |
| **No composition** | Can't chain "when this finishes, do that" |
| **No completion callback** | You must poll `isDone()` or block |
| **No combining** | Can't express "when all of these finish" |

### ⚠️ Exceptions are swallowed

```java
pool.submit(() -> { throw new RuntimeException("boom"); });
// nothing printed. The exception is stored in the Future you ignored.
```

```java
pool.execute(() -> { throw new RuntimeException("boom"); });
// ✅ this one DOES reach the UncaughtExceptionHandler (9.1)
```

> ⭐ **`submit()` swallows; `execute()` doesn't.** Silently-failing scheduled tasks are a
> classic production bug — a `scheduleAtFixedRate` task that throws **stops running
> forever**, with no log line.
>
> **Always either call `get()`, or wrap the task body in try/catch and log** (4.4).

## `ForkJoinPool` and work stealing

Designed for **divide-and-conquer** CPU-bound work.

```java
class SumTask extends RecursiveTask<Long> {
    private final int[] arr; private final int lo, hi;

    protected Long compute() {
        if (hi - lo < 1000) {                      // small enough — do it directly
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += arr[i];
            return sum;
        }
        int mid = (lo + hi) / 2;
        var left = new SumTask(arr, lo, mid);
        left.fork();                               // run asynchronously
        var right = new SumTask(arr, mid, hi);
        long r = right.compute();                  // ⭐ compute one side on THIS thread
        return r + left.join();
    }
}
```

**Work stealing:** each thread has its own deque. It pushes and pops its own tasks from one
end; **an idle thread steals from the other end of a busy thread's deque**. That keeps all
cores busy without central coordination.

### ⚠️ The common pool — who else is using it

```java
ForkJoinPool.commonPool()       // parallelism = availableProcessors() - 1
```

**Shared by the entire JVM**, and used by:
- **Parallel streams** (6.8)
- **`CompletableFuture`** without an explicit executor (9.9)
- Any library that didn't specify a pool

> ⭐ **One blocking task on the common pool stalls every other user of it** — parallel
> streams elsewhere, `CompletableFuture` chains, library code. **Never do blocking I/O on
> the common pool.** (6.8 has the full version of this hazard.)

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `newFixedThreadPool` | **Unbounded queue** → OOM under load |
| `newCachedThreadPool` | **Unbounded threads** → OOM under burst |
| `maxPoolSize` with an unbounded queue | **Silently ignored** — the queue fills first |
| Forgetting `shutdown()` | Non-daemon threads keep the JVM alive |
| Relying on `shutdownNow()` to stop tasks | It only **interrupts**. A task can ignore it |
| `submit()` and never calling `get()` | The exception **vanishes** |
| A `scheduleAtFixedRate` task that throws | **Stops rescheduling, silently, forever** |
| Blocking I/O on the common pool | Stalls parallel streams and `CompletableFuture` JVM-wide |
| One pool for CPU and I/O work | I/O tasks starve the CPU work |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `new Thread()` per task | An executor, or virtual threads (9.11) |
| `newCachedThreadPool()` in a server | A bounded `ThreadPoolExecutor`, or virtual threads |
| `Executors.newFixedThreadPool` for untrusted load | Explicit `ThreadPoolExecutor` with a bounded queue |
| Unnamed pool threads | A `ThreadFactory` with names |

---

## Recap

| Concept | One line |
|---|---|
| Submit tasks, don't create threads | Reuse, backpressure, lifecycle, results |
| **Factory methods** | `newFixedThreadPool` = unbounded **queue**; `newCachedThreadPool` = unbounded **threads** |
| **Parameter order** | core → **queue** → max → reject. Unbounded queue ⟹ max ignored |
| Rejection | **`CallerRunsPolicy`** for natural backpressure |
| Sizing | CPU: `cores`. I/O: `cores × (1 + wait/compute)` — **obsoleted by 9.11** |
| Shutdown | `shutdown` → `awaitTermination` → `shutdownNow`. Or try-with-resources `Java 19` |
| `Future` | Blocking `get`, no composition, **swallows exceptions** |
| Common pool | Shared JVM-wide. **Never block on it** |
