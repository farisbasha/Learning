# 9.2 — What actually goes wrong

> **What this is:** **Three distinct problems that beginners merge into one vague idea of
> "thread safety".** Separating them is the whole point of this page — each has a different
> cause and a different fix.

---

## ⭐ The three problems

| | Problem | One line |
|---|---|---|
| **1** | **Atomicity** | An operation you think is one step is several |
| **2** | **Visibility** | One thread's write may **never** become visible to another |
| **3** | **Reordering** | Your instructions don't execute in the order you wrote them |

**All three are invisible in single-threaded code.** That's why they're hard.

---

## 1. Atomicity — `count++` is three operations

```java
count++;
```

Compiles to (8.1):

```
getfield  count     // 1. READ
iconst_1
iadd                // 2. MODIFY
putfield  count     // 3. WRITE
```

**The lost update:**

```
count = 0

Thread A            Thread B
────────            ────────
read  count → 0
                    read  count → 0
add 1        → 1
                    add 1        → 1
write count = 1
                    write count = 1

count == 1          ← two increments, one result
```

```java
class Counter {
    private int count;
    void increment() { count++; }     // ❌
    int get() { return count; }
}
```

**Measured** — 8 threads × 100,000 increments = 800,000 expected, OpenJDK 17:

```
run 1: plain++ = 397,584     AtomicInteger = 800,000
run 2: plain++ = 455,895     AtomicInteger = 800,000
run 3: plain++ = 685,705     AtomicInteger = 800,000
```

> ⭐ **Over half the increments vanished, and the loss is different every run.** This is
> not a subtle 1-in-a-million effect — under real contention `count++` loses updates
> constantly. Fixed by an atomic (9.6) or a lock (9.4).

**The two shapes of race condition:**

| Shape | Example |
|---|---|
| **Read-modify-write** | `count++`, `balance -= amount` |
| **Check-then-act** | `if (map.get(k) == null) map.put(k, v);` |

Check-then-act is the sneakier one because each individual operation *is* atomic — the
**composition** isn't:

```java
// ❌ both operations are individually thread-safe. The pair is not.
if (!map.containsKey(key)) {
    map.put(key, value);         // another thread may have put it between the two lines
}

// ✅
map.putIfAbsent(key, value);     // ONE atomic operation (9.7)
```

> **This is why `Collections.synchronizedMap` doesn't make your code correct** (9.7) —
> it makes each *method* atomic, not your *sequence* of methods.

## ⭐ 2. Visibility — the one that shocks people

```java
class Worker {
    private boolean running = true;     // ⚠️ not volatile

    void stop() { running = false; }

    void run() {
        while (running) {                // may loop FOREVER
            doWork();
        }
    }
}
```

Thread A calls `run()`. Thread B calls `stop()`.

**Thread A may never see the change. Not "late" — possibly never.**

### Why

```
    CPU 0                      CPU 1
  ┌────────┐                ┌────────┐
  │ Thread │                │ Thread │
  │   A    │                │   B    │
  ├────────┤                ├────────┤
  │ L1 cache│               │ L1 cache│
  │running= │               │running= │
  │  true   │               │  false  │   ← B wrote here
  └────┬───┘                └────┬───┘
       └────────┬────────────────┘
            main memory
```

Three separate mechanisms can each cause this:

1. **CPU caches** — B's write sits in its store buffer or L1 cache and isn't flushed
2. **The JIT hoists the read out of the loop** — this is the big one:

```java
// what you wrote
while (running) { doWork(); }

// what the JIT is ALLOWED to compile it to, because nothing says otherwise
if (running) { while (true) { doWork(); } }     // read once, loop forever
```

3. **The compiler may keep it in a register** and never re-read memory at all

> ⭐ **The JVM is not doing anything wrong here.** Without synchronisation, there is no
> *happens-before* relationship (9.3) between B's write and A's read, so the JVM is
> **permitted** to assume no other thread modifies it. Single-threaded, this is a valid and
> valuable optimisation.

**The fix is in 9.3** — `volatile`, or any other happens-before edge.

> ⚠️ **This is the one you cannot find by testing.** It typically doesn't reproduce in a
> debugger (which inhibits optimisation), doesn't reproduce with a `println` in the loop
> (which synchronises internally), and often doesn't reproduce until the JIT reaches C2
> (8.8) — which needs ~10,000 iterations. **It shows up in production and nowhere else.**

## ⭐ 3. Reordering

**The compiler, the JIT and the CPU all reorder your instructions, and are permitted to.**

```java
// you wrote
a = 1;        // (1)
b = 2;        // (2)

// any of these may actually execute
(1) then (2)
(2) then (1)        ← legal! they're independent
```

Single-threaded, the result is identical — that's the rule (*as-if-serial*). **Another
thread can observe the difference.**

### The classic demonstration

```java
int x = 0, y = 0;
int a = 0, b = 0;

Thread 1:  x = 1;  a = y;
Thread 2:  y = 1;  b = x;
```

Can `a == 0 && b == 0`?

**Intuitively no** — one of the writes must happen first. **In practice yes**, and you can
observe it on real hardware: both CPUs buffer their write and read the other's stale
value.

Who reorders:

| Level | Does |
|---|---|
| **`javac`** | Very little |
| **The JIT** | A lot — hoisting, sinking, combining (8.8) |
| **The CPU** | Out-of-order execution, store buffers |
| **The cache system** | Writes become visible in a different order than issued |

> ⚠️ **x86 reorders much less than ARM.** Code that's broken by reordering often works
> perfectly on an Intel laptop and fails on ARM servers (Graviton, Apple silicon,
> Ampere). **"It works on my machine" is a specifically dangerous phrase here.**

## Unsafe publication — a half-constructed object

```java
// ❌
class Holder {
    private int value;
    Holder(int value) { this.value = value; }
    void check() { if (value != value) throw new AssertionError("impossible"); }
}

// Thread A
holder = new Holder(42);        // ← not as atomic as it looks

// Thread B
holder.check();                  // 💥 can actually throw
```

`new Holder(42)` is three steps:

```
1. allocate memory
2. run the constructor (value = 42)
3. assign the reference to `holder`
```

**Steps 2 and 3 can be reordered.** Thread B can see a non-null `holder` whose `value` is
still `0`. And because the field is read twice with no synchronisation, `value != value`
can genuinely be true.

> This is *exactly* the bug in broken double-checked locking (9.3), and it's why the
> **`final` field guarantee** (9.3) matters so much: a `final` field is guaranteed visible
> and correctly initialised to any thread that sees the object, with no synchronisation at
> all. **It's the strongest argument for immutability** (2.1, 2.10).

## ⭐ Deadlock, livelock, starvation, lock convoy

### Deadlock — a cycle in the wait-for graph

```java
// ❌
void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

```
transfer(A, B)  locks A, wants B
transfer(B, A)  locks B, wants A        ← neither ever proceeds
```

**The four conditions, all required:**
1. Mutual exclusion  2. Hold and wait  3. No preemption  4. **Circular wait**

**The practical defence is to break #4 — consistent lock ordering** (9.4):

```java
// ✅ always lock in the same global order
Account first  = from.id() < to.id() ? from : to;
Account second = from.id() < to.id() ? to   : from;
synchronized (first) { synchronized (second) { ... } }
```

Spot it in a thread dump (8.9) — the JVM prints `Found one Java-level deadlock`.

### Livelock — everyone's busy, nobody progresses

Threads keep responding to each other and never make progress. Two people stepping aside
in a corridor, repeatedly.

```java
while (!lock.tryLock()) {
    Thread.sleep(10);        // both retry in lockstep, forever
}
```

Fix: **randomised backoff.**

### Starvation — one thread never gets the resource

A low-priority thread never scheduled, or a writer permanently blocked by a stream of
readers under a `ReadWriteLock` (9.5). Fix: fair locks (at a throughput cost).

### Lock convoy

Many threads contend for one lock. Each acquisition causes a context switch, the queue
never drains, and **throughput collapses** — often to *worse* than single-threaded.

Fix: reduce the critical section, shard the lock, or go lock-free (9.6).

## ⚠️ Why your machine may never reproduce what production does

| Your laptop | Production |
|---|---|
| x86 — strong memory ordering | **ARM** — weak ordering, reorders aggressively |
| 8 cores | 64 cores — far more real interleaving |
| Low load — few interleavings explored | Sustained load — millions of them |
| Debugger attached — inhibits JIT optimisation | Fully C2-optimised (8.8) |
| Short runs — the JIT never reaches C2 | Hours of C2-compiled execution |

> **A concurrency bug's probability is not fixed** — it's a function of load, core count,
> hardware and JIT state. Something that happens 1-in-10⁹ locally happens hourly at
> production volume.
>
> **This is why 9.3 is necessary**: you must be able to reason about whether code is
> correct, because you cannot observe it into correctness.

## Recap

| Problem | Cause | Fixed by |
|---|---|---|
| **Atomicity** | Multi-step operations interleave | `synchronized` (9.4), atomics (9.6) |
| **Visibility** | Caches, JIT hoisting, registers | `volatile` (9.3), locks |
| **Reordering** | Compiler, JIT and CPU are all permitted to | happens-before (9.3) |
| **Unsafe publication** | Constructor and assignment reorder | `final` fields, safe publication (9.3) |
| **Deadlock** | Circular wait | **Consistent lock ordering** |
| **Livelock** | Responding without progressing | Randomised backoff |
| **Starvation** | Never scheduled | Fairness |
| **Lock convoy** | Contention → context switches | Shorter critical sections, sharding |

| Race shapes | `count++` (read-modify-write) · `if (absent) put` (check-then-act) |
|---|---|
