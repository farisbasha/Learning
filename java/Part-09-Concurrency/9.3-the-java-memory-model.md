# 9.3 — The Java Memory Model

> **What this is:** **The theoretical core.** Genuinely difficult and genuinely necessary —
> it is the specification that says **which executions are legal at all**.
>
> 9.2 showed you what goes wrong. This page is the rulebook that tells you when it can't.

---

## ⭐ Why a memory model is needed

Without a specification, the three mechanisms from 9.2 are unbounded:

- **CPU caches and store buffers** — a write may sit in one core's buffer indefinitely
- **Compilers that are allowed to lie** — the JIT can hoist, sink, eliminate and reorder
  (8.8)

You need to know what the JVM is **permitted** to do, so you can know what it **can never**
do. The JMM (formalised in Java 5, JSR-133) is that contract.

> **The JMM is not a description of how the JVM works.** It's a contract about which
> executions are *legal* — deliberately loose, so the JIT and the CPU keep their freedom to
> optimise, and precise enough that you can write correct code.

---

## ⭐ happens-before — the single relation the whole model is built on

> **If action A *happens-before* action B, then A's effects are guaranteed visible to B,
> and A is guaranteed to appear to occur before B.**
>
> **If there is no happens-before between two actions, the JVM guarantees *nothing*.**

That's the whole model. Everything else is a list of what creates the relation.

### The rules you must know

| # | Rule |
|---|---|
| **1** | **Program order** — within **one thread**, earlier statements happen-before later ones |
| **2** | **Monitor lock** — unlocking a monitor happens-before any subsequent lock **of the same monitor** |
| **3** | **`volatile`** — a write to a volatile field happens-before every subsequent read **of that field** |
| **4** | **`Thread.start()`** — everything before `start()` happens-before anything in the new thread |
| **5** | **`Thread.join()`** — everything in a thread happens-before `join()` returns |
| **6** | **Transitivity** — A hb B and B hb C ⟹ A hb C |

Plus: interruption happens-before the interrupted thread detects it; a constructor
finishing happens-before its finalizer (irrelevant now, 8.7).

**Rule 1 is weaker than it sounds.** Program order applies *within* a thread — it's why
single-threaded code always behaves as written. It says **nothing** across threads.

**Rule 6 is the one that does the work:**

```java
// Thread A
data = 42;              // (1)
ready = true;           // (2)  volatile write

// Thread B
if (ready) {            // (3)  volatile read
    use(data);          // (4)  — sees 42. Guaranteed.
}
```

```
(1) hb (2)   by program order
(2) hb (3)   by the volatile rule
(3) hb (4)   by program order
─────────────────────────────
(1) hb (4)   by transitivity ⟹ `data` is visible, even though it isn't volatile
```

> ⭐ **This is the key insight.** One volatile write flushes *everything* the thread did
> before it. `data` needs no synchronisation of its own — it's carried along by the
> happens-before edge.

## ⭐ `volatile` — what it guarantees and what it doesn't

```java
private volatile boolean running = true;
```

**✅ Guarantees:**

| | |
|---|---|
| **Visibility** | A write is immediately visible to every subsequent read |
| **Ordering** | No reordering across the volatile access (it's a memory barrier) |
| **Atomicity of the access itself** | Including `long` and `double` (see below) |

This fixes 9.2's infinite loop:

```java
private volatile boolean running = true;
while (running) { doWork(); }        // ✅ the JIT may no longer hoist the read
```

**❌ Does NOT guarantee:**

```java
private volatile int count;
count++;                              // ❌ STILL A RACE
```

**`volatile` does not make compound operations atomic.** `count++` is still read-modify-write
(9.2) — now with guaranteed-fresh reads, and still losing updates.

```java
// ✅ use an atomic (9.6)
private final AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
```

> **The rule: `volatile` is for a flag one thread writes and others read.** The moment the
> new value depends on the old one, you need an atomic or a lock.

### The `long`/`double` non-atomicity footnote

Without `volatile`, a 64-bit `long` or `double` write **may be split into two 32-bit
writes**, and another thread can observe half of each — a value that was never written.

```java
private long id;                  // ⚠️ a torn read is legal
private volatile long id;         // ✅ atomic
private final long id;            // ✅ also safe (final field semantics, below)
```

Rare on 64-bit JVMs in practice, but it's in the spec, and it's free to avoid.

## ⭐ Safe publication — the four correct ways

**Publication** = making an object visible to another thread. 9.2 showed unsafe
publication handing out a half-constructed object.

**The four safe ways:**

| # | Method |
|---|---|
| **1** | Initialise the reference from a **static initialiser** (class init is thread-safe, 8.2) |
| **2** | Store it in a **`volatile`** field or an `AtomicReference` |
| **3** | Store it in a **`final`** field of a properly-constructed object |
| **4** | Store it into a field guarded by a **lock** (including a concurrent collection, 9.7) |

```java
// 1 — static initialiser; the JVM guarantees safe publication (8.2)
private static final Config CONFIG = new Config();

// 2 — volatile
private volatile Config config;
config = new Config();

// 3 — final field
private final Config config;          // set in the constructor

// 4 — guarded by a lock, or a concurrent collection
map.put("config", new Config());      // ConcurrentHashMap publishes safely
```

## ⭐ `final` field semantics — the guarantee that makes immutability free

> **If an object's fields are `final` and the constructor doesn't leak `this`, then any
> thread that sees a reference to the object is guaranteed to see its fields fully
> initialised — with no synchronisation at all.**

```java
public final class Point {
    private final int x, y;                     // final
    public Point(int x, int y) { this.x = x; this.y = y; }
}

// any thread that gets this reference, by ANY means, sees x and y correctly.
// no volatile, no lock, no cost.
```

**This is the single strongest argument for immutability** (2.1, 2.10), and the technical
reason records (2.6) are a concurrency feature as well as a syntax one.

> ⚠️ **The guarantee is void if the constructor leaks `this`** — registering a listener,
> starting a thread, or calling an overridable method from the constructor (2.1, 2.3). A
> reference escaping before construction finishes bypasses the whole guarantee.
>
> ```java
> // ❌ leaks `this` before construction completes
> public Point(int x, int y) {
>     this.x = x;
>     registry.register(this);     // another thread can now see a half-built Point
>     this.y = y;
> }
> ```

## ⭐ Data race, defined precisely

> **A data race is: two accesses to the same variable, at least one a write, with no
> happens-before relationship between them.**

**A program with a data race has no defined behaviour under the JMM.** Not "an unpredictable
value" — the *entire execution* is unspecified. Any result is legal, including ones that
seem impossible (like `value != value` in 9.2).

Note the distinction:

| | |
|---|---|
| **Data race** | A precise JMM term — unsynchronised conflicting access |
| **Race condition** | A general correctness term — the result depends on timing |

You can have a race condition with no data race (check-then-act on a
`ConcurrentHashMap`, 9.2) and vice versa.

## ⭐ Double-checked locking

The canonical JMM example — worth working through once.

```java
// ❌ BROKEN before Java 5, and still broken today without volatile
private static Singleton instance;

public static Singleton getInstance() {
    if (instance == null) {                    // first check, no lock
        synchronized (Singleton.class) {
            if (instance == null) {            // second check, with lock
                instance = new Singleton();    // 💥
            }
        }
    }
    return instance;
}
```

**Why it's broken:** `new Singleton()` is (9.2):

```
1. allocate
2. run the constructor
3. assign to `instance`
```

**Steps 2 and 3 may be reordered.** Another thread hitting the *first* check sees a
non-null `instance` — and gets a **half-constructed object**. It never enters the
synchronized block, so nothing saves it.

```java
// ✅ volatile fixes it
private static volatile Singleton instance;      // ← the only change
```

The volatile write (rule 3) prevents the reordering and establishes happens-before with
the unsynchronised read.

> Before Java 5 the old memory model didn't guarantee even this, which is why you'll find
> articles declaring double-checked locking "unfixable in Java". **That was true until
> 2004.** Another 0.3 dating signal.

### ⭐ The holder idiom is better

```java
public class Singleton {
    private Singleton() { }

    private static class Holder {                 // not initialised until first use
        static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

| | Double-checked locking | Holder idiom |
|---|---|---|
| Lazy | ✅ | ✅ |
| Thread-safe | Only with `volatile` | ✅ **By the JVM's class-init guarantee** (8.2) |
| Synchronisation cost after init | A volatile read every call | **None** |
| Easy to get wrong | ✅ Very | ❌ |

`Holder` isn't initialised until `getInstance()` first touches it, and **class
initialisation is guaranteed thread-safe and exactly-once by the JVM** (8.2). No locks, no
volatile, nothing to get wrong.

> **And for a singleton specifically, `enum Singleton { INSTANCE; }` is better still**
> (2.7) — it adds reflection and serialisation safety on top.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `volatile` makes `count++` safe | It doesn't. Compound ops still race |
| `volatile` on a collection reference protects the collection | It protects the **reference**, not the contents |
| Double-checked locking without `volatile` | Broken. A half-constructed object escapes |
| "It's only a boolean, it'll be fine" | Visibility has nothing to do with size |
| Synchronising the write but not the read | Happens-before needs **both** sides |
| `final` guarantees when the constructor leaks `this` | Void |

That fifth one is worth stating clearly:

```java
// ❌ only half-synchronised — no happens-before edge is created
synchronized void set(int v) { value = v; }
int get() { return value; }                    // unsynchronised read: no guarantee
```

**Both sides must use the same lock**, or you get no relation at all.

## Recap

| Concept | One line |
|---|---|
| **happens-before** | The only guarantee there is. No edge ⟹ no guarantees |
| The 6 rules | Program order · monitor · **volatile** · `start()` · `join()` · **transitivity** |
| Transitivity | A volatile write flushes everything before it |
| `volatile` ✅ | Visibility + ordering + atomic single access |
| `volatile` ❌ | **Compound operations.** `count++` still races |
| Safe publication | Static init · volatile · **final field** · lock/concurrent collection |
| **`final` fields** | Fully-initialised visibility **free** — unless the constructor leaks `this` |
| Data race | Conflicting access with no happens-before ⟹ **undefined behaviour** |
| DCL | Needs `volatile`. **Use the holder idiom** — or an enum |
