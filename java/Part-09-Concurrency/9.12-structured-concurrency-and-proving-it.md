# 9.12 — Structured concurrency, scoped values, and proving it works

> **What this is:** Where Java concurrency is going, **plus the only honest way to test any
> of this**. The last section of this page is the most important thing in Part 09.

---

## ⭐ The problem with unstructured concurrency

```java
var executor = Executors.newVirtualThreadPerTaskExecutor();

Future<User>   user   = executor.submit(() -> fetchUser(id));
Future<Orders> orders = executor.submit(() -> fetchOrders(id));

return new Page(user.get(), orders.get());
```

**What's wrong with this — and it's structural, not stylistic:**

| Problem | |
|---|---|
| `fetchUser` throws | `orders` **keeps running**, pointlessly, to completion |
| The caller is cancelled | **Neither** subtask is cancelled — they leak |
| `fetchOrders` hangs | You block on `user.get()` and never find out |
| Where did the work go? | **Nothing in the code or the stack says these tasks belong to this method** |

> ⭐ **Concurrency lost the one structure that makes sequential code tractable.** In
> sequential code, a block owns its work — when it exits, the work is done or it threw.
> `submit()` breaks that: work escapes the block with no lifetime relationship to it.
>
> **This is the same argument `goto` lost in 1968** — unstructured control flow versus
> block structure.

---

## ⭐ Structured concurrency

> **Child tasks are scoped to a block. If the block exits, they are cancelled. Errors
> propagate to the parent.**

`preview — 7th round in Java 27`

```java
try (var scope = StructuredTaskScope.open()) {

    var user   = scope.fork(() -> fetchUser(id));      // a virtual thread each (9.11)
    var orders = scope.fork(() -> fetchOrders(id));

    scope.join();                                       // wait for both

    return new Page(user.get(), orders.get());

}   // ⭐ the block CANNOT exit with tasks still running
```

**What the scope guarantees:**

| Guarantee | |
|---|---|
| **Cancellation propagates down** | Scope fails ⟹ all subtasks are interrupted (9.1) |
| **Errors propagate up** | A subtask's exception surfaces at `join()` |
| **No leaks** | `close()` cannot return while a subtask runs |
| **Visible in the stack** | Thread dumps show the parent–child relationship (8.9, 9.11) |

### The two shapes, via joiners

```java
// ⭐ ALL must succeed — fail fast if any one fails
try (var scope = StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())) {
    var a = scope.fork(() -> callServiceA());
    var b = scope.fork(() -> callServiceB());
    scope.join();                              // throws if either failed
    return combine(a.get(), b.get());
}

// ⭐ FIRST success wins — cancel the losers
try (var scope = StructuredTaskScope.open(Joiner.<String>anySuccessfulResultOrThrow())) {
    scope.fork(() -> queryMirror1());
    scope.fork(() -> queryMirror2());
    return scope.join();                       // the first result; others cancelled
}
```

> ⚠️ **The API has changed across preview rounds** — `ShutdownOnFailure`/`ShutdownOnSuccess`
> in early rounds became `Joiner` in later ones. This is exactly the preview instability
> 7.5 warns about. **Check the API for your JDK**, and don't ship it in production.

## ⭐ Scoped values `Java 25`

An **immutable, inheritable replacement for `ThreadLocal`** that works with millions of
virtual threads (9.11).

```java
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

// bind for the duration of a block — and ONLY that block
ScopedValue.where(CURRENT_USER, user).run(() -> {
    handleRequest();                 // anything called here can read it
});

// anywhere down the call stack
User u = CURRENT_USER.get();
```

| | `ThreadLocal` (9.1) | `ScopedValue` |
|---|---|---|
| Mutable | ✅ `set()` anywhere | ❌ **Immutable** — bound once per scope |
| Lifetime | Until `remove()` — **or forever** in a pool | **The block.** Automatic |
| Leaks | ⚠️ The classic pooled-thread leak (8.7) | **Impossible by construction** |
| Inheritance | Copies to each child | **Shared, not copied** — no per-thread cost |
| Cost at a million threads | Heavy | Negligible |

> ⭐ **The leak class from 9.1 and 8.7 is eliminated by construction**, not by discipline.
> You cannot forget to `remove()` because there is no `remove()` — the binding ends when
> the block ends.

**It composes with structured concurrency:** a value bound in the parent scope is
automatically visible to every forked subtask, with no copying.

```java
ScopedValue.where(CURRENT_USER, user).run(() -> {
    try (var scope = StructuredTaskScope.open()) {
        scope.fork(() -> { CURRENT_USER.get(); ... });   // ✅ inherited
        scope.join();
    }
});
```

## ⭐ Testing concurrent code

**This is the most important section in Part 09**, and it's why the part opened with a
warning.

### Why unit tests give false confidence

```java
@Test
void counterIsThreadSafe() throws Exception {
    var counter = new Counter();                  // has the count++ bug from 9.2
    var pool = Executors.newFixedThreadPool(10);
    for (int i = 0; i < 1000; i++) pool.submit(counter::increment);
    pool.shutdown();
    pool.awaitTermination(1, MINUTES);
    assertEquals(1000, counter.get());            // ⚠️ often PASSES
}
```

**This test passes far more often than it should.** Why:

| | |
|---|---|
| **Too few iterations** | The JIT hasn't reached C2 (8.8) — the code is still interpreted and slow enough not to interleave |
| **Too little contention** | 1,000 operations complete before real overlap happens |
| **x86 is forgiving** | Your Mac reorders far less than an ARM server (9.2) |
| **A passing test proves nothing** | It explored *one* interleaving out of astronomically many |

> ⭐ **You cannot test your way to concurrent correctness.** A test that passes tells you
> that one interleaving worked. It says nothing about the other 10²⁰.
>
> **This is why 9.2 and 9.3 are mandatory.** Reasoning is the primary tool; testing is a
> weak secondary check.

### Stress testing — better, still not proof

```java
@RepeatedTest(100)
void stress() throws Exception {
    var counter = new Counter();
    int threads = Runtime.getRuntime().availableProcessors() * 4;   // oversubscribe
    var start = new CountDownLatch(1);                              // starting gun (9.10)
    var done  = new CountDownLatch(threads);

    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < threads; i++) {
            exec.submit(() -> {
                start.await();                     // ⭐ maximise simultaneous start
                for (int j = 0; j < 100_000; j++) counter.increment();   // enough for C2
                done.countDown();
                return null;
            });
        }
        start.countDown();
        done.await();
    }
    assertEquals(threads * 100_000, counter.get());
}
```

**What makes this better:** a starting gun for real simultaneity, enough iterations for the
JIT to reach C2, oversubscribed threads, and repetition.

**It still only samples the interleaving space.** It raises your probability of catching a
bug; it does not prove absence.

### ⭐ `jcstress` — memory-model-level verification

The OpenJDK tool for testing **memory model** behaviour (9.3). It runs a tiny snippet
billions of times with carefully-constructed interleavings and **enumerates every outcome
it observed**:

```java
@JCStressTest
@Outcome(id = "1, 1", expect = ACCEPTABLE,            desc = "both saw the write")
@Outcome(id = "0, 0", expect = ACCEPTABLE_INTERESTING, desc = "⭐ reordering observed")
@State
public class Reordering {
    int x, y;

    @Actor public void actor1(II_Result r) { x = 1; r.r1 = y; }
    @Actor public void actor2(II_Result r) { y = 1; r.r2 = x; }
}
```

Run this and it will report `0, 0` — **you will actually observe the reordering from
9.2**, with a count. Nothing else makes the JMM concrete in the same way.

> **Run jcstress once on the 9.2 reordering example.** Seeing `0, 0` appear with a real
> occurrence count is the single most convincing thing in this part.

### Static analysis and annotations

```java
@ThreadSafe
public class Counter {
    @GuardedBy("lock")
    private int count;

    private final Object lock = new Object();

    public void increment() {
        synchronized (lock) { count++; }
    }
}
```

From `jcip-annotations` (the *Java Concurrency in Practice* annotations) or
`com.google.errorprone.annotations`.

| Annotation | Means |
|---|---|
| `@ThreadSafe` / `@NotThreadSafe` | **Documents intent** — the most valuable part |
| `@Immutable` | All fields final, no mutation (2.10, 9.3) |
| `@GuardedBy("lock")` | This field may only be accessed holding that lock |

**ErrorProne and SpotBugs check `@GuardedBy` at build time** — catching unsynchronised
access to a guarded field. That's a genuine static guarantee, not documentation.

> **Even without a checker, `@GuardedBy` is worth writing.** The next person to touch the
> class needs to know which lock protects what, and there is no other place to record it.

## ⭐ The discipline that beats all of the above

> **Confine state to one thread, or make it immutable.**
>
> **Most correct concurrent Java has very few locks in it.**

| Strategy | How |
|---|---|
| ⭐ **Immutability** | Records (2.6), `final` fields. **The `final` field guarantee (9.3) makes them free to share** |
| ⭐ **Confinement** | One thread owns the data. A `BlockingQueue` (9.7) hands off ownership |
| **Copy at the boundary** | `List.copyOf` (5.7, 2.10) — the receiver can't see your mutations |
| **Concurrent collections** | Someone already got the hard part right (9.7) |
| **Higher-level tools** | Executors, `CompletableFuture`, structured concurrency |
| Locks | **Last.** When you genuinely have shared mutable state |

```java
// ❌ shared mutable state, protected by discipline
class Service {
    private final Map<String, Integer> counts = new HashMap<>();
    private final Object lock = new Object();
    void record(String k) { synchronized (lock) { counts.merge(k, 1, Integer::sum); } }
}

// ✅ the same thing, no lock to get wrong
class Service {
    private final ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
    void record(String k) { counts.merge(k, 1, Integer::sum); }     // atomic (9.7)
}

// ✅✅ better still — no shared mutable state at all
record Event(String key, Instant at) { }                             // immutable (2.6)
// events flow through a BlockingQueue; one consumer owns the aggregation
```

> **Everything in 9.4–9.10 is for the cases where you cannot do this.** Reach for those
> second, not first. A codebase full of `synchronized` blocks usually has a design problem,
> not a concurrency problem.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| A passing concurrency test means correct | It explored **one** interleaving |
| `submit()` + `get()` | Unstructured — no cancellation, no propagation, leaks |
| Using `StructuredTaskScope` in production | **Preview.** The API changes between rounds (7.5) |
| `ScopedValue` is a mutable `ThreadLocal` | **Immutable**, block-scoped |
| Adding locks until it works | Confine or make immutable instead |
| Skipping 9.2/9.3 because the tools look simple | Testing cannot substitute for reasoning |

## Recap

| Concept | One line |
|---|---|
| **Unstructured** | `submit()` lets work escape the block — no cancellation, no propagation |
| **Structured concurrency** | Subtasks scoped to a block; cancel down, propagate up. `preview` |
| Joiners | `allSuccessfulOrThrow` · `anySuccessfulResultOrThrow` |
| **`ScopedValue`** `Java 25` | Immutable, block-scoped, inheritable. **Leaks impossible by construction** |
| Unit tests | **False confidence.** One interleaving |
| Stress tests | Starting gun + 100k iterations + repetition. Sampling, not proof |
| **jcstress** | Memory-model verification. Run it once on the 9.2 example |
| `@GuardedBy` | Documents *and* checks which lock protects what |
| ⭐ **The discipline** | **Confine or make immutable. Most correct concurrent Java has very few locks.** |
