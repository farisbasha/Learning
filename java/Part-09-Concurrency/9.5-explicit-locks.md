# 9.5 — Explicit locks

> **What this is:** **More capability, more responsibility** — you now have to release the
> lock yourself.

---

## ⭐ The mandatory shape

```java
private final ReentrantLock lock = new ReentrantLock();

void method() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock();          // ⭐ MANDATORY, and in finally
    }
}
```

> **`synchronized` releases automatically, even on an exception. `ReentrantLock` does
> not.** Forget the `finally` and one thrown exception leaks the lock permanently —
> every other thread blocks forever, and the stack trace points at the wrong place.
>
> **Acquire *outside* the try.** If `lock()` itself throws, you must not `unlock()` a lock
> you never acquired.

---

## `ReentrantLock` — what you get over `synchronized`

```java
lock.lock();                                  // blocks, like synchronized

lock.tryLock();                               // ⭐ returns false immediately
lock.tryLock(5, TimeUnit.SECONDS);            // ⭐ times out
lock.lockInterruptibly();                     // ⭐ responds to interrupt (9.1)

new ReentrantLock(true);                      // ⭐ fair — FIFO order
```

### `tryLock` — deadlock avoidance without lock ordering

```java
// acquire both or neither — and back off if you can't
boolean transfer(Account from, Account to, int amount) {
    if (from.lock.tryLock()) {
        try {
            if (to.lock.tryLock()) {
                try {
                    from.debit(amount); to.credit(amount);
                    return true;
                } finally { to.lock.unlock(); }
            }
        } finally { from.lock.unlock(); }
    }
    return false;                             // caller retries with backoff
}
```

This breaks deadlock by removing **hold-and-wait** (condition #2 from 9.2) instead of
circular wait. Consistent ordering (9.4) is usually simpler — but `tryLock` works when you
can't impose an order.

> ⚠️ Retry with **randomised backoff**, or you get livelock (9.2).

### Fairness — and why it's usually wrong

```java
new ReentrantLock(true);       // fair: longest-waiting thread wins
new ReentrantLock();           // unfair (default): barging allowed
```

**Fair locks can be 10–100× slower.** An unfair lock lets a running thread barge in and
take a just-released lock, avoiding a context switch entirely. A fair lock must always
hand off to the queued thread — a guaranteed switch every time.

> **Use fairness only when starvation (9.2) is a demonstrated problem.** Not by default.

### Diagnostics `synchronized` can't give you

```java
lock.isLocked();
lock.isHeldByCurrentThread();      // ⭐ genuinely useful in assertions
lock.getHoldCount();
lock.getQueueLength();
```

## `Condition` — multiple wait sets on one lock

`wait`/`notify` (9.4) gives you **one** wait set per object. `Condition` gives you many.

```java
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();
private final Condition notEmpty = lock.newCondition();
private final Queue<Item> queue = new ArrayDeque<>();

void put(Item item) throws InterruptedException {
    lock.lock();
    try {
        while (queue.size() == CAPACITY) notFull.await();     // still WHILE (9.4)
        queue.add(item);
        notEmpty.signal();                  // ⭐ wake only a CONSUMER
    } finally { lock.unlock(); }
}

Item take() throws InterruptedException {
    lock.lock();
    try {
        while (queue.isEmpty()) notEmpty.await();
        Item item = queue.poll();
        notFull.signal();                   // ⭐ wake only a PRODUCER
        return item;
    } finally { lock.unlock(); }
}
```

**How it improves on `wait`/`notify`:** with one wait set you must use `notifyAll` and wake
*everyone*, because `notify` might wake a producer when you needed a consumer (9.4). With
two conditions you signal exactly the right group — so `signal()` is safe, and you avoid
the thundering herd.

| `wait`/`notify` | `Condition` |
|---|---|
| `wait()` | `await()` |
| `notify()` | `signal()` |
| `notifyAll()` | `signalAll()` |
| One wait set | **Many** |
| Needs `notifyAll` | `signal()` is usually correct |

> Still `while`, still spurious wakeups (9.4). And note the method names differ — `await`
> not `wait` — which is deliberate, so you can't call the wrong one by habit.

## `ReadWriteLock` — many readers or one writer

```java
private final ReadWriteLock rw = new ReentrantReadWriteLock();

Value read(String key) {
    rw.readLock().lock();
    try { return map.get(key); }
    finally { rw.readLock().unlock(); }
}

void write(String key, Value v) {
    rw.writeLock().lock();
    try { map.put(key, v); }
    finally { rw.writeLock().unlock(); }
}
```

**Many readers concurrently, or one writer exclusively.**

### ⚠️ When the bookkeeping outweighs the gain

A `ReadWriteLock` has to track reader counts, and its acquire/release is **more expensive
than a plain lock**. It only pays off when:

1. **Reads massively outnumber writes** (10:1 at minimum)
2. **The critical section is long** — otherwise the bookkeeping dominates

For a short read like `map.get()`, a plain `ReentrantLock` — or better, a
`ConcurrentHashMap` (9.7) — beats it easily.

> ⚠️ Also: writers can **starve** (9.2) under a continuous stream of readers. A fair
> `ReentrantReadWriteLock(true)` fixes it, at a cost.

**Lock downgrading is allowed; upgrading is not:**

```java
// ✅ write → read
writeLock.lock();
try { modify(); readLock.lock(); }        // acquire read BEFORE releasing write
finally { writeLock.unlock(); }
try { read(); } finally { readLock.unlock(); }

// ❌ read → write = instant deadlock
readLock.lock();
writeLock.lock();          // 💥 waits for all readers, including yourself
```

## `StampedLock` — optimistic reads

```java
private final StampedLock sl = new StampedLock();

double distanceFromOrigin() {
    long stamp = sl.tryOptimisticRead();     // ⭐ acquires NOTHING — just a version stamp
    double curX = x, curY = y;
    if (!sl.validate(stamp)) {               // did a writer intervene?
        stamp = sl.readLock();               // fall back to a real read lock
        try { curX = x; curY = y; }
        finally { sl.unlockRead(stamp); }
    }
    return Math.hypot(curX, curY);
}
```

**Optimistic reading takes no lock at all** — it reads a version stamp, does the work, then
checks whether anything changed. Under read-heavy load with rare writes, that's close to
free.

### ⚠️ The care it demands

| | |
|---|---|
| **Not reentrant** | Re-acquiring deadlocks against yourself — unlike everything else in this part |
| **Stamps must be passed to unlock** | `unlockRead(stamp)`, not `unlockRead()` |
| **You must copy fields to locals** | Then validate. Reading after validation is wrong |
| **No `Condition` support** | — |
| **Easy to get wrong** | Genuinely the sharpest tool here |

> **Use `StampedLock` only when profiling shows a read-heavy lock is the bottleneck.** In
> almost every case a concurrent collection (9.7) or an immutable snapshot is simpler and
> fast enough.

## ⭐ When to choose an explicit lock — and when not to bother

**Use `ReentrantLock` when you need:**

| Need | Why `synchronized` can't |
|---|---|
| **`tryLock`** — give up rather than block | No equivalent |
| **Timed acquisition** | No equivalent |
| **Interruptible** acquisition (9.1) | `synchronized` isn't interruptible |
| **Multiple conditions** | One wait set per object |
| **Fairness** | No equivalent |
| **Lock across method boundaries** | `synchronized` is block-scoped |

**Otherwise use `synchronized`** (9.4):

- Shorter, and **impossible to forget to release**
- Better tooling — thread dumps show monitor ownership clearly (8.9)
- The JIT can **elide** it (8.8); it can't elide a `ReentrantLock`
- Uncontended cost is comparable — **measured 9 ns vs 12 ns** on OpenJDK 17 (9.4)

> **The honest default: `synchronized` first. Reach for `ReentrantLock` when you need a
> capability it doesn't have** — and usually the real answer is a concurrent collection
> (9.7) or an executor (9.8) rather than either.

## `AbstractQueuedSynchronizer` — worth reading once

**AQS** is the machinery underneath `ReentrantLock`, `Semaphore`, `CountDownLatch`,
`ReadWriteLock` and `FutureTask`.

It provides: an `int` state, a CAS to change it (9.6), and a **FIFO queue of parked
threads**. A synchroniser subclasses it and defines what the state *means*:

| Synchroniser | `state` means |
|---|---|
| `ReentrantLock` | Hold count |
| `Semaphore` | Permits remaining (9.10) |
| `CountDownLatch` | Remaining count (9.10) |
| `ReadWriteLock` | Reader count (high 16 bits) + writer count (low 16) |

> **Read `AbstractQueuedSynchronizer`'s source once** (13.1). It's ~2,000 lines and it
> makes every synchroniser in the JDK stop being magic. You will essentially never
> subclass it yourself.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| No `finally { unlock(); }` | An exception leaks the lock **permanently** |
| `lock()` **inside** the try | You may unlock a lock you never took |
| Fair locks by default | 10–100× slower |
| `ReadWriteLock` for short reads | Bookkeeping costs more than it saves |
| Upgrading read → write | Instant deadlock |
| `StampedLock` reentrantly | Deadlocks — it isn't reentrant |
| `ReentrantLock` because "it's newer" | `synchronized` is simpler and elidable |

---

## Recap

| Tool | Use when |
|---|---|
| **`synchronized`** (9.4) | **Default.** Auto-release, elidable |
| **`ReentrantLock`** | `tryLock`, timeout, interruptible, fairness, multiple conditions |
| **`Condition`** | Several distinct wait sets — producer/consumer |
| **`ReadWriteLock`** | Reads ≫ writes **and** long critical sections |
| **`StampedLock`** | Profiled read-heavy bottleneck. Not reentrant. Sharp |
| **AQS** | The machinery underneath. Read once |

**The shape:** `lock(); try { ... } finally { unlock(); }` — acquire outside, release in
`finally`.
