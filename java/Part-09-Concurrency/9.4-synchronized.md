# 9.4 — `synchronized`

> **What this is:** The built-in lock. **Old, still correct, still the right first answer.**
> Despite what you'll read, it has not been superseded — 0.3 lists it explicitly under
> "things people call obsolete that are not".

---

## The concepts

### Every object has a monitor

```java
synchronized void method() { ... }          // locks `this`
static synchronized void method() { ... }   // locks the CLASS object

synchronized (someObject) { ... }           // locks that object
```

A monitor is **mutual exclusion + a wait set**. Only one thread holds it at a time.

**And critically — it gives you both guarantees from 9.3:**

| | |
|---|---|
| **Mutual exclusion** | Fixes **atomicity** (9.2) |
| **happens-before** on unlock→lock | Fixes **visibility** and **reordering** (9.3) |

> ⭐ **Both sides must use the same lock.** A synchronized write and an unsynchronised read
> creates no happens-before edge and guarantees nothing (9.3).

---

## ⭐ What you're locking on — prefer a private final lock object

```java
// ❌ locks `this` — anyone holding a reference to your object can lock it
public synchronized void method() { ... }

// ❌ locks a public object — same problem, more explicit
synchronized (this) { ... }

// ✅ a private lock nobody else can reach
private final Object lock = new Object();
void method() {
    synchronized (lock) { ... }
}
```

**Why it matters:** `synchronized` on a method makes your lock **part of your public API**.
Any caller can write `synchronized (yourObject) { ... }` and hold your lock for as long as
they like — deadlocking your class from outside, with no change to your code.

A `private final` lock object cannot be reached, so the locking protocol stays entirely
yours.

> ⚠️ **Never lock on a `String` literal or a boxed primitive:**
> ```java
> synchronized ("lock") { }              // ❌ interned — shared JVM-wide (1.3)
> synchronized (Integer.valueOf(1)) { }  // ❌ cached — shared (1.1)
> ```
> Unrelated code can accidentally share these locks. Use `new Object()`.

> ⚠️ **And never lock on a mutable reference** — reassigning it means two threads lock
> different objects:
> ```java
> private Object lock = new Object();    // ❌ not final
> ```

## Reentrancy

**A thread that holds a monitor can re-acquire it.** The JVM tracks a hold count.

```java
synchronized void a() { b(); }        // holds the lock
synchronized void b() { ... }         // ✅ re-acquires it — no deadlock
```

Without reentrancy this would deadlock against itself. It matters for:
- Recursive methods
- A synchronized method calling another on the same object
- A subclass's synchronized method calling `super`'s (2.3)

---

## ⭐ Lock granularity

```java
// ❌ too coarse — the whole method is serialised, including the slow part
synchronized void process(Item item) {
    var result = expensiveComputation(item);    // 500ms, touches nothing shared
    cache.put(item.id(), result);               // the only shared state
}

// ✅ lock only what needs it
void process(Item item) {
    var result = expensiveComputation(item);    // concurrent
    synchronized (lock) {
        cache.put(item.id(), result);           // serialised — microseconds
    }
}
```

| | Risk |
|---|---|
| **Too coarse** | Kills throughput — lock convoy (9.2) |
| **Too fine** | **Breaks correctness** — a compound operation spanning two locked blocks isn't atomic |

```java
// ❌ too fine — each block is atomic, the PAIR isn't (check-then-act, 9.2)
synchronized (lock) { if (map.containsKey(k)) return; }
synchronized (lock) { map.put(k, v); }          // another thread got in between
```

> **The rule: the critical section must cover the whole invariant, and nothing more.**
> Never do I/O, never call unknown code, never block inside one.

---

## ⭐ Consistent lock ordering — the defence against deadlock

The `transfer` deadlock from 9.2, fixed:

```java
void transfer(Account from, Account to, int amount) {
    Account first  = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to   : from;

    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

By imposing a **global order** on lock acquisition, a circular wait becomes impossible —
it breaks condition #4 from 9.2.

> ⚠️ Handle the `from.id() == to.id()` case (transfer to self), or you'll try to lock the
> same object twice — harmless thanks to reentrancy, but it means you should check for it
> and return early.

**Document your lock order.** If there's no documented order, there's no way for anyone to
add a third lock safely.

## ⭐ `wait` / `notify` / `notifyAll`

The classic condition mechanism. Every object has a wait set alongside its monitor (2.5).

```java
synchronized (lock) {
    while (!condition) {        // ⭐ WHILE, never if
        lock.wait();            // releases the lock and sleeps
    }
    // condition is true, and we hold the lock
}

synchronized (lock) {
    condition = true;
    lock.notifyAll();           // wake the waiters
}
```

**The rules, all mandatory:**

| Rule | Why |
|---|---|
| **Must hold the monitor** to call `wait`/`notify` | Otherwise `IllegalMonitorStateException` |
| **`wait()` releases the lock** | That's the point — otherwise nobody could change the condition |
| ⭐ **Always in a `while` loop, never `if`** | See below |
| **Prefer `notifyAll` over `notify`** | `notify` wakes *one arbitrary* waiter — if it's waiting for a different condition, the right thread never wakes and you get a lost wakeup |

### ⭐ Why spurious wakeups exist

```java
// ❌ broken
if (!condition) lock.wait();

// ✅ correct
while (!condition) lock.wait();
```

`wait()` can return **without any `notify`** — the JVM permits it, because the underlying
OS primitives (futex, pthread condvars) permit it, and forbidding it would cost
performance on every platform.

**And even without spurious wakeups the `while` is still required:** between being notified
and re-acquiring the lock, *another* thread may have run and consumed the condition. You
must **re-check**, always.

> ⚠️ `Thread.sleep()` does **not** release the lock. `wait()` does. Sleeping while holding
> a lock is a classic throughput killer.

> **In modern code you rarely write this.** A `BlockingQueue` (9.7) or a `Condition` (9.5)
> is clearer and harder to get wrong. Learn `wait`/`notify` to *read* existing code and to
> understand what the higher-level tools are built on.

## How the JVM implements it

Locking is much cheaper than its reputation suggests:

| Stage | Cost |
|---|---|
| **Thin lock** (uncontended) | A single **CAS** on the object header's mark word (8.4, 9.6) — nanoseconds |
| **Inflation** | Under contention, a full OS-level monitor is allocated |
| **Heavyweight monitor** | Contended — involves the OS scheduler, microseconds |

Plus two JIT optimisations (8.8):

| | |
|---|---|
| **Lock elision** | Escape analysis proves the object never escapes ⟹ **the lock is removed entirely** |
| **Lock coarsening** | Repeated lock/unlock on the same object merged into one region |

```java
// the JIT may delete this lock entirely — `sb` never escapes
void f() {
    var sb = new StringBuilder();     // StringBuilder isn't synchronized, but
    sb.append("a");                   // StringBuffer would be — and the lock elided (1.3)
}
```

💀 **Biased locking** (which optimised the single-threaded-lock case further) was
**deprecated in 15 and removed in 18** — it was complex and the workloads that benefited
became rare.

### ⭐ Measured: what an uncontended lock actually costs

OpenJDK 17, 20M iterations, JIT-warmed:

| | ns/op |
|---|---|
| Plain volatile write (baseline) | ~0 |
| **`synchronized` block** | **9 ns** |
| `ReentrantLock` (9.5) | 12 ns |
| `synchronized` in a tight loop where the JIT can **coarsen** | **2.3 ns** |

> **The practical point: an uncontended `synchronized` block costs single-digit
> nanoseconds** — and drops to ~2 ns when the JIT coarsens it (8.8).
>
> **"Locks are slow" is about *contention*, not about locking.** Don't avoid a lock you
> genuinely need; a contended one is what costs you, not the `synchronized` keyword.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Synchronising only the writer | No happens-before. Both sides need the same lock |
| `synchronized` on the method | Publishes your lock — callers can hold it |
| Locking a `String` literal or boxed `Integer` | Shared JVM-wide |
| Locking a non-`final` field | Reassignment ⟹ two threads, two locks |
| `if (!cond) wait()` | **Must be `while`** — spurious wakeups and stolen conditions |
| `notify()` instead of `notifyAll()` | Can wake the wrong waiter. Lost wakeup |
| `Thread.sleep()` inside a lock | Doesn't release it |
| Locking on `this` in a class others extend | The subclass shares your lock |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `synchronized` on a `Vector`/`Hashtable` (5.1) | `ConcurrentHashMap` (9.7) |
| Hand-rolled `wait`/`notify` producer-consumer | `BlockingQueue` (9.7) |
| Biased locking flags | Removed in Java 18 |

## Recap

| Concept | One line |
|---|---|
| Monitor | Mutual exclusion **+ happens-before** — fixes all three problems from 9.2 |
| **Lock object** | `private final Object lock` — not `this`, not a String, not mutable |
| Reentrant | Same thread can re-acquire |
| Granularity | Cover the whole invariant, nothing more. No I/O inside |
| **Deadlock defence** | **Consistent global lock ordering** |
| `wait`/`notify` | **Always `while`**; prefer `notifyAll`; `wait` releases the lock, `sleep` doesn't |
| Cost | Uncontended ≈ **9 ns** (2 ns coarsened). The JIT can elide it entirely |
