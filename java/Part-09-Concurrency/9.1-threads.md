# 9.1 — Threads

> **What this is:** The primitive. **You will rarely use it directly**, but everything
> above it is built on it.

---

## Coming from JS/Python/Dart

| | Node | Java |
|---|---|---|
| Model | One thread, event loop | **Many real OS threads** |
| Parallelism | Worker threads, message-passing only | **Shared memory** |
| Python | GIL — one bytecode at a time | **No GIL.** Genuine parallelism |
| Dart | Isolates — no shared memory | **Shared memory** |

Python and Dart both avoid the hard problem by preventing sharing. Java lets you share,
which is why Parts 9.2 and 9.3 exist.

## The concepts

### A platform thread is an OS thread

```java
Thread t = new Thread(() -> IO.println("running"));
t.start();          // ← creates a real OS thread
```

**One Java platform thread = one OS thread.** That mapping is the whole reason for its
costs:

| Cost | |
|---|---|
| Stack | **~1 MB reserved** (8.3) |
| Creation | ~1 ms — a syscall |
| Switching | ~1–10 µs — a kernel context switch |
| Practical limit | **Thousands**, not millions |

> This is exactly the constraint virtual threads remove (9.11).

### Creating threads — implement `Runnable`, don't extend `Thread`

```java
// ✅ implement Runnable (or pass a lambda)
Thread t = new Thread(() -> doWork());
t.start();

// ❌ extend Thread
class MyThread extends Thread {
    @Override public void run() { doWork(); }
}
```

**Why:** extending `Thread` uses your **one** inheritance slot (2.3) for no benefit, and it
conflates *what to do* with *how to run it*. A `Runnable` can be submitted to an executor
(9.8), retried, or run inline. A `Thread` subclass can only be a thread.

> **`start()` vs `run()`** — the classic mistake:
> ```java
> t.start();     // ✅ starts a new thread
> t.run();       // ❌ just calls the method ON THE CURRENT THREAD. No concurrency at all.
> ```
> This compiles, runs, and silently does nothing concurrent.

### Thread states

```
   NEW ──start()──► RUNNABLE ◄─────────────┐
                      │  │                 │
                      │  └─►BLOCKED ────────┤  waiting for a monitor (9.4)
                      │                    │
                      ├─► WAITING ──────────┤  wait(), join(), park()
                      │                    │
                      ├─► TIMED_WAITING ────┘  sleep(n), wait(n)
                      │
                      └─► TERMINATED
```

| State | Means |
|---|---|
| `NEW` | Created, not started |
| `RUNNABLE` | Running **or ready to run** — ⚠️ also covers blocking I/O |
| `BLOCKED` | Waiting for a `synchronized` monitor |
| `WAITING` | `wait()`, `join()`, `park()` — indefinitely |
| `TIMED_WAITING` | Same, with a timeout |
| `TERMINATED` | Finished |

> ⚠️ **`RUNNABLE` does not mean "using CPU".** A thread blocked on a socket read shows as
> `RUNNABLE` because the JVM can't see into the OS. This misleads people reading thread
> dumps (8.9).

### `join`, `sleep`, `yield`, priorities

```java
t.join();            // wait for t to finish
t.join(1000);        // ...for at most 1s
Thread.sleep(1000);  // current thread sleeps — releases NO locks (9.4)
Thread.yield();      // a hint to the scheduler. Usually ignored
t.setPriority(Thread.MAX_PRIORITY);   // 1–10
```

> ⚠️ **Priorities do almost nothing.** They're a *hint*, mapped to OS priorities
> differently on every platform, and often ignored entirely. **Never write code whose
> correctness depends on priority.** The same goes for `yield()`.

### Daemon vs non-daemon

```java
t.setDaemon(true);   // must be set BEFORE start()
```

> **The JVM exits when the last non-daemon thread finishes.** Daemon threads are killed
> abruptly at that point — no `finally` blocks, no cleanup.

| Use | For |
|---|---|
| **Non-daemon** (default) | Work that must complete |
| **Daemon** | Background housekeeping — metrics, cache eviction, monitoring |

⚠️ Never use a daemon thread for anything that writes data — it can be killed mid-write.

## ⭐ Interruption done properly

**This is the part people get wrong, and 4.3 introduced it. Here's the full picture.**

> **Interruption is a cooperative *request*, not a kill.** Nothing stops a thread that
> ignores it.

```java
t.interrupt();                      // sets the thread's interrupt FLAG
```

**Two ways a thread notices:**

**1. It's in a blocking call** — `sleep`, `wait`, `join`, `BlockingQueue.take`. That call
throws `InterruptedException` **and clears the flag**.

**2. It checks the flag itself:**

```java
while (!Thread.currentThread().isInterrupted()) {
    doWork();                        // for a CPU-bound loop, you must check
}
```

### ⭐ Why swallowing `InterruptedException` is always a bug

```java
// ❌ this is broken
try { Thread.sleep(1000); }
catch (InterruptedException e) { /* ignore */ }
```

**The mechanism:** when `InterruptedException` is thrown, **the JVM clears the interrupt
flag**. If you swallow the exception, the cancellation request is now gone *completely* —
nothing upstream can tell it was ever made. Your thread keeps working through a shutdown.

**The two correct responses:**

```java
// (a) propagate — best, when your signature allows it
void doWork() throws InterruptedException {
    Thread.sleep(1000);
}

// (b) restore the flag, then stop — when you can't propagate (e.g. inside a Runnable)
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();     // ⭐ put the flag back
    return;                                  // and actually stop
}
```

> **`Thread.currentThread().interrupt()` is the line to memorise.** Restoring the flag lets
> code further up the stack — an executor, a framework — see the cancellation it asked
> for.

**Two flag-reading methods, and they differ:**

```java
Thread.interrupted()                        // ⚠️ reads AND CLEARS the flag (static)
Thread.currentThread().isInterrupted()      // ✅ reads only (instance)
```

Using `interrupted()` by accident is a real source of lost cancellations.

### 💀 `Thread.stop()` — removed in Java 26

```java
t.stop();     // 💀 removed
```

**Why killing a thread is unsafe in principle:** `stop()` threw an exception at an
*arbitrary* point in the target thread — possibly halfway through updating a data
structure, while holding locks. It **released every lock it held**, exposing objects in a
half-modified state to every other thread.

There is no safe way to kill a thread from outside. **This is why interruption is
cooperative** — only the thread itself knows where it's safe to stop.

(Same reasoning as `finalize()` in 8.7: a mechanism that runs code at an arbitrary point is
unfixable.)

## `UncaughtExceptionHandler`

**What happens to an exception thrown on a thread nobody is watching?**

```java
Thread t = new Thread(() -> { throw new RuntimeException("boom"); });
t.start();
// the stack trace prints to stderr, the thread dies, the JVM keeps running
// ⚠️ nothing in your code finds out
```

```java
t.setUncaughtExceptionHandler((thread, ex) ->
    log.error("thread {} died", thread.getName(), ex));

Thread.setDefaultUncaughtExceptionHandler(...);   // JVM-wide fallback
```

> ⚠️ **In an executor, exceptions are swallowed even more quietly** — a task submitted with
> `submit()` captures the exception in its `Future` and you **never see it unless you call
> `get()`** (9.8). Silently-dying background tasks are a classic production bug.

## `ThreadLocal`

Per-thread state — each thread sees its own value:

```java
private static final ThreadLocal<SimpleDateFormat> FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

FORMAT.get().format(date);       // each thread gets its own instance
```

**Legitimate uses:**
- Making a non-thread-safe object usable per-thread (the classic example is
  `SimpleDateFormat` — though you should use `DateTimeFormatter`, which is thread-safe, 0.3)
- Request context — user, trace ID, tenant — without threading it through every signature
- Transaction and connection context in frameworks

### ⚠️ The leak in pooled threads

```java
// ❌
void handleRequest(Request r) {
    CONTEXT.set(new UserContext(r.user()));
    handle(r);
    // never removed
}
```

**In a thread pool the thread is reused, not destroyed** (9.8). The value stays attached
indefinitely — leaking memory (8.7), and potentially **leaking one request's user data into
another request**, which is a security bug, not just a memory one.

```java
try {
    CONTEXT.set(new UserContext(r.user()));
    handle(r);
} finally {
    CONTEXT.remove();                        // ✅ mandatory
}
```

> **With millions of virtual threads, `ThreadLocal` becomes a problem of a different
> scale** — which is why **scoped values** exist (9.12).

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `t.run()` instead of `t.start()` | Runs on the current thread. No concurrency, no error |
| Swallowing `InterruptedException` | Destroys the cancellation signal |
| `Thread.interrupted()` | **Clears** the flag. Use `isInterrupted()` to just read |
| `RUNNABLE` means using CPU | Blocking I/O also shows as `RUNNABLE` |
| Relying on priorities or `yield()` | Hints. Frequently ignored |
| `setDaemon` after `start()` | `IllegalThreadStateException` |
| `ThreadLocal` without `remove()` in a pool | Memory leak **and** cross-request data leak |
| Assuming an exception on a thread surfaces somewhere | It doesn't, unless you handle it |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Thread.stop()` / `suspend()` / `resume()` | **Removed.** Cooperative interruption |
| `extends Thread` | `Runnable` / lambda |
| Creating threads directly | An `ExecutorService` (9.8) or virtual threads (9.11) |
| `new Thread()` per request | `Executors.newVirtualThreadPerTaskExecutor()` (9.11) |

## Recap

| Concept | One line |
|---|---|
| Platform thread | **One OS thread.** ~1 MB stack → thousands, not millions |
| `Runnable` over `extends Thread` | Keeps your inheritance slot; separates task from execution |
| `start()` vs `run()` | `run()` silently runs inline |
| States | `RUNNABLE` includes blocking I/O |
| Daemon | JVM exits when the last **non-daemon** thread ends |
| **Interruption** | A **cooperative request**. Propagate, or `Thread.currentThread().interrupt()` |
| 💀 `Thread.stop()` | Removed. Killing a thread is unsafe in principle |
| `ThreadLocal` | Useful; **always `remove()` in a pooled thread** |
