# 12.5 — Code quality and conventions

> **What this is:** **What "idiomatic Java" actually means, beyond taste.**

## ⭐ Naming and layout — and why uniformity is a feature

```java
package com.example.orders;              // lowercase, reverse domain (1.6)

public class OrderService {              // UpperCamelCase
    private static final int MAX_RETRIES = 3;      // UPPER_SNAKE constants (2.2)
    private final OrderRepository repository;      // lowerCamelCase

    public Order placeOrder(Cart cart) { }         // verb phrase
    public boolean isValid() { }                   // boolean: is/has/can
    public String name() { }                       // ⭐ modern accessor (2.1, 2.6)
}
```

| Element | Convention |
|---|---|
| Package | `lowercase.no.underscores` |
| Class / interface / record / enum | `UpperCamelCase` |
| Method / field / parameter | `lowerCamelCase` |
| Constant (`static final`) | `UPPER_SNAKE_CASE` |
| Type parameter | `T`, `E`, `K`, `V`, `R` (3.2) |

**Indentation 4 spaces, brace on the same line, ~120 columns.**

> ⭐ **The ecosystem's uniformity is a feature, not conformism.** Java code from any company
> looks the same, so you can read an unfamiliar codebase immediately, and code review
> discusses behaviour instead of formatting. Python has PEP 8; Go has `gofmt`; Java has a
> convention everyone actually follows. **Don't fight it** — a codebase with a bespoke style
> costs every new reader.

**Interface naming:** no `IOrderService` (that's C#), no `OrderServiceImpl` unless there's
genuinely one implementation and you've considered whether the interface earns its place
(2.4, 2.10).

## ⭐ Nullability annotations and JSpecify

Java has no null safety in the type system (6.7). Annotations plus a checker get you most
of the way:

```java
import org.jspecify.annotations.*;

@NullMarked                              // ⭐ everything here is non-null BY DEFAULT
package com.example.orders;
```

```java
public class OrderService {
    public Order find(String id) { }              // non-null — both param and return
    public @Nullable Order findOrNull(String id) { }   // explicitly nullable
}
```

> ⭐ **JSpecify** (2024) is the standardised set, backed by Google, JetBrains, Oracle,
> Microsoft and others. Before it there were **a dozen incompatible `@Nullable`
> annotations** — JSR-305, JetBrains, Eclipse, Checker Framework, Android — and tools
> disagreed about all of them. **Use JSpecify for new code.**

**`@NullMarked` at the package level is the important idea**: flip the default so non-null
is normal and nullable is the annotated exception. That matches how you actually write
code.

**The annotation alone does nothing** (11.7) — a checker enforces it:

```bash
# NullAway — fast enough for every build
-Xep:NullAway:ERROR -XepOpt:NullAway:AnnotatedPackages=com.example
```

```java
@Nullable String name;
name.length();          // ❌ BUILD ERROR — dereference of a @Nullable value
```

> This is the closest Java gets to Kotlin's null safety. Adopted consistently on a
> codebase, it eliminates most NPEs at compile time.

## ⭐ Static analysis — and what each tool catches

| Tool | Catches | Runs |
|---|---|---|
| ⭐ **Error Prone** | **Real bugs** — Google's, ~500 checks, lowest false positives | At compile time, in `javac` |
| **SpotBugs** | Bug patterns in bytecode; the FindBugs successor | On the `.class` files |
| **PMD** | Style, complexity, dead code, duplication | On source |
| **Checkstyle** | Formatting and conventions | On source |
| **SonarQube** | Aggregates all of the above + tracks trends | CI |

**Real Error Prone catches** — every one of these appears earlier in this roadmap:

```java
new BigDecimal(0.1);                      // ⚠️ precision loss (11.2)
"x".equals(null);                         // always false
if (list.size() == -1) { }                // impossible condition
str.toUpperCase();                        // ⚠️ default locale (11.4)
optional.get();                           // ⚠️ discouraged (6.7)
new Random().nextInt();                   // ⚠️ for a token (11.5)
someFuture;                               // ⚠️ unused return value
synchronized (someString) { }             // ⚠️ interned lock object (9.4)
```

> ⭐ **Start with Error Prone.** It runs as a `javac` plugin, so there's no extra build
> step, and its false-positive rate is low enough to run as `ERROR` rather than warnings.
> The other tools are worth adding once that's clean.

```xml
<compilerArgs>
    <arg>-XDcompilePolicy=simple</arg>
    <arg>-Xplugin:ErrorProne</arg>
    <arg>-Xlint:all</arg>            <!-- ⭐ the compiler's own warnings too (1.7) -->
</compilerArgs>
```

## ⭐ Formatting is a settled question

```bash
# google-java-format — no options, by design
java -jar google-java-format.jar --replace **/*.java
```

```xml
<!-- Spotless — enforces it in the build -->
<plugin>
  <groupId>com.diffplug.spotless</groupId>
  <configuration>
    <java><googleJavaFormat/></java>
  </configuration>
</plugin>
```

```bash
mvn spotless:apply     # format everything
mvn spotless:check     # fail the build if unformatted
```

> ⭐ **Pick a formatter, run it in CI, and never discuss formatting again.** The specific
> style matters far less than that it's **automatic and non-negotiable**. `google-java-format`
> deliberately has no configuration options, which is the point — there's nothing to argue
> about.
>
> **Do the reformat in its own commit**, so it doesn't pollute `git blame`. Add that commit
> to `.git-blame-ignore-revs`.

## ⭐ Logging

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);
//                          ↑ SLF4J — the FACADE

log.info("placed order {} for customer {}", orderId, customerId);   // ⭐ placeholders
log.error("failed to place order {}", orderId, exception);          // ⭐ throwable LAST
```

**SLF4J is a facade**; Logback or Log4j2 is the implementation behind it:

```
your code → SLF4J API → (binding) → Logback / Log4j2 → console, file, JSON
```

> **Why a facade:** your library shouldn't force a logging implementation on its consumers.
> Depend on `slf4j-api`; let the application choose the backend.

### ⭐ Parameterised messages — not concatenation

```java
// ❌ builds the string even when DEBUG is disabled
log.debug("processing order " + order.id() + " with " + order.items().size() + " items");

// ✅ formats ONLY if DEBUG is enabled
log.debug("processing order {} with {} items", order.id(), order.items().size());
```

In a hot path with debug disabled, the first version still does the concatenation (1.3) and
throws the result away. The second does nothing.

```java
log.debug("expensive: {}", () -> computeExpensiveValue());   // Log4j2 lambda (6.1)
```

```java
// ⭐ the throwable goes LAST, with no placeholder (4.4)
log.error("failed for user {}", userId, exception);      // ✅ full stack trace
log.error("failed: " + e.getMessage());                  // ❌ no stack trace at all
```

### ⚠️ Why `System.out` is not logging

| | `System.out` | A logger |
|---|---|---|
| Levels | ❌ | TRACE…ERROR |
| Turn off in production | ❌ | ✅ Per package |
| Timestamps, thread, class | ❌ | ✅ |
| Structured / JSON output | ❌ | ✅ |
| Route to a file, syslog, a collector | ❌ | ✅ |
| Performance | ⭐ **Synchronised** — a hot loop serialises your app | Async appenders |

> `System.out.println` in a server is a debugging artifact someone forgot to delete (10.1).

### ⭐ What to log and what never to log

**Log:**
- Service start/stop and configuration **at INFO**
- Errors **with the exception object** and enough identifiers to find the record (4.4)
- Slow operations, retries, circuit-breaker state
- A **correlation/trace ID** on everything (`MDC.put("traceId", id)`)

**⚠️ Never log:**

| Never | Why |
|---|---|
| **Passwords, tokens, API keys, session IDs** | Logs are widely readable, shipped off-box, retained for years |
| **Card numbers, CVVs** | PCI-DSS violation |
| **Personal data** without a lawful basis | GDPR — logs are processing |
| **Full request/response bodies** | Contains all of the above |

> ⭐ **The same rule as `toString()` (2.5) and exception messages (4.4): log the
> *identifier*, never the *secret*.**
>
> ```java
> log.info("authenticated user {}", user.id());          // ✅
> log.info("token {} accepted", token);                  // ❌ a credential, in a log file, forever
> ```
>
> **Logs leak.** They go to aggregators, get shared in tickets, and are retained long after
> the data should have been deleted. Treat a log line as public.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| String concatenation in `log.debug` | Built even when disabled |
| `log.error("x: " + e.getMessage())` | **No stack trace.** Pass `e` as the last argument |
| `System.out` in a service | No levels, no structure, **synchronised** |
| Logging tokens or PII | Logs leak. Treat them as public |
| A mix of `@Nullable` annotations | Use **JSpecify** |
| Formatting in code review | Automate it; discuss behaviour |
| A bespoke house style | Every new reader pays for it |

## Recap

| Concept | One line |
|---|---|
| Conventions | ⭐ **Uniformity is a feature.** Don't invent a house style |
| **JSpecify** | The standard `@Nullable`. `@NullMarked` flips the default |
| Checkers | **NullAway** / Checker Framework — the annotation alone does nothing (11.7) |
| ⭐ **Error Prone** | **Start here.** Real bugs, at compile time, low false positives |
| Formatting | **google-java-format + Spotless in CI.** Settled, not discussed |
| **SLF4J** | The facade; Logback/Log4j2 behind it |
| ⭐ **Placeholders** | `log.info("x {}", y)` — not concatenation. Throwable **last** |
| ⭐ **Never log** | **Passwords, tokens, card numbers, PII.** Log the identifier |
