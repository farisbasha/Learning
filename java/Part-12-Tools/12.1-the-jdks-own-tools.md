# 12.1 — The JDK's own tools

> **What this is:** **These ship with Java and need no build system at all.** Most Java
> developers know `java` and `javac` and nothing else, which is why they're helpless when
> the IDE or the build breaks.

---

## `javac` flags worth knowing

```bash
javac -d out src/**/*.java              # output directory
javac -cp lib/*.jar Main.java           # classpath (1.6)

javac -Xlint:all Main.java              # ⭐ turn on ALL warnings (1.7)
javac -Xlint:all -Werror Main.java      # ⭐ warnings become errors
javac --release 17 Main.java            # ⭐ compile FOR Java 17, properly
javac -parameters Main.java             # ⭐ keep parameter names in the bytecode
javac -g Main.java                      # full debug info
```

### ⭐ `--release` versus `-source`/`-target`

```bash
javac -source 17 -target 17 Main.java   # ⚠️ compiles against the CURRENT JDK's API
javac --release 17 Main.java            # ✅ compiles against Java 17's API
```

**`-source`/`-target` only sets the language level and class-file version** — it still
compiles against your current JDK's library. So on JDK 25 you can call a Java 21 method,
produce a Java 17 class file, and get `NoSuchMethodError` at runtime on an actual Java 17
JVM (8.2).

> ⭐ **`--release` is the correct flag.** It uses the historical API signatures, so calling
> something that didn't exist yet is a **compile error**. Always use `--release`.

### ⭐ `-parameters`

```java
// without -parameters, reflection (11.6) sees:
method.getParameters()[0].getName();     // "arg0" 😞

// with -parameters:
                                          // "userId" ✅
```

Frameworks that bind by parameter name — Spring's `@PathVariable`, Jackson's record
deserialisation — need it. Spring Boot's parent POM sets it for you, which is why it "just
works" there and breaks in a hand-rolled build.

## `java` flags

```bash
java -cp out com.example.Main            # NOT a file path — a class name (0.4, 1.6)
java -jar app.jar
java Main.java                           # single-file launch (0.4) Java 11

java -Dkey=value Main                    # ⭐ system property
java -Xmx4g -Xms4g -Xss1m Main           # heap and stack sizing (8.3)
java -XX:+UseZGC Main                    # ⭐ -XX: is the JVM-tuning family (8.6)
java -Xlog:gc* Main                      # unified logging (8.6)
java --enable-preview Main               # preview features (7.5)
java --add-opens java.base/java.lang=ALL-UNNAMED Main   # modules (11.10)
```

| Family | Means |
|---|---|
| `-D` | A **system property** — `System.getProperty("key")` |
| `-X` | Non-standard, but stable (`-Xmx`, `-Xlog`) |
| `-XX:` | ⭐ **JVM internals.** `+`/`-` for booleans, `=` for values |
| `--` | Standard (module and preview flags) |

### ⭐ `@argfiles` — when the command line gets long

```bash
# args.txt
-Xmx4g
-XX:+UseZGC
--add-opens java.base/java.lang=ALL-UNNAMED
-cp lib/a.jar:lib/b.jar
com.example.Main
```

```bash
java @args.txt
```

Solves the Windows command-length limit and makes a long invocation reviewable in version
control. Build tools generate these for you.

## ⭐ The tools you should actually know

| Tool | Does |
|---|---|
| **`jshell`** | ⭐ The REPL (0.4). **Your main tool for Parts 1–7** |
| **`javap`** | ⭐ Disassemble (8.1). `-c -p -v`. Answers "what does this compile to?" |
| `jar` | Create, list and extract jars (1.6) |
| **`jdeps`** | ⭐ Dependency analysis — what does this jar actually use? |
| **`jdeprscan`** | ⭐ Scan for deprecated API usage before an upgrade |
| `jlink` | Build a trimmed runtime (8.10, 11.10) |
| `jpackage` | Native installer (8.10) |
| `jcmd`, `jstack`, `jmap`, `jstat` | Observing a live JVM (8.9) |
| `jwebserver` | A local static file server (10.6) `Java 18` |
| `keytool` | Keystores and truststores (10.6) |

### `jdeps` and `jdeprscan` — the two upgrade tools

```bash
jdeps --list-deps app.jar                    # which JDK modules does it need?
jdeps --jdk-internals app.jar                # ⭐ does it use sun.* internals? (11.10)
jdeps -R -cp 'lib/*' app.jar                 # the full transitive graph
```

```bash
jdeprscan --release 21 app.jar               # ⭐ what deprecated API does it use?
jdeprscan --for-removal --release 21 app.jar # only what's scheduled for removal (11.7)
```

> ⭐ **Run both before a JDK upgrade.** `jdeps --jdk-internals` tells you exactly which
> libraries will need `--add-opens` (11.10), and `jdeprscan --for-removal` tells you what's
> about to stop compiling. Ten minutes that saves a day of confused debugging.

## `javadoc` — writing it well

```java
/**
 * Transfers money between accounts.
 *
 * <p>The transfer is atomic: either both accounts are updated or neither is.
 *
 * @param from   the source account, must not be {@code null}
 * @param amount the amount, must be positive
 * @return the resulting transaction id
 * @throws InsufficientFundsException if {@code from} lacks the balance
 * @see Account#balance()
 * @since 2.5
 */
public String transfer(Account from, Account to, BigDecimal amount) { ... }
```

```bash
javadoc -d docs -sourcepath src com.example
```

**What makes it good:**

| Do | Don't |
|---|---|
| Document the **contract** — preconditions, postconditions, invariants | Restate the method name |
| Document **what it throws and when** (4.4) | `@param name the name` |
| Document **null and threading** behaviour | Comment obvious code |
| `{@code ...}` for identifiers | Let it drift out of date |

```java
// ❌ pure noise
/** Gets the name. @return the name */
public String getName()
```

### Markdown in doc comments `Java 23`

```java
/// Transfers money between accounts.
///
/// The transfer is atomic: either both accounts are updated or neither is.
///
/// @param from the source account, must not be `null`
/// @throws InsufficientFundsException if `from` lacks the balance
public String transfer(...) { }
```

`///` comments use **Markdown** instead of HTML — no more `<p>` and `{@code}`. A genuine
readability improvement for anyone writing docs by hand.

## ⭐ Build and run a multi-class program with nothing but `javac` and `java`

**Do this once.** It demystifies every build tool (12.2).

```
myapp/
├── src/
│   └── com/example/
│       ├── Main.java
│       └── Greeter.java
└── lib/
    └── gson-2.10.jar
```

```bash
# 1. compile everything into out/
javac -d out -cp "lib/*" $(find src -name "*.java")

# 2. run it — note the CLASS NAME, not a path (1.6)
java -cp "out:lib/*" com.example.Main

# 3. package it
jar --create --file app.jar --main-class com.example.Main -C out .

# 4. run the jar
java -cp "lib/*:app.jar" com.example.Main
#    (or java -jar app.jar, if the manifest's Class-Path covers the deps)

# 5. look inside — a jar is just a zip (1.6)
jar --list --file app.jar
unzip -p app.jar META-INF/MANIFEST.MF
```

> ⭐ **That's the whole job.** Compile with a classpath, run with a classpath, zip it with a
> manifest.
>
> **A build tool automates exactly these steps and adds one thing you can't do by hand:
> downloading dependencies** (12.2). Understanding this makes "works in the IDE, fails on
> the command line" (1.6) immediately diagnosable — it's the classpath, every time.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `-source`/`-target` instead of `--release` | Compiles against the **current** JDK's API |
| Missing `-parameters` | Reflection sees `arg0`; name-based binding breaks |
| `java -cp out com/example/Main.class` | It's a **class name**: `com.example.Main` |
| Skipping `-Xlint:all` | The `unchecked` warnings that matter (3.3) stay hidden |
| Upgrading the JDK without `jdeps`/`jdeprscan` | You find out at runtime |
| Javadoc that restates the signature | Noise. Document the **contract** |

---

## Recap

| Tool / flag | One line |
|---|---|
| ⭐ `--release N` | Compile against **that version's API**, not just its class format |
| ⭐ `-Xlint:all -Werror` | Turn warnings on and make them count |
| ⭐ `-parameters` | Keep parameter names for reflection |
| `-D` / `-X` / `-XX:` | Properties / non-standard / JVM internals |
| `@argfile` | A long command line, in a file |
| ⭐ `jshell`, `javap` | REPL and disassembler — your two daily tools |
| ⭐ `jdeps`, `jdeprscan` | **Run both before a JDK upgrade** |
| `javadoc` | Document the **contract**. Markdown `///` since `Java 23` |
| Build by hand, once | `javac -d out -cp` → `java -cp` → `jar` |
