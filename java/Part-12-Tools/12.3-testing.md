# 12.3 — Testing

> **What this is:** **Not optional in the Java world** — the ecosystem assumes it, and it
> is how you will verify everything in Parts 1 to 11.

---

## JUnit 5

```java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class AccountTest {

    private Account account;

    @BeforeEach void setUp()    { account = new Account("A1", BigDecimal.TEN); }
    @AfterEach  void tearDown() { }
    @BeforeAll  static void once() { }        // ⭐ must be static
    @AfterAll   static void done() { }

    @Test
    @DisplayName("withdrawing more than the balance is rejected")   // ⭐ readable output
    void rejectsOverdraft() {
        assertThrows(InsufficientFundsException.class,
                     () -> account.withdraw(BigDecimal.valueOf(100)));
    }

    @Nested
    @DisplayName("when the account is closed")                       // ⭐ grouping
    class WhenClosed {
        @BeforeEach void closeIt() { account.close(); }

        @Test void rejectsDeposits() {
            assertThrows(IllegalStateException.class, () -> account.deposit(ONE));
        }
    }
}
```

| Annotation | Does |
|---|---|
| `@Test` | A test method (11.7 — and you wrote this mechanism yourself) |
| `@BeforeEach` / `@AfterEach` | Per test |
| `@BeforeAll` / `@AfterAll` | Once per class — **must be `static`** |
| ⭐ `@Nested` | Group tests sharing a setup. Reads like a spec |
| ⭐ `@DisplayName` | A readable sentence instead of a method name |
| `@Disabled("reason")` | Skip, with a reason |
| `@Tag("slow")` | Filter test runs |

**Assumptions** — skip rather than fail when a precondition isn't met:

```java
assumeTrue(System.getenv("CI") == null);        // skips on CI
assumingThat(isLinux(), () -> { /* only here */ });
```

> ⚠️ **JUnit 4 → 5 renames:** `@Before`→`@BeforeEach`, `@BeforeClass`→`@BeforeAll`,
> `@Ignore`→`@Disabled`, `org.junit.Test`→`org.junit.jupiter.api.Test`. Mixing the two
> silently skips tests — the JUnit 4 runner ignores JUnit 5 annotations and vice versa.
> **Check your imports** (0.3).

## Assertions

```java
assertEquals(expected, actual);                // ⭐ expected FIRST
assertEquals(expected, actual, "context");     // a message on failure
assertTrue(cond);  assertNull(x);  assertSame(a, b);
assertArrayEquals(a, b);

// ⭐ assertThrows — and USE the returned exception
var ex = assertThrows(InsufficientFundsException.class, () -> account.withdraw(HUNDRED));
assertEquals("A1", ex.accountId());            // (4.4 — carry the data, not just a message)

// ⭐ assertAll — report ALL failures, not just the first
assertAll("account",
    () -> assertEquals("A1", account.id()),
    () -> assertEquals(TEN, account.balance()),
    () -> assertFalse(account.isClosed()));

assertTimeout(Duration.ofSeconds(1), () -> fastOperation());
```

> ⭐ **`assertAll` matters more than it looks.** Without it, the first failure hides the
> rest, so you fix one thing, rerun, find the next — three cycles instead of one.

### AssertJ's fluent style

```java
import static org.assertj.core.api.Assertions.*;

assertThat(account.balance()).isEqualByComparingTo("10.00");   // ⭐ BigDecimal (11.2)
assertThat(names).containsExactly("a", "b")
                 .doesNotContain("c")
                 .hasSize(2);
assertThat(user).extracting(User::name, User::age)
                .containsExactly("Basha", 30);
assertThatThrownBy(() -> account.withdraw(HUNDRED))
    .isInstanceOf(InsufficientFundsException.class)
    .hasMessageContaining("insufficient");
```

**Why most teams use AssertJ:** one `assertThat` entry point with IDE autocompletion,
far better failure messages, and collection assertions that JUnit's don't cover.

> ⭐ Note `isEqualByComparingTo` for `BigDecimal` — `isEqualTo` uses `equals`, which
> compares **scale** (11.2). AssertJ has a dedicated method precisely because this bites
> people.

## `@ParameterizedTest`

```java
@ParameterizedTest
@ValueSource(strings = {"", " ", "\t"})
void rejectsBlankNames(String name) {
    assertThrows(IllegalArgumentException.class, () -> new User(name));
}

@ParameterizedTest
@CsvSource({
    "1, 1, 2",
    "2, 3, 5",
    "-1, 1, 0"
})
void adds(int a, int b, int expected) {
    assertEquals(expected, Calculator.add(a, b));
}

@ParameterizedTest
@EnumSource(Status.class)                       // ⭐ every enum constant (2.7)
void everyStatusHasALabel(Status s) {
    assertNotNull(s.label());
}

@ParameterizedTest
@MethodSource("accountProvider")                // ⭐ arbitrary objects
void handlesAccounts(Account a, BigDecimal expected) { ... }

static Stream<Arguments> accountProvider() {    // (6.4)
    return Stream.of(Arguments.of(new Account("A1", TEN), TEN));
}
```

Sources: `@ValueSource`, `@CsvSource`, `@CsvFileSource`, `@EnumSource`, `@MethodSource`,
`@ArgumentsSource`, `@NullAndEmptySource`.

> **One parameterised test replaces five near-identical copy-pasted ones** — and when the
> assertion changes, you change it once.

## ⭐ Test doubles, explained clearly

People use these words interchangeably and they mean different things:

| Double | Is | Example |
|---|---|---|
| **Dummy** | Passed but never used | `null`, or a placeholder to fill a parameter |
| **Stub** | ⭐ Returns **canned answers** | "`findById` always returns this user" |
| **Fake** | ⭐ A **working** lightweight implementation | An in-memory `Map`-backed repository |
| **Mock** | ⭐ Records calls; you **assert on the interaction** | "assert `send()` was called once" |
| **Spy** | A **real** object with some calls recorded or overridden | A real service with one method stubbed |

```java
// STUB — I care about the RESULT
when(repo.findById("1")).thenReturn(Optional.of(user));      // (6.7)

// MOCK — I care about the INTERACTION
verify(emailService).send(eq("a@b.com"), anyString());
verify(emailService, never()).send(any(), any());

// SPY — real object, one method overridden
var spy = spy(new RealService());
doReturn("stubbed").when(spy).expensiveCall();
```

> ⭐ **Prefer stubs and fakes over mocks.** A mock asserts *how* your code works — so every
> refactor breaks the test even when behaviour is unchanged. A stub or fake asserts *what*
> it produces.
>
> ⚠️ **A test full of `verify()` calls is testing your implementation, not your behaviour.**
> Use `verify` when the interaction *is* the behaviour — an email genuinely was sent, a
> payment genuinely was charged.

**An in-memory fake is often better than any mock:**

```java
class InMemoryUserRepository implements UserRepository {     // (2.4)
    private final Map<String, User> users = new HashMap<>();
    public Optional<User> findById(String id) { return Optional.ofNullable(users.get(id)); }
    public User save(User u) { users.put(u.id(), u); return u; }
}
```

Fast, no framework, no stubbing per test, and it catches sequencing bugs a mock never
would.

## ⭐ Why constructor injection is what makes any of this possible

**This is the payoff from 2.10 and 2.2.**

```java
// ❌ untestable — the dependency is created inside, or reached statically
class OrderService {
    private final PaymentGateway gateway = new StripeGateway();     // hard-wired

    Order place(Cart cart) {
        var result = PaymentApi.charge(cart.total());               // static (2.2)
        ...
    }
}
```

**There is no seam.** You cannot substitute the gateway. Testing this means really calling
Stripe.

```java
// ✅ constructor injection — the seam is the constructor
class OrderService {
    private final PaymentGateway gateway;
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }

    Order place(Cart cart) { return gateway.charge(cart.total()); }
}
```

```java
@Test void rejectsDeclinedPayments() {
    var service = new OrderService(cart -> new Declined("card expired"));   // a lambda! (6.1)
    assertThrows(PaymentException.class, () -> service.place(cart));
}
```

> ⭐ **Constructor injection isn't an architectural nicety — it's the mechanism that makes
> the class testable at all.** It's also exactly what a DI container reads by reflection
> (11.6).
>
> **If a class is hard to test, that is a design signal, not a testing problem.** Static
> business logic (2.2), hard-wired dependencies and hidden global state are the usual
> causes.

## Property-based testing with jqwik

For the parts of Parts 3 and 5 that deserve it — where you can state an **invariant** that
must hold for *all* inputs rather than three examples:

```java
@Property
void sortingIsIdempotent(@ForAll List<@AlphaChars String> input) {
    var once  = input.stream().sorted().toList();
    var twice = once.stream().sorted().toList();
    assertEquals(once, twice);
}

@Property
void reverseTwiceIsIdentity(@ForAll List<Integer> list) {
    assertEquals(list, reverse(reverse(list)));
}

@Property
void serialisationRoundTrips(@ForAll("users") User u) {
    assertEquals(u, deserialize(serialize(u)));                     // (10.5)
}
```

jqwik generates hundreds of inputs, and **shrinks** a failure to the smallest reproducing
case — often revealing an empty list or a boundary value you'd never have written by hand.

> **Where it earns its place:** comparators (5.5 — is it really transitive?), `equals`/
> `hashCode` contracts (2.5), parsers, encoders, and anything with a round-trip property.

## Testing concurrency honestly — see 9.12

```java
// ⚠️ this test PASSES against genuinely broken code
@Test void counterIsThreadSafe() { /* 1000 increments across 10 threads */ }
```

**Covered in full in 9.12.** The short version:

- A passing test explored **one interleaving** out of astronomically many
- Too few iterations means the JIT never reached C2 (8.8) and nothing interleaved
- x86 reorders far less than the ARM server you deploy to (9.2)
- **Use `jcstress`** for memory-model verification, and **reason** rather than test

> ⭐ **This is the one area where testing genuinely cannot give you confidence.** Everywhere
> else, tests are your primary tool. Here they're a weak secondary check.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Mixing JUnit 4 and 5 annotations | Tests **silently don't run** |
| `assertEquals(actual, expected)` | Backwards — the failure message lies |
| `assertEquals` on `BigDecimal` | Compares scale (11.2). Use `isEqualByComparingTo` |
| A `verify()` for every call | Testing implementation. Refactors break it |
| `@BeforeAll` non-static | JUnit won't run it |
| Shared mutable state between tests | Order-dependent failures (2.2) |
| Testing concurrency with a unit test | False confidence (9.12) |
| A class that's hard to test | **A design problem**, not a testing problem |

## Recap

| Concept | One line |
|---|---|
| JUnit 5 | `@Test`, `@BeforeEach`, ⭐ `@Nested`, `@DisplayName` |
| Assertions | ⭐ `assertThrows` + use the exception; ⭐ `assertAll` |
| AssertJ | Fluent, better messages, `isEqualByComparingTo` for `BigDecimal` |
| `@ParameterizedTest` | One test, many inputs |
| **Doubles** | Dummy · **stub** (answers) · **fake** (works) · **mock** (interactions) · spy |
| ⭐ Prefer | **Stubs and fakes over mocks.** Mocks couple tests to implementation |
| ⭐ **Constructor injection** | **The seam that makes testing possible at all** |
| jqwik | Invariants over all inputs, with shrinking |
| Concurrency | **Tests give false confidence** (9.12) |
