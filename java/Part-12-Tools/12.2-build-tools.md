# 12.2 — Build tools, at the minimum

> **What this is:** **You need to read these files and fix them. You do not need to master
> them.**

---

## What a build tool does

| Job | |
|---|---|
| ⭐ **Resolve dependencies** | Download jars **and their dependencies, transitively** — the one thing you can't do by hand (12.1) |
| **Compile** | `javac` with the right classpath and flags |
| **Test** | Run JUnit, fail the build on failure (12.3) |
| **Package** | A jar, a fat jar, a container image |
| **Publish** | Push to a repository |

> Everything except dependency resolution is automating what 12.1 showed you doing by
> hand. **That one job is why build tools exist.**

---

## Maven — the declarative one

```xml
<project>
    <groupId>com.example</groupId>            <!-- ⭐ the three COORDINATES -->
    <artifactId>myapp</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>25</maven.compiler.release>   <!-- ⭐ --release (12.1) -->
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.17.0</version>
        </dependency>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.10.2</version>
            <scope>test</scope>                                <!-- ⭐ -->
        </dependency>
    </dependencies>
</project>
```

**Coordinates** — `groupId:artifactId:version` — uniquely identify any jar on Maven Central.

```bash
mvn clean            # delete target/
mvn compile
mvn test
mvn package          # → target/myapp-1.0.0.jar
mvn install          # → into your local ~/.m2 repository
mvn dependency:tree  # ⭐ the one you'll use most
```

**The lifecycle is fixed and ordered**: `validate → compile → test → package → verify →
install → deploy`. Running `mvn package` runs everything before it. You don't write the
sequence; you configure the phases.

> **Why nearly every tutorial uses Maven:** it's declarative and boringly predictable. Any
> Maven project builds with `mvn package`, with no need to read the build file first.

## Gradle — the programmable one

```kotlin
// build.gradle.kts — Kotlin DSL (preferred over Groovy for IDE support)
plugins {
    java
    application
}

java {
    toolchain { languageVersion = JavaLanguageVersion.of(25) }
}

dependencies {
    implementation("com.fasterxml.jackson.core:jackson-databind:2.17.0")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}

tasks.test { useJUnitPlatform() }
```

```bash
./gradlew build        # ⭐ the WRAPPER — pins the Gradle version, commit it
./gradlew test
./gradlew dependencies # the dependency tree
```

| | Maven | Gradle |
|---|---|---|
| Format | XML, **declarative** | Kotlin/Groovy, **a program** |
| Build sequence | Fixed lifecycle | A **task graph** |
| Speed | Slower | ⭐ **Incremental + build cache + daemon** |
| Predictability | ⭐ High | Depends on what the file does |
| Learning curve | Shallow | Steep |

> **Why large projects prefer Gradle:** incremental builds and caching. On a 500-module
> project the difference is minutes per build. On a 5-module project it doesn't matter.

⚠️ **Always use the Gradle wrapper (`./gradlew`)** and commit it — it pins the Gradle
version so everyone and CI build identically.

## ⭐ Transitive dependencies and version conflicts

**You declare one dependency; you get dozens.**

```
your-app
└── spring-boot-starter-web
    ├── spring-web
    │   └── spring-core
    ├── jackson-databind
    │   ├── jackson-core
    │   └── jackson-annotations
    └── tomcat-embed-core
```

**When two paths want different versions**, the tools resolve differently:

| | Rule |
|---|---|
| **Maven** | ⭐ **Nearest wins** — the shortest path in the tree, not the highest version |
| **Gradle** | ⭐ **Highest version wins** |

> ⭐ **Maven's "nearest wins" surprises everyone.** A transitive dependency at depth 1 beats
> a *newer* one at depth 3 — so adding an unrelated library can silently downgrade
> something and produce `NoSuchMethodError` (8.2) at runtime.

**Diagnosing it — the single most valuable build-tool skill:**

```bash
mvn dependency:tree -Dverbose            # ⭐ shows what was omitted and why
mvn dependency:tree -Dincludes=com.fasterxml.jackson*
./gradlew dependencyInsight --dependency jackson-databind
```

**Fixing it:**

```xml
<!-- Maven: pin versions for everything transitively -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson</groupId>
            <artifactId>jackson-bom</artifactId>     <!-- ⭐ a BOM: a coherent version set -->
            <version>2.17.0</version>
            <type>pom</type><scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<!-- or exclude a transitive dep entirely -->
<dependency>
    <groupId>com.example</groupId><artifactId>lib</artifactId>
    <exclusions>
        <exclusion><groupId>commons-logging</groupId><artifactId>commons-logging</artifactId></exclusion>
    </exclusions>
</dependency>
```

> ⭐ **`NoSuchMethodError` or `NoClassDefFoundError` at runtime in code that compiled fine
> is almost always a version conflict** (8.2). `dependency:tree` first, every time.

## Scopes and configurations

| Maven scope | Gradle | Available at | Passed to consumers |
|---|---|---|---|
| `compile` (default) | `implementation` | Compile + runtime | ⭐ Gradle: **no**; Maven: yes |
| — | `api` | Compile + runtime | ✅ Yes |
| `runtime` | `runtimeOnly` | Runtime only | Yes |
| **`test`** | `testImplementation` | Tests only | No |
| `provided` | `compileOnly` | Compile only | No |

> ⭐ **Gradle's `implementation` vs `api` is a real improvement.** `implementation` keeps a
> dependency off your consumers' compile classpath — so it doesn't leak into your public
> API, and changing it doesn't force them to recompile. **Default to `implementation`; use
> `api` only when the type genuinely appears in your public signatures** (2.4, 11.10).

`provided`/`compileOnly` is for things the runtime supplies — a servlet API, Lombok.

## Maven Central and fat jars

**Maven Central** is the default public repository. Anything with coordinates comes from
there unless configured otherwise. Search at [central.sonatype.com](https://central.sonatype.com).

```bash
~/.m2/repository/                # your local cache — both tools use it
```

**Fat jar (uber jar)** — your code **plus every dependency**, in one runnable jar:

```bash
java -jar app.jar        # no -cp needed; everything is inside
```

| | |
|---|---|
| **Fat jar** | Dependencies unpacked and merged. Spring Boot's is nested and layered instead |
| ⭐ **Shaded jar** | Fat jar **+ packages renamed** — `com.google.common` → `myapp.shaded.com.google.common` |

> ⭐ **Shading exists to solve version conflicts you can't otherwise fix** — if your library
> needs Guava 31 and your consumer needs Guava 20, shade yours and both coexist. It's a
> last resort (it bloats the jar and breaks reflection), but sometimes the only option.

⚠️ Fat jars can break on duplicate resource files — two jars both containing
`META-INF/services/...` (11.10) need a merge strategy, or service discovery silently
loses providers.

## Reproducible builds and locking

```xml
<project.build.outputTimestamp>2026-01-01T00:00:00Z</project.build.outputTimestamp>
```

**A reproducible build** produces a byte-identical artifact from the same source — no
embedded timestamps, stable file ordering. It lets you verify that a published jar really
came from the source it claims.

**Locking** pins the *resolved* versions so a build today and in six months use identical
dependencies:

```bash
mvn dependency:lock                      # or the versions plugin
./gradlew dependencies --write-locks     # Gradle dependency locking
```

> ⚠️ **Never use version ranges or Gradle's `latest.release`** in production. A build that
> silently picks up a new version is a build that breaks without a commit — and a supply
> chain risk.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `NoSuchMethodError` at runtime | **Version conflict.** `dependency:tree` first |
| Maven picks the newest version | ⭐ **Nearest wins**, not newest |
| Not committing `gradlew` | Everyone builds with a different Gradle |
| `api` everywhere in Gradle | Leaks your dependencies into consumers' classpaths |
| Version ranges | Non-reproducible builds |
| Fat jar with duplicate service files | Silently loses `ServiceLoader` providers |
| `mvn install` to "make it work" | Hides the real problem; pollutes `~/.m2` |

## Recap

| Concept | One line |
|---|---|
| The one irreplaceable job | ⭐ **Transitive dependency resolution** |
| Maven | XML, **declarative**, fixed lifecycle, predictable |
| Gradle | Kotlin/Groovy, **programmable**, incremental, fast at scale |
| Coordinates | `groupId:artifactId:version` |
| ⭐ **Conflicts** | Maven: **nearest wins**. Gradle: **highest wins** |
| ⭐ **`dependency:tree`** | **The skill that matters.** Run it before guessing |
| Scopes | `implementation` over `api`; `test`; `provided` |
| Fat vs shaded | Merged vs **merged with packages renamed** |
| Locking | Pin versions. **Never use ranges** |

2. Why does Maven's "nearest wins" let an unrelated new dependency downgrade an existing one?
3. When is `api` the right Gradle configuration rather than `implementation`?
