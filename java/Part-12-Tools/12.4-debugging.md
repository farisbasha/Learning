# 12.4 — Debugging

> **What this is:** **An underrated skill that pays back immediately.** Most developers use
> ~20% of their debugger.

---

## Breakpoints beyond the basic one

| Kind | Use |
|---|---|
| **Line** | The default |
| ⭐ **Conditional** | `userId.equals("12345")` — stop on **one** iteration out of a million |
| ⭐ **Exception** | Stop **where an exception is thrown**, not where it's caught |
| ⭐ **Field watchpoint** | Stop when a field is **read or written** — "who is setting this to null?" |
| **Method** | Stop on entry/exit of any method (slow) |
| **Log breakpoint** | ⭐ Print and continue — **no code change, no redeploy** |

### The three that change how you work

**Conditional breakpoints** — stop on the case that matters:

```java
// right-click the breakpoint → Condition:
order.id().equals("ORD-99123") && order.total().compareTo(TEN) > 0
```

Also: **hit count** ("stop on the 500th hit") and **pass count**.

**Exception breakpoints** — this one is genuinely transformative:

```
Break on: NullPointerException, caught and uncaught
```

Stops **at the throw site**, with the full stack and every local still alive. Compare with
reading a stack trace after the fact (1.5) — here you can inspect the actual state that
caused it.

> ⭐ **Use it for swallowed exceptions.** If something is failing silently because of an
> empty catch block (4.4), an exception breakpoint finds it immediately — there's no log
> line to search for.

**Field watchpoints** — for "this field became null and I have no idea where":

```
Right-click the field → Toggle Field Watchpoint → break on modification
```

Answers the question directly instead of by bisection.

## Stepping, frames, and evaluating

| Action | Does |
|---|---|
| **Step over** (F8) | Run the line, don't descend |
| **Step into** (F7) | Descend into the call |
| ⭐ **Step out** (Shift+F8) | Finish this method, return to the caller |
| ⭐ **Run to cursor** | Continue until this line — no breakpoint needed |
| ⭐ **Drop frame** | **Rewind** — pop the current frame and re-enter the method |
| **Force return** | Return a value immediately without executing the rest |

> ⭐ **"Drop frame" is the one most people don't know.** Stepped one line too far? Drop the
> frame and the method restarts. It can't undo side effects that already happened (a
> database write, a sent message) but for pure logic it's a time machine.

**The frames panel is the live version of a stack trace** (1.5) — click any frame to
inspect **that** method's locals. Walking up the stack to see what the caller passed is
usually faster than re-reading the code.

**Evaluate expression** — run arbitrary code in the paused JVM:

```java
// in the evaluate window, while paused:
order.items().stream().filter(i -> i.price() == null).toList()     // (6.5)
repository.findById("123")                                          // call methods
user.setName("test")                                                // ⚠️ mutate state
```

> ⭐ **This is the most underused debugger feature.** You can test a fix, explore a
> collection, or call a method — without recompiling. It's a REPL (0.4) attached to your
> running program's actual state.

**Hot-swapping a method body:**

```
Edit the method → Build → Reload Changed Classes
```

⚠️ **Method bodies only.** You cannot add or remove methods or fields, or change a
signature — that requires a restart. Still, for tuning a condition or fixing an
off-by-one, it removes the whole restart cycle.

## ⭐ Remote debugging

**Debug a JVM running elsewhere** — in Docker, on a test server, in a container.

```bash
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar
```

| Option | Means |
|---|---|
| `transport=dt_socket` | TCP |
| `server=y` | The JVM listens; the IDE connects |
| ⭐ `suspend=n` | **Start immediately.** `y` waits for a debugger — useful for startup bugs |
| `address=*:5005` | ⚠️ `*` binds all interfaces — needed in Docker, dangerous in production |

Then: IDE → **Run → Attach to Process / Remote JVM Debug** → host + port 5005.

> ⚠️ **JDWP is completely unauthenticated.** Anyone who can reach that port can execute
> arbitrary code in your JVM. **Never expose it on a public interface.** Bind to localhost
> and use an SSH tunnel:
> ```bash
> ssh -L 5005:localhost:5005 user@server
> ```

For Docker, publish the port to localhost only: `-p 127.0.0.1:5005:5005`.

## ⭐ Debugging multi-threaded code

**The hard case**, and it connects to Part 09.

| Setting | Does |
|---|---|
| ⭐ **Suspend: Thread** | Freeze **only the breakpointing thread** — others keep running |
| **Suspend: All** | Freeze everything (the default) |

```
Right-click a breakpoint → Suspend: Thread
```

> ⭐ **"Suspend: All" is usually wrong for concurrency work.** Freezing every thread means
> you can never observe two threads interacting — which is the thing you're trying to
> see. Suspending one thread lets the others race ahead, which is often exactly what you
> need to reproduce.

### ⚠️ The debugger changes the timing you're trying to observe

**This is the fundamental problem** (9.2):

| Effect | |
|---|---|
| **Breakpoints add delays** | Which changes interleaving entirely |
| **Suspending serialises threads** | The race you're hunting stops happening |
| ⭐ **The debugger inhibits JIT optimisation** | So the reordering and hoisting from 9.2 **stop occurring** |
| **`toString()` in the variables panel** | Calls your code — which may synchronise, or have side effects |

> ⭐ **A visibility bug (9.2) typically vanishes under a debugger**, because the debugger
> prevents the JIT from hoisting the read out of the loop — the exact optimisation causing
> the bug.
>
> **So: for concurrency, prefer thread dumps (8.9), logging, and `jcstress` (9.12) over
> stepping.** The debugger is for logic bugs; concurrency bugs need different tools.

**What works instead:**
- **Thread dumps** — three, ten seconds apart (8.9)
- **Log breakpoints** — print without suspending, so timing barely changes
- **Conditional breakpoints** on the specific bad state, rather than stepping

## Reading a stack trace properly

Covered fully in 1.5 — the three things, in order:

1. ⭐ **The last `Caused by:`** — usually the actual root cause
2. **The first frame in your own package** — where *your* code is involved
3. **`Suppressed:`** — from try-with-resources (4.3), a second failure during cleanup

```
Exception in thread "main" ServiceException: could not place order
    at com.example.OrderService.place(OrderService.java:42)     ← ② your code
    ...
Caused by: DataAccessException: query failed
    ...
Caused by: SQLException: connection refused                      ← ① the real cause
    Suppressed: IOException: failed to close connection          ← ③
```

> **Don't read top to bottom.** Jump to the bottom-most `Caused by:`, then find your own
> package.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Stepping through a loop a thousand times | Use a **conditional breakpoint** or hit count |
| Searching logs for a swallowed exception | Use an **exception breakpoint** |
| "Suspend: All" for concurrency | You can never observe the interaction |
| Trusting a debugger for race conditions | ⭐ **It inhibits the JIT optimisations causing the bug** |
| JDWP on a public interface | **Unauthenticated remote code execution** |
| Expecting hot-swap to add a method | Method **bodies** only |
| Reading a stack trace top-down | The root cause is the last `Caused by:` |

## Recap

| Technique | One line |
|---|---|
| ⭐ **Conditional breakpoint** | Stop on the one case that matters |
| ⭐ **Exception breakpoint** | Stop **at the throw** — finds swallowed exceptions |
| ⭐ **Field watchpoint** | "Who set this to null?" |
| Log breakpoint | Print without suspending or recompiling |
| ⭐ **Drop frame** | Rewind and re-enter the method |
| ⭐ **Evaluate expression** | A REPL attached to your live program state |
| Remote debug | `-agentlib:jdwp=...` ⚠️ **unauthenticated — tunnel it** |
| Threads | **Suspend: Thread**, not All |
| ⭐ **The observer effect** | The debugger inhibits the JIT — concurrency bugs vanish |
| Stack traces | Last `Caused by:` → your package → `Suppressed:` |
