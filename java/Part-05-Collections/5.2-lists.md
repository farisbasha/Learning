# 5.2 — Lists

> **What this is:** The one you use ninety percent of the time, and **the one people
> choose wrongly** — usually because of a Big-O table that doesn't reflect how real
> hardware works.

---

## Coming from JS/Python/Dart

`ArrayList` is a JS `Array` or a Python `list` — a growable array. That's your default
and it's almost always right.

The trap unique to Java: `LinkedList` exists, looks better on paper, and is nearly always
worse. Your other languages didn't offer you the chance to make that mistake.

---

## The concepts

### `ArrayList` — backed by an array

```java
List<String> names = new ArrayList<>();
names.add("Basha");             // amortised O(1)
names.get(0);                   // O(1) — direct array index
names.add(0, "First");          // O(n) — shifts everything right
names.remove(0);                // O(n) — shifts everything left
```

**Growth and amortised append.** The backing array has a *capacity* bigger than the
*size*. When it fills:

```
capacity 10, size 10 → add() → allocate a new array of capacity 15 (1.5×)
                             → System.arraycopy the 10 elements
                             → capacity 15, size 11
```

Each individual resize is O(n), but it happens rarely enough (every ~1.5× growth) that
the **average** cost per `add` is O(1). That's what "amortised" means.

### `LinkedList` — and why it's almost always wrong

```java
List<String> names = new LinkedList<>();
```

A doubly-linked list. The Big-O table looks better:

| Operation | `ArrayList` | `LinkedList` |
|---|---|---|
| `get(i)` | **O(1)** | O(n) |
| `add(e)` at end | O(1)* | **O(1)** |
| `add(0, e)` at front | O(n) | **O(1)** |
| `remove(0)` | O(n) | **O(1)** |
| Iterate | O(n) | O(n) |

**So why is it almost always the wrong choice?**

**(1) Cache locality.** An `ArrayList`'s elements are contiguous in memory. Modern CPUs
fetch memory in 64-byte cache lines, so reading element 0 also pulls in elements 1–7 for
free. A `LinkedList`'s nodes are scattered across the heap — every `next` is a
potentially-cache-missing pointer chase, and a cache miss is ~100× a cache hit.

**(2) Per-node overhead.** Every `LinkedList` element allocates a `Node` object:

```java
private static class Node<E> {
    E item;         // 4–8 bytes (a reference)
    Node<E> next;   // 4–8 bytes
    Node<E> prev;   // 4–8 bytes
}                   // + ~16 bytes object header (8.4)
```

**~32–40 bytes of overhead per element**, versus 4–8 bytes for an `ArrayList` slot.

**(3) The O(1) insert is a lie in practice.** `LinkedList.add(i, e)` is O(1) *once you
have the node*. Getting to position `i` is O(n). So:

```java
list.add(500, x);        // O(n) traversal + O(1) insert = O(n). Same as ArrayList.
```

The only genuinely O(1) inserts are at the head/tail, or via an `Iterator` you already
hold.

> **The rule: use `ArrayList`. If you need fast add/remove at both ends, use
> `ArrayDeque` (5.4), not `LinkedList`.** There is essentially no case where
> `LinkedList` is the right answer in modern Java. Even the JDK authors have said so.

### Capacity versus size, and pre-sizing

```java
var list = new ArrayList<String>();
list.size();        // 0  — how many elements are in it
                    // capacity is 10 by default (allocated lazily on first add)
```

If you know the count up front, say so — it avoids all the intermediate resizes and copies:

```java
var list = new ArrayList<String>(10_000);    // capacity 10,000, size 0
```

Same for `HashMap` (5.3): `new HashMap<>(expectedSize)`.

> Worth doing when you know the size and it's large. Not worth doing for a list of 5.

### ⚠️ `subList` is a **view**, not a copy

```java
var list = new ArrayList<>(List.of("a","b","c","d","e"));
List<String> sub = list.subList(1, 3);     // [b, c]

sub.set(0, "X");
IO.println(list);          // [a, X, c, d, e]  ← modified the ORIGINAL
```

And the reverse — modifying the backing list **invalidates** the view:

```java
var sub = list.subList(1, 3);
list.add("f");                  // structural modification to the parent
IO.println(sub);                // 💥 ConcurrentModificationException
```

**Useful trick** — because it's a view, this clears a range in place:

```java
list.subList(1, 3).clear();     // removes elements 1 and 2 from `list`
```

**To get an actual copy:**
```java
var copy = new ArrayList<>(list.subList(1, 3));
```

### ⚠️ `Arrays.asList` — a classic trap

```java
List<String> list = Arrays.asList("a", "b", "c");

list.set(0, "X");        // ✅ works! It's a VIEW of the array
list.add("d");           // 💥 UnsupportedOperationException — fixed size
list.remove(0);          // 💥 UnsupportedOperationException
```

It's **fixed-size and array-backed**: `set` works, `add`/`remove` don't. This
half-mutable behaviour catches everyone once.

Worse, with an actual array it's a **live view**:

```java
String[] array = {"a", "b"};
List<String> list = Arrays.asList(array);
array[0] = "CHANGED";
IO.println(list);        // [CHANGED, b]
```

**And the primitive trap:**

```java
int[] nums = {1, 2, 3};
List<int[]> wrong = Arrays.asList(nums);     // 😱 a List of ONE element (the array itself)
IO.println(wrong.size());                     // 1

Integer[] boxed = {1, 2, 3};
List<Integer> right = Arrays.asList(boxed);   // ✅ 3 elements
```

Varargs (1.5) can't decompose an `int[]` into `Integer` elements, so it treats the whole
array as one `T`.

> **Modern replacement:** `List.of(...)` for immutable, `new ArrayList<>(List.of(...))`
> for mutable. Use `Arrays.stream(nums).boxed().toList()` for primitives (6.4).

### `List.of` versus `new ArrayList<>()`

| | `List.of(...)` `Java 9` | `new ArrayList<>()` |
|---|---|---|
| Mutable | ❌ throws `UnsupportedOperationException` | ✅ |
| `null` elements | ❌ **throws `NullPointerException`** | ✅ allowed |
| `contains(null)` | ❌ throws NPE | ✅ returns false |
| Memory | Compact — specialised classes for 0, 1, 2 elements | Array + object overhead |
| Use for | Constants, defaults, return values | Anything you'll modify |

```java
List<String> fixed = List.of("a", "b");                     // immutable
List<String> open  = new ArrayList<>(List.of("a", "b"));    // mutable copy
```

> ⚠️ **`List.of` is null-hostile.** `List.of(maybeNull)` throws. This catches people
> migrating from `Arrays.asList`, which tolerates nulls. It's deliberate — 5.7.

### ⚠️ `indexOf`, `contains`, `remove(Object)` are linear scans that call `equals`

```java
list.contains(user);        // O(n) — calls user.equals(...) on every element
list.indexOf(user);         // O(n)
list.remove(user);          // O(n)
```

Two consequences:

**(1) Performance.** `contains` in a loop over a list is accidentally O(n²):

```java
// ❌ O(n × m)
for (String id : incoming) {
    if (existingList.contains(id)) { ... }
}

// ✅ O(n + m)
Set<String> existing = new HashSet<>(existingList);
for (String id : incoming) {
    if (existing.contains(id)) { ... }
}
```

**(2) It depends on `equals` being correct** (2.5). If your class didn't override
`equals`, `contains` uses reference identity and will never find an equal-but-different
object.

Also note the overload trap from 1.5:

```java
List<Integer> nums = new ArrayList<>(List.of(10, 20, 30));
nums.remove(1);                     // removes INDEX 1 → [10, 30]
nums.remove(Integer.valueOf(20));   // removes the VALUE 20
```

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `LinkedList` for frequent inserts | Cache misses and node overhead lose to `ArrayList`. Use `ArrayDeque` |
| `subList` gives a copy | It's a **view** — and mutating the parent invalidates it |
| `Arrays.asList` is a normal list | Fixed-size: `set` works, `add` throws |
| `Arrays.asList(intArray)` | One element, not n. Boxing doesn't happen |
| `List.of(x)` where x may be null | Throws NPE |
| `list.contains()` in a loop | O(n²). Use a `Set` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `LinkedList` | `ArrayList`, or `ArrayDeque` for ends |
| `Vector` | `ArrayList` (5.1) |
| `Arrays.asList` in new code | `List.of` / `new ArrayList<>(List.of(...))` |

---

## Recap

| Concept | One line |
|---|---|
| `ArrayList` | Array-backed. **Your default.** O(1) get, amortised O(1) append |
| `LinkedList` | Better Big-O, worse in reality — cache locality and node overhead |
| Pre-sizing | `new ArrayList<>(n)` when n is known and large |
| `subList` | A **view** — mutations flow both ways |
| `Arrays.asList` | Fixed-size array view. `set` ✅, `add` 💥 |
| `List.of` | Immutable, **null-hostile**, compact |
| `contains`/`indexOf`/`remove(Object)` | O(n) scans calling `equals` |
