# 5.5 — Ordering

> **What this is:** Two mechanisms for "what comes first", and **a contract that sorting
> silently depends on**.

---

## Coming from JS/Python/Dart

| | JS/Python | Java |
|---|---|---|
| Sort a list | `sort(key=...)` / `sort((a,b)=>...)` | `Comparator` |
| Natural order on your own class | `__lt__` | `Comparable` |
| Broken comparator | Usually just a weird order | **`IllegalArgumentException`** at runtime |

Java's sort *detects* an inconsistent comparator and throws. That's stricter than you're
used to, and it catches the `a - b` bug below.

---

## The concepts

### `Comparable` — natural ordering

The class defines its *own* default order:

```java
public record Person(String name, int age) implements Comparable<Person> {
    @Override
    public int compareTo(Person other) {
        return Integer.compare(this.age, other.age);
    }
}

var people = new ArrayList<>(List.of(...));
Collections.sort(people);        // uses compareTo
people.sort(null);               // same thing
new TreeSet<>(people);           // TreeMap/TreeSet require it (5.3, 5.4)
```

**The contract:**

| Rule | Means |
|---|---|
| Sign | `a.compareTo(b)` < 0, 0, or > 0 for less/equal/greater |
| Antisymmetry | `sgn(a.compareTo(b)) == -sgn(b.compareTo(a))` |
| Transitivity | `a > b` and `b > c` ⟹ `a > c` |
| Consistency | `a.compareTo(b) == 0` ⟹ both compare the same to every `c` |

### ⭐ Its contract with `equals` — and what `TreeSet` does when they disagree

> **Strongly recommended:** `a.compareTo(b) == 0` **if and only if** `a.equals(b)`.

It's "recommended", not required — but breaking it produces genuinely surprising
behaviour, because **`TreeSet` and `TreeMap` use `compareTo`, not `equals`**, to decide
what's a duplicate:

```java
record Person(String name, int age) implements Comparable<Person> {
    public int compareTo(Person o) { return Integer.compare(age, o.age); }
    // equals compares name AND age (records generate it, 2.6)
}

var a = new Person("Basha", 30);
var b = new Person("Ali", 30);       // different name, SAME age

a.equals(b);                          // false — different people

Set<Person> hash = new HashSet<>(List.of(a, b));
IO.println(hash.size());              // 2 ✅ uses equals

Set<Person> tree = new TreeSet<>(List.of(a, b));
IO.println(tree.size());              // 1 😱 — compareTo said 0, so b was dropped
```

**The same data, two `Set`s, different sizes.** `TreeSet` silently discarded a person.

> **The fix:** make `compareTo` consistent with `equals` — compare every field that
> `equals` compares, using a tiebreaker:
> ```java
> public int compareTo(Person o) {
>     return Comparator.comparingInt(Person::age)
>                      .thenComparing(Person::name)      // ← tiebreaker
>                      .compare(this, o);
> }
> ```
>
> The JDK documents this deviation where it exists — `BigDecimal` is the famous case:
> `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` is **false**, but `compareTo`
> returns **0**. So a `TreeSet<BigDecimal>` treats them as the same and a `HashSet`
> doesn't.

### `Comparator` — external ordering, and why it's more flexible

```java
Comparator<Person> byName = Comparator.comparing(Person::name);
people.sort(byName);
```

| | `Comparable` | `Comparator` |
|---|---|---|
| Lives | Inside the class | Outside |
| How many | **One** natural order | **Unlimited** |
| Works on classes you don't own | ❌ | ✅ |
| Lambda-friendly | ❌ | ✅ (it's a functional interface, 2.4) |

> **Default to `Comparator`.** Use `Comparable` only when the type has one genuinely
> obvious order (`Integer`, `String`, `LocalDate`) *and* you own it.

### ⭐ Comparator construction `Java 8`

This is the part you'll use daily. Build them by composition, never by hand:

```java
import static java.util.Comparator.*;

Comparator<Person> c =
    comparing(Person::lastName)                  // primary
        .thenComparing(Person::firstName)        // tiebreaker
        .thenComparingInt(Person::age)           // second tiebreaker, no boxing
        .reversed();                             // flip the WHOLE thing
```

The full toolkit:

```java
comparing(Person::name)                          // by a key
comparing(Person::name, String.CASE_INSENSITIVE_ORDER)  // key + how to compare it
comparingInt(Person::age)                        // primitive — avoids boxing
comparingLong(...)  comparingDouble(...)

naturalOrder()                                   // uses Comparable
reverseOrder()

c.reversed()
c.thenComparing(...)

nullsFirst(comparing(Person::name))              // tolerate null ELEMENTS
nullsLast(...)
```

**Handling null *fields*** (not null elements):

```java
comparing(Person::nickname, nullsLast(naturalOrder()))
```

> ⚠️ **`.reversed()` applies to everything before it**, not just the last key:
> ```java
> comparing(A).thenComparing(B).reversed()
> // = reverse of (A then B) — BOTH flip
>
> comparing(A).reversed().thenComparing(B)
> // = A descending, then B ascending
> ```

### ⭐ Why subtracting two ints is a broken compare

The single most common comparator bug:

```java
// ❌ BROKEN
Comparator<Person> byAge = (a, b) -> a.age() - b.age();
```

It works for small numbers and **overflows silently** (1.1) for large ones:

```java
int a = Integer.MAX_VALUE;   //  2147483647
int b = -1;
IO.println(a - b);           // -2147483648  ← NEGATIVE. Says a < b. Wrong.
```

With real data (timestamps, IDs, hash codes) this produces an **inconsistent
comparator**, and Java's sort detects it:

```
java.lang.IllegalArgumentException: Comparison method violates its general contract!
```

That error message is famous, and this is usually its cause.

```java
// ✅
Comparator.comparingInt(Person::age)
(a, b) -> Integer.compare(a.age(), b.age())
```

> **Rule: never write `a - b`. Use `Integer.compare` / `Long.compare` /
> `Double.compare`.** (`Double.compare` also handles `NaN` and `-0.0` correctly, which
> `<` does not.)

### Stable sorting, and which algorithm each method uses

**Stable** = equal elements keep their original relative order.

```java
// sort by age; people of the same age stay in their original order
people.sort(comparing(Person::age));
```

This is what makes **multi-pass sorting** work:

```java
people.sort(comparing(Person::firstName));    // first pass
people.sort(comparing(Person::lastName));     // second pass
// → sorted by last name, and within each last name, still by first name
```

| Method | Algorithm | Stable? |
|---|---|---|
| `Collections.sort(list)` | delegates to `List.sort` | ✅ |
| `List.sort(cmp)` | **TimSort** | ✅ |
| `Arrays.sort(Object[])` | **TimSort** | ✅ |
| `Arrays.sort(int[])` | **Dual-pivot quicksort** | ❌ *(irrelevant — primitives are indistinguishable)* |
| `Stream.sorted()` | TimSort | ✅ |

**TimSort** is a merge sort that detects already-sorted runs — O(n) on sorted or
nearly-sorted input, O(n log n) worst case, and stable. It's also what Python's `sorted()`
uses.

**Dual-pivot quicksort** is used for primitives because it's faster and needs no extra
memory, and stability is meaningless when the elements carry no identity.

> **It is TimSort that throws "Comparison method violates its general contract!"** — the
> merge step detects the inconsistency. Quicksort on primitives can't and won't.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `a - b` as a comparator | Overflows → `IllegalArgumentException` |
| `compareTo` inconsistent with `equals` | `TreeSet` silently drops elements |
| `.reversed()` reverses only the last key | It reverses the **whole chain** so far |
| Sorting an immutable list | `List.of(...).sort()` → `UnsupportedOperationException` |
| `Arrays.sort(int[])` is stable | It's quicksort. (Doesn't matter for primitives) |
| Using `<` on doubles in a comparator | Mishandles `NaN`. Use `Double.compare` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `(a,b) -> a.x - b.x` | `Comparator.comparingInt(T::x)` |
| Hand-written multi-field `compareTo` with if-chains | `comparing(...).thenComparing(...)` |
| `Collections.sort(list, cmp)` | `list.sort(cmp)` |

---

## Recap

| Concept | One line |
|---|---|
| `Comparable` | One natural order, inside the class |
| `Comparator` | Unlimited orders, outside, lambda-friendly. **Default choice** |
| Consistency with `equals` | Strongly recommended — `TreeSet` drops elements otherwise |
| `comparing().thenComparing().reversed()` | Build by composition |
| `a - b` | **Broken.** Overflow → contract violation |
| Stable | TimSort for objects; enables multi-pass sorting |
