# 5.3 — Maps, and how hashing actually works

> **What this is:** The most important data structure in practice, and the one where your
> **`hashCode` from 2.5 finally has consequences**.

---

## Coming from JS/Python/Dart

A `HashMap` is a Python `dict` or a JS `Map`. The difference is that Python and JS
guarantee **insertion order** on iteration; Java's `HashMap` guarantees **nothing** —
you need `LinkedHashMap` for that.

The other difference: Python objects get a working `__hash__` by default and you rarely
think about it. In Java, forgetting `hashCode` silently loses your data (2.5).

---

## ⭐ `HashMap` internals

This is worth understanding properly — it explains `hashCode`, performance, and several
bugs.

### Buckets

A `HashMap` is an **array of buckets**. Each bucket holds a chain of entries.

```
table (array of 16)
  [0] → null
  [1] → (key="Basha", value=30) → null
  [2] → null
  [3] → (key="Ali", value=25) → (key="Sara", value=28) → null    ← collision chain
  ...
```

Putting a key:

```
1. h = key.hashCode()
2. h = spread(h)                    ← see below
3. index = h & (table.length - 1)   ← fast modulo, since length is a power of 2
4. walk the chain at table[index], comparing with equals()
5. replace if found, append if not
```

**Two methods are used on every operation: `hashCode()` to find the bucket, `equals()` to
find the entry within it.** That's the contract from 2.5, made concrete.

### The hash spreading function

```java
// java.util.HashMap — real code
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**Why:** the index is `h & (n-1)`, which only uses the **low bits** of the hash. A
`hashCode` that varies only in its high bits would collide constantly. XOR-ing the high
16 bits down mixes them in, cheaply.

This is why a mediocre `hashCode` still performs acceptably — `HashMap` defends itself a
little.

### Load factor and resizing

```java
new HashMap<>();                 // capacity 16, load factor 0.75
new HashMap<>(100);              // capacity 128 (next power of 2), load factor 0.75
new HashMap<>(100, 0.5f);        // explicit load factor
```

When `size > capacity × loadFactor`, the map **doubles** its table and **rehashes every
entry** into the new buckets. That's an O(n) operation.

| Load factor | Effect |
|---|---|
| Lower (0.5) | Fewer collisions, more memory, more frequent resizes |
| **0.75 (default)** | The measured sweet spot. Leave it alone |
| Higher (0.9) | Less memory, longer chains, slower lookups |

> **Pre-size when you know the count** — `new HashMap<>(expected / 0.75f + 1)` avoids all
> the intermediate resizes. Java 19 added `HashMap.newHashMap(expected)` which does that
> arithmetic for you.

### Treeification `Java 8`

If a single bucket's chain reaches **8 entries** (and the table is at least 64), that
chain converts from a linked list into a **red-black tree**:

```
chain of 8+  →  O(n) lookup within the bucket
tree         →  O(log n) lookup within the bucket
```

**Why it was added:** a denial-of-service defence. An attacker who can submit keys that
all hash to the same bucket (e.g. HTTP parameter names) could turn every lookup into an
O(n) scan and stall the server. Treeification caps the damage at O(log n).

It requires keys to be `Comparable` to order the tree; otherwise it falls back to
comparing identity hashes.

> You will never trigger this with sensible keys. It's a safety net, not a feature.

## ⭐ What happens when `hashCode` is broken

### Case 1 — `hashCode` not overridden (but `equals` is)

Covered in 2.5. Two equal objects get **different** identity hashes → land in
**different buckets** → `get` looks in the wrong bucket → returns `null`. **Silent data
loss.**

### Case 2 — `hashCode` returns a constant

```java
@Override public int hashCode() { return 42; }   // technically "legal"!
```

This satisfies the contract (equal objects have equal hashes) but puts **every entry in
one bucket**. The map degenerates into a linked list:

| Entries | Lookup |
|---|---|
| Correct `hashCode` | O(1) |
| Constant `hashCode` | O(n), or O(log n) after treeification |

A `HashMap` with 100,000 entries becomes ~17 comparisons per lookup instead of 1.

### Case 3 — a key mutated after insertion

```java
var key = new MutablePoint(1, 2);
map.put(key, "value");

key.setX(99);                   // the key's hash changed

map.get(key);                   // null 💥 — looking in the new bucket, entry is in the old
map.containsKey(key);           // false
```

The entry is in the map — `size()` says 1 — and is **permanently unreachable**. It won't
even be found by iterating and comparing, because `get` uses the hash.

> **Keys must be immutable.** This is the practical reason for `final` fields (2.1),
> records (2.6) and why `String` being immutable (1.3) matters so much.

## The other Map implementations

### `LinkedHashMap` — insertion order, and a free LRU cache

```java
Map<String,Integer> m = new LinkedHashMap<>();
m.put("c",1); m.put("a",2); m.put("b",3);
IO.println(m);      // {c=1, a=2, b=3}  ← insertion order, guaranteed
```

A `HashMap` plus a doubly-linked list threading through the entries. Slightly more memory,
**predictable iteration**.

> **Use it whenever iteration order matters** — building JSON, config output, anything a
> human reads. `HashMap` iteration order is unspecified and *does* change between JDK
> versions.

**Access-order mode gives you an LRU cache in five lines:**

```java
var cache = new LinkedHashMap<String, String>(16, 0.75f, true) {  // true = access order
    @Override protected boolean removeEldestEntry(Map.Entry<String,String> eldest) {
        return size() > 100;              // keep the 100 most recently USED
    }
};
```

With `accessOrder = true`, every `get` moves that entry to the end of the list. The
`removeEldestEntry` hook is called after each `put`. That's a complete LRU cache.

### `TreeMap` — sorted, and `NavigableMap`

```java
NavigableMap<String,Integer> m = new TreeMap<>();
m.put("banana",2); m.put("apple",1); m.put("cherry",3);
IO.println(m);      // {apple=1, banana=2, cherry=3}  ← SORTED by key
```

A red-black tree. **O(log n)** for everything instead of O(1), in exchange for sorted
order and range queries:

```java
m.firstKey();  m.lastKey();
m.floorKey("b");        // "apple"   — greatest key ≤ "b"
m.ceilingKey("b");      // "banana"  — smallest key ≥ "b"
m.lowerKey("banana");   // "apple"   — strictly less
m.higherKey("banana");  // "cherry"  — strictly greater

m.headMap("banana");              // everything before  — a VIEW
m.tailMap("banana");              // "banana" onwards   — a VIEW
m.subMap("apple", "cherry");      // a range            — a VIEW
m.descendingMap();                // reversed           — a VIEW
```

Keys must be `Comparable`, or you supply a `Comparator` (5.5):

```java
new TreeMap<>(Comparator.reverseOrder());
new TreeMap<String,Integer>(String.CASE_INSENSITIVE_ORDER);
```

> **Use `TreeMap` when you need range queries or sorted iteration.** Otherwise
> `HashMap`/`LinkedHashMap` are faster.

## ⭐ The modern method surface `Java 8`

These replaced a lot of clumsy older code. Learn them — they come up constantly.

```java
Map<String,Integer> m = new HashMap<>();

m.getOrDefault("x", 0);                  // value, or 0 if absent — no null check
m.putIfAbsent("x", 1);                   // only put if not already present

m.computeIfAbsent("x", k -> expensive(k));   // compute and store only if absent
m.computeIfPresent("x", (k,v) -> v + 1);     // update only if present
m.compute("x", (k,v) -> v == null ? 1 : v+1);// always run, handle both cases

m.merge("x", 1, Integer::sum);           // put 1, or apply sum to the existing value

m.forEach((k,v) -> IO.println(k + "=" + v));
m.replaceAll((k,v) -> v * 2);
```

### The counting idiom

```java
// ❌ the old dance
Integer count = map.get(word);
if (count == null) map.put(word, 1);
else map.put(word, count + 1);

// ✅
map.merge(word, 1, Integer::sum);
```

### ⭐ `computeIfAbsent` as the idiomatic multimap

Java has no `Multimap` (Guava does). `computeIfAbsent` is how you build one:

```java
// ❌ the get-check-put dance
Map<String, List<String>> byDept = new HashMap<>();
List<String> list = byDept.get(dept);
if (list == null) {
    list = new ArrayList<>();
    byDept.put(dept, list);
}
list.add(name);

// ✅ one line
byDept.computeIfAbsent(dept, k -> new ArrayList<>()).add(name);
```

**Why it beats the dance:**
- One map lookup instead of two (or three).
- Atomic on `ConcurrentHashMap` — the dance has a race condition (Part 09).
- Reads as what it means.

> ⚠️ **Don't modify the map inside the mapping function.** `computeIfAbsent(k, key ->
> { map.put(other, x); return v; })` can corrupt the map or throw
> `ConcurrentModificationException`. The function should only compute a value.

### `merge` vs `compute` vs `computeIfAbsent`

| Method | Runs when | Function receives |
|---|---|---|
| `computeIfAbsent` | Key absent (or mapped to null) | `key` |
| `computeIfPresent` | Key present | `key, value` |
| `compute` | Always | `key, value` (value may be null) |
| `merge` | Always | `oldValue, newValue` (only if old exists) |

All four **remove the entry** if the function returns `null` — a useful and
easy-to-miss behaviour.

## ⚠️ Null keys and values — which implementations permit them

| Implementation | Null key | Null value |
|---|---|---|
| `HashMap` | ✅ one | ✅ |
| `LinkedHashMap` | ✅ one | ✅ |
| `TreeMap` | ❌ NPE | ✅ |
| `Hashtable` 💀 | ❌ NPE | ❌ NPE |
| `ConcurrentHashMap` | ❌ NPE | ❌ NPE |
| `Map.of(...)` | ❌ NPE | ❌ NPE |

`TreeMap` rejects null keys because it must call `compareTo` on them.
`ConcurrentHashMap` rejects nulls so `get()` returning `null` is unambiguous —
with nulls allowed you couldn't tell "absent" from "present with a null value" without a
second racy call.

> **The ambiguity bites in `HashMap` too:**
> ```java
> map.get("x");            // null — absent, or present-with-null?
> map.containsKey("x");    // the only way to tell
> ```
> This is a good reason not to store null values.

### `IdentityHashMap` and `WeakHashMap`

Rare, but know they exist:

**`IdentityHashMap`** — uses `==` instead of `equals()` for key comparison.

```java
var m = new IdentityHashMap<String,Integer>();
m.put(new String("a"), 1);
m.put(new String("a"), 2);
IO.println(m.size());     // 2 — different objects, even though equal
```

Used for object-graph traversal (serialisation, deep-copying) where you're tracking
"have I seen this exact object".

**`WeakHashMap`** — keys are held by **weak references**, so an entry disappears when
nothing else refers to its key.

```java
var cache = new WeakHashMap<Config, ExpensiveResult>();
```

Used for caches and metadata keyed by objects you don't want to keep alive. Full
treatment of reference strength in 8.7.

> ⚠️ `WeakHashMap` is a common source of confusion — entries vanish nondeterministically,
> whenever GC runs. Don't use it unless you specifically want that.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `HashMap` iteration order | Unspecified, and changes between JDK versions. Use `LinkedHashMap` |
| Mutating a key after `put` | Entry becomes permanently unreachable |
| `map.get(k) == null` means absent | Could be present-with-null. Use `containsKey` |
| `get`-check-`put` | Use `computeIfAbsent` — fewer lookups, atomic on concurrent maps |
| `null` into `TreeMap`/`ConcurrentHashMap`/`Map.of` | NPE |
| Constant `hashCode` | Legal, and turns O(1) into O(n) |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Hashtable` | `HashMap`, or `ConcurrentHashMap` if you need thread-safety |
| `get`-null-check-`put` | `computeIfAbsent` / `merge` |
| Relying on `HashMap` order | `LinkedHashMap` |

## Recap

| Concept | One line |
|---|---|
| Buckets | `index = spread(hashCode) & (n-1)`; `equals` finds the entry in the chain |
| Load factor 0.75 | Resize doubles the table and rehashes everything |
| Treeification | 8+ chain → red-black tree. A DoS defence |
| Broken `hashCode` | Constant → O(n). Missing → silent data loss |
| Mutated key | Permanently unreachable |
| `LinkedHashMap` | Insertion order; access-order mode = free LRU |
| `TreeMap` | Sorted, O(log n), range queries via `NavigableMap` |
| `computeIfAbsent` | The multimap idiom. One lookup, atomic |
| `merge` | The counting idiom |
