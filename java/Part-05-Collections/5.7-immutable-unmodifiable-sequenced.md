# 5.7 — Immutable, unmodifiable and sequenced

> **What this is:** **Three distinct ideas that share vocabulary.** Confusing them is
> common and causes real bugs, because two of them look identical at the call site.

---

## Coming from JS/Python/Dart

Python's `tuple`/`frozenset` are genuinely immutable — that's Java's `List.of`.
JS's `Object.freeze` is shallow and advisory — closest to `Collections.unmodifiableList`.

Java has **both**, they look the same, and only one of them is safe.

---

## ⭐ Immutable vs unmodifiable — the distinction that matters

| | **Immutable** (`List.of`) | **Unmodifiable view** (`Collections.unmodifiableList`) |
|---|---|---|
| Can *you* modify it? | ❌ | ❌ |
| Can *anyone* modify it? | ❌ **Nobody, ever** | ✅ **Whoever holds the original** |
| It's a | Self-contained collection | **View** onto something still mutable |
| Safe to share | ✅ | ⚠️ Only if the original is unreachable |

```java
// UNMODIFIABLE VIEW — the dangerous one
var backing = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(backing);

view.add("c");            // 💥 UnsupportedOperationException — as expected
backing.add("c");         // ✅ allowed!
IO.println(view);         // [a, b, c]  😱 the "unmodifiable" list changed
```

```java
// IMMUTABLE — safe
var backing = new ArrayList<>(List.of("a", "b"));
List<String> copy = List.copyOf(backing);   // a real COPY

backing.add("c");
IO.println(copy);         // [a, b]  ✅ unaffected
```

> **The rule: `Collections.unmodifiableList` protects the *caller* from modifying;
> `List.copyOf` protects *you* from the caller.** For defensive copying at API boundaries
> (2.10), you almost always want `copyOf`.

## `List.of`, `Set.of`, `Map.of` `Java 9`

```java
List<String>          l = List.of("a", "b", "c");
Set<String>           s = Set.of("a", "b");
Map<String,Integer>   m = Map.of("a", 1, "b", 2);          // up to 10 pairs
Map<String,Integer>   big = Map.ofEntries(
    Map.entry("a", 1),
    Map.entry("b", 2)                                       // any number
);
```

**Three properties to remember:**

**(1) Truly immutable.** Not a view. Nothing can change them.

**(2) ⚠️ Null-hostile — they throw, they don't tolerate:**

```java
List.of("a", null);          // 💥 NullPointerException
Map.of("a", null);           // 💥 NullPointerException
List.of("a").contains(null); // 💥 NullPointerException — even querying!
```

That last one catches people. `new ArrayList<>().contains(null)` returns `false`;
`List.of().contains(null)` **throws**. It's deliberate — the designers decided null
elements are almost always a bug, and chose to surface it loudly.

**(3) ⚠️ Unspecified iteration order for `Set.of` and `Map.of`:**

```java
var s = Set.of("a", "b", "c");
IO.println(s);      // order is unspecified — AND RANDOMISED PER JVM RUN
```

Set and Map factories deliberately apply a **per-JVM random seed** (`SALT`) to their
iteration order, specifically so you *cannot* accidentally depend on it. Run the same
program twice and get different orders.

> `List.of` **does** preserve order — lists are ordered by definition.

**Memory:** these use specialised classes for small sizes — `List12` for 1–2 elements,
`ListN` beyond. A two-element `List.of` is significantly smaller than an `ArrayList`.

## `List.copyOf` and friends `Java 10`

```java
List<String>        l = List.copyOf(someList);
Set<String>         s = Set.copyOf(someCollection);
Map<String,Integer> m = Map.copyOf(someMap);
```

- Returns an **immutable** copy.
- **Rejects nulls** (same as `of`).
- **Optimisation:** if the input is already one of these immutable collections, it returns
  the *same instance* rather than copying. So calling it defensively is cheap.

```java
public record Team(String name, List<String> members) {
    Team { members = List.copyOf(members); }     // 2.6 — the defensive copy idiom
}
```

## `Collections.unmodifiableXxx` — when it's actually right

```java
public class Registry {
    private final List<String> items = new ArrayList<>();

    public List<String> items() {
        return Collections.unmodifiableList(items);   // ✅ correct use
    }
    public void add(String s) { items.add(s); }
}
```

Here the view is **the right choice**: callers can't modify, but they *do* see live
updates when `add` is called, and you avoid copying on every call.

> **Use a view when the caller should see live changes. Use `copyOf` when they shouldn't.**

## ⭐ `Stream.toList()` vs `collect(toList())` `Java 16`

A subtle difference that bites:

```java
List<String> a = stream.collect(Collectors.toList());   // Java 8
List<String> b = stream.toList();                       // Java 16
```

| | `collect(toList())` | `toList()` |
|---|---|---|
| Mutable | ✅ (in practice an `ArrayList` — **not guaranteed**) | ❌ **Unmodifiable** |
| Allows null elements | ✅ | ✅ **yes** |
| Since | Java 8 | Java 16 |

**Two gotchas:**

```java
var list = stream.toList();
list.add("x");                // 💥 UnsupportedOperationException
Collections.sort(list);       // 💥 same
```

And note `toList()` **does** permit nulls, unlike `List.of` — so it is *not* the same as
`List.copyOf`. Three similar-looking things, three null policies:

| | Mutable | Nulls |
|---|---|---|
| `collect(toList())` | ✅ | ✅ |
| `toList()` | ❌ | ✅ |
| `List.copyOf` / `List.of` | ❌ | ❌ |

> **Default to `.toList()`** — it's shorter and immutability is usually what you want.
> Use `collect(toCollection(ArrayList::new))` when you genuinely need a mutable result.

## ⭐ Sequenced collections `Java 21`

**A gap in the framework that stood for 25 years.**

The problem: "give me the first element" had no uniform answer.

```java
list.get(0);                                    // List
deque.peekFirst();                              // Deque
linkedHashSet.iterator().next();                // LinkedHashSet — awkward!
treeSet.first();                                // SortedSet
linkedHashMap.entrySet().iterator().next();     // LinkedHashMap — worse
```

And "give me the **last** element of a `LinkedHashSet`" required iterating the entire set.

**Java 21 added three interfaces:**

```
SequencedCollection<E>
    ├── List<E>
    ├── Deque<E>
    └── SequencedSet<E>
            ├── SortedSet<E>
            └── LinkedHashSet<E>

SequencedMap<K,V>
    ├── SortedMap<K,V>
    └── LinkedHashMap<K,V>
```

**The uniform API:**

```java
SequencedCollection<String> c = ...;

c.getFirst();       c.getLast();
c.addFirst("x");    c.addLast("x");
c.removeFirst();    c.removeLast();
c.reversed();       // a VIEW in reverse order — O(1), not a copy
```

```java
SequencedMap<String,Integer> m = new LinkedHashMap<>();
m.firstEntry();     m.lastEntry();
m.putFirst("a", 1); m.putLast("z", 26);
m.pollFirstEntry(); m.pollLastEntry();
m.reversed();
m.sequencedKeySet();  m.sequencedValues();  m.sequencedEntrySet();
```

**Now it's uniform:**

```java
new ArrayList<>(...).getFirst();        // ✅
new LinkedHashSet<>(...).getFirst();    // ✅ was: iterator().next()
new LinkedHashSet<>(...).getLast();     // ✅ was: iterate the whole thing
new TreeMap<>(...).firstEntry();        // ✅
list.reversed();                         // ✅ was: Collections.reverse (mutating!)
```

> ⚠️ **`reversed()` is a view**, like `subList` (5.2). It's O(1) and reflects changes to
> the original. `Collections.reverse(list)` mutates in place — completely different.

> ⚠️ **One breaking change:** `List.getFirst()` throws `NoSuchElementException` on an
> empty list, whereas `list.get(0)` throws `IndexOutOfBoundsException`. Rare, but it
> exists.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `Collections.unmodifiableList` = immutable | It's a **view**. The original can still change |
| `List.of(x)` where x might be null | NPE |
| `List.of("a").contains(null)` | **Throws**, doesn't return false |
| Relying on `Set.of` iteration order | Randomised per JVM run, deliberately |
| `stream.toList()` then `sort()` | Immutable → `UnsupportedOperationException` |
| `toList()` == `List.copyOf` | No — `toList()` allows nulls |
| `list.reversed()` mutates | It's a view. `Collections.reverse` mutates |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Collections.emptyList()` | `List.of()` |
| `Collections.singletonList(x)` | `List.of(x)` |
| `Collections.unmodifiableList(new ArrayList<>(x))` | `List.copyOf(x)` |
| `collect(Collectors.toList())` when you don't need mutability | `.toList()` |
| `linkedHashSet.iterator().next()` | `.getFirst()` `Java 21` |

---

## Recap

| Idea | One line |
|---|---|
| **Immutable** | `List.of` / `List.copyOf` — nobody can change it, ever |
| **Unmodifiable view** | `Collections.unmodifiableList` — *you* can't, the owner can |
| `of` factories | Immutable, **null-hostile**, randomised set/map order |
| `copyOf` | Defensive copy; returns the same instance if already immutable |
| `.toList()` | `Java 16`. Unmodifiable, **but allows nulls** |
| **Sequenced** | `Java 21`. `getFirst`/`getLast`/`reversed` uniformly; `reversed()` is a view |
