# 5.8 — Choosing by cost

> **What this is:** The step that turns the previous seven into **judgement**. The whole
> point of Part 05 is choosing the right structure, and the choice is always about
> **what you do to it most often**.

---

## ⭐ The cost table

Build this yourself from 5.2–5.4. Amortised costs; `n` is the collection size.

### Lists

| | `ArrayList` | `LinkedList` 💀 |
|---|---|---|
| `get(i)` | **O(1)** | O(n) |
| `add(e)` at end | O(1)* | O(1) |
| `add(0, e)` | O(n) | O(1) |
| `remove(i)` | O(n) | O(n) *(traversal)* |
| `contains(x)` | O(n) | O(n) |
| Iterate | O(n) **fast** | O(n) **slow — cache misses** |
| Memory/element | ~4–8 bytes | **~32–40 bytes** |

\* amortised — occasional O(n) resize

### Sets and Maps

| | `HashSet`/`HashMap` | `LinkedHash*` | `TreeSet`/`TreeMap` |
|---|---|---|---|
| `add`/`put` | **O(1)** | O(1) | O(log n) |
| `contains`/`get` | **O(1)** | O(1) | O(log n) |
| `remove` | **O(1)** | O(1) | O(log n) |
| Iterate | O(n + capacity) | **O(n)** | O(n) |
| Order | **None** | Insertion | **Sorted** |
| Range queries | ❌ | ❌ | ✅ |

> Note `HashMap` iteration is O(n + capacity) — it walks the whole bucket array, including
> empty slots. A map that once held a million entries and now holds three is still slow to
> iterate.

### Queues and Deques

| | `ArrayDeque` | `PriorityQueue` | `LinkedList` 💀 |
|---|---|---|---|
| `offer` / `addLast` | **O(1)** | O(log n) | O(1) |
| `poll` / `removeFirst` | **O(1)** | O(log n) | O(1) |
| `peek` | **O(1)** | **O(1)** | O(1) |
| `contains` | O(n) | O(n) | O(n) |
| Order out | FIFO/LIFO | **Smallest first** | FIFO/LIFO |

## ⭐ Why asymptotic complexity misleads at small sizes

Big-O describes **growth**, not **speed**. It hides the constant factor, and at realistic
sizes the constant factor usually wins.

**The classic example:**

```java
// Big-O says LinkedList wins for front insertion: O(1) vs O(n)
list.add(0, element);
```

In practice, for lists up to a few thousand elements, **`ArrayList` is faster anyway**.
`System.arraycopy` moving 1,000 contiguous elements is a single tight memory-move
instruction — often faster than allocating one `Node` object and updating two pointers.

**Two rules of thumb:**

| Size | What decides |
|---|---|
| n < ~1,000 | **Constant factors and memory locality.** Big-O is noise |
| n > ~100,000 | **Big-O.** Constants stop mattering |

> **The honest advice: use `ArrayList` and `HashMap` until a profiler tells you
> otherwise.** Choosing an exotic structure for a 50-element collection is the definition
> of premature optimisation (1.4).

### Memory locality often decides

A cache miss costs ~100× a cache hit. That single fact explains:

- Why `ArrayList` beats `LinkedList` at iteration (5.2)
- Why `ArrayDeque` beats `LinkedList` as a queue (5.4)
- Why `int[]` beats `List<Integer>` by more than the memory numbers suggest (below)

Contiguous memory is prefetchable; pointer-chasing is not.

## ⭐ Memory overhead per element

This is where the differences are dramatic, and it's the strongest argument for
primitives at scale.

Every Java object carries an **object header** (8.4) — 12–16 bytes — plus padding to an
8-byte boundary.

**For 1,000,000 integers:**

| Structure | Per element | Total | Ratio |
|---|---|---|---|
| `int[]` | 4 bytes | **~4 MB** | 1× |
| `Integer[]` | 4 (ref) + 16 (object) | ~20 MB | 5× |
| `ArrayList<Integer>` | 4 (ref) + 16 (object) | ~20 MB | 5× |
| `HashMap<Integer,Integer>` | ~48 (Node) + 2×16 | **~80 MB** | **20×** |
| `LinkedList<Integer>` | ~40 (Node) + 16 | ~56 MB | 14× |

Where the `Integer` overhead comes from:

```
an Integer object:
  12 bytes  object header (mark word + class pointer)
   4 bytes  the actual int value
  ──────────
  16 bytes  total, for 4 bytes of data
```

Plus a 4-byte reference in the array pointing at it. **20 bytes to store a 4-byte number.**

> **And it's worse than the numbers suggest**, because those million `Integer` objects are
> scattered across the heap. Summing an `int[]` is a linear scan; summing a
> `List<Integer>` is a million pointer dereferences (§ memory locality above).

**The `Integer` cache mitigates this slightly** — values −128..127 are shared (1.1) — but
only for small numbers.

**Practical consequences:**

```java
// ❌ 20MB and slow for a million values
List<Integer> values = new ArrayList<>();

// ✅ 4MB and fast
int[] values = new int[1_000_000];

// ✅ also avoids boxing — Part 06
IntStream.range(0, 1_000_000).sum();
```

## ⭐ Choosing by the question

> **"What do I do most often to this collection?"**

| What you do most | Use |
|---|---|
| Index access, iterate, append | **`ArrayList`** |
| Look up by key | **`HashMap`** |
| Membership tests (`contains`) | **`HashSet`** |
| Look up by key, **iterate in insertion order** | `LinkedHashMap` |
| Look up by key, **sorted / range queries** | `TreeMap` |
| Add and remove at **both ends** | **`ArrayDeque`** |
| Always take the smallest/highest priority | `PriorityQueue` |
| Fixed set of enum keys | **`EnumMap` / `EnumSet`** (2.7) |
| Read-heavy, rarely written, shared across threads | `CopyOnWriteArrayList` (Part 09) |
| Shared across threads, read *and* written | `ConcurrentHashMap` (9.7) |
| Millions of primitives | **`int[]` / `long[]`**, or a primitive-collection library |

**The two questions that answer 90% of cases:**

1. **Do I look things up by key?** → `Map`. Otherwise → `List`.
2. **Do I care about order?** → `LinkedHash*` (insertion) or `Tree*` (sorted).
   Otherwise → `Hash*`.

**And the one mistake worth watching for** (5.2):

```java
// ❌ O(n²) — `contains` on a List is a linear scan
for (String id : incoming) if (existingList.contains(id)) { ... }

// ✅ O(n)
Set<String> existing = new HashSet<>(existingList);
for (String id : incoming) if (existing.contains(id)) { ... }
```

Converting a `List` to a `Set` for membership testing is the single highest-value
collection optimisation in ordinary code.

## When to reach outside the JDK

Rarely. But there are two specific cases:

### Primitive collections — Eclipse Collections, fastutil, HPPC, Agrona

```java
// JDK — 80MB for a million int→int mappings
Map<Integer,Integer> m = new HashMap<>();

// fastutil — ~12MB, no boxing
Int2IntOpenHashMap m = new Int2IntOpenHashMap();
```

**Justified when:** you hold **millions** of primitives in a `Map`/`List`, and you've
measured a memory or GC problem. `List<Integer>` with 10,000 elements does not justify a
dependency.

### Immutable/persistent collections — Guava, Vavr

```java
ImmutableList.of(...)                    // Guava — predates List.of
Multimap<String,String>                  // Guava — the JDK has no multimap (5.3)
Table<R,C,V>                             // Guava — two-dimensional key
```

**Justified when:** you need a genuine multimap, bimap or table, and
`computeIfAbsent` (5.3) is getting unwieldy.

> `List.of`/`Map.of` (Java 9) removed most of the historical reason for Guava's immutable
> collections. Check the JDK first.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Choosing by Big-O alone | Constants and cache locality dominate below ~1,000 |
| `LinkedList` "because O(1) insert" | Loses to `ArrayList` in practice (5.2) |
| `List.contains` in a loop | O(n²). Convert to a `Set` |
| `List<Integer>` for millions of ints | 5× the memory and much slower. Use `int[]` |
| Iterating a huge-then-emptied `HashMap` | Still O(capacity) — it never shrinks |
| Adding a dependency for 10,000 elements | Premature |

---

## Recap

| Question | Answer |
|---|---|
| Default list | **`ArrayList`** |
| Default map/set | **`HashMap` / `HashSet`** |
| Need insertion order | `LinkedHashMap` / `LinkedHashSet` |
| Need sorted or ranges | `TreeMap` / `TreeSet` |
| Both ends | **`ArrayDeque`** |
| Enum keys | `EnumMap` / `EnumSet` |
| Millions of primitives | `int[]`, `IntStream`, or fastutil |
| Below ~1,000 elements | **Big-O is noise.** Use the default |
