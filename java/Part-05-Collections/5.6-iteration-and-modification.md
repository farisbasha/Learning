# 5.6 — Iteration and modification

> **What this is:** A short step that prevents **one of the most common runtime
> exceptions in Java**.

---

## Coming from JS/Python/Dart

Python raises `RuntimeError: dictionary changed size during iteration`. JS lets you
mutate an array while iterating and gives you skipped elements. **Java throws
`ConcurrentModificationException`**, and the name is misleading — it usually has nothing
to do with concurrency.

---

## The concepts

### What the enhanced `for` loop compiles to

```java
for (String s : list) {
    IO.println(s);
}
```

Becomes exactly:

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    IO.println(s);
}
```

**That's why you can't remove during a for-each** — you have no reference to the iterator.

> For **arrays**, the same syntax compiles to an indexed loop instead. Arrays aren't
> `Iterable` (1.4) — the compiler special-cases them.

### ⭐ `ConcurrentModificationException`

```java
var list = new ArrayList<>(List.of("a", "b", "c"));

for (String s : list) {
    if (s.equals("b")) list.remove(s);     // 💥 ConcurrentModificationException
}
```

**How it's detected — `modCount`:**

Every `ArrayList`/`HashMap` keeps an int field:

```java
protected transient int modCount = 0;      // java.util.AbstractList
```

Incremented on every **structural** modification (add, remove, clear — anything changing
the size). When you create an iterator, it snapshots that value:

```java
// java.util.ArrayList.Itr — real code, simplified
int expectedModCount = modCount;

final void checkForComodification() {
    if (modCount != expectedModCount)
        throw new ConcurrentModificationException();
}
```

Every `next()` calls that check. If the list changed underneath, the counts differ and it
throws.

**`set()` is not structural** — it doesn't change the size, doesn't bump `modCount`, and
is safe during iteration:

```java
for (int i = 0; i < list.size(); i++) list.set(i, transform(list.get(i)));   // ✅ fine
```

### ⚠️ "Fail-fast" is best-effort, not a guarantee

The JDK documentation is explicit about this:

> *"Fail-fast iterators throw `ConcurrentModificationException` on a best-effort basis.
> Therefore, it would be wrong to write a program that depended on this exception for its
> correctness."*

**Here's the classic case where it silently doesn't fire:**

```java
var list = new ArrayList<>(List.of("a", "b", "c"));

for (String s : list) {
    if (s.equals("b")) list.remove(s);     // removing the SECOND-TO-LAST element
}
IO.println(list);        // [a, c] — no exception! 😱
```

**Why:** `hasNext()` is just `cursor != size`. After removing "b", size drops from 3 to 2,
and the cursor is at 2. So `hasNext()` returns `false`, the loop **exits early**, and
`next()` — which contains the check — is never called again.

The result: the last element is silently skipped, no exception, wrong answer.

> **So `ConcurrentModificationException` is a debugging aid, not a safety mechanism.**
> Never rely on it. Don't structurally modify while iterating, full stop.

### The safe ways to remove while iterating

**(1) `Iterator.remove()` — the only safe manual way:**

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) {
        it.remove();               // ✅ updates expectedModCount too
    }
}
```

`Iterator.remove()` removes the element last returned by `next()`, and keeps the
iterator's `expectedModCount` in sync. Rules: call `next()` first, and only call
`remove()` once per `next()`.

**(2) `removeIf` `Java 8` — the clean answer:**

```java
list.removeIf(s -> s.equals("b"));
list.removeIf(user -> user.age() < 18);
```

One line, correct, and on `ArrayList` it's also **faster** — it does a single pass and one
compaction, rather than shifting the array on every removal (O(n) instead of O(n²)).

> **Use `removeIf`.** It's on `Collection`, so it works for lists, sets and
> `map.values()`.

**(3) Collect into a new collection** — often the clearest:

```java
var kept = list.stream().filter(s -> !s.equals("b")).toList();    // Part 06
```

**(4) For maps:**

```java
map.entrySet().removeIf(e -> e.getValue() < 10);
map.values().removeIf(v -> v < 10);
```

Views are live (5.1), so removing from them removes from the map.

### Fail-fast versus weakly-consistent iterators

| | Fail-fast | Weakly consistent |
|---|---|---|
| Collections | `ArrayList`, `HashMap`, `HashSet`, `TreeMap`… | `ConcurrentHashMap`, `CopyOnWriteArrayList`, `ConcurrentLinkedQueue` |
| On concurrent modification | Throws `CME` (best-effort) | **Never throws** |
| What you see | — | Elements as of iterator creation, *plus possibly* later changes |

```java
var map = new ConcurrentHashMap<String,Integer>(Map.of("a",1,"b",2));
for (var e : map.entrySet()) {
    map.put("c", 3);              // ✅ no exception — weakly consistent
}
```

**Weakly consistent** means: the iterator won't throw, won't show an element twice, and
will show every element that was present for the whole iteration — but whether it reflects
concurrent additions is **unspecified**.

> This is a genuine trade-off, not a free upgrade: you trade "loud failure" for "vague
> guarantees". Full treatment in 9.7.

### Writing your own `Iterable`

Implement one method, and for-each works:

```java
public class Range implements Iterable<Integer> {
    private final int from, to;
    public Range(int from, int to) { this.from = from; this.to = to; }

    @Override
    public Iterator<Integer> iterator() {
        return new Iterator<>() {
            private int current = from;
            @Override public boolean hasNext() { return current < to; }
            @Override public Integer next() {
                if (!hasNext()) throw new NoSuchElementException();
                return current++;
            }
        };
    }
}

for (int i : new Range(1, 5)) IO.print(i + " ");    // 1 2 3 4
```

Note `next()` throwing `NoSuchElementException` when exhausted — that's the contract
(5.4's "throws" family).

Since Java 8, `Iterable` also has a default `forEach` (2.4), so you get that free:

```java
new Range(1, 5).forEach(IO::println);
```

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `list.remove(x)` inside a for-each | `CME` — or worse, silently skips an element |
| `CME` always fires | Best-effort. Removing the second-to-last element exits silently |
| `CME` means threads | Usually single-threaded — the name is misleading |
| Modifying a map's `keySet()` while iterating it | Same problem; views share `modCount` |
| `it.remove()` without `it.next()` | `IllegalStateException` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Index loop + `remove(i)` + manual `i--` | `removeIf` |
| `for (X x : list) list.remove(x)` | `removeIf` |
| Relying on `CME` to catch bugs | Don't modify while iterating |

---

## Recap

| Concept | One line |
|---|---|
| For-each | Compiles to `Iterator`; you can't reach it to remove |
| `modCount` | Structural-change counter; the iterator snapshots it |
| `set()` | Not structural — safe during iteration |
| **`CME` is best-effort** | Removing the second-to-last element skips silently |
| `Iterator.remove()` | The only safe manual removal |
| **`removeIf`** | The clean answer. Also O(n) not O(n²) on `ArrayList` |
| Weakly consistent | Concurrent collections never throw; guarantees are vaguer |
