# 5.1 — The map of the framework

> **What this is:** Get the **shape** of the hierarchy first; the individual classes then
> have obvious homes. The whole point of this part is *choosing the right one*, and the
> choice is always about **what operations you do most**.

---

## Coming from JS/Python/Dart

| You know | Java |
|---|---|
| `Array` / `list` | `List` → `ArrayList` |
| `Object` / `dict` | `Map` → `HashMap` |
| `Set` | `Set` → `HashSet` |
| — | `Queue`, `Deque` — no direct equivalent, you used arrays |

The new idea: **the interface and the implementation are separate, and you name both**.
`List<String> x = new ArrayList<>()` — in Python there's just `list`.

---

## The concepts

### The hierarchy

```
              Iterable<E>
                  │
             Collection<E>
            ┌─────┼─────┐
         List   Set    Queue
                  │      │
           SortedSet   Deque
                  │
         NavigableSet


              Map<K,V>          ← NOT a Collection
                  │
             SortedMap
                  │
             NavigableMap
```

| Interface | Means | Duplicates? | Ordered? |
|---|---|---|---|
| `List` | Indexed sequence | ✅ | ✅ by position |
| `Set` | No duplicates | ❌ | Depends on impl |
| `Queue` | FIFO-ish, add/remove at ends | ✅ | ✅ |
| `Deque` | **D**ouble-**e**nded queue — both ends | ✅ | ✅ |
| `Map` | Key → value | Keys ❌, values ✅ | Depends on impl |

### ⭐ Why `Map` is deliberately not a `Collection`

This surprises people. `Map` sits outside the whole `Collection` tree.

**The reason:** `Collection<E>` has methods like `add(E)`, `remove(Object)`,
`iterator()` — all built around **one** element type. A `Map` has *two* (`K` and `V`),
and `add(K, V)` doesn't fit the shape at all.

Rather than force a bad fit, the designers gave `Map` three **views** onto its contents:

```java
Map<String, Integer> ages = new HashMap<>();
ages.put("Basha", 30);

Set<String>              keys    = ages.keySet();     // a Set view
Collection<Integer>      values  = ages.values();     // a Collection view
Set<Map.Entry<String,Integer>> entries = ages.entrySet();  // a Set of pairs
```

**These are views, not copies.** Changes flow both ways:

```java
ages.keySet().remove("Basha");
IO.println(ages);              // {} ← removing from the view removed from the map
```

```java
// iterate a map properly
for (var entry : ages.entrySet()) {
    IO.println(entry.getKey() + " = " + entry.getValue());
}

// or, since Java 8
ages.forEach((name, age) -> IO.println(name + " = " + age));
```

> ⚠️ **You cannot `add` to a view** — `keySet().add("x")` throws
> `UnsupportedOperationException`, because there'd be no value to pair it with.

### Interface versus implementation

```java
// ✅ declare the interface, construct the implementation
List<String>        names  = new ArrayList<>();
Map<String, User>   users  = new HashMap<>();
Set<String>         seen   = new HashSet<>();
Deque<Task>         stack  = new ArrayDeque<>();
```

Covered in 2.4 — your **fields, parameters and return types say `List`; your
constructors say `ArrayList`**. It's the single most-repeated rule in Java style guides,
and it's what lets you swap implementations later.

### ⭐ The naming convention that tells you the implementation

This is genuinely useful — the prefix tells you the data structure:

| Prefix | Backed by | Ordering | Example |
|---|---|---|---|
| `Hash*` | Hash table | **None guaranteed** | `HashMap`, `HashSet` |
| `Linked*` | Hash table + linked list | **Insertion order** | `LinkedHashMap`, `LinkedHashSet` |
| `Tree*` | Red-black tree | **Sorted** | `TreeMap`, `TreeSet` |
| `Array*` | Array | Positional | `ArrayList`, `ArrayDeque` |
| `Concurrent*` | Thread-safe structure | Varies | `ConcurrentHashMap` |
| `Copy­OnWrite*` | Copy on every write | Insertion | `CopyOnWriteArrayList` |

Read `LinkedHashMap` as *"a HashMap that also remembers insertion order"*. Read
`TreeSet` as *"a Set kept sorted in a tree"*. The names are systematic once you see it.

### ⚠️ Optional operations and `UnsupportedOperationException`

A design wart worth knowing about.

```java
List<String> list = List.of("a", "b");
list.add("c");        // 💥 UnsupportedOperationException — at RUNTIME
```

The `List` interface declares `add()`, but implementations are allowed to just... not
support it. So `List.of(...)` compiles fine and throws at runtime.

**Why it's a wart:** the type system says "this is a List, you can add to it", and it's
lying. A proper design would have `ImmutableList` as a separate type without `add`.

**Why it happened:** the framework was designed in 1998, before generics, and changing it
now would break the world. Same constraint as erasure (3.3) and checked exceptions (4.2).

**What throws it:**

```java
List.of(...), Set.of(...), Map.of(...)          // truly immutable (5.7)
Collections.unmodifiableList(...)                // unmodifiable view
Arrays.asList(...)                               // fixed-size — add/remove throw, set works!
map.keySet().add(...)                            // views
```

> **Practical defence:** never assume a `List` parameter is mutable. If you need to
> modify it, copy it first: `new ArrayList<>(input)`.

### 💀 The legacy classes you'll see and must not use

| 💀 Legacy | Use instead | Why |
|---|---|---|
| `Vector` | `ArrayList` | `synchronized` on every method, for no benefit |
| `Hashtable` | `HashMap` | Same. Also rejects `null` keys |
| `Stack` | `ArrayDeque` | Extends `Vector`; also iterates **bottom-to-top**, which is wrong for a stack |
| `Enumeration` | `Iterator` | The 1.0 version; no `remove()` |

These are all from Java 1.0 (1996) and predate the collections framework entirely
(added in 1.2). They still exist for compatibility and appear constantly in old code and
tutorials (0.3).

**`Stack` deserves a specific warning** — it's not just old, it's *wrong*:

```java
Stack<Integer> stack = new Stack<>();
stack.push(1); stack.push(2); stack.push(3);
for (int i : stack) IO.println(i);     // prints 1, 2, 3 — BOTTOM to top 😱
```

A stack should iterate top-first. `ArrayDeque` does:

```java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2); stack.push(3);
for (int i : stack) IO.println(i);     // 3, 2, 1 ✅
```

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `Map` is a `Collection` | It isn't — it has two type parameters |
| `keySet()` returns a copy | It's a **view**. Removing from it modifies the map |
| A `List` parameter can be added to | Might be `List.of` → `UnsupportedOperationException` |
| `Stack` is fine for a stack | Iterates backwards. Use `ArrayDeque` |
| `Vector`/`Hashtable` are "thread-safe so safer" | Per-method locking doesn't make compound operations safe (Part 09) |

## Recap

| Concept | One line |
|---|---|
| `Iterable → Collection → List/Set/Queue/Deque` | The tree |
| `Map` is separate | Two type parameters don't fit `Collection` |
| `keySet`/`values`/`entrySet` | **Views**, not copies |
| Declare interface, construct impl | `List<X> x = new ArrayList<>()` |
| `Hash*` / `Linked*` / `Tree*` / `Array*` | Unordered / insertion-ordered / sorted / array-backed |
| `UnsupportedOperationException` | Optional operations — a 1998 design wart |
| 💀 `Vector`, `Hashtable`, `Stack`, `Enumeration` | Never in new code |
