# 3.3 — Type erasure

> **What this is:** **The single most important thing to understand about Java generics**,
> and the source of every strange restriction. Once you understand erasure, a dozen rules
> that looked arbitrary become obvious consequences of one decision.
>
> This is the page where TypeScript intuition stops helping and starts hurting.

---

## Coming from JS/Python/Dart

TypeScript types also vanish at runtime — so far, so familiar. **But TypeScript compiles
to a dynamically typed language**, so nothing depends on the types being there.

Java compiles to bytecode that the JVM *does* type-check. Java generics are erased into
a **statically typed** runtime, and the mismatch between "the compiler knows `T` is
`String`" and "the JVM has no idea" is where all the restrictions live.

C# made the opposite choice (reified generics) and you'll see the contrast at the end.

---

## The concepts

### What erasure is

**Generic type arguments exist for the compiler and are gone at runtime.**

```java
List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();

IO.println(strings.getClass() == ints.getClass());   // true 😳
IO.println(strings.getClass().getName());            // java.util.ArrayList
```

Both are **the same class**. There is no `ArrayList<String>` at runtime — there is only
`ArrayList`.

What the compiler actually produces:

```java
// what you write
class Box<T> {
    private T value;
    T get() { return value; }
    void set(T v) { value = v; }
}
Box<String> b = new Box<>();
String s = b.get();
```

```java
// what the bytecode contains — T replaced by its bound (Object here)
class Box {
    private Object value;
    Object get() { return value; }
    void set(Object v) { value = v; }
}
Box b = new Box();
String s = (String) b.get();      // ← the compiler INSERTS the cast
```

> **The one-sentence version: the compiler checks your types, then throws them away and
> inserts the casts you would have written by hand in 2003.**

With a bound, `T` erases to the **bound** rather than `Object`:

```java
class Box<T extends Number> { T value; }
// erases to:
class Box { Number value; }
```

### See it yourself

```bash
javac Box.java
javap -c Box.class        # the erased bytecode
javap -s Box.class        # the erased signatures
```

You'll see `Object` everywhere `T` was. The original generic signature *is* stored — in a
separate `Signature` attribute the **compiler** reads when you compile against the class.
The JVM itself ignores it.

```bash
javap -v Box.class | grep -i signature
```

That's the key asymmetry: **generic info survives for the compiler, not for the running
program.**

## ⭐ Why erasure was chosen

Java 5 shipped in 2004, eight years into Java's life. There were millions of lines of
`List`-using code and thousands of compiled libraries in the wild.

**The requirement: `List<String>` must be usable by old code expecting `List`, and old
`List` code must keep running unchanged on the new JVM.**

Erasure delivers **migration compatibility** — because `List<String>` and `List` are
literally the same class at runtime, old and new code interoperate perfectly, and no
existing `.class` file needed recompiling.

The alternative (reification, as C# did) would have required either a new incompatible
collections library or a flag day for the entire ecosystem. Java chose compatibility.

> **Whether it was the right call is genuinely debated.** What isn't debated is that
> every restriction below follows from it.

## ⭐ The consequences — each with an obvious reason

This is the payoff section. Every one of these is "because the type isn't there at
runtime".

### 1. You cannot write `new T()`

```java
class Factory<T> {
    T create() { return new T(); }      // ❌ compile error
}
```

**Why:** at runtime there is no `T`. The JVM would have to execute `new <nothing>`.

**Workaround — pass a factory in:**
```java
class Factory<T> {
    private final Supplier<T> supplier;
    Factory(Supplier<T> supplier) { this.supplier = supplier; }
    T create() { return supplier.get(); }
}

var f = new Factory<>(ArrayList::new);
```

Or pass a `Class<T>` token (3.5).

### 2. You cannot write `new T[10]`

```java
T[] array = new T[10];      // ❌ generic array creation
```

Same reason, plus the array covariance problem from 1.4 — an array stores its element
type at runtime for the `ArrayStoreException` check, and there'd be nothing to store.

**The workaround every collection uses internally** (3.5):
```java
@SuppressWarnings("unchecked")
T[] array = (T[]) new Object[10];
```

### 3. You cannot write `x instanceof List<String>`

```java
if (x instanceof List<String>) { }      // ❌ illegal generic type for instanceof
if (x instanceof List<?>) { }           // ✅ this is fine — asks nothing about the element
if (x instanceof List) { }              // ✅ also fine (raw, but legal here)
```

**Why:** `instanceof` is a runtime check, and at runtime there is only `List`.

### 4. `List<String>` and `List<Integer>` are the same class

Already shown above. Consequences: you cannot distinguish them by reflection, and:

### 5. You cannot overload on `List<String>` and `List<Integer>`

```java
void process(List<String> items)  { }
void process(List<Integer> items) { }   // ❌ both erase to process(List)
```

```
error: name clash: process(List<Integer>) and process(List<String>)
       have the same erasure
```

**Why:** after erasure both have the signature `process(List)` — a duplicate method.

**Workaround:** different method names. `processNames` / `processIds`.

### 6. You cannot catch or throw a generic exception type

```java
class MyException<T> extends Exception { }      // ❌ generic class may not extend Throwable

try { }
catch (T e) { }                                  // ❌ cannot catch a type variable
```

**Why:** `catch` matching is a runtime type comparison. Catching `T` would mean catching
`Object` after erasure — i.e. everything.

You **can** declare `throws T`, which is the basis of the "sneaky throws" trick — but
that's a curiosity, not something to write.

### 7. Static fields cannot use the class's type parameter

```java
class Box<T> {
    private static T shared;        // ❌ non-static type variable T cannot be
}                                    //    referenced from a static context
```

**Why:** there is **one** `Box` class at runtime, shared by `Box<String>` and
`Box<Integer>`. A static field belongs to the class (2.2), so which `T` would it be?
The question has no answer, so it's forbidden.

Static *methods* can be generic — they just declare their own parameter (3.2):
```java
static <U> U pick(List<U> items) { return items.get(0); }   // ✅ U is the method's own
```

## Bridge methods — the synthetic methods you'll see in stack traces

Erasure creates a problem for overriding. Consider:

```java
class StringBox implements Comparable<StringBox> {
    @Override public int compareTo(StringBox other) { return 0; }
}
```

`Comparable<T>` erases to `compareTo(Object)`. But `StringBox` declares
`compareTo(StringBox)`. **Different signatures — so it wouldn't actually override
anything**, and dynamic dispatch (2.3) would break.

The compiler fixes this by inserting a **bridge method**:

```java
// synthetic, generated — you never write this
public int compareTo(Object o) {
    return compareTo((StringBox) o);        // casts and delegates
}
```

See it:

```bash
javap -p StringBox.class
```
```
public int compareTo(StringBox);
public int compareTo(java.lang.Object);    ← the bridge
```

> **Why you care:** bridge methods appear in stack traces and in reflection results. When
> you see the same method listed twice with different parameter types, or a stack frame
> for a method you didn't write, that's a bridge.

## ⭐ Heap pollution and unchecked warnings

**Heap pollution** = a variable of a parameterised type refers to an object that isn't of
that type. Erasure makes it possible, because nothing checks at runtime.

```java
List<String> strings = new ArrayList<>();
List raw = strings;                   // ⚠️ warning: unchecked
raw.add(42);                          // ⚠️ warning. COMPILES AND RUNS.

IO.println(strings.size());           // 1 — no error yet
String s = strings.get(0);            // 💥 ClassCastException — HERE
```

The heap now contains a `List<String>` holding an `Integer`. Nothing detected it at the
point of the mistake.

**That's what an `unchecked` warning means:** *"I am inserting a cast I cannot prove is
correct. If you're wrong, it blows up somewhere else."*

```bash
javac -Xlint:unchecked MyClass.java     # always turn this on (1.7)
```

> **Rule: never suppress an `unchecked` warning without a comment proving why it's safe.**
> ```java
> // Safe: the array is never exposed and only ever holds T
> @SuppressWarnings("unchecked")
> T[] array = (T[]) new Object[10];
> ```
> And put `@SuppressWarnings` on the **narrowest possible scope** — a single variable
> declaration, never a whole class.

## Contrast: C# reified generics

| | Java (erased) | C# (reified) |
|---|---|---|
| `List<string>` at runtime | Just `List` | A genuine distinct type |
| `new T()` | ❌ | ✅ |
| `new T[10]` | ❌ | ✅ |
| `x is List<string>` | ❌ | ✅ |
| Overload on `List<int>`/`List<string>` | ❌ | ✅ |
| `List<int>` boxing | Boxes every element | **No boxing** — specialised code |
| Old code compatibility | ✅ Perfect | Required a new runtime |

**What Java gave up:** runtime type information, the ability to specialise generics over
primitives (hence `List<Integer>` boxing, 1.1), and a lot of API expressiveness.

**What Java got:** the 2004 migration happened without breaking anything.

> **Where this is heading:** Project Valhalla aims to bring specialised generics over
> value types to the JVM — `List<int>` with no boxing. It has been in development for a
> decade. `not yet` — don't plan around it.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "Generics make the runtime type-safe" | No. They're compile-time only. The runtime is 2003 |
| Suppressing `unchecked` to make a warning go away | You've disabled the only thing that would have warned you |
| `getClass()` telling you the type argument | It can't. It returns `ArrayList` |
| Expecting `instanceof List<String>` to work | Use `List<?>` |
| Overloading on different type arguments | Same erasure = name clash |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `@SuppressWarnings("unchecked")` on a class or method | On the single declaration, with a justifying comment |
| Raw types to "get around" a generics error | Fix the generics — the raw type just moves the failure |

---

## Recap

| Consequence | Because |
|---|---|
| No `new T()` | No `T` at runtime |
| No `new T[10]` | No `T`, and arrays need a runtime element type |
| No `instanceof List<String>` | Runtime check, erased type |
| `List<String>.class == List<Integer>.class` | One class, both |
| No overload on type arguments | Same erasure → name clash |
| No generic `Throwable` | `catch` is a runtime check |
| No `static T` | One class shared by all instantiations |
| Bridge methods | Restore overriding after erasure |
| Heap pollution | Nothing checks at runtime — that's the `unchecked` warning |
