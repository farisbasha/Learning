# 3.5 — The edges

> **What this is:** Techniques you will **meet in library code** and occasionally need
> yourself. Read this once so you recognise them; come back when you hit one.

---

## Coming from JS/Python/Dart

This page has no equivalent in your other languages, because it's all workarounds for
erasure (3.3) — a problem TypeScript doesn't have to solve (nothing depends on its types
at runtime) and Python solves with `__class_getitem__` and runtime introspection.

## 1. Generic arrays — why they're forbidden

```java
T[] array = new T[10];        // ❌ generic array creation
```

**Why:** arrays are **covariant and reified** (1.4) — an array knows its element type at
runtime and checks every store. Generics are **invariant and erased** (3.3). The two
cannot be combined soundly:

```java
// if new T[] were allowed, here's the hole:
List<String>[] arrays = new List<String>[10];   // pretend this compiles
Object[] objects = arrays;                       // ✅ arrays are covariant
objects[0] = List.of(1, 2, 3);                   // ✅ runtime check sees only "List" — passes!
String s = arrays[0].get(0);                     // 💥 ClassCastException
```

The array's runtime check can only verify `List`, not `List<String>`, because the type
argument was erased. So the compiler forbids the creation instead.

### The `@SuppressWarnings("unchecked")` idiom every collection uses

```java
public class SimpleList<E> {
    private Object[] elements;              // ← store as Object[]
    private int size;

    public SimpleList(int capacity) {
        elements = new Object[capacity];     // ✅ legal
    }

    @SuppressWarnings("unchecked")
    public E get(int index) {
        return (E) elements[index];          // ← the unchecked cast, contained
    }

    public void add(E e) { elements[size++] = e; }
}
```

**This is exactly what `ArrayList` does.** Look at the JDK source:

```java
// java.util.ArrayList — real code
transient Object[] elementData;

@SuppressWarnings("unchecked")
E elementData(int index) {
    return (E) elementData[index];
}
```

**The rules that make it safe:**
1. The array is `private` and **never escapes** the class.
2. Only `E` values are ever written into it.
3. The suppression is on the **narrowest scope** — one method, not the class.
4. There's a comment saying why it's safe.

The other legal form:

```java
@SuppressWarnings("unchecked")
E[] array = (E[]) new Object[10];        // ⚠️ only safe if it never escapes
```

**Do not return this from a public method** — the caller's `E[]` variable is really an
`Object[]` and will throw `ClassCastException` on assignment.

## 2. `Class<T>` as a runtime type token

Erasure removed the type. A `Class<T>` object **carries it back in explicitly**.

```java
public class Factory<T> {
    private final Class<T> type;

    public Factory(Class<T> type) { this.type = type; }

    public T create() throws Exception {
        return type.getDeclaredConstructor().newInstance();   // ✅ now we can!
    }
}

var f = new Factory<>(User.class);
User u = f.create();
```

`User.class` is a `Class<User>` — the type argument is preserved because it's a **value**
you passed, not a type argument that got erased.

### The typesafe heterogeneous container

The pattern that makes this genuinely useful:

```java
public class Favorites {
    private final Map<Class<?>, Object> map = new HashMap<>();

    public <T> void put(Class<T> type, T instance) {
        map.put(type, Objects.requireNonNull(type).cast(instance));
    }

    public <T> T get(Class<T> type) {
        return type.cast(map.get(type));          // cast() is the typesafe version
    }
}

var f = new Favorites();
f.put(String.class, "hello");
f.put(Integer.class, 42);

String s = f.get(String.class);       // ✅ no cast needed by the caller
Integer i = f.get(Integer.class);     // ✅ different types in one map, all typesafe
```

`Class.cast()` is the runtime-checked equivalent of a `(T)` cast — it throws
`ClassCastException` immediately rather than polluting the heap.

> **This is how frameworks work.** Spring's `getBean(Class<T>)`, Jackson's
> `readValue(json, Class<T>)`, JPA's `find(Class<T>, id)` — all the same pattern,
> recovering erased information by passing a token.

## 3. Super type tokens — the abstract-subclass trick

`Class<T>` can't express a **generic** type:

```java
List<User>.class        // ❌ no such syntax
```

So how does Jackson deserialise JSON into a `List<User>`?

**The trick: generic info survives in a class's `Signature` attribute** (3.3). An
anonymous subclass (2.9) has a *superclass*, and that superclass's type argument is
recorded in the class file:

```java
var token = new TypeReference<List<User>>() { };
//                                          ↑↑↑ anonymous subclass — this is the trick
```

Simplified implementation:

```java
public abstract class TypeReference<T> {
    private final Type type;

    protected TypeReference() {
        Type superclass = getClass().getGenericSuperclass();
        this.type = ((ParameterizedType) superclass).getActualTypeArguments()[0];
    }

    public Type getType() { return type; }
}
```

`getGenericSuperclass()` reads the recorded signature — `TypeReference<List<User>>` — and
pulls `List<User>` out of it.

**You'll use this, not write it:**

```java
// Jackson
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});

// Gson
List<User> users = gson.fromJson(json, new TypeToken<List<User>>(){}.getType());
```

> **The `{}` at the end is mandatory.** Without it there's no anonymous subclass, no
> recorded superclass signature, and the trick fails at runtime. This is a real and
> common bug.

## 4. `@SafeVarargs` and generic varargs

Generic varargs create an array of a generic type — which 3.5§1 just said is unsafe:

```java
static <T> List<T> listOf(T... items) {      // ⚠️ warning: possible heap pollution
    return Arrays.asList(items);
}
```

The compiler creates a `T[]` internally, which erases to `Object[]`. Here's the hole:

```java
static <T> T[] toArray(T... items) { return items; }

static <T> T[] danger(T a, T b) {
    return toArray(a, b);                    // creates an Object[] at runtime
}

String[] s = danger("x", "y");               // 💥 ClassCastException
```

**`@SafeVarargs` is your promise that the method doesn't do that:**

```java
@SafeVarargs
static <T> List<T> listOf(T... items) {
    return List.of(items);                   // ✅ only reads, never stores or returns the array
}
```

**The two rules for using it honestly:**
1. **Never store anything into the varargs array.**
2. **Never let the array escape** (don't return it, don't pass it to untrusted code).

Applicable to `static`, `final`, and `private` methods only — it can't be applied to an
overridable method, because a subclass could break the promise.

## 5. Intersection types, and what `var` can infer

Sometimes the compiler infers a type you **cannot write down**:

```java
var x = condition ? new ArrayList<String>() : new LinkedList<String>();
```

The inferred type is roughly:

```
AbstractList<String> & Cloneable & Serializable & SequencedCollection<String>
```

That's an **intersection type** — "all of these at once". Java has no syntax for writing
one in a variable declaration, but `var` (1.1) can hold it, and you can call methods from
**every** component:

```java
x.add("hi");            // from List
x.clone();              // from Cloneable
```

You can write intersections in a **bound** (3.2):
```java
<T extends Comparable<T> & Serializable> void f(T item) { }
```

And in a cast, which is the trick for typing a lambda as two interfaces at once:

```java
Runnable r = (Runnable & Serializable) () -> IO.println("hi");
```

> This is the one genuine capability `var` has that an explicit type annotation does not.

## 6. Where this is heading — Project Valhalla `not yet`

The known cost of erasure is **boxing**: `List<Integer>` stores pointers to `Integer`
objects, not raw `int`s (1.1). A million-element `List<Integer>` is ~20MB and chases
pointers; an `int[]` is 4MB and is contiguous.

**Project Valhalla** aims to add *value classes* and *specialised generics* so that
`List<int>` compiles to specialised code with no boxing — reified where it matters,
without breaking the existing ecosystem.

It has been in development for over a decade. Some pieces are landing (compact object
headers in Java 25, 8.4), but generic specialisation is not here.

> **Do not design around it.** If you need primitive performance today, use `int[]`,
> `IntStream` (6.4), or the primitive-specialised functional interfaces (6.3).

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Returning `(E[]) new Object[n]` from a public method | Caller's `E[]` assignment throws |
| `new TypeReference<List<User>>()` without `{}` | The trick silently fails |
| `@SafeVarargs` on a method that stores into the array | You lied; heap pollution returns |
| `@SuppressWarnings` on a whole class | Hides real warnings. Narrowest scope only |
| Waiting for Valhalla | Use `int[]` / `IntStream` today |

## Recap

| Technique | Use it for |
|---|---|
| `Object[]` + contained unchecked cast | Implementing a generic container |
| `Class<T>` token | Recovering the erased type; `newInstance`, typesafe containers |
| Super type token `new X<List<User>>(){}` | Recovering a **generic** erased type. The `{}` is mandatory |
| `@SafeVarargs` | Generic varargs — promise: don't store, don't escape |
| Intersection types | `var`, bounds, and dual-interface lambda casts |
| Valhalla | Not yet. Use primitive arrays and streams |
