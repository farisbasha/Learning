# 3.1 — The problem generics solve

> **What this is:** Spend twenty minutes writing pre-generics code. **Nothing explains
> generics faster.** This page is that twenty minutes.

---

## Coming from JS/Python/Dart

TypeScript generics will feel almost identical here — `List<String>` is `Array<string>`,
`<T>` is `<T>`. Enjoy the familiarity while it lasts: it holds for 3.1 and 3.2, and
then **erasure** (3.3) breaks it completely.

Python's `list[str]` is the closer analogy in one way — it's also erased, also a hint to
a checker rather than something the runtime enforces.

---

## The concepts

### Collections before Java 5

Generics arrived in 2004. Before that, every collection held `Object`:

```java
List names = new ArrayList();     // no type argument — this is a RAW type
names.add("Basha");
names.add("Faris");

String first = (String) names.get(0);    // cast required on EVERY read
```

Three problems, all of them daily:

**(1) Every read needs a cast.** Noise on every single line.

**(2) Every mistake is a runtime `ClassCastException`:**

```java
List names = new ArrayList();
names.add("Basha");
names.add(42);                           // ✅ compiles fine — it's an Object

for (Object o : names) {
    String s = (String) o;               // 💥 ClassCastException on the second element
}
```

The bug is on the `add` line. The explosion is somewhere else entirely, possibly in
another file, possibly in production, possibly three weeks later.

**(3) The API tells you nothing.**

```java
public List getUsers()       // a list of... what?
```

You have to read the implementation, or guess.

### What generics buy

**One thing: the error moves from runtime to compile time.**

```java
List<String> names = new ArrayList<>();
names.add("Basha");
names.add(42);                           // ❌ compile error. The program never runs.

String first = names.get(0);             // no cast
```

```java
public List<User> getUsers()             // the signature documents itself
```

That's the whole value proposition. Same runtime behaviour, error caught 3 weeks earlier.

> **The framing to hold onto:** generics are a **compile-time** feature. They add no
> runtime checking at all — which is exactly what 3.3 is about, and why so many of the
> rules look strange.

### Raw types — what `List` means today

```java
List raw = new ArrayList();        // still compiles in Java 25!
```

Java kept raw types working forever, for backwards compatibility with 2004-era code and
libraries. **They are never correct in new code.**

What you lose when a raw type appears:

```java
List<String> safe = new ArrayList<>();
List raw = safe;                   // ⚠️ unchecked — but allowed
raw.add(42);                       // ⚠️ warning only. Compiles.

String s = safe.get(0);            // 💥 ClassCastException — from a line that looks fine
```

A single raw type **disables generic checking for the whole expression**, and the damage
surfaces somewhere unrelated. This is "heap pollution" (3.3).

Worse — raw types disable generics on *unrelated* methods of that type too:

```java
List<String> list = new ArrayList<>();
List rawRef = list;
for (String s : rawRef) { }        // ❌ won't even compile — everything degrades to Object
```

**Turn the warning on** (1.7):
```bash
javac -Xlint:rawtypes,unchecked MyClass.java
```

> **Use `List<?>` if you genuinely don't care about the element type** (3.4) — it's the
> type-safe version of a raw type.

### The diamond operator `<>` `Java 7`

```java
// Java 5–6: type argument repeated on both sides
Map<String, List<Integer>> map = new HashMap<String, List<Integer>>();

// Java 7+: the compiler infers the right side
Map<String, List<Integer>> map = new HashMap<>();

// Java 10+: or infer the left side instead
var map = new HashMap<String, List<Integer>>();
```

> **This is a reliable tutorial-dating signal** (0.3). If you see the type argument
> written out twice, the article is from before 2011.

**`<>` is not the same as raw:**

```java
new ArrayList<>()       // ✅ diamond — infers String from context
new ArrayList()         // ❌ raw — no type at all
```

One character, completely different meaning.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `List` and `List<Object>` are the same | They aren't. Raw disables checking; `List<Object>` is checked |
| A raw type is "just untyped" | It **poisons** the whole expression and causes `ClassCastException` elsewhere |
| `new ArrayList()` vs `new ArrayList<>()` | Raw vs diamond. Always use `<>` |
| Generics make the runtime safer | No — they move errors to **compile time**. Runtime is unchanged (3.3) |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Raw types — `List`, `Map`, `Comparable` | `List<String>`, or `List<?>` if truly unknown |
| `new ArrayList<String>()` on the right of an assignment | `new ArrayList<>()` |
| Casting on every collection read | That's what generics removed |

---

## Recap

| Concept | One line |
|---|---|
| Pre-2004 | Everything is `Object`; cast on read; `ClassCastException` at runtime |
| Generics buy | **Errors move from runtime to compile time.** That's it |
| Raw types | Still compile, never correct, disable checking for the whole expression |
| `<>` | Java 7. Infers the type argument. `<>` ≠ raw |
