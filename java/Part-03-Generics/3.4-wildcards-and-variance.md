# 3.4 — Wildcards and variance

> **What this is:** The part everyone finds hard. It is **one question**:
> *can I put things **in**, or take things **out**?*
>
> Answer that for a given signature and every wildcard rule follows.

---

## Coming from JS/Python/Dart

TypeScript arrays are **covariant** (`string[]` is assignable to `object[]`) and unsound
by design — TS accepts the risk. Java refused to, so you get wildcards instead.

If you've used Kotlin's `out`/`in`, those are exactly `? extends` / `? super`. If you've
used Scala's `+T`/`-T`, same idea declared on the type instead of at the use site.

---

## The concepts

### Why `List<String>` is not a `List<Object>`

```java
List<String> strings = new ArrayList<>();
List<Object> objects = strings;        // ❌ compile error
```

This feels wrong at first — every `String` **is** an `Object`. Here's why it must be
rejected:

```java
// suppose it were allowed...
List<Object> objects = strings;        // pretend this compiles
objects.add(42);                       // ✅ 42 IS an Object. Perfectly legal.

String s = strings.get(0);             // 💥 ClassCastException
```

The two variables point at the **same list**. Allowing the assignment would let you put an
`Integer` into a `List<String>` through the back door.

> **Generics are invariant:** `List<String>` and `List<Object>` are unrelated types,
> full stop. Not subtypes, not supertypes.

### How this differs from arrays

Arrays made the opposite choice (1.4):

```java
Object[] objects = new String[1];      // ✅ compiles — arrays ARE covariant
objects[0] = 42;                       // 💥 ArrayStoreException at RUNTIME
```

| | Arrays | Generics |
|---|---|---|
| Covariant? | ✅ Yes | ❌ No — invariant |
| Error caught | **Runtime** (`ArrayStoreException`) | **Compile time** |
| Cost | A type check on **every single array store**, forever | Some syntax |

Generics were designed in 2004 explicitly **not to repeat the array mistake**. The cost
of that decision is this page.

### The problem invariance creates

```java
void printAll(List<Object> items) {
    for (Object o : items) IO.println(o);
}

printAll(new ArrayList<String>());     // ❌ won't compile. But it's obviously safe!
```

The method only **reads**. It can't possibly break anything. But invariance says no.

**Wildcards are the fix.**

## ⭐ The three wildcards

### `List<?>` — unbounded

*"A list of some specific unknown type."*

```java
void printAll(List<?> items) {
    for (Object o : items) IO.println(o);     // ✅ reading as Object is always safe
}

printAll(List.of("a", "b"));        // ✅
printAll(List.of(1, 2));            // ✅
```

**What you can do:** read as `Object`, call `size()`, `isEmpty()`, `clear()`,
`iterator()`.

**What you cannot do:** add anything.

```java
void f(List<?> items) {
    items.add("hi");        // ❌ — items might be a List<Integer>
    items.add(null);        // ✅ null is the one exception — it's valid for every type
}
```

> `List<?>` is the **type-safe replacement for a raw `List`** (3.1). Use it when you
> genuinely don't care about the element type.

### `List<? extends T>` — upper bound, a **PRODUCER**

*"A list of T or some subtype of T."* You can take things **out**.

```java
double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();   // ✅ reading as Number is safe
    return total;
}

sum(List.of(1, 2, 3));            // ✅ List<Integer>
sum(List.of(1.5, 2.5));           // ✅ List<Double>
sum(List.of(1L, 2L));             // ✅ List<Long>
```

**Read-only.** You cannot add:

```java
void f(List<? extends Number> nums) {
    Number n = nums.get(0);       // ✅ whatever it is, it's a Number
    nums.add(1);                  // ❌ it might be a List<Double>
    nums.add(1.0);                // ❌ it might be a List<Integer>
    nums.add(null);               // ✅ only null
}
```

> **The logic:** you know everything coming *out* is at least a `Number`. You have no idea
> what's safe to put *in*, because the actual list could be `List<Integer>` or
> `List<Double>` or `List<BigDecimal>`.

### `List<? super T>` — lower bound, a **CONSUMER**

*"A list of T or some supertype of T."* You can put things **in**.

```java
void addNumbers(List<? super Integer> list) {
    list.add(1);                  // ✅ an Integer fits in List<Integer>, List<Number>,
    list.add(2);                  //    and List<Object> — all the possibilities
}

addNumbers(new ArrayList<Integer>());   // ✅
addNumbers(new ArrayList<Number>());    // ✅
addNumbers(new ArrayList<Object>());    // ✅
```

**Write-only, effectively.** Reading gives you `Object`:

```java
void f(List<? super Integer> list) {
    list.add(1);                  // ✅
    Integer i = list.get(0);      // ❌ might be a List<Object> holding a String
    Object o = list.get(0);       // ✅ only Object is guaranteed
}
```

## ⭐ PECS — Producer Extends, Consumer Super

The mnemonic that makes this stick:

> **If the parameter PRODUCES values for you → `? extends T`**
> **If the parameter CONSUMES values from you → `? super T`**
> **If it does both → no wildcard, just `T`**

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    //                            ↑ consumer          ↑ producer
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i));
    }
}
```

`src` produces values (you read from it) → `extends`.
`dest` consumes values (you write to it) → `super`.

### Reading real JDK signatures

This is the exercise that makes it click. Work through these:

```java
// Collections
public static <T> void copy(List<? super T> dest, List<? extends T> src)
public static <T> boolean addAll(Collection<? super T> c, T... elements)
public static <T> void sort(List<T> list, Comparator<? super T> c)

// Stream — Part 06
<R> Stream<R> map(Function<? super T, ? extends R> mapper)
Stream<T> filter(Predicate<? super T> predicate)
void forEach(Consumer<? super T> action)

// Collection
boolean addAll(Collection<? extends E> c)
```

Take `Collection.addAll(Collection<? extends E> c)`: the argument **produces** elements
that you then add to yourself. Producer → `extends`. Which is why this works:

```java
List<Number> nums = new ArrayList<>();
nums.addAll(List.of(1, 2, 3));        // ✅ List<Integer> is a Collection<? extends Number>
```

And `Comparator<? super T>` in `sort`: the comparator **consumes** your elements.
Consumer → `super`. Which is why this works:

```java
List<Integer> ints = new ArrayList<>();
Comparator<Number> byDouble = Comparator.comparingDouble(Number::doubleValue);
ints.sort(byDouble);                  // ✅ a Comparator<Number> can compare Integers
```

Without `? super`, that would be rejected, and you'd need a separate comparator per
subtype.

### Where wildcards belong: parameters, not return types

```java
// ❌ don't do this
public List<? extends Number> getNumbers() { ... }
```

Now **every caller** has to deal with the wildcard:

```java
List<? extends Number> result = getNumbers();
result.add(1);                        // ❌ they can't add anything
```

You've pushed your flexibility problem onto everyone who calls you.

```java
// ✅ be specific in what you return
public List<Number> getNumbers() { ... }
```

> **The rule: be liberal in what you accept (wildcards on parameters), specific in what
> you return (no wildcards).** This is Postel's law, applied to type signatures.

## Wildcard capture, and the helper-method trick

This one produces a baffling error message, so recognise it:

```java
void reverse(List<?> list) {
    Object tmp = list.get(0);
    list.set(0, list.get(1));         // ❌ error!
    list.set(1, tmp);
}
```

```
error: no suitable method found for set(int,Object)
       ... List<CAP#1> where CAP#1 is a fresh type-variable
```

**Why:** the compiler knows the list is a `List<something>` but cannot name that
`something`. Each use of `?` gets a fresh "capture" variable, and `CAP#1` from `get` isn't
provably the same as the `CAP#2` that `set` wants.

**The fix — a private generic helper that gives the type a name:**

```java
void reverse(List<?> list) {
    reverseHelper(list);                    // capture happens here
}

private <T> void reverseHelper(List<T> list) {   // now it has a NAME: T
    T tmp = list.get(0);
    list.set(0, list.get(1));               // ✅ both are T
    list.set(1, tmp);
}
```

The public method keeps the friendly wildcard signature; the private helper does the work
with a real type parameter. **This is a standard idiom** — you'll find it throughout the
JDK source.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `List<String>` is a `List<Object>` | No. Generics are invariant |
| Adding to a `List<? extends T>` | Impossible (except `null`) |
| Reading a specific type from `List<? super T>` | You only get `Object` |
| Wildcards on return types | Pushes the problem onto every caller |
| `CAP#1` errors | Wildcard capture. Use a private generic helper |
| Using `<? extends T>` when you need both read and write | Use plain `T` |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Raw `List` to dodge variance | `List<?>` |
| Wildcards in return types | Concrete type arguments |

---

## Recap

| Wildcard | Means | You can | Mnemonic |
|---|---|---|---|
| `List<?>` | Some unknown type | Read as `Object` only | Type-safe raw type |
| `List<? extends T>` | T or a subtype | **Read** as T. Cannot add | **P**roducer **E**xtends |
| `List<? super T>` | T or a supertype | **Add** T. Read as `Object` | **C**onsumer **S**uper |
| `List<T>` | Exactly T | Both | Neither producing nor consuming only |

**Placement:** wildcards on **parameters**. Never on return types.
