# 3.2 — Writing generic types and methods

> **What this is:** The mechanics, which are mostly unsurprising. If you've written
> TypeScript generics, most of this page is recognition rather than learning.

---

## Coming from JS/Python/Dart

```typescript
// TypeScript
class Box<T> { constructor(private value: T) {} get(): T { return this.value; } }
function first<T>(items: T[]): T { return items[0]; }
```

```java
// Java — same shape
class Box<T> { private final T value; Box(T v){this.value=v;} T get(){return value;} }
static <T> T first(List<T> items) { return items.get(0); }
```

The one piece of syntax with no TS equivalent is `<T extends Comparable<T>>` for
bounds, and where `<T>` goes in a **method** signature.

---

## The concepts

### Type parameters on classes and interfaces

```java
public class Box<T> {
    private T value;

    public void set(T value) { this.value = value; }
    public T get()           { return value; }
}

var stringBox = new Box<String>();
stringBox.set("hi");
String s = stringBox.get();       // no cast
```

Multiple parameters:

```java
public class Pair<K, V> {
    private final K key;
    private final V value;
    public Pair(K key, V value) { this.key = key; this.value = value; }
    public K key()   { return key; }
    public V value() { return value; }
}

var p = new Pair<String, Integer>("age", 30);
```

### The naming conventions

These are conventions, not rules — but the whole ecosystem follows them, so follow them:

| Letter | Means | Seen in |
|---|---|---|
| `T` | **T**ype — the generic default | `Box<T>`, `Optional<T>` |
| `E` | **E**lement | `List<E>`, `Set<E>` |
| `K`, `V` | **K**ey, **V**alue | `Map<K,V>` |
| `R` | **R**eturn type | `Function<T,R>` |
| `U`, `S` | A second/third type when `T` is taken | `Function.andThen` |
| `N` | **N**umber | — |

Single capital letters. Never `TItem` or `TypeParam` — that's C# style, and Java code
doesn't do it.

### Generic methods — and where `<T>` goes

**This is the one piece of syntax people get wrong.** The type parameter goes
**before the return type**:

```java
//         ↓ here
public static <T> T first(List<T> items) {
    return items.get(0);
}

public static <K, V> Map<V, K> invert(Map<K, V> map) { ... }
```

A generic method can live in a **non**-generic class — that's the common case:

```java
public final class Utils {            // not generic
    public static <T> List<T> repeat(T item, int times) {   // this method is
        var result = new ArrayList<T>();
        for (int i = 0; i < times; i++) result.add(item);
        return result;
    }
}
```

**A generic method's `<T>` is independent of the class's `<T>`** — and if you name them
the same, the method's shadows the class's, which is confusing:

```java
class Box<T> {
    <T> void confusing(T item) { }    // ⚠️ this T is NOT the class's T. Rename it
    <U> void clear(U item) { }        // ✅
}
```

### Type inference — and when you must help

Usually you write nothing:

```java
var list = Utils.repeat("hi", 3);              // T inferred as String
Map<String,Integer> m = new HashMap<>();       // inferred from the target type
```

The compiler infers from arguments *and* from the assignment target. When it can't:

```java
// nothing to infer from — an empty list of what?
List<String> empty = Collections.emptyList();       // ✅ inferred from the target

process(Collections.emptyList());                    // ❌ ambiguous if process is overloaded
process(Collections.<String>emptyList());            // ✅ explicit witness
```

The `Collections.<String>emptyList()` syntax is called an **explicit type witness**. Rare,
but you'll meet it in library code and in error messages.

### ⭐ Bounded type parameters

`extends` on a type parameter means *"T must be this or a subtype"*:

```java
public static <T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T item : items) {
        if (item.compareTo(best) > 0) best = item;   // ✅ compareTo available
    }
    return best;
}

max(List.of(3, 1, 2));              // ✅ Integer implements Comparable<Integer>
max(List.of(new Object()));         // ❌ Object is not Comparable
```

**Without the bound, `T` is just `Object`** and you can only call `Object`'s methods
(2.5). The bound is what gives you access to `compareTo`.

**`extends` is used for both classes and interfaces here** — there is no `implements` in
a type bound. `<T extends Runnable>` is an interface bound.

**Multiple bounds with `&`:**

```java
public static <T extends Comparable<T> & Serializable> void f(T item) { }
```

Rules: at most one **class** bound, and it must come first; any number of interfaces.

```java
<T extends Number & Comparable<T>>          // ✅ class first
<T extends Comparable<T> & Number>          // ❌ class must be first
```

### Recursive generic bounds

The pattern that looks like a typo:

```java
<T extends Comparable<T>>
```

Read it as: *"T is comparable **to itself**"* — i.e. you can compare two `T`s, not a `T`
to some unrelated type.

The JDK's own example:

```java
public abstract class Enum<E extends Enum<E>> implements Comparable<E>
```

`Status extends Enum<Status>`. This is how `Status.ACTIVE.compareTo(other)` is typed to
accept only another `Status`, never a `Day`.

You'll also meet it in the **self-returning builder** pattern:

```java
abstract class Builder<T extends Builder<T>> {
    protected String name;

    @SuppressWarnings("unchecked")
    public T name(String name) {
        this.name = name;
        return (T) this;              // returns the SUBCLASS type, not Builder
    }
}

class PizzaBuilder extends Builder<PizzaBuilder> {
    public PizzaBuilder cheese() { ... return this; }
}

new PizzaBuilder().name("x").cheese();   // ✅ name() returned PizzaBuilder, not Builder
```

Without the recursive bound, `.name()` would return `Builder` and `.cheese()` wouldn't
exist on it.

> **You rarely write this. You need to be able to read it** — it's all over the JDK and
> library code, and it's genuinely confusing the first few times.

### Generic records and generic interfaces

```java
public record Pair<K, V>(K key, V value) { }

var p = new Pair<>("age", 30);      // diamond works on records too
```

```java
public interface Repository<T, ID> {
    Optional<T> findById(ID id);
    List<T> findAll();
    T save(T entity);
}

class UserRepository implements Repository<User, Long> { ... }
```

Generic sealed interfaces work too, which is how you build a `Result<T>` type (2.8):

```java
public sealed interface Result<T> permits Ok, Err { }
public record Ok<T>(T value)      implements Result<T> { }
public record Err<T>(String msg)  implements Result<T> { }
```

### ⚠️ What you cannot do (preview of 3.3)

```java
class Box<T> {
    private static T shared;         // ❌ static fields cannot use T
    T make()      { return new T(); }      // ❌ cannot instantiate T
    T[] array()   { return new T[10]; }    // ❌ cannot create a T array
}
```

Every one of these has the same cause, and 3.3 is that cause.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `public T <T> first(...)` | Wrong order. `<T>` comes **before** the return type |
| Reusing the class's `T` on a method | Shadows it. Use a different letter |
| `<T implements Comparable<T>>` | No such syntax. Always `extends` |
| `<T extends Comparable<T> & Number>` | Class bound must be first |
| Forgetting the bound | `T` is just `Object` — no useful methods |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `TItem`, `TKey` (C# naming) | `T`, `K`, `V`, `E`, `R` |
| Explicit type witness when inference works | Let the compiler infer |

---

## Recap

| Concept | One line |
|---|---|
| `class Box<T>` | Type parameter on the class |
| `static <T> T f(...)` | `<T>` goes **before the return type** |
| Conventions | `T`, `E`, `K`/`V`, `R` — single capitals |
| `<T extends X>` | Bound — gives you X's methods. `extends` for classes *and* interfaces |
| `& ` | Multiple bounds; class first |
| `<E extends Enum<E>>` | Recursive bound — "comparable to itself". Read it, rarely write it |
