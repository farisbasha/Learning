## Intermediate operations

All return a `Stream` and all are lazy (6.4).

```java
.filter(Predicate)          // keep matching
.map(Function)              // transform 1 → 1
.flatMap(Function)          // transform 1 → many, then flatten
.mapMulti(BiConsumer)       // Java 16 — 1 → many, push-style, no intermediate stream
.distinct()                 // dedupe via equals/hashCode — STATEFUL
.sorted()                   // natural order — STATEFUL
.sorted(Comparator)         // STATEFUL
.peek(Consumer)             // ⚠️ debugging only — see below
.limit(n)                   // first n — short-circuits
.skip(n)                    // drop the first n
.takeWhile(Predicate)       // Java 9 — take until the first failure, then stop
.dropWhile(Predicate)       // Java 9 — drop until the first failure, then take the rest
```

### `takeWhile` / `dropWhile` vs `filter` `Java 9`

The difference people miss:

```java
var nums = List.of(1, 2, 3, 10, 4, 5);

nums.stream().filter(x -> x < 5).toList();      // [1, 2, 3, 4]     — checks EVERY element
nums.stream().takeWhile(x -> x < 5).toList();   // [1, 2, 3]        — STOPS at 10
nums.stream().dropWhile(x -> x < 5).toList();   // [10, 4, 5]       — drops until 10, keeps rest
```

`filter` tests everything. `takeWhile` stops at the first failure. On sorted data,
`takeWhile` is a large win.

## Terminal operations

```java
// collecting
.toList()                   // Java 16 — UNMODIFIABLE, allows nulls (5.7)
.collect(Collector)         // the general form — 6.6
.toArray()                  // Object[]
.toArray(String[]::new)     // String[] (6.2)

// reducing
.reduce(BinaryOperator)             // → Optional<T>
.reduce(identity, BinaryOperator)   // → T
.count()                            // long
.min(Comparator) / .max(Comparator) // → Optional<T>

// matching — all short-circuit
.anyMatch(Predicate)    .allMatch(Predicate)    .noneMatch(Predicate)

// finding — short-circuit
.findFirst()            // → Optional, respects encounter order
.findAny()              // → Optional, may be faster in parallel (6.8)

// side effects
.forEach(Consumer)          // no order guarantee in parallel
.forEachOrdered(Consumer)   // preserves encounter order, costs performance
```

> ⚠️ **`allMatch` on an empty stream returns `true`.** ("Vacuous truth" — every element of
> nothing satisfies everything.) Same for `noneMatch`. This is mathematically correct and
> catches people.

## ⭐ `flatMap` properly

**`map` is 1 → 1. `flatMap` is 1 → many, then flattened.**

```java
record Order(String id, List<Item> items) { }

// ❌ map gives you a Stream of Lists
Stream<List<Item>> wrong = orders.stream().map(Order::items);

// ✅ flatMap flattens them into one Stream of Items
Stream<Item> right = orders.stream().flatMap(o -> o.items().stream());
```

```
map:      [Order1, Order2]  →  [[a,b], [c]]        ← nested
flatMap:  [Order1, Order2]  →  [a, b, c]           ← flat
```

**The function must return a `Stream`**, not a collection:

```java
.flatMap(o -> o.items().stream())        // ✅
.flatMap(Order::items)                   // ❌ returns List, not Stream
```

### Common uses

```java
// flatten nested collections
Stream<String> allTags = posts.stream().flatMap(p -> p.tags().stream());

// split strings into words
Stream<String> words = lines.stream().flatMap(l -> Arrays.stream(l.split("\\s+")));

// unwrap Optionals (6.7)
Stream<User> found = ids.stream().flatMap(id -> repo.findById(id).stream());
```

That last one uses `Optional.stream()` `Java 9` — an `Optional` becomes a stream of 0 or 1
elements, so empty ones vanish. Very idiomatic.

### ⭐ The empty-stream trick for filtering

Because `flatMap` can return an **empty** stream, it can drop elements *and* transform
them in one step:

```java
// filter + map in one pass, when the test and the transform share work
orders.stream()
      .flatMap(o -> {
          var result = expensiveParse(o);
          return result.isValid() ? Stream.of(result) : Stream.empty();   // ← drops it
      })
      .toList();
```

The alternative would parse twice (once in `filter`, once in `map`) or need an
intermediate `Optional`.

> `mapMulti` `Java 16` does the same thing more efficiently — it *pushes* results into a
> consumer instead of allocating a `Stream` per element. Worth using when the fan-out is
> small and the stream is hot.
> ```java
> .<Result>mapMulti((o, consumer) -> {
>     var r = expensiveParse(o);
>     if (r.isValid()) consumer.accept(r);
> })
> ```

## ⭐ `reduce` in its three forms

```java
// 1. no identity → Optional (the stream might be empty)
Optional<Integer> sum = nums.stream().reduce((a, b) -> a + b);

// 2. with identity → always a value
int sum = nums.stream().reduce(0, (a, b) -> a + b);

// 3. with identity + combiner → for parallel, and for a different result type
int totalLength = words.stream().reduce(
    0,                              // identity
    (acc, w) -> acc + w.length(),   // accumulator: partial + element
    (a, b) -> a + b                 // combiner: partial + partial (parallel only)
);
```

### ⭐ The associativity requirement

> **The accumulator must be associative:** `(a op b) op c` must equal `a op (b op c)`.

```java
// ✅ associative
(a, b) -> a + b
(a, b) -> a * b
Integer::max
String::concat

// ❌ NOT associative — gives different answers in parallel
(a, b) -> a - b
(a, b) -> (a + b) / 2
```

```java
List.of(1, 2, 3, 4).stream().reduce(0, (a,b) -> a - b);           // -10
List.of(1, 2, 3, 4).parallelStream().reduce(0, (a,b) -> a - b);   // 💥 different answer
```

**And the identity must be a true identity:** `identity op x == x`.
`0` for addition ✅, `1` for multiplication ✅, `0` for multiplication ❌ (everything
becomes 0 — and in parallel it's applied multiple times).

> **In practice, prefer `Collectors` (6.6) over `reduce` for anything non-trivial.**
> `reduce` with a mutable accumulator is a common bug — use `collect` for mutable
> reduction.

```java
// ❌ mutable reduction with reduce — broken in parallel
.reduce(new ArrayList<>(), (list, x) -> { list.add(x); return list; })

// ✅
.collect(Collectors.toList())
```

## ⚠️ `peek` is for debugging only

```java
list.stream()
    .peek(x -> IO.println("before filter: " + x))
    .filter(...)
    .peek(x -> IO.println("after filter: " + x))
    .toList();
```

**Why not for real work:**

**(1) It may not run.** The JDK is explicitly allowed to skip it if the result isn't
needed:

```java
list.stream().peek(IO::println).count();
// ⚠️ may print NOTHING — since Java 9, count() can skip the pipeline entirely
//    when it can determine the size from the source
```

**(2) It's a side effect in a lazy pipeline**, so *when* and *how many times* it runs is
unspecified (6.4).

> **Use it to debug, delete it before committing.** Never use it to mutate.

## ⭐ Side effects in lambdas — why mutating an external list is a smell

```java
// ❌ this "works" sequentially and breaks in parallel
List<String> results = new ArrayList<>();
list.stream().filter(...).forEach(results::add);
```

Three problems:

1. **Not thread-safe.** `ArrayList` isn't synchronised; `parallelStream()` corrupts it or
   throws (Part 09).
2. **It defeats the point.** You've written an imperative loop with extra syntax.
3. **The result is unordered** in parallel.

```java
// ✅
List<String> results = list.stream().filter(...).toList();
```

> **The rule: a stream pipeline should *produce* a value, not *modify* something.**
> If your terminal operation is `forEach` with a mutation inside, you probably want
> `collect` — or a plain `for` loop.

The exception: `forEach` for genuine side effects that aren't accumulation — logging,
sending, printing.

```java
orders.stream().filter(Order::isOverdue).forEach(notifier::send);     // ✅ fine
```

## ⭐ When a plain `for` loop is the better code

Streams are not automatically better. Use a loop when:

### 1. You need an early exit with complex logic

```java
// ✅ clear
for (var order : orders) {
    if (order.isInvalid()) { log.warn("bad order {}", order.id()); continue; }
    if (order.total() > limit) { return order; }
    process(order);
}
```

The stream version needs `takeWhile`/`filter`/`findFirst` gymnastics and reads worse.

### 2. Checked exceptions (6.1, 4.2)

```java
// ✅ just works
for (Path p : paths) {
    contents.add(Files.readString(p));      // IOException propagates normally
}
```

### 3. You need the index

```java
for (int i = 0; i < list.size(); i++) {
    IO.println(i + ": " + list.get(i));
}
```

`IntStream.range(0, list.size()).mapToObj(i -> ...)` works but is worse to read.

### 4. Debugging

A breakpoint in a `for` loop shows you the local variables. A breakpoint in a stream lambda
shows you a stack full of `ReferencePipeline$3$1.accept` frames. This is a genuine
day-to-day cost.

### 5. It's genuinely simpler

```java
// ❌ stream for the sake of it
IntStream.range(0, 3).forEach(i -> IO.println("hi"));

// ✅
for (int i = 0; i < 3; i++) IO.println("hi");
```

> **The test: does the stream version express the *intent* more clearly?** `filter → map →
> collect` over a collection: yes, obviously. A loop with three conditions and an early
> return: no.
>
> **"Use streams everywhere" and "never use streams" are both wrong.** The PDF's framing
> is right — knowing where the seams are is what separates people who use streams well
> from people who use them everywhere.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `allMatch` on an empty stream | Returns `true` |
| `.flatMap(Order::items)` | Must return a `Stream`, not a `List` |
| `reduce` with a non-associative op | Wrong answer in parallel |
| `reduce` with a mutable accumulator | Use `collect` |
| `peek` for real work | May not run at all |
| `forEach(list::add)` | Not thread-safe; use `toList()` |
| Streams for everything | Loops are better for index, early exit, checked exceptions, debugging |

---

## Recap

| Group | Members |
|---|---|
| **Intermediate** | `filter`, `map`, `flatMap`, `mapMulti`, `distinct`*, `sorted`*, `peek`, `limit`*, `skip`*, `takeWhile`, `dropWhile` (*stateful) |
| **Terminal** | `toList`, `collect`, `reduce`, `count`, `min`/`max`, `*Match`, `findFirst`/`findAny`, `forEach` |
| `flatMap` | 1 → many, flattened. Empty stream = drop |
| `reduce` | Must be **associative**; identity must be a true identity |
| `peek` | Debugging only. May not run |
| Side effects | A pipeline should **produce**, not **mutate** |
| Loops win for | Index, early exit, checked exceptions, debugging, simplicity |
