# 6.1 — Lambdas

> **What this is:** Familiar syntax from every language you know, with **an unfamiliar
> thing underneath**. Java 8 added first-class functions to a language designed without
> them, and the seams show.

---

## Coming from JS/Python/Dart

The syntax is nearly identical to a JS arrow function:

```javascript
const f = (a, b) => a + b;        // JS
```
```java
BinaryOperator<Integer> f = (a, b) -> a + b;    // Java
```

**The difference that matters:** in JS, `f` is a *function*. In Java, there is **no
function type** — `f` is an *object* implementing an interface. That distinction explains
almost everything odd on this page.

---

## The concepts

### Syntax forms

```java
() -> IO.println("hi")                    // zero parameters
x -> x * 2                                // one parameter — parens optional
(x) -> x * 2                              // same
(x, y) -> x + y                           // many — parens required
(int x, int y) -> x + y                   // explicit types — rare, but legal
(var x, var y) -> x + y                   // Java 11 — lets you add annotations

x -> { return x * 2; }                    // block body — return required
x -> {                                    // multi-statement block
    var doubled = x * 2;
    return doubled + 1;
}
```

Rules: either **all** parameters have explicit types or **none** do. Expression bodies
return implicitly; block bodies need `return`.

### ⭐ A lambda is not a function type

```java
Runnable r = () -> IO.println("hi");
Callable<String> c = () -> "hi";
```

Both lambdas have the same shape — no parameters. They become **different types**,
decided entirely by the **target type** on the left:

```java
var x = () -> IO.println("hi");     // ❌ compile error: cannot infer type
```

There's nothing to infer *from*. Java has no `Function` type in the type system — only
**functional interfaces** (2.4), each with exactly one abstract method.

```java
// this lambda can BE any of these, depending on context
() -> "hello"

Supplier<String> s  = () -> "hello";
Callable<String> c  = () -> "hello";         // Callable.call() throws Exception
PrivilegedAction<String> p = () -> "hello";
```

> **The framing: a lambda is an *implementation* of an interface's single method,
> written compactly.** Everything about how Java handles them follows from that.

**Consequences you'll hit:**

```java
// you can't declare a "function of int to int" generically
int (int) f;                      // ❌ no such syntax

// you can't pass a lambda where no functional interface is expected
Object o = () -> "hi";            // ❌ Object isn't a functional interface
```

### Variable capture — the same rule as 2.9

```java
void f() {
    int x = 5;                          // effectively final (1.1)
    Runnable r = () -> IO.println(x);   // ✅

    int y = 5;
    y = 6;                              // reassigned
    Runnable r2 = () -> IO.println(y);  // ❌ must be final or effectively final
}
```

**Locals must be effectively final. Fields need not be:**

```java
class Counter {
    private int count;                          // a field
    void f() {
        Runnable r = () -> count++;             // ✅ fine — `this` is captured, not `count`
    }
}
```

**Why the rule exists:** the local's **value** is copied into the lambda at creation. If
the local changed afterwards, the copy and the original would disagree and there'd be no
sensible answer to which one you meant.

> JavaScript closures capture the **variable**, not the value — which is exactly why
> `var` in a loop is the classic JS bug. Java sidestepped it by refusing the case.

**The workaround when you genuinely need mutation:**

```java
// ❌
int count = 0;
items.forEach(i -> count++);

// ✅ mutate the contents of an effectively-final holder
var count = new AtomicInteger();
items.forEach(i -> count.incrementAndGet());

// ✅ better — don't mutate
long count = items.stream().filter(...).count();
```

### `this` inside a lambda

```java
public class Outer {
    private String name = "outer";

    void withLambda() {
        Runnable r = () -> IO.println(this.name);      // ✅ `this` = the Outer instance
    }

    void withAnonymous() {
        Runnable r = new Runnable() {
            public void run() {
                // IO.println(this.name);              // ❌ `this` = the anonymous object
                IO.println(Outer.this.name);           // ✅ must qualify
            }
        };
    }
}
```

**A lambda has no `this` of its own** — it's *lexically scoped*, like a JS arrow function.
An anonymous class creates a new object, so `this` shifts.

This is one of the genuine reasons lambdas are less confusing than anonymous classes (2.9).

## ⭐ What a lambda actually compiles to

**Not an anonymous class.** This surprises most people.

```java
// Lam.java
public class Lam {
    public static void main(String[] a) {
        Runnable r = () -> System.out.println("hi");
        r.run();
    }
}
```

```bash
javac Lam.java
ls *.class
# Lam.class          ← that's ALL. No Lam$1.class
```

Compare with an anonymous class, which **does** produce `Lam$1.class` (2.9).

**What's in the bytecode instead:**

```bash
javap -c -p Lam.class
```

```
public static void main(java.lang.String[]);
    0: invokedynamic #2,  0    // InvokeDynamic #0:run:()Ljava/lang/Runnable;
    ...

private static void lambda$main$0();     ← your lambda body, as a private static method
    0: getstatic     #4      // System.out
    3: ldc           #5      // "hi"
    5: invokevirtual #6      // println
```

Two pieces:
1. Your lambda body becomes a **private static method** (`lambda$main$0`).
2. The call site is an **`invokedynamic`** instruction.

**What `invokedynamic` does:** the first time that line executes, the JVM calls
`LambdaMetafactory.metafactory()`, which **generates a class at runtime** implementing
`Runnable` and delegating to `lambda$main$0`. That generated class is then cached — every
subsequent execution reuses it.

```
compile time:  invokedynamic + a private static method
first run:     LambdaMetafactory spins up an implementation class
later runs:    reuse the cached instance
```

### ⭐ Why that matters

| | Anonymous class | Lambda |
|---|---|---|
| Class files on disk | **One per lambda** | **Zero** |
| Class loading at startup | Each must be loaded and verified (8.2) | Generated lazily on first use |
| Stateless instance | New object each time | **Cached and reused** |
| Capturing instance | New object each time | New object each time |

**Practical effects:**

- **Faster startup, smaller jars** — a codebase with 5,000 lambdas ships 5,000 fewer class
  files than the anonymous-class equivalent.
- **Non-capturing lambdas are free after the first call.** `x -> x * 2` captures nothing,
  so one instance is reused forever. `x -> x * factor` captures `factor`, so a new
  instance is allocated each time the lambda expression is evaluated.
- **The strategy is not fixed.** Because the linkage is decided at runtime, a future JVM
  could change how lambdas are implemented without recompiling anything. That flexibility
  was a deliberate design goal.

> **Verify it yourself:** `javac` a file with a lambda and one with an anonymous class,
> then `ls *.class`. The missing `$1` is the whole story.

## ⭐ Lambdas and checked exceptions

The problem from 4.2, stated concretely.

```java
paths.stream()
     .map(p -> Files.readString(p))     // ❌ unhandled exception type IOException
     .toList();
```

**Why:** `Stream.map` takes a `Function<T,R>`, whose method is declared:

```java
R apply(T t);          // no throws clause
```

A lambda cannot throw a checked exception the interface didn't declare — and **none of the
JDK's functional interfaces declare any** (6.3).

### The wrapper idiom people use

```java
@FunctionalInterface
public interface ThrowingFunction<T, R> {
    R apply(T t) throws Exception;

    static <T, R> Function<T, R> unchecked(ThrowingFunction<T, R> f) {
        return t -> {
            try {
                return f.apply(t);
            } catch (Exception e) {
                throw new RuntimeException(e);       // or a domain exception (4.4)
            }
        };
    }
}
```

```java
import static ThrowingFunction.unchecked;

paths.stream()
     .map(unchecked(Files::readString))      // ✅
     .toList();
```

Libraries ship versions of this (Vavr's `CheckedFunction`, jOOL's `Unchecked`). It works,
but it's **tunnelling** (4.2) — you're converting a checked exception into an unchecked one
to get past the type system.

**The honest alternatives:**

```java
// (a) handle it inline — explicit, verbose
.map(p -> {
    try { return Files.readString(p); }
    catch (IOException e) { throw new UncheckedIOException(e); }
})

// (b) use a for loop — sometimes just better (6.5)
var contents = new ArrayList<String>();
for (Path p : paths) {
    contents.add(Files.readString(p));      // checked exception propagates normally
}
```

> **That the JDK shipped `UncheckedIOException` in Java 8 — specifically so streams could
> work — is the clearest evidence that checked exceptions and lambdas don't compose.**

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `var f = () -> ...` | No target type to infer. Compile error |
| Mutating a captured local | Must be effectively final |
| `this` in a lambda vs anonymous class | Lambda = enclosing instance; anonymous = the anonymous object |
| Expecting a `$1.class` per lambda | There isn't one — `invokedynamic` |
| Throwing a checked exception from a lambda | Not allowed unless the interface declares it |
| Lambdas are "just anonymous class sugar" | Different mechanism, different performance |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Anonymous class for a single-method interface | Lambda |
| A captured `int[] holder = {0}` to fake mutation | `AtomicInteger`, or restructure to avoid mutation |

---

## Recap

| Concept | One line |
|---|---|
| Not a function type | A lambda is an **instance of a functional interface**; the target type decides which |
| Capture | Locals must be **effectively final**; fields needn't be |
| `this` | The **enclosing** instance — unlike an anonymous class |
| Compiles to | **`invokedynamic` + a private static method.** No class file |
| Why that matters | Faster startup, no per-lambda class, non-capturing lambdas are cached |
| Checked exceptions | Don't compose. Wrap, handle inline, or use a loop |
