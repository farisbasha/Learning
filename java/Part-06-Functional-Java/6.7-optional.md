# 6.7 — Optional

> **What this is:** **Widely misused.** The design intent is much narrower than how people
> apply it. Brian Goetz (Java's language architect) said it plainly: `Optional` was added
> to give **library method return types** a way to say "there might not be an answer".
> That's it.

---

## Coming from JS/Python/Dart

| | Your languages | Java |
|---|---|---|
| Absence | `null` / `None` / `undefined` | `null`, **plus** `Optional` |
| Null safety in the type system | TS strict mode, Dart sound null safety | ❌ **none** |

**Java's `Optional` is not Kotlin's `String?` or Dart's nullable types.** Those are
enforced by the compiler everywhere. `Optional` is an ordinary object you opt into at one
specific place — a return type. Treating it as a general null-replacement is the root of
every misuse below.

---

## What it's for

```java
// ❌ the caller has no idea this can return null
User findById(String id);

// ❌ absence as an exception (4.2)
User findById(String id) throws UserNotFoundException;

// ✅ absence is in the signature, and the compiler makes you deal with it
Optional<User> findById(String id);
```

> **The test: is "not found" a *normal outcome* of this method?** If yes → `Optional`.
> If absence means something went wrong → throw (4.4).

---

## Creating

```java
Optional.of(value)              // ⚠️ throws NPE if value is null
Optional.ofNullable(maybeNull)  // ✅ empty if null — the one you usually want
Optional.empty()
```

`Optional.of` throwing on null is deliberate — it's an assertion that you *know* it isn't
null.

## Using it — the good methods

```java
Optional<User> user = repo.findById(id);

// transform
user.map(User::name)                          // Optional<String>
user.flatMap(u -> repo.findManager(u.id()))   // when the function returns an Optional
user.filter(u -> u.age() >= 18)               // Optional<User>, empty if the test fails

// unwrap
user.orElse(defaultUser)                      // eager — see the trap below
user.orElseGet(() -> expensiveDefault())      // lazy
user.orElseThrow()                            // Java 10 — NoSuchElementException
user.orElseThrow(() -> new NotFoundException(id))

// act
user.ifPresent(u -> IO.println(u.name()));
user.ifPresentOrElse(                         // Java 9
    u -> IO.println(u.name()),
    () -> IO.println("not found"));

// combine
user.or(() -> repo.findByEmail(email))        // Java 9 — fallback Optional
user.stream()                                 // Java 9 — 0 or 1 elements (6.5)
```

**Chaining is where it pays off:**

```java
// ❌ nested null checks
String city = null;
if (user != null) {
    var address = user.getAddress();
    if (address != null) {
        city = address.getCity();
    }
}
if (city == null) city = "Unknown";

// ✅
String city = repo.findById(id)
    .map(User::address)
    .map(Address::city)
    .orElse("Unknown");
```

`map` short-circuits — if anything in the chain is empty, the rest is skipped.

## ⭐ `orElse` versus `orElseGet` — the performance trap

```java
user.orElse(createExpensiveDefault())         // ⚠️ ALWAYS evaluates the argument
user.orElseGet(() -> createExpensiveDefault()) // ✅ only if empty
```

**`orElse` takes a value.** Java evaluates arguments before the call, so
`createExpensiveDefault()` **runs even when the Optional is present** and its result is
thrown away.

```java
Optional.of("found").orElse(expensiveCall());      // expensiveCall() RUNS
Optional.of("found").orElseGet(() -> expensiveCall());  // does NOT run
```

This is invisible in the code and can be genuinely costly:

```java
// ❌ hits the database on every call, even when the cache has the value
cache.get(key).orElse(database.load(key));

// ✅
cache.get(key).orElseGet(() -> database.load(key));
```

Same trap in:
```java
map.getOrDefault(k, expensive())       // ⚠️ eager (5.3)
map.computeIfAbsent(k, x -> expensive())  // ✅ lazy
```

> **Rule: `orElse` only for cheap constants (`""`, `0`, `List.of()`). `orElseGet` for
> anything that does work.**

## `get()` and why it was effectively deprecated

```java
user.get();          // ⚠️ throws NoSuchElementException if empty
```

`get()` is the whole point of `Optional`, defeated. It's `Optional`'s version of
dereferencing a null — the same crash, one layer removed.

Java 10 added **`orElseThrow()`** as a no-arg synonym, precisely so the name *says* it can
throw. `get()` is documented as discouraged (it wasn't formally deprecated only because
it would break too much code).

```java
user.get();            // ❌ reads like it's safe
user.orElseThrow();    // ✅ identical behaviour, honest name
```

## ⭐ The anti-patterns

### 1. `isPresent()` followed by `get()`

```java
// ❌ you've reinvented the null check, with more typing
if (user.isPresent()) {
    IO.println(user.get().name());
}

// ✅
user.ifPresent(u -> IO.println(u.name()));

// ✅ when you need a value out
String name = user.map(User::name).orElse("Unknown");
```

If your code has `isPresent()` and `get()` together, there is always a better method.

### 2. `Optional` fields

```java
// ❌
public class User {
    private Optional<String> nickname;    // never do this
}
```

Why not:
- **`Optional` isn't `Serializable`** — the class can't be serialised (see below).
- It's an extra object per field, for no benefit.
- The field can be `null` *and* empty — two ways to say nothing.

```java
// ✅ nullable field, Optional at the boundary
public class User {
    private String nickname;                             // may be null
    public Optional<String> nickname() {                 // the ACCESSOR returns Optional
        return Optional.ofNullable(nickname);
    }
}
```

### 3. `Optional` parameters

```java
// ❌ now the caller must wrap, and can pass null anyway
void createUser(String name, Optional<String> nickname);
createUser("a", Optional.empty());        // ugly
createUser("a", null);                    // 💥 still possible!

// ✅ overloads
void createUser(String name);
void createUser(String name, String nickname);

// ✅ or a builder / record with defaults (2.10)
```

### 4. `Optional` in collections

```java
// ❌ two ways to represent nothing
List<Optional<User>> users;
Map<String, Optional<User>> byId;

// ✅ just leave them out
List<User> users;                          // absent = not in the list
Map<String, User> byId;                    // absent = key not present
```

To drop empties from a stream (6.5):
```java
ids.stream()
   .map(repo::findById)          // Stream<Optional<User>>
   .flatMap(Optional::stream)    // Stream<User> — Java 9
   .toList();
```

### 5. `Optional<List<T>>`

```java
// ❌
Optional<List<Order>> findOrders(String id);

// ✅ an empty list already means "none" (4.4)
List<Order> findOrders(String id);
```

## ⭐ Why `Optional` is not `Serializable` — and what that tells you

```java
public final class Optional<T> { }     // note: no `implements Serializable`
```

This was **deliberate**, and it's the clearest statement of intent the designers made.

Serialisation is for things that get **stored** or **sent across a boundary** — fields of
persisted objects, DTOs on a wire. By refusing `Serializable`, the JDK team made
`Optional` unusable in exactly the places they didn't want it:

- ❌ a field of a serialisable class
- ❌ a DTO crossing a network boundary
- ❌ anything persisted

> **`Optional` is meant to live briefly, between a method returning it and the caller
> unwrapping it.** Not stored, not passed around, not put in a field. The missing
> interface enforces the design.

(Java serialisation is itself something you should avoid — 0.3, Part 10.5 — but the signal
here is about intent.)

## `OptionalInt` and friends

```java
OptionalInt, OptionalLong, OptionalDouble
```

Primitive versions, avoiding boxing (6.3). You get them from primitive streams (6.4):

```java
IntStream.range(1, 5).max();        // OptionalInt
IntStream.range(1, 5).average();    // OptionalDouble
list.stream().mapToInt(User::age).max();   // OptionalInt
```

⚠️ They have a **reduced API** — no `map`, no `filter`, no `flatMap`:

```java
OptionalInt o = IntStream.of(1,2,3).max();
o.getAsInt();       // note: getAsInt, not get
o.orElse(0);
o.ifPresent(...);
// o.map(...)       ❌ doesn't exist
```

To get the full API, box it:
```java
o.stream().boxed().findFirst();     // → Optional<Integer>
```

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `orElse(expensiveCall())` | **Always evaluates.** Use `orElseGet` |
| `isPresent()` + `get()` | There's always a better method |
| `Optional` field | Not serialisable; can be null *and* empty |
| `Optional` parameter | Use overloads |
| `Optional<List<T>>` | Return an empty list |
| `Optional.of(maybeNull)` | Throws. Use `ofNullable` |
| `optional == null` | An `Optional` should never be null. If it is, that's the bug |
| Thinking it's Kotlin's `?` | It's one object at one return type, not a type system |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `.get()` | `.orElseThrow()` |
| `if (o.isPresent()) o.get()` | `ifPresent` / `map().orElse()` |
| `Optional` as a field, parameter, or collection element | Nullable field + `Optional` accessor; overloads; leave it out |
| Returning `null` from a method that returns `Optional` | Never. Return `Optional.empty()` |

---

## Recap

| Concept | One line |
|---|---|
| **Intent** | A **return type** for "might legitimately find nothing" |
| Create | `ofNullable` usually; `of` asserts non-null |
| Chain | `map`, `flatMap`, `filter`, `or` — short-circuits on empty |
| Unwrap | `orElse` (cheap constants) / `orElseGet` (lazy) / `orElseThrow` |
| **`orElse` is eager** | Its argument runs even when present |
| `get()` | Discouraged. Use `orElseThrow()` |
| Not `Serializable` | **Deliberate** — it's not meant to be stored or sent |
| Never | Fields, parameters, collection elements, `Optional<List<T>>` |
