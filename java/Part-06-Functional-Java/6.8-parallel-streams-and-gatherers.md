# 6.8 — Parallel streams, and gatherers

> **What this is:** **One feature that is riskier than it looks**, and one that finally
> filled a real gap.

---

## Part 1 — Parallel streams

### What `parallelStream()` actually does

```java
list.parallelStream().filter(...).map(...).toList();
list.stream().parallel().filter(...).toList();     // same thing
```

It splits the source into chunks, processes them on multiple threads, and merges the
results.

**⭐ The critical fact: it uses the shared `ForkJoinPool.commonPool()`.**

```java
ForkJoinPool.commonPool().getParallelism();     // = availableProcessors() - 1
```

**One pool, shared by the entire JVM.** Every parallel stream in your application — and in
every library you depend on — uses the same threads.

### ⭐ Why that shared pool is a hazard in a server

```java
// in one request handler
hugeList.parallelStream()
        .map(item -> slowRemoteCall(item))    // 2 seconds each, blocking
        .toList();
```

On an 8-core machine the common pool has **7 threads**. This one request occupies all of
them for the duration. Meanwhile:

- Every other request's parallel stream **queues behind it**
- Any library using the common pool stalls
- `CompletableFuture` without an explicit executor (9.9) also uses this pool — so that
  stalls too

**One slow parallel stream stalls everything else in the JVM.**

> **The rule: never do blocking I/O in a parallel stream.** Parallel streams are for
> **CPU-bound** work on data already in memory.

**The workaround if you must** — run it in your own pool:

```java
var pool = new ForkJoinPool(4);
try {
    var result = pool.submit(() -> list.parallelStream().map(...).toList()).get();
} finally {
    pool.shutdown();
}
```

This works because a parallel stream started *inside* a `ForkJoinPool` task uses that
pool. It's a well-known hack rather than a designed API — which tells you something.

> Since Java 21, **virtual threads** (9.11) are the right answer for concurrent blocking
> I/O, not parallel streams. Full treatment in Part 09.

### ⭐ When parallelism genuinely helps

All four must hold:

| Condition | Why |
|---|---|
| **Large data** | Roughly ≥10,000 elements. Below that, splitting costs more than it saves |
| **CPU-bound work** | Per-element work must be substantial. `x -> x * 2` is not |
| **Cheap splitting** | See `Spliterator` below |
| **No shared mutable state** | Otherwise it's a race condition (Part 09) |

**The "N × Q" heuristic:** parallelism pays when *N* (element count) × *Q* (cost per
element) is large. A million cheap operations often loses to sequential, because the
overhead is per-chunk, not per-element.

```java
// ❌ pointless — trivial work, overhead dominates
IntStream.range(0, 1000).parallel().map(x -> x * 2).sum();

// ✅ plausible — real CPU work on lots of data
images.parallelStream().map(this::applyFilter).toList();
```

> **Measure it.** Parallel streams making code slower is the common outcome, not the rare
> one.

### `Spliterator` and why splitting characteristics matter

A `Spliterator` is the "splittable iterator" underneath every stream. Its job is
`trySplit()` — hand back half the elements.

| Source | Splits |
|---|---|
| `ArrayList`, arrays, `IntStream.range` | ✅ **Perfectly** — just divide the index range, O(1) |
| `HashMap`, `HashSet` | ✅ Well — split the bucket array |
| `LinkedList` | ❌ **Badly** — must traverse to find the midpoint |
| `Files.lines`, `Stream.iterate` | ❌ **Very badly** — inherently sequential |

```java
// ✅ splits in O(1)
arrayList.parallelStream()

// ❌ splitting requires walking the list — parallelism can be slower than sequential
linkedList.parallelStream()

// ❌ can't know the size or split ahead
Stream.iterate(1, x -> x + 1).parallel()
```

> **Another reason `ArrayList` beats `LinkedList`** (5.2) — contiguous storage splits for
> free.

`Spliterator` also reports **characteristics** (`SIZED`, `ORDERED`, `DISTINCT`, `SORTED`)
that let the JDK optimise. A `SIZED` source lets `toList()` pre-allocate exactly; that's
why `count()` on a sized source can skip the pipeline entirely (6.5's `peek` trap).

### Ordering and `forEachOrdered`

```java
list.parallelStream().forEach(IO::println);         // ⚠️ arbitrary order
list.parallelStream().forEachOrdered(IO::println);  // ✅ encounter order — but slower
```

**Encounter order costs performance in parallel** — the JDK must buffer results to reassemble
them. Operations that preserve it (`findFirst`, `limit`, `skip`, `forEachOrdered`,
`toList`) all pay for it.

```java
.findFirst()     // must find the FIRST — expensive in parallel
.findAny()       // any match will do — much cheaper in parallel
```

If order doesn't matter, say so:

```java
.unordered()     // explicitly drop the ordering constraint
```

> **`toSet()` and `groupingByConcurrent()` are unordered by nature**, so they parallelise
> better than `toList()`.

### ⚠️ Shared mutable state

```java
// ❌ race condition — corrupts or throws
var results = new ArrayList<String>();
list.parallelStream().forEach(results::add);

// ✅
var results = list.parallelStream().toList();
```

And from 6.5 — the accumulator must be **associative**:

```java
list.parallelStream().reduce(0, (a,b) -> a - b);     // 💥 wrong answer
```

## Part 2 — Stream gatherers `Java 24`

> **Custom intermediate operations at last.**

### The gap they fill

Until Java 24, you could write your own **terminal** operation (a `Collector`, 6.6) but
**not** your own intermediate one. The fixed set was `filter`, `map`, `flatMap`, `distinct`,
`sorted`, `limit`, `skip`, `takeWhile`, `dropWhile` — and if you needed anything else, you
dropped out of the stream entirely.

Things that were awkward or impossible:

- **Windowing** — process elements in groups of 3
- **Running totals** — each element plus everything before it
- **Deduplicate by a key** — `distinct()` only works on whole-element equality
- **Fold with a different type** — like `reduce` but as an intermediate step

```java
// ❌ before gatherers — drop out of the stream, write a loop, come back
```

### The built-in gatherers

```java
import java.util.stream.Gatherers;

// fixed-size windows
Stream.of(1,2,3,4,5,6,7)
      .gather(Gatherers.windowFixed(3))
      .toList();
// [[1,2,3], [4,5,6], [7]]

// sliding windows
Stream.of(1,2,3,4,5)
      .gather(Gatherers.windowSliding(2))
      .toList();
// [[1,2], [2,3], [3,4], [4,5]]

// fold — like reduce, but intermediate, and can change type
Stream.of("a","b","c")
      .gather(Gatherers.fold(() -> "", (acc, s) -> acc + s))
      .toList();
// ["abc"]

// scan — running accumulation, emits every step
Stream.of(1,2,3,4)
      .gather(Gatherers.scan(() -> 0, Integer::sum))
      .toList();
// [1, 3, 6, 10]   ← running total

// mapConcurrent — bounded concurrency using VIRTUAL THREADS (9.11)
urls.stream()
    .gather(Gatherers.mapConcurrent(10, this::fetch))
    .toList();
```

### ⭐ `mapConcurrent` is the one to notice

```java
// ❌ the old way — blocking I/O on the shared common pool. The hazard from Part 1.
urls.parallelStream().map(this::fetch).toList();

// ✅ bounded concurrency on virtual threads — no shared pool, no starvation
urls.stream().gather(Gatherers.mapConcurrent(10, this::fetch)).toList();
```

`mapConcurrent` runs each element on a **virtual thread**, with a concurrency limit you
specify, and **preserves encounter order**. It's the answer to "I want to do 100 HTTP
calls concurrently" — which is what people were wrongly using `parallelStream()` for.

> **This is the single most practically useful thing in Java 24 for ordinary code**, and
> it retroactively makes "never use parallel streams for I/O" an easy rule to follow —
> because now there's a right way to do it.

### Writing your own

```java
// deduplicate by a key — distinct() can't do this
static <T, K> Gatherer<T, ?, T> distinctBy(Function<T, K> keyFn) {
    return Gatherer.ofSequential(
        HashSet::new,                              // initialiser (state)
        (seen, element, downstream) -> {           // integrator
            if (((Set<K>) seen).add(keyFn.apply(element))) {
                return downstream.push(element);   // false → stop the stream
            }
            return true;                           // continue
        }
    );
}

users.stream().gather(distinctBy(User::email)).toList();
```

A `Gatherer` has four parts, mirroring `Collector` (6.6):

| Part | Does |
|---|---|
| **initialiser** | Creates private state (optional — stateless gatherers skip it) |
| **integrator** | Handles one element; pushes 0..n downstream; returns `false` to short-circuit |
| **combiner** | Merges state for parallel (optional — omit for sequential-only) |
| **finisher** | Emits anything buffered at the end (optional) |

> `Gatherers` is to intermediate operations what `Collectors` is to terminal ones.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Blocking I/O in `parallelStream()` | Stalls the **entire JVM's** common pool |
| `parallelStream()` on small data | Overhead exceeds the benefit |
| `linkedList.parallelStream()` | Splits badly. Use `ArrayList` |
| `forEach(list::add)` in parallel | Race condition |
| Non-associative `reduce` in parallel | Wrong answer |
| Assuming parallel is faster | Usually it isn't. **Measure** |
| `findFirst` in parallel | Expensive. Use `findAny` if order doesn't matter |

## Recap

### Parallel streams

| Point | |
|---|---|
| Uses | The **shared** `ForkJoinPool.commonPool()` — one per JVM |
| Hazard | One slow parallel stream stalls every other user of that pool |
| Needs | Large data + CPU-bound + cheap splitting + no shared state |
| Splits well | `ArrayList`, arrays, ranges, `HashMap` |
| Splits badly | `LinkedList`, `Files.lines`, `Stream.iterate` |
| For blocking I/O | **Never.** Use virtual threads or `mapConcurrent` |

### Gatherers `Java 24`

| Gatherer | Does |
|---|---|
| `windowFixed(n)` | Non-overlapping groups |
| `windowSliding(n)` | Overlapping windows |
| `fold` | Reduce as an intermediate step, can change type |
| `scan` | Running accumulation, emits each step |
| **`mapConcurrent(n, fn)`** | **Bounded concurrency on virtual threads.** The right tool for concurrent I/O |
