# 6.3 — The functional interface catalogue

> **What this is:** **A vocabulary to memorise**, because every stream and every callback
> API uses these names. There's no deep idea here — it's learning the words.

---

## Coming from JS/Python/Dart

You've never had to name these. In JS a function is a function. Java needs a **named
interface** for every shape (6.1), so the JDK ships a catalogue in `java.util.function`.

Once you know the six core names, most stream signatures become readable at a glance.

---

## ⭐ The core six

| Interface | Method | Takes | Returns | Means |
|---|---|---|---|---|
| `Function<T,R>` | `apply` | T | R | **Transform** |
| `Supplier<T>` | `get` | — | T | **Produce** |
| `Consumer<T>` | `accept` | T | — | **Consume** |
| `Predicate<T>` | `test` | T | `boolean` | **Test** |
| `UnaryOperator<T>` | `apply` | T | T | Transform, same type |
| `BinaryOperator<T>` | `apply` | T, T | T | Combine two of the same type |

```java
Function<String,Integer>  length   = String::length;         // T → R
Supplier<String>          maker    = () -> "hi";             // → T
Consumer<String>          printer  = IO::println;            // T →
Predicate<String>         isEmpty  = String::isEmpty;        // T → boolean
UnaryOperator<String>     upper    = String::toUpperCase;    // T → T
BinaryOperator<Integer>   sum      = Integer::sum;           // (T,T) → T
```

**The mnemonic:** *Function transforms, Supplier produces, Consumer consumes, Predicate
tests.* The last two are just `Function` specialisations:

```java
UnaryOperator<T>  extends Function<T,T>
BinaryOperator<T> extends BiFunction<T,T,T>
```

### Where you meet each one

```java
stream.map(Function)              // transform each element
stream.filter(Predicate)          // keep matching elements
stream.forEach(Consumer)          // do something with each
stream.reduce(BinaryOperator)     // combine pairwise
list.replaceAll(UnaryOperator)    // transform in place
Optional.orElseGet(Supplier)      // produce a fallback lazily (6.7)
map.computeIfAbsent(k, Function)  // produce a value from the key (5.3)
```

## The two-argument forms

| Interface | Method | Shape |
|---|---|---|
| `BiFunction<T,U,R>` | `apply` | (T, U) → R |
| `BiConsumer<T,U>` | `accept` | (T, U) → |
| `BiPredicate<T,U>` | `test` | (T, U) → boolean |

```java
map.forEach((k, v) -> ...)              // BiConsumer
map.merge(k, 1, Integer::sum)           // BiFunction (as BinaryOperator)
map.replaceAll((k, v) -> v * 2)         // BiFunction
```

> There is no `BiSupplier` — a supplier takes nothing, so there's nothing to have two of.
> And nothing beyond two arguments: if you need three, write your own interface.

## ⭐ Default methods for composition

Every one of these has default methods (2.4) for combining them. **This is what makes them
worth using instead of ad-hoc interfaces.**

```java
// Function
Function<Integer,Integer> doubler = x -> x * 2;
Function<Integer,Integer> inc     = x -> x + 1;

doubler.andThen(inc).apply(5);      // 11  — double FIRST, then increment
doubler.compose(inc).apply(5);      // 12  — increment FIRST, then double
Function.identity();                 // x -> x
```

> `andThen` = left to right. `compose` = right to left (maths convention, `f∘g`).
> When in doubt, use `andThen` — it reads in execution order.

```java
// Predicate
Predicate<String> notEmpty = s -> !s.isEmpty();
Predicate<String> isShort  = s -> s.length() < 10;

notEmpty.and(isShort)
notEmpty.or(isShort)
notEmpty.negate()
Predicate.not(String::isEmpty)          // Java 11 — static, works with method refs
Predicate.isEqual("target")
```

`Predicate.not(...)` `Java 11` is worth knowing — before it, negating a method reference
meant writing a lambda:

```java
.filter(s -> !s.isEmpty())              // pre-11
.filter(Predicate.not(String::isEmpty)) // ✅ Java 11
```

```java
// Consumer
Consumer<String> log   = s -> log.info(s);
Consumer<String> print = IO::println;
log.andThen(print).accept("hi");        // both run, in order
```

```java
// Comparator (5.5) — also a functional interface
comparing(User::name).thenComparing(User::age).reversed()
```

## ⭐ The primitive specialisations, and the boxing cost they avoid

```java
Function<Integer,Integer> f = x -> x * 2;
```

Every call **boxes** the input and **unboxes** the output (1.1) — allocating an `Integer`
object per element. For a million elements, that's a million allocations and a lot of GC
pressure (5.8).

So the JDK ships primitive versions:

| Generic | Primitive versions |
|---|---|
| `Function<T,R>` | `IntFunction<R>`, `IntToLongFunction`, `ToIntFunction<T>`, `IntUnaryOperator`… |
| `Supplier<T>` | `IntSupplier`, `LongSupplier`, `DoubleSupplier`, `BooleanSupplier` |
| `Consumer<T>` | `IntConsumer`, `LongConsumer`, `DoubleConsumer` |
| `Predicate<T>` | `IntPredicate`, `LongPredicate`, `DoublePredicate` |
| `BinaryOperator<T>` | `IntBinaryOperator`, `LongBinaryOperator`… |

**Reading the names** — this is the useful skill:

| Name | Means |
|---|---|
| `IntFunction<R>` | **int** in, R out |
| `ToIntFunction<T>` | T in, **int** out |
| `IntToLongFunction` | **int** in, **long** out |
| `IntUnaryOperator` | **int** in, **int** out |
| `IntBinaryOperator` | (**int**, **int**) in, **int** out |

The prefix describes the **input**; `To*` describes the **output**.

```java
IntUnaryOperator doubler = x -> x * 2;           // no boxing at all
ToIntFunction<String> length = String::length;   // object in, primitive out

IntStream.range(0, 1_000_000).map(doubler).sum();      // ✅ zero boxing
Stream.iterate(0, x -> x+1).limit(1_000_000)
      .map(x -> x*2).mapToInt(i->i).sum();             // ❌ a million Integers
```

> **Practical rule: use `IntStream`/`LongStream`/`DoubleStream` (6.4) for numeric work.**
> They use these interfaces automatically, and you never have to name them.

There's no `ByteFunction`, `ShortPredicate` etc. — only `int`, `long`, `double`. Byte and
short widen to int; float widens to double.

## Older interfaces that are functional by accident

These predate Java 8 but happen to have one abstract method, so they were retrofitted:

```java
Runnable      r = () -> IO.println("hi");           // () ->
Callable<T>   c = () -> compute();                  // () -> T, THROWS Exception
Comparator<T> cmp = (a,b) -> ...;                   // (T,T) -> int
```

| | Like | But |
|---|---|---|
| `Runnable` | `Consumer` with no arg | Used by threads (Part 09) |
| `Callable<T>` | `Supplier<T>` | **Declares `throws Exception`** |
| `Comparator<T>` | `BiFunction<T,T,Integer>` | Has the whole comparator toolkit (5.5) |

> **`Callable` is the one exception** to "no JDK functional interface declares a checked
> exception" (6.1, 4.2). That's why `ExecutorService.submit(Callable)` lets you throw
> and `stream.map(Function)` doesn't.

Also functional: `AutoCloseable` (4.3), `Iterable` (5.6), `ActionListener`, `Flow.Subscriber`
methods.

## Writing your own, and when a named interface beats a generic one

```java
@FunctionalInterface
public interface Validator {
    ValidationResult validate(User user);

    default Validator and(Validator other) {
        return user -> {
            var result = validate(user);
            return result.isValid() ? other.validate(user) : result;
        };
    }
}
```

**When your own beats `Function<User, ValidationResult>`:**

| Reason | Why |
|---|---|
| **The name documents intent** | `Validator` says more than `Function<User,ValidationResult>` |
| **Domain-specific defaults** | The `and` above short-circuits on failure — `Function.andThen` can't |
| **More than 2 parameters** | The JDK stops at `Bi*` |
| **You need a checked exception** | Declare it on your own interface (6.1) |
| **The signature repeats everywhere** | `Function<Order, Map<String, List<Item>>>` is unreadable |

**When the generic one is fine:** a one-off transformation, an internal helper, anything
where the shape *is* the meaning.

> Use `@FunctionalInterface` — it's optional, but it makes the compiler reject the
> interface if someone adds a second abstract method (2.4).

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `Function<Integer,Integer>` for numeric work | Boxes on every call. Use `IntUnaryOperator`/`IntStream` |
| `andThen` vs `compose` | `andThen` = left-to-right; `compose` = right-to-left |
| Expecting a checked exception | Only `Callable` declares one |
| `ToIntFunction` vs `IntFunction` | `To*` = int **output**; prefix = int **input** |
| Writing `TriFunction` | There isn't one. Write your own, or use a record parameter |

## Recap

| Group | Names |
|---|---|
| **Core six** | `Function`, `Supplier`, `Consumer`, `Predicate`, `UnaryOperator`, `BinaryOperator` |
| **Two-arg** | `BiFunction`, `BiConsumer`, `BiPredicate` |
| **Composition** | `andThen`, `compose`, `negate`, `and`, `or`, `identity`, `Predicate.not` |
| **Primitive** | Prefix = input type, `To*` = output type. Avoids boxing |
| **Accidental** | `Runnable`, `Callable` (throws!), `Comparator` |
| **Your own** | When the name, the defaults, or the arity justify it |
