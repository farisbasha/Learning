# 6.4 — Streams: the model

> **What this is:** **Understand the execution model before the method list**, or you will
> misuse streams confidently. This page has no method reference table — that's 6.5. This
> page is the mental model that makes 6.5 make sense.

---

## Coming from JS/Python/Dart

| | JS `.map().filter()` | Python generators | **Java Stream** |
|---|---|---|---|
| Lazy | ❌ eager, builds arrays | ✅ lazy | ✅ **lazy** |
| Reusable | ✅ | ❌ | ❌ **single-use** |
| Stores data | ✅ each step | ❌ | ❌ |

**If you're coming from JS, unlearn this:** `array.map().filter()` in JS builds a whole
intermediate array at each step. Java streams don't. That single difference changes how
they behave and when they're fast.

Python generators are the much closer match.

---

## ⭐ A stream is not a collection

Three properties, all of which surprise people:

### 1. No storage

```java
List<String> list = ...;
Stream<String> s = list.stream();
```

`s` holds **no elements**. It's a *description of a computation* over a source. Nothing
has been copied.

### 2. Single use

```java
Stream<String> s = list.stream();
s.forEach(IO::println);      // ✅
s.forEach(IO::println);      // 💥 IllegalStateException:
                             //    stream has already been operated upon or closed
```

A stream is consumed by its terminal operation. To traverse twice, create two streams.

### 3. Lazy

**Nothing runs until the terminal operation.**

```java
Stream<String> s = list.stream()
    .filter(x -> { IO.println("filtering " + x); return true; })
    .map(x -> { IO.println("mapping " + x); return x; });

IO.println("nothing printed yet!");      // ← this prints FIRST
s.toList();                              // ← NOW the filtering/mapping output appears
```

## ⭐ The three-part pipeline

```
SOURCE  →  zero or more INTERMEDIATE ops  →  exactly one TERMINAL op
```

```java
list.stream()                    // SOURCE
    .filter(u -> u.age() > 18)   // intermediate — returns a Stream, lazy
    .map(User::name)             // intermediate — returns a Stream, lazy
    .sorted()                    // intermediate — returns a Stream, lazy
    .toList();                   // TERMINAL — returns a List, RUNS EVERYTHING
```

| | Returns | Runs immediately? |
|---|---|---|
| **Intermediate** | A `Stream` | ❌ just records the step |
| **Terminal** | Anything else | ✅ **triggers the whole pipeline** |

> **How to tell them apart without memorising:** if it returns a `Stream`, it's
> intermediate. If it returns a `List`, `Optional`, `long`, `boolean` or `void`, it's
> terminal.

**A pipeline with no terminal operation does nothing at all:**

```java
list.stream().map(x -> { doSomethingImportant(x); return x; });   // ❌ never runs
```

Static analysis tools flag this. It's a real bug people ship.

## ⭐ Laziness — element by element, not stage by stage

**This is the single most important idea in Part 06.** It is invisible in the code and
completely changes the behaviour.

### What people assume

```
filter all 1,000,000  →  then map all of those  →  then take the first 2

  [two intermediate lists, all 1,000,000 elements processed twice]
```

### What actually happens

```java
list.stream()              // 1,000,000 elements
    .filter(this::keep)
    .map(this::transform)
    .limit(2)
    .toList();
```

```
              filter          map          limit(2)
  el 1    ──────►────────────►────────────►  kept — 1 of 2
  el 2    ──► dropped   (map never runs on it)
  el 3    ──────►────────────►────────────►  kept — 2 of 2
  el 4…   ──► pipeline STOPS. Elements 4 … 1,000,000 are never touched.
```

**Each element flows all the way through every stage before the next element starts.**

Three consequences:

**(a) Work is skipped entirely.** In the diagram, `map` ran twice, not a million times.

**(b) Infinite sources terminate:**

```java
Stream.iterate(1, x -> x + 1)     // INFINITE
      .filter(x -> x % 7 == 0)
      .limit(5)
      .toList();                   // [7, 14, 21, 28, 35] — terminates fine
```

If stages ran to completion, this would hang forever.

**(c) Side effects in `map` are unpredictable.** You cannot reason about *when* or *how
many times* your lambda runs. Which is why 6.5 says side effects in a pipeline are a
smell.

> **The rule to hold: a stream pulls one element through every stage before touching the
> next.**

### Short-circuiting operations

Operations that can stop early:

| Intermediate | Terminal |
|---|---|
| `limit(n)` | `findFirst`, `findAny` |
| `takeWhile(p)` `Java 9` | `anyMatch`, `allMatch`, `noneMatch` |

```java
bigList.stream().anyMatch(x -> x > 100);     // stops at the first match
```

`allMatch` and `noneMatch` short-circuit on the first **counter**example.

## Sources

```java
// from a collection
list.stream()
list.parallelStream()
set.stream()
map.entrySet().stream()

// from values
Stream.of("a", "b", "c")
Stream.empty()
Stream.ofNullable(maybeNull)              // Java 9 — 0 or 1 elements

// from an array
Arrays.stream(array)
Arrays.stream(array, 1, 3)                // a range

// generated — INFINITE unless limited
Stream.iterate(1, x -> x * 2)             // 1, 2, 4, 8, ...
Stream.iterate(1, x -> x < 100, x -> x*2) // Java 9 — with a built-in stop condition
Stream.generate(Math::random)             // infinite random doubles

// numeric ranges
IntStream.range(0, 10)                    // 0..9
IntStream.rangeClosed(1, 10)              // 1..10

// from I/O and text
Files.lines(path)                         // ⚠️ must be closed — see below
"a\nb\nc".lines()                         // Java 11
"abc".chars()                             // IntStream of code units
Pattern.compile(",").splitAsStream(csv)
new Random().ints(10, 0, 100)
```

> ⚠️ **`Files.lines()` holds a file handle.** It's the one stream you must close:
> ```java
> try (var lines = Files.lines(path)) {       // try-with-resources (4.3)
>     return lines.filter(...).toList();
> }
> ```
> Streams implement `AutoCloseable`, but only I/O-backed ones actually need it.

## ⭐ Primitive streams

```java
IntStream, LongStream, DoubleStream
```

**Why they exist:** `Stream<Integer>` boxes every element (1.1, 6.3). For numeric work
that's an allocation per element and a large memory multiplier (5.8).

```java
// ❌ boxes a million Integers
Stream.iterate(0, i -> i + 1).limit(1_000_000)
      .mapToObj(...)  // ...

// ✅ no boxing at all
IntStream.range(0, 1_000_000).sum();
```

**They have extra methods** the object stream doesn't:

```java
IntStream.range(1, 5).sum();        // 10
IntStream.range(1, 5).average();    // OptionalDouble[2.5]
IntStream.range(1, 5).max();        // OptionalInt[4]
IntStream.range(1, 5).summaryStatistics();
// IntSummaryStatistics{count=4, sum=10, min=1, average=2.5, max=4}
```

**Converting between them:**

```java
stream.mapToInt(String::length)         // Stream<String> → IntStream
stream.mapToObj(i -> "n" + i)           // IntStream → Stream<String>
intStream.boxed()                       // IntStream → Stream<Integer>
intStream.asLongStream()                // widen
```

> **Rule: the moment you're doing arithmetic, get into an `IntStream`/`LongStream`/
> `DoubleStream` and stay there.**

## ⭐ Stateless vs stateful operations

A distinction that explains why some pipelines are slow and some don't work on infinite
streams.

| **Stateless** | **Stateful** |
|---|---|
| `filter`, `map`, `flatMap`, `peek` | `sorted`, `distinct`, `limit`, `skip` |
| Each element handled independently | Needs to remember other elements |
| Streams freely | **Must buffer** |

```java
// sorted() CANNOT emit anything until it has seen EVERY element
list.stream().sorted().findFirst();       // reads the whole list first
```

**Why `sorted` and `distinct` must buffer:**

- **`sorted`** — the smallest element could be the last one in the source. It has to
  collect everything before it can emit the first output.
- **`distinct`** — it must remember every element seen so far (in a `HashSet`) to know
  whether the next one is a duplicate.

**Two consequences:**

**(1) They break the laziness benefit:**

```java
// ❌ sorts all 1,000,000 elements, then takes 2
list.stream().sorted().limit(2).toList();

// ✅ better for small n on large data
list.stream().collect(Collectors.toCollection(
    () -> new PriorityQueue<>(...)));      // or just sort a bounded structure
```

**(2) They hang on infinite streams:**

```java
Stream.iterate(1, x -> x + 1).sorted().limit(5);     // 💥 hangs forever
Stream.iterate(1, x -> x + 1).distinct().limit(5);   // ✅ works — distinct is bounded here
                                                      //    but memory grows unboundedly in general
```

> **`distinct` also relies on `equals`/`hashCode`** (2.5). A class with a broken
> `hashCode` will silently fail to deduplicate.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Reusing a stream | `IllegalStateException` |
| A pipeline with no terminal op | Does nothing. Silently |
| Assuming stage-by-stage execution | It's element-by-element |
| `sorted().limit(2)` on a huge list | Sorts everything first |
| `Stream<Integer>` for arithmetic | Boxes. Use `IntStream` |
| Not closing `Files.lines()` | Leaks a file handle |
| `sorted()` on an infinite stream | Hangs |

---

## Recap

| Concept | One line |
|---|---|
| Not a collection | **No storage, single use, lazy** |
| Pipeline | source → intermediates → **exactly one** terminal |
| Intermediate vs terminal | Returns a `Stream` vs returns anything else |
| **Laziness** | One element through **every** stage, then the next |
| Short-circuiting | `limit`, `takeWhile`, `findFirst`, `*Match` |
| Primitive streams | No boxing, plus `sum`/`average`/`summaryStatistics` |
| Stateful ops | `sorted`, `distinct`, `limit`, `skip` — must buffer |

3. A pipeline is `filter → map → limit(2)` over 1,000,000 elements where element 1 and 3 pass the filter. How many times does `map` run?
