# 6.6 — Collectors

> **What this is:** The deepest corner of the streams API, and **where most real work
> happens**. If you only learn one thing from Part 06 beyond laziness, learn `groupingBy`.

---

## Coming from JS/Python/Dart

`groupingBy` is Python's `itertools.groupby` (but without needing pre-sorted input) or
`collections.defaultdict(list)`. There's no JS equivalent — you'd write a `reduce` with an
object accumulator.

The Java version composes: collectors nest inside other collectors, which is what makes
the API deep.

---

## The simple ones

```java
import static java.util.stream.Collectors.*;

.collect(toList())              // mutable ArrayList (in practice) — prefer .toList() (5.7)
.collect(toSet())               // HashSet — no order guarantee
.collect(toCollection(TreeSet::new))    // any collection you choose
.collect(toUnmodifiableList())          // Java 10 — immutable, null-HOSTILE

.collect(joining())                     // "abc"
.collect(joining(", "))                 // "a, b, c"
.collect(joining(", ", "[", "]"))       // "[a, b, c]"

.collect(counting())                    // Long
```

### ⚠️ `toMap` and its duplicate-key exception

```java
Map<String,User> byId = users.stream()
    .collect(toMap(User::id, Function.identity()));
```

**If two elements produce the same key, it throws:**

```
java.lang.IllegalStateException: Duplicate key alice (attempted merging values ...)
```

This catches everyone once. **The fix is a merge function:**

```java
.collect(toMap(
    User::email,
    Function.identity(),
    (existing, replacement) -> existing        // keep the first
))

.collect(toMap(User::dept, User::salary, Integer::sum))   // or combine them
```

**And a fourth argument picks the map type:**

```java
.collect(toMap(User::id, u -> u, (a,b) -> a, LinkedHashMap::new))   // preserve order (5.3)
```

> ⚠️ **`toMap` throws on null *values*** (unlike `HashMap`, 5.3). If your value function
> can return null, use `groupingBy` or filter first.

## Statistics

```java
.collect(summingInt(User::age))          // int
.collect(averagingDouble(User::salary))  // Double
.collect(summarizingInt(User::age))
// IntSummaryStatistics{count=3, sum=90, min=25, average=30.0, max=35}

.collect(minBy(comparing(User::age)))    // Optional<User>
.collect(maxBy(comparing(User::age)))    // Optional<User>
```

> For pure numbers, a primitive stream is simpler (6.4):
> ```java
> users.stream().mapToInt(User::age).sum();
> users.stream().mapToInt(User::age).summaryStatistics();
> ```

## ⭐ `groupingBy` — the one that matters

### One level

```java
Map<String, List<User>> byDept = users.stream()
    .collect(groupingBy(User::department));

// { "eng": [alice, bob], "sales": [carol] }
```

That's the multimap you were building by hand with `computeIfAbsent` (5.3), in one line.

### With a downstream collector

The second argument says **what to do with each group** instead of collecting to a list:

```java
// count per group
Map<String, Long> countByDept = users.stream()
    .collect(groupingBy(User::department, counting()));
// { "eng": 2, "sales": 1 }

// names per group
Map<String, List<String>> namesByDept = users.stream()
    .collect(groupingBy(User::department, mapping(User::name, toList())));
// { "eng": ["alice","bob"], "sales": ["carol"] }

// average salary per group
Map<String, Double> avgByDept = users.stream()
    .collect(groupingBy(User::department, averagingDouble(User::salary)));

// a set instead of a list
Map<String, Set<String>> tagsByDept = users.stream()
    .collect(groupingBy(User::department, mapping(User::name, toSet())));

// highest earner per group
Map<String, Optional<User>> topByDept = users.stream()
    .collect(groupingBy(User::department, maxBy(comparing(User::salary))));
```

> **This is the key insight: the second argument is itself a collector.** Everything
> composes.

### Choosing the map type

```java
Map<String, List<User>> sorted = users.stream()
    .collect(groupingBy(User::department, TreeMap::new, toList()));   // sorted keys (5.3)
```

### Multi-level nesting

```java
Map<String, Map<String, List<User>>> byDeptThenCity = users.stream()
    .collect(groupingBy(User::department,
             groupingBy(User::city)));

// { "eng": { "london": [alice], "berlin": [bob] },
//   "sales": { "london": [carol] } }
```

```java
// three levels, ending in a count
Map<String, Map<String, Long>> counts = users.stream()
    .collect(groupingBy(User::department,
             groupingBy(User::city,
             counting())));
```

> ⚠️ Beyond two levels this gets unreadable fast. Consider grouping by a **record key**
> instead:
> ```java
> record DeptCity(String dept, String city) { }
> Map<DeptCity, List<User>> m = users.stream()
>     .collect(groupingBy(u -> new DeptCity(u.department(), u.city())));
> ```
> Records give you `equals`/`hashCode` free (2.6), so they're perfect map keys.

## `partitioningBy` — grouping into exactly two

```java
Map<Boolean, List<User>> byAdult = users.stream()
    .collect(partitioningBy(u -> u.age() >= 18));

byAdult.get(true);      // adults
byAdult.get(false);     // minors
```

**Differences from `groupingBy(p)` with a boolean key:**

| | `partitioningBy` | `groupingBy` |
|---|---|---|
| Keys present | **Always both `true` and `false`** | Only keys that occurred |
| Empty group | Empty list | **Missing key → `null`** |
| Backing map | Optimised 2-slot map | `HashMap` |

That first row is the reason to use it — `groupingBy` on data where nobody is a minor
gives you a map with no `false` key, and `get(false)` returns `null`.

Downstream collectors work the same way:

```java
.collect(partitioningBy(u -> u.age() >= 18, counting()));    // Map<Boolean, Long>
```

## The adapter collectors

These **wrap** another collector to change what reaches it:

```java
mapping(User::name, toList())           // transform before collecting
filtering(u -> u.active(), toList())    // Java 9 — filter WITHIN the group
flatMapping(u -> u.tags().stream(), toSet())   // Java 9 — flatten within the group
reducing(0, User::age, Integer::sum)    // reduce within the group
collectingAndThen(toList(), List::copyOf)      // post-process the result
```

### ⚠️ `filtering` vs filtering the stream

This is a real difference:

```java
// ❌ departments with no active users DISAPPEAR
users.stream()
     .filter(User::active)
     .collect(groupingBy(User::department));

// ✅ every department appears; inactive-only ones get an empty list
users.stream()
     .collect(groupingBy(User::department, filtering(User::active, toList())));
```

Filtering upstream removes elements before grouping, so their keys never appear.
`filtering` filters *within* each group, so the keys survive.

### `collectingAndThen` — the immutable-result idiom

```java
.collect(collectingAndThen(toList(), Collections::unmodifiableList))
.collect(groupingBy(User::dept, collectingAndThen(toList(), List::copyOf)))
```

Useful for making the *inner* collections of a grouping immutable (5.7).

## `teeing` — two collectors at once `Java 12`

```java
record Stats(long count, double average) { }

Stats stats = users.stream().collect(teeing(
    counting(),                          // collector 1
    averagingInt(User::age),             // collector 2
    Stats::new                           // merge the two results
));
```

**One pass, two results.** Before `teeing`, you'd either traverse twice or use
`summarizingInt`.

```java
// min and max in one pass
record Range(Optional<User> youngest, Optional<User> oldest) { }

var range = users.stream().collect(teeing(
    minBy(comparing(User::age)),
    maxBy(comparing(User::age)),
    Range::new
));
```

## ⭐ What a `Collector` actually is

Four (sometimes five) pieces:

```java
public interface Collector<T, A, R> {
    Supplier<A>          supplier();     // create an empty accumulator
    BiConsumer<A,T>      accumulator();  // fold one element into it
    BinaryOperator<A>    combiner();     // merge two accumulators (parallel only)
    Function<A,R>        finisher();     // convert accumulator → final result
    Set<Characteristics> characteristics();
}
```

| | `T` | `A` | `R` |
|---|---|---|---|
| Meaning | Element type | **A**ccumulator type | **R**esult type |
| For `toList()` | `String` | `ArrayList<String>` | `List<String>` |
| For `joining()` | `String` | `StringBuilder` | `String` |

### Writing one yourself, once

```java
Collector<String, StringBuilder, String> myJoining = Collector.of(
    StringBuilder::new,                              // supplier
    (sb, s) -> sb.append(s).append(", "),            // accumulator
    (a, b) -> a.append(b),                           // combiner
    sb -> sb.isEmpty() ? "" : sb.substring(0, sb.length() - 2)   // finisher
);

Stream.of("a","b","c").collect(myJoining);    // "a, b, c"
```

**Do this once**, to understand what `collect` does. Then use the built-ins forever —
there's almost always one that fits, or a composition that does.

> **The combiner is why `reduce` and `collect` differ** (6.5). `collect` does **mutable
> reduction** — it builds up a mutable container and merges containers in parallel.
> `reduce` produces a new immutable value at every step. That's why
> `reduce(new ArrayList<>(), ...)` is broken and `collect(toList())` isn't.

**Characteristics** (worth recognising):

| | Means |
|---|---|
| `CONCURRENT` | Accumulator is thread-safe; one shared container in parallel |
| `UNORDERED` | Result doesn't depend on encounter order |
| `IDENTITY_FINISH` | The finisher is a no-op — the JDK can skip it |

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `toMap` with duplicate keys | `IllegalStateException`. Pass a merge function |
| `toMap` with a null value | NPE |
| `filter` before `groupingBy` | Empty groups disappear. Use `filtering` |
| `groupingBy` with a boolean | Missing key if a branch is empty. Use `partitioningBy` |
| `collect(toList())` is guaranteed mutable | Documented as unspecified. Use `toCollection(ArrayList::new)` |
| Three-level `groupingBy` | Unreadable. Group by a record key |
| `reduce` for building a collection | Use `collect` — mutable reduction |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `collect(toList())` when you don't need mutability | `.toList()` (5.7) |
| Manual `computeIfAbsent` loop for grouping | `groupingBy` |
| Two passes for count + average | `teeing` or `summarizingInt` |

---

## Recap

| Collector | Does |
|---|---|
| `toList` / `toSet` / `toCollection` | Gather |
| `joining` | Concatenate strings |
| `toMap(k, v, merge, mapFactory)` | Build a map — **merge function avoids the throw** |
| **`groupingBy(key, downstream)`** | **The one that matters.** Composes arbitrarily |
| `partitioningBy` | Two groups; **both keys always present** |
| `mapping` / `filtering` / `flatMapping` | Adapt what reaches the downstream collector |
| `collectingAndThen` | Post-process |
| `teeing` | Two collectors, one pass |
| A `Collector` is | supplier + accumulator + combiner + finisher |
