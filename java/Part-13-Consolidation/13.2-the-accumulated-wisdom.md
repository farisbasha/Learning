# 13.2 — The accumulated wisdom

> **What this is:** Now that you know the mechanisms, **the advice books make sense rather
> than sounding like rules.**

---

## ⭐ *Effective Java* — Joshua Bloch

**The standard reference.** 90 numbered items, each a specific piece of advice with its
reasoning.

> ⭐ **Read it *after* this roadmap, not before.** Its items are answers to questions you
> now have. Read cold, "Item 17: Minimize mutability" is a rule to obey; read after 2.1,
> 2.10 and **9.3's `final` field guarantee**, it's an explanation of something you already
> understand.

**⚠️ It predates records and pattern matching.** The 3rd edition (2018) covers up to
Java 9. So:

| The book says | Now |
|---|---|
| Item 1: static factories over constructors | ✅ Still true (2.2) |
| Item 10–11: obey the `equals`/`hashCode` contract | ✅ True — **but use a record** (2.6) |
| Item 15–17: minimise mutability | ✅ **Records make this the default** |
| Item 2: a builder for many parameters | ✅ True (2.10) |
| Item 34–38: enums over int constants | ✅ Still excellent (2.7) |
| Item 49: validate parameters | ✅ — compact constructors (2.6) |
| Item 85: **avoid Java serialization** | ✅ ⭐ Even more true (10.5) |
| Items on the visitor pattern / type-safe dispatch | ⚠️ **Superseded by sealed + switch** (7.4) |

**The items that have aged best:** 10/11 (`equals`/`hashCode`), 17 (minimise mutability),
18 (composition over inheritance — the `CountingSet` example is in 2.3), 85–90
(serialization).

## ⭐ *Java Concurrency in Practice* — Brian Goetz et al.

**Old (2006) but still the clearest treatment of the memory model** that exists.

> Everything in 9.2 and 9.3 — atomicity, visibility, reordering, happens-before, safe
> publication — is explained here at book length, and better than anywhere else.

**⚠️ Supplement it heavily.** It predates:

| Missing | Covered in |
|---|---|
| **Virtual threads** | 9.11 — invalidates much of its thread-pool sizing advice (9.8) |
| `CompletableFuture` | 9.9 |
| Lambdas and parallel streams | 6.1, 6.8 |
| `LongAdder`, `StampedLock`, `VarHandle` | 9.6, 9.5 |
| Structured concurrency, scoped values | 9.12 |

> ⭐ **Read Part I (chapters 1–5) and chapter 16 (the memory model).** Those are timeless.
> Treat the executor and pool-sizing chapters as historical context, then read JEP 444
> (13.1) for where it went.

**Its `@GuardedBy` annotations** (9.12) came from this book and are still the standard way
to document which lock protects what.

## ⭐ The recurring principles

Every book, every style guide and every senior reviewer converges on these six. You've now
met each one mechanically:

| Principle | Why it's true — the mechanism |
|---|---|
| ⭐ **Minimise mutability** | `final` fields are **safely published with no synchronisation** (9.3); safe as hash keys (2.5); thread-safe for free |
| ⭐ **Favour composition over inheritance** | Inheritance **breaks encapsulation** — the fragile base class problem (2.3) |
| **Prefer interfaces** | Substitutability, testability (12.3); a monomorphic call site is **as fast as a direct call** (8.8) |
| ⭐ **Validate at boundaries** | Constructors and entry points, then **trust inside** (4.4, 2.10) |
| **Fail fast** | An NPE at construction naming the field beats one three hours later (4.1, 4.4) |
| ⭐ **Make illegal states unrepresentable** | Sealed + records means the compiler proves completeness (2.8, 7.4) |

> **None of these are style preferences.** Each has a concrete mechanism underneath it, and
> you can now name every one.

## ⭐ Idioms to recognise on sight

You'll meet these in any Java codebase. Each should be instantly readable now:

```java
// STATIC FACTORY (2.2) — named, can cache, can return a subtype
List.of(...)  Optional.of(...)  Integer.valueOf(...)  LocalDate.of(...)

// BUILDER (2.10) — many or optional parameters
Pizza.builder(12).cheese().pepperoni().build();

// DEFENSIVE COPY (2.10, 5.7) — in the constructor, and on the way out
record Team(String name, List<String> members) {
    Team { members = List.copyOf(members); }
}

// ⭐ HOLDER IDIOM (9.3, 8.2) — lazy, thread-safe, no locks, nothing to get wrong
private static class Holder { static final Expensive INSTANCE = new Expensive(); }

// ENUM SINGLETON (2.7) — the safest one: reflection- and serialization-proof
public enum Registry { INSTANCE; }

// NULL OBJECT — a do-nothing implementation instead of a null check
static final Logger NO_OP = new Logger() { public void log(String m) { } };

// TRY-WITH-RESOURCES (4.3) — and suppressed exceptions handled correctly
try (var r = open()) { ... }

// ⭐ THE MODERN IDIOM (7.4) — sealed + records + exhaustive switch
sealed interface Result permits Ok, Err { }
switch (result) { case Ok(var v) -> ...; case Err(var e) -> ...; }
```

## ⭐ Anti-patterns to name

**Naming them is the skill** — you can't argue against something you can't name.

### Anaemic domain model

```java
// ❌ a bag of getters and setters; all the logic lives in a "service"
class Order {
    private Status status;
    public Status getStatus() { return status; }
    public void setStatus(Status s) { status = s; }     // anyone can set anything
}
class OrderService {
    void ship(Order o) { o.setStatus(SHIPPED); }        // the invariants live... here? nowhere?
}
```

**Why it's wrong:** the object cannot protect its own invariants (2.1), so validation is
scattered across every service that touches it — and one missed call corrupts state.

```java
// ✅ behaviour with the data
class Order {
    private Status status;
    void ship(String tracking) {
        if (status != PAID) throw new IllegalStateException("cannot ship an unpaid order");
        this.status = SHIPPED;
    }
}
```

> ⚠️ **The honest caveat:** this is in genuine tension with **data-oriented programming**
> (7.4), where data is transparent and behaviour lives outside. Both are right — for
> different things. **Entities with lifecycle and invariants** want behaviour inside;
> **values and messages** (2.5's value semantics) want to be transparent records.

### The rest

| Anti-pattern | Shape | Fix |
|---|---|---|
| **Utility-class sprawl** | `StringUtils`, `DateUtils`, `CommonUtils` with 200 static methods | The behaviour belongs on a type (2.2) |
| ⭐ **Exception swallowing** | `catch (Exception e) { }` | **The worst thing in Part 04** (4.4) |
| **Premature abstraction** | An interface per class, one implementation each | YAGNI. Add it at the **second** implementation (2.10) |
| **The singleton habit** | Mutable global state everywhere | Inject it (2.2, 12.3) |
| **Stringly-typed** | `String status`, `Map<String,Object> config` | Enums, records, sealed types (2.7, 2.8) |
| **Primitive obsession** | `transfer(String from, String to, double amt)` | `AccountId`, `Money` (2.10, 11.2) |
| **God class** | 3,000 lines, 40 fields | Single responsibility (2.10) |
| **Log and throw** | Both, at every layer | ⭐ **One failure, six stack traces** (4.4) |

> ⭐ **The two with the highest real-world cost: exception swallowing and stringly-typed
> code.** The first makes failures invisible; the second makes the compiler useless.
