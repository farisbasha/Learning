## ⭐ Staying current

**Thirty minutes every six months is enough.**

| Source | What |
|---|---|
| ⭐ **Release notes** | Every March and September. Skim the JEP list |
| ⭐ **[inside.java](https://inside.java)** | The JDK team's own writing |
| **[openjdk.org/jeps/0](https://openjdk.org/jeps/0)** | The JEP index (13.1) |
| **Inside Java Newscast** | Video, ~15 min per release |
| `jdeprscan` / `jdeps` | ⭐ Run before every upgrade (12.1) |

> **The cadence that works:** when a new LTS lands (every two years — 21, 25, 27…), read
> its JEP list, run `jdeprscan --for-removal` against your codebase, and upgrade. Non-LTS
> releases are worth skimming for what's coming.
>
> **Java moves slowly enough that this is genuinely sufficient** — which is itself one of
> the language's better properties.

## ⭐ The frameworks this prepares you for

**And here is the payoff.** You'll now see the mechanism under each of them:

| Framework | |
|---|---|
| ⭐ **Spring / Spring Boot** | The industry default. Enormous, well-documented |
| **Quarkus** | Build-time DI (11.7), fast startup, native-first (8.10) |
| **Micronaut** | Compile-time DI, no runtime reflection |
| **Helidon Níma** | Built on virtual threads (9.11) from the ground up |

> ⭐ **You will now see reflection, annotations, classloading and proxies underneath all of
> them.**
>
> | The "magic" | Is actually |
> |---|---|
> | `@Autowired` / constructor injection | Reflection reading constructor parameter types (**11.6**) |
> | `@Transactional`, `@Cacheable` | A **dynamic proxy** wrapping your bean (11.6, 11.7) |
> | `@Component` scanning | Classpath scanning + `Class.forName` (8.2, 11.6) |
> | `@Entity` field population | `setAccessible(true)` on private fields (11.6) |
> | `--add-opens` in the build | Module encapsulation (11.10) |
> | Quarkus's fast startup | Doing at **build time** what Spring does at startup (11.7) |
> | Spring Boot 3.2's virtual thread support | `spring.threads.virtual.enabled=true` (9.11) |
>
> **Why `this.transactionalMethod()` silently does nothing** (11.6) is the kind of thing
> that costs other developers a day and will cost you thirty seconds.

**Start with Spring Boot.** It has the most material and the largest job market, and the
concepts transfer.

## Persistence

**In this order — the order matters:**

### 1. JDBC first

```java
try (var conn = dataSource.getConnection();                          // (4.3)
     var stmt = conn.prepareStatement("SELECT * FROM users WHERE id = ?")) {
    stmt.setString(1, id);                                           // ⭐ parameterised
    try (var rs = stmt.executeQuery()) {
        while (rs.next()) { ... }
    }
}
```

**Learn this before any ORM.** You need to know what SQL is actually being sent, what a
connection pool is, and why `PreparedStatement` (not string concatenation) is how you avoid
SQL injection.

### 2. Then JPA and Hibernate

Entities, the persistence context, lazy loading, the **N+1 query problem**, cascades,
transactions.

> ⚠️ **Most Hibernate pain is caused by not understanding what it generates.** If you
> learned JDBC first, you can turn on SQL logging and see immediately why a page does 400
> queries. If you didn't, it's magic that's mysteriously slow.

### 3. ⭐ Then question whether you want an ORM at all

| Option | |
|---|---|
| **jOOQ** | Type-safe SQL, generated from your schema. Excellent |
| **Spring Data JDBC** | Simpler than JPA, no persistence context |
| **MyBatis** | SQL you write, mapped to objects |
| ⭐ **Plain JDBC** | Genuinely fine for many services |

> **The honest position:** an ORM is a good fit for CRUD over a rich object graph, and a
> poor fit for reporting, bulk operations and anything performance-sensitive. Many teams
> arrive at "JPA for writes, SQL for reads."

## Other JVM languages, and what each fixes

| Language | Fixes | Cost |
|---|---|---|
| ⭐ **Kotlin** | **Null safety in the type system** (6.7, 12.5), data classes, coroutines, far less ceremony | Another toolchain; Android's default |
| **Scala** | A genuinely powerful type system, real functional programming | Steep; complexity is easy to reach |
| **Clojure** | Lisp, immutability by default (2.10), excellent concurrency | Dynamically typed; unfamiliar |
| **Groovy** | Scripting, dynamic, concise | Mostly seen in Gradle files (12.2) |

> ⭐ **Kotlin is worth a look specifically for what Java still lacks: null safety.** Much
> of what else it offered — records, sealed types, pattern matching, `var` — Java has now
> caught up on (2.6, 2.8, 7.4). The null-safety gap remains real, and 12.5's JSpecify +
> NullAway is Java's partial answer.

## The specialisations

| Field | Notes |
|---|---|
| **Android** | Kotlin-first now, but Java underneath. A different runtime (ART) and lifecycle |
| ⭐ **Big data** | **Spark, Flink, Kafka** — all JVM. Part 08 (GC, memory, 8.4–8.6) matters enormously here |
| ⭐ **Low-latency / HFT** | Where Parts 08 and 09 are the **whole job** — GC tuning, off-heap (11.9), false sharing (9.6), lock-free |
| **Desktop** | JavaFX; `jpackage` for distribution (8.10) |
| **Cloud-native** | Quarkus/Micronaut, native images (8.10), containers |

> ⭐ **Note how much of Part 08 pays off in the specialisations.** Object layout (8.4),
> collectors (8.6), JIT behaviour (8.8) and observability (8.9) are exactly the knowledge
> that separates people who can make a JVM service fast from people who can only make it
> work. The PDF's framing was right: *"Parts 8 and 9 are the ones almost nobody does, and
> the ones that change what you can do."*

## ⭐ Three things about the order — a reminder

From the roadmap's own closing notes, and worth re-reading now:

> **1. Don't skip Part 03.** Erasure looks like trivia and it is not — it explains a dozen
> rules that otherwise feel arbitrary, and it's the reason half the questions you'll ask
> about generics have the answer *"because the type isn't there any more."*

> **2. Don't start Part 09 early.** Concurrency is the one topic where **partial knowledge
> is worse than none**, because it produces code that looks right and passes tests. It
> needs Part 08 — you cannot reason about visibility without knowing there is a shared heap
> and per-thread stacks.

> **3. Don't treat 0.3 as optional.** Most Java material online is a decade old. The single
> highest-leverage skill early on is being able to tell whether what you're reading
> describes the language **as it is now**.

**And on the shape of it:**

| Parts | What to expect |
|---|---|
| **1–2** | Slow and familiar — you know these ideas, you're learning Java's spelling of them |
| **3–7** | Where Java stops being "a language like the others" and starts having a character |
| ⭐ **8–9** | **The ones almost nobody does, and the ones that change what you can do** |
| **10–13** | **Reference more than sequence.** Take them when a project demands them |
