# 1.5 — Methods and the call stack

> **What this is:** One idea in here causes more confusion than any other in Java —
> **pass-by-value** — and it is worth an hour on its own. Get this exactly right.

---

## Coming from JS/Python/Dart

All four languages actually behave **identically** here. The difference is that Java
has a precise vocabulary for it, and people misuse that vocabulary constantly.

If you've ever been surprised that mutating a list inside a Python function changes the
caller's list, but reassigning it doesn't — you already understand this. Java is the
same, it just names it.

---

## The concepts

### Signatures

```java
public static int add(int a, int b) {
    return a + b;
}
//     ↑     ↑   ↑        ↑
//  modifier │  name   parameters
//      return type
```

The **signature** is the name + parameter types: `add(int, int)`. The return type is
*not* part of the signature — which is why you cannot have two methods differing only
by return type.

`void` means "returns nothing". You can still `return;` early from a `void` method.

---

## ⭐ Java is always pass-by-value

**Always. No exceptions. There is no pass-by-reference in Java.**

The confusion comes from this: when you pass an object, **the value being copied is the
reference** (the arrow), not the object.

### Case 1 — primitive

```java
static void change(int x) {
    x = 99;
}

int a = 5;
change(a);
IO.println(a);      // 5   ← unchanged
```

`x` is a *copy* of `a`'s value. Changing the copy does nothing.

### Case 2 — object, **mutating** it

```java
static void addItem(List<String> list) {
    list.add("new");        // follows the arrow, changes the object
}

List<String> mine = new ArrayList<>();
addItem(mine);
IO.println(mine);           // [new]   ← CHANGED
```

The parameter `list` is a *copy of the arrow*. But both arrows point at the **same
object**, so mutating through either one is visible to both.

### Case 3 — object, **reassigning** it

```java
static void replace(List<String> list) {
    list = new ArrayList<>();   // points the COPY at a new object
    list.add("new");
}

List<String> mine = new ArrayList<>();
replace(mine);
IO.println(mine);               // []   ← UNCHANGED
```

Reassigning the parameter just re-points the local copy. The caller's arrow is untouched.

### The picture

```
Before the call:
   mine ──────────────▶ [ ArrayList ]

Inside the method (both cases):
   mine ──────────────▶ [ ArrayList ]
   list ──────────────▶ (same object)

Case 2 — list.add("x"):
   mine ──────────────▶ [ ArrayList: "x" ]   ← caller sees it
   list ──────────────▶ (same object)

Case 3 — list = new ArrayList():
   mine ──────────────▶ [ ArrayList        ]  ← caller unaffected
   list ──────────────▶ [ new ArrayList    ]
```

> **The exact sentence:** *Java passes the value of the variable. For objects, that value
> is a reference. So you can change what the object contains, but you can never change
> which object the caller's variable points to.*

**Test yourself right now:**
```java
static void mystery(String s) { s = s + "!"; }
String name = "Basha";
mystery(name);
IO.println(name);       // ?
```
Answer: `Basha`. Strings are immutable, so `s + "!"` makes a new object and reassigns
the local copy. Case 3.

### Overloading

Same name, different parameter types.

```java
static int max(int a, int b) { ... }
static double max(double a, double b) { ... }
static String max(String a, String b) { ... }
```

The compiler picks at **compile time**, based on the *declared* types of the arguments.
(Contrast with overriding in 2.3, which resolves at runtime.)

**Resolution order** — the compiler tries, in this order:
1. Exact match, or widening (`int` → `long` → `float` → `double`)
2. Boxing / unboxing (`int` → `Integer`)
3. Varargs

**The boxed/primitive trap:**

```java
static void f(int x)     { IO.println("int"); }
static void f(Integer x) { IO.println("Integer"); }
static void f(Object x)  { IO.println("Object"); }

f(5);                       // "int"      — exact match wins
f(Integer.valueOf(5));      // "Integer"
f((Object) 5);              // "Object"
```

Now a real bug:

```java
List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
list.remove(1);           // removes INDEX 1 → removes 20
list.remove(Integer.valueOf(1));  // removes the VALUE 1 → nothing here
```

`List` has both `remove(int index)` and `remove(Object o)`. Overloading with boxed and
primitive types is a genuine trap — avoid designing APIs this way.

### Varargs

```java
static int sum(int... numbers) {      // numbers IS an int[]
    int total = 0;
    for (int n : numbers) total += n;
    return total;
}

sum();              // 0
sum(1, 2, 3);       // 6
sum(new int[]{1,2});// 3  — you can pass the array directly
```

Rules:
- Only **one** varargs parameter, and it must be **last**.
- It's genuinely an array underneath.

**Ambiguity problem:**
```java
static void f(String... s) { }
static void f(String a, String... s) { }
f("x");     // ❌ ambiguous — compile error
```

`@SafeVarargs` suppresses the "possible heap pollution" warning you get with generic
varargs (`<T> void f(T... items)`). It's a promise from you that you won't write into
the array. Full story in Part 03.

### Recursion, the call stack, and `StackOverflowError`

Every method call pushes a **stack frame** — holding parameters, local variables, and
where to return to. The stack has a fixed size (typically 512KB–1MB).

```java
static int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

factorial(5);        // fine
factorial(100_000);  // 💥 StackOverflowError
```

**Java has no tail-call optimisation.** A tail-recursive function still consumes a frame
per call. This is deliberate — the JVM preserves full stack traces for debugging and
security checks. So in Java, **deep recursion must be rewritten as a loop.**

```java
// iterative — constant stack
static long factorial(int n) {
    long result = 1;
    for (int i = 2; i <= n; i++) result *= i;
    return result;
}
```

### Reading a stack trace properly

```
Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "String.length()" because "name" is null
    at com.example.UserService.validate(UserService.java:42)     ← ① where it broke
    at com.example.UserService.save(UserService.java:28)
    at com.example.Main.main(Main.java:10)                        ← ② the entry point
Caused by: java.sql.SQLException: connection refused             ← ③ the REAL cause
    at ...
    ... 12 more
```

How to read it:

1. **Top frame is where it threw.** Line 1 of the trace = the deepest call.
2. **Read downwards to find your code.** Frames from `java.*` or a library are usually
   not where your bug is — scan down to the first `com.yourcompany.*` line.
3. **`Caused by:` is more important than the top.** When you see a chain, the *last*
   `Caused by:` is usually the root cause. Read bottom-up for causes, top-down for flow.
4. **`... 12 more`** means those frames are identical to the ones already printed above.

> **The habit:** don't read a stack trace top to bottom. Jump to the last `Caused by:`,
> then find the first line mentioning your own package.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "Objects are passed by reference" | No. The **reference** is passed **by value** |
| Reassigning a parameter to affect the caller | Never works |
| `list.remove(1)` on `List<Integer>` | Removes index 1, not value 1 |
| Expecting tail-call optimisation | Java has none. Use a loop |
| Reading only the top of a stack trace | The root cause is usually the last `Caused by:` |

---

## Recap

| Concept | One line |
|---|---|
| **Pass-by-value** | Always. For objects the *reference* is what's copied |
| Mutate vs reassign | Mutating is visible to the caller; reassigning is not |
| Overloading | Resolved at **compile** time by declared argument types |
| Varargs | Sugar for an array; must be last; only one |
| No TCO | Deep recursion → `StackOverflowError`. Rewrite as a loop |
| Stack traces | Root cause = last `Caused by:`; find your own package |
