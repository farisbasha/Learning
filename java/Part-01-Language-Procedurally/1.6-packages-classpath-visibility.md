# 1.6 — Packages, the classpath, and visibility

> **What this is:** How Java code is physically organised. **This is the layer that IDEs
> hide, and the layer that breaks.** When "it works in IntelliJ but not from the
> terminal", the answer is always on this page.

---

## Coming from JS/Python/Dart

| | Node | Java |
|---|---|---|
| Module identity | File path | **Package name**, which must match the directory |
| Resolution | `node_modules` walk | The **classpath** — a flat list you provide |
| Privacy | `export` or don't | Four access levels on every member |
| Bundle format | `package.json` + folder | A **JAR** (which is just a zip) |

The big mental shift: there is no `node_modules` auto-discovery. Java has **no idea**
where your dependencies are until you tell it, explicitly, every time.

## The concepts

### Packages and the directory rule

```java
// File: src/com/example/app/UserService.java
package com.example.app;

public class UserService { }
```

**The package declaration must match the directory structure.** `com.example.app` means
the file lives in `com/example/app/`. The compiler enforces this at runtime.

**Reverse-domain naming** — `com.yourcompany.project` — exists so that two libraries
can both have a `UserService` without colliding. It's the same reason npm has scopes.

A class with no `package` declaration is in the **default package**. Never do this in
real code — you can't import from it.

### Imports cost nothing at runtime

```java
import java.util.List;              // single class
import java.util.*;                 // wildcard — everything in java.util
import static java.lang.Math.PI;    // static import — use PI directly
import static java.lang.Math.*;     // now max(), abs(), etc. unqualified
```

> **Imports are purely a compile-time convenience.** They generate no code. An unused
> import costs literally nothing at runtime — it's a style issue, not a performance one.

Wildcard imports are fine, with one caveat: if two packages both have a `List`, you get
an ambiguity error and have to be explicit.

`java.lang.*` is imported automatically — that's why `String`, `Integer`, `Math` and
`System` just work.

### The classpath

The classpath is **the list of places the JVM looks for `.class` files.** That's it.

```bash
# compile, output to a directory
javac -d out src/com/example/app/*.java

# run — tell the JVM where the classes are
java -cp out com.example.app.Main

# multiple entries (: on mac/linux, ; on windows)
java -cp out:lib/gson.jar:lib/slf4j.jar com.example.app.Main

# a whole folder of jars
java -cp "out:lib/*" com.example.app.Main
```

Note you pass the **fully-qualified class name** (`com.example.app.Main`), not a path.

**What a JAR actually is:** a zip file with a `META-INF/MANIFEST.MF` inside. Prove it:

```bash
unzip -l myapp.jar
cat META-INF/MANIFEST.MF
```

The manifest can declare a `Main-Class`, which is what makes `java -jar myapp.jar` work.

> **This is the layer Maven and Gradle automate.** They download jars and build the
> `-cp` string for you. That is genuinely *most* of what a Java build tool does.

**When "works in the IDE, fails in terminal":** the IDE built a classpath you never saw.
Run your build tool's `dependency:build-classpath` (Maven) or
`printRuntimeClasspath` (Gradle) to see it.

### The four access levels

| Modifier | Same class | Same package | Subclass (other package) | Anywhere |
|---|:---:|:---:|:---:|:---:|
| `private` | ✅ | ❌ | ❌ | ❌ |
| *(none)* — **package-private** | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

```java
public class Account {
    private double balance;        // only this class
    double internalId;             // package-private — the DEFAULT
    protected String owner;        // package + subclasses
    public String accountNumber;   // everyone
}
```

> **The one people forget:** no modifier ≠ public. **No modifier = package-private.**
> In JS, no `export` means private. In Java, no modifier means "visible to the package",
> which is a genuinely different thing.

### Why package-private is underused and often the right answer

The reflex from tutorials is `public` on everything. But:

```java
// com/example/orders/OrderService.java
public class OrderService {                   // the API — public
    public Order place(Cart cart) { ... }

    PriceCalculator calculator() { ... }      // package-private — internal
}

// com/example/orders/PriceCalculator.java
class PriceCalculator { }                     // package-private class — invisible outside
```

Now `PriceCalculator` can be refactored, renamed or deleted freely. Nothing outside
`com.example.orders` can depend on it, because nothing outside can *see* it.

> **The rule:** put classes that collaborate in the same package, make the entry point
> `public`, and leave everything else package-private. You get real encapsulation at
> the *module* level, not just the class level.

`protected` is the one to be suspicious of — it's a promise to every future subclass,
forever. Use it sparingly (see 2.3).

### Fully-qualified names and collisions

```java
// Two Lists. You cannot import both.
import java.util.List;

java.awt.List awtList = new java.awt.List();   // qualify the other one
```

**`java.*` is protected.** You cannot create a package starting with `java.` — the
class loader rejects it. This stops someone shipping a fake `java.lang.String`.
(More in 8.2.)

## ⚠️ Traps

| Trap | Reality |
|---|---|
| No modifier means private | No — **package-private** |
| `java -cp out com/example/Main.class` | Wrong. It's `java -cp out com.example.Main` |
| Wildcard imports are slow | They cost nothing at runtime |
| Package doesn't match folder | Compiles from the IDE sometimes, fails at runtime |
| Default package | Can't be imported from anywhere. Never use it |
| `protected` as "a bit private" | It's a public API commitment to all subclasses |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| The default (unnamed) package | Always declare a package |
| `CLASSPATH` environment variable | Pass `-cp` explicitly, or let the build tool do it |

## Recap

| Concept | One line |
|---|---|
| Package | Must match the directory structure |
| Import | Compile-time only, zero runtime cost |
| Classpath | The list of places the JVM looks for classes |
| JAR | A zip with a manifest |
| 4 access levels | `private` < **package-private** < `protected` < `public` |
| Package-private | Underused, and usually the right default for internals |
