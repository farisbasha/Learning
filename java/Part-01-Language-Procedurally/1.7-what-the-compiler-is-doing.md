# 1.7 — What the compiler is actually doing

> **What this is:** A short step, placed here deliberately. Knowing **what `javac`
> checks** tells you which mistakes are possible at all — and therefore which bugs you
> can rule out before running anything.

---

## Coming from JS/Python/Dart

In Python and JS, almost everything is a runtime error. In TypeScript you already know
the feeling of a whole category of bug disappearing before you run. Java is that,
but the checks are baked into the language rather than bolted on.

---

## The concepts

### Compile time vs runtime — which mistakes are caught when

| Caught at **compile** time | Caught at **runtime** |
|---|---|
| Type mismatches | `NullPointerException` |
| Unknown method or field | `ArrayIndexOutOfBoundsException` |
| Wrong argument count/types | `ClassCastException` |
| Unhandled checked exceptions | `ArithmeticException` (divide by zero) |
| Using an unassigned local | `OutOfMemoryError` |
| Unreachable code | `StackOverflowError` |
| Missing `return` | Logic being wrong |
| Non-exhaustive switch *expression* | Anything involving actual data |

> **The useful framing:** the compiler checks *shape*. It never checks *values*.
> "Does this type have this method?" — yes. "Is this reference null?" — no.

### The flow analyses `javac` performs

These are genuinely useful and worth knowing by name.

**1. Definite assignment** — a local must be assigned before it's read.

```java
int x;
IO.println(x);      // ❌ variable x might not have been initialized
```

```java
int x;
if (cond) x = 1;
IO.println(x);      // ❌ still an error — not assigned on every path

int y;
if (cond) y = 1;
else y = 2;
IO.println(y);      // ✅ assigned on every path
```

> Note this applies to **locals only**. Fields get default values (1.4), which is
> exactly why a field can silently be `null` and a local cannot.

**2. Unreachable code**

```java
return x;
IO.println("hi");   // ❌ unreachable statement
```

```java
while (true) { }
IO.println("hi");   // ❌ unreachable
```

**3. Missing return**

```java
int f(boolean b) {
    if (b) return 1;
}                   // ❌ missing return statement
```

**4. Exhaustiveness** (switch expressions, 1.2) — if it produces a value, every case
must be covered.

### What a `.class` file is

One `.class` file = **one class**. It contains:

- The **constant pool** — every string literal, method name and type reference
- Field and method definitions
- **Bytecode** for each method
- Metadata: superclass, interfaces, annotations

**One source file can produce several `.class` files:**

```java
// Outer.java
public class Outer {
    static class Nested { }          // → Outer$Nested.class
    class Inner { }                  // → Outer$Inner.class
    void f() {
        Runnable r = new Runnable() { ... };   // → Outer$1.class
    }
}
```

```bash
javac Outer.java
ls
# Outer.class  Outer$Nested.class  Outer$Inner.class  Outer$1.class
```

The `$` naming is worth recognising — it shows up in stack traces constantly, and the
`$1` form tells you an anonymous class was involved (2.9).

### Looking at it yourself

```bash
javac Hello.java
javap Hello.class          # public signatures only
javap -p Hello.class       # include private members
javap -c Hello.class       # DISASSEMBLE — show the bytecode
```

```java
// Hello.java
void main() { IO.println(1 + 2); }
```

```bash
javap -c Hello.class
```

You'll see the compiler already folded `1 + 2` into `3`. That's **constant folding** —
one of the small optimisations `javac` does before the JVM ever sees the code.

> `javap -c` is how you answer "what does this actually compile to?" — and you'll use
> it in Part 03 (erasure), Part 06 (lambdas) and Part 08 (the JIT).

### Warnings worth turning on

```bash
javac -Xlint:all MyClass.java
```

| Warning | Means |
|---|---|
| `deprecation` | You're calling something scheduled for removal |
| `unchecked` | An unsafe generic operation — erasure is hiding something (Part 03) |
| `rawtypes` | You wrote `List` instead of `List<String>` |
| `fallthrough` | A `case` with no `break` |
| `serial` | A serializable class missing `serialVersionUID` |

`-Xlint:all -Werror` turns warnings into errors. Most serious projects do this.

### Reading a compiler error from the bottom up

`javac` reports errors in source order, but **the last error is often the only real one** —
earlier errors are frequently cascading consequences.

```
Foo.java:5: error: cannot find symbol
        Userr u = new User();
        ^
  symbol:   class Userr
Foo.java:6: error: cannot find symbol
        u.getName();
        ^
  symbol:   variable u
2 errors
```

There is **one** bug here (a typo on line 5). The second error exists only because `u`
never got declared. Fix the first, recompile, and both vanish.

> **The habit:** fix the *first* error, recompile, don't read the rest. With generics
> (Part 03), a single mistake can produce a dozen errors, and reading them all is wasted
> effort.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "It compiled, so it works" | The compiler checks shape, never values |
| Fixing all N errors at once | Fix the first, recompile — most are cascades |
| Expecting null-safety from the compiler | Java has none built in (unlike Kotlin) |
| One file = one class file | Nested and anonymous classes each get their own |

---

## Recap

| Concept | One line |
|---|---|
| Compile time | Types, shapes, definite assignment, reachability, exhaustiveness |
| Runtime | Nulls, indexes, casts, division, memory — anything about values |
| `.class` | One per class; `Outer$Inner`, `Outer$1` for nested and anonymous |
| `javap -c` | Shows what your code actually compiled to |
| `-Xlint:all` | Turn the warnings on; `unchecked` matters most |
| Errors | Fix the first one, recompile |

## Self-check

1. `int x; if (a) x = 1; IO.println(x);` — compile error or not? What about the same code with a field instead of a local?
2. You compile one `.java` file and get four `.class` files. What was in the source?
3. Why should you fix only the first compiler error before recompiling?
