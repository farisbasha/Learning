# 1.3 — Strings and text

> **What this is:** Strings are objects with special privileges, and their
> **immutability** drives design decisions all over the language.

---

## Coming from JS/Python/Dart

Strings are immutable in JS and Python too, so that part is familiar. What's new:

- Java has a **string pool** — identical literals are the *same object*, which makes
  `==` appear to work and then betray you.
- `+` in a loop is a real performance problem in a way it isn't in modern JS.
- No template literals. `Java 25` still has no string interpolation (string templates
  were previewed and then **removed**).

---

## The concepts

### Immutability — and what it buys

```java
String s = "hello";
s.toUpperCase();
IO.println(s);          // "hello"  ← unchanged! The method RETURNS a new string

s = s.toUpperCase();
IO.println(s);          // "HELLO"  ← now
```

Every `String` method returns a **new** `String`. The original never changes.

What immutability buys:
- **Safe sharing** — you can hand a `String` to any code without defensive copying.
- **Safe hash keys** — a `HashMap` key's hash can never change under it (see 2.5).
- **Thread safety** — free, no locking (Part 09).
- **The string pool** — only possible because strings can't change.

### The string pool and interning

Java keeps a pool of string literals. Identical literals point at the **same object**.

```java
String a = "hello";
String b = "hello";
String c = new String("hello");
String d = "hel" + "lo";                 // resolved at COMPILE time
String e = "hel" + someVariable;         // built at RUNTIME

a == b     // true   — both from the pool
a == c     // false  — new String() forces a new object
a == d     // true   — compiler folded it into a literal
a == e     // false  — built at runtime, not pooled
```

> This is exactly why `==` on strings is dangerous: it works in your small test and
> fails in production where the string came from a file or a request.
> **Always use `.equals()`.**

```java
a.equals(c)   // true — always
```

`.intern()` forces a string into the pool. You will almost never need it.

### Concatenation — what `+` compiles to

```java
String greeting = "Hello, " + name + "!";
```

Since `Java 9` this compiles to an `invokedynamic` call that the JVM optimises into a
single efficient buffer operation. Outside a loop, `+` is completely fine.

**Inside a loop it is terrible:**

```java
// ❌ builds a NEW string every iteration — O(n²)
String result = "";
for (String word : words) {
    result += word;      // allocates a whole new string each time
}

// ✅ one buffer, appended to
StringBuilder sb = new StringBuilder();
for (String word : words) {
    sb.append(word);
}
String result = sb.toString();
```

With 10,000 words the first version does ~50 million character copies. The second does 10,000.

### `StringBuilder` — and `StringBuffer` 💀

```java
StringBuilder sb = new StringBuilder();
sb.append("Hello").append(", ").append(name);
sb.insert(0, ">> ");
sb.reverse();
String out = sb.toString();
```

> `StringBuffer` is the same class with `synchronized` on every method. It exists for
> 1996 reasons. **Never use it.**

### The method surface worth knowing

```java
"  hi  ".strip()          // "hi"   ← Unicode-aware. Use this. (Java 11)
"  hi  ".trim()           // "hi"   ← only strips ASCII ≤ U+0020. Legacy.

"".isEmpty()              // true   — length is 0
"   ".isBlank()           // true   — only whitespace (Java 11)

"a,b,c".split(",")        // ["a", "b", "c"]
String.join("-", "a","b") // "a-b"

"a\nb".lines()            // a Stream of lines (Java 11)
"ab".repeat(3)            // "ababab" (Java 11)
"abc".chars()             // an IntStream of code units

"Hi %s".formatted("you")  // "Hi you" (Java 15) — instance version of String.format
```

Plus the obvious: `length()`, `charAt()`, `substring()`, `indexOf()`, `contains()`,
`startsWith()`, `replace()`, `toUpperCase()`, `equalsIgnoreCase()`.

> **`strip()` over `trim()`** — `trim()` predates Unicode awareness and misses things
> like non-breaking spaces.

### Text blocks `Java 15`

Multi-line literals, finally.

```java
String json = """
    {
        "name": "Basha",
        "role": "dev"
    }
    """;
```

**Incidental whitespace** is the clever part: Java finds the *least-indented* line
(including the closing `"""`) and strips that much from every line. So the indentation
in your source doesn't end up in the string.

```java
String sql = """
    SELECT *
    FROM users
    WHERE id = ?
    """;
// → "SELECT *\nFROM users\nWHERE id = ?\n"  — no leading spaces
```

Escapes specific to text blocks:
```java
String s = """
    no trailing \
    newline here""";     //  \  at end of line = join lines

String t = """
    keep trailing space   \s
    """;                  //  \s = an explicit space that survives stripping
```

### Formatting

```java
String.format("Name: %s, Age: %d, Score: %.2f", "Basha", 30, 95.5)
// "Name: Basha, Age: 30, Score: 95.50"

"Name: %s".formatted("Basha")     // Java 15 — same thing, nicer
```

Common format specifiers:

| Spec | Means |
|---|---|
| `%s` | Any object (calls `toString()`) |
| `%d` | Integer |
| `%f` / `%.2f` | Decimal / 2 decimal places |
| `%n` | Platform newline (prefer over `\n`) |
| `%%` | A literal `%` |
| `%-10s` | Left-align in 10 columns |

### Compact strings `Java 9`

Internally, if a `String` contains only Latin-1 characters, the JVM stores it as **one
byte per character** instead of two. Pure memory optimisation, invisible to you —
but it's why Java 9+ apps use noticeably less heap for text.

## 💀 Dead / never use

| Thing | Instead | Why |
|---|---|---|
| `StringBuffer` | `StringBuilder` | Pointless synchronisation |
| `+=` in a loop | `StringBuilder` | O(n²) |
| `==` on strings | `.equals()` | Compares identity, not content |
| `trim()` | `strip()` | Not Unicode-aware |
| **String templates** | — | Previewed in 21, **removed in 23**. Blog posts about `STR."..."` describe something that does not exist. |

---

## ⚠️ Traps

- **`==` sometimes appears to work.** The pool makes it true for literals. It will fail
  the moment the string comes from input.
- **`substring` is O(n) since Java 7.** It copies. (Before 7 it shared the array and
  caused memory leaks.)
- **`split` takes a regex, not a literal.** `"a.b".split(".")` returns an empty array,
  because `.` means "any character". Use `split("\\.")`.

---

## Recap

| Concept | One line |
|---|---|
| Immutable | Every method returns a new String |
| String pool | Literals are shared — why `==` lies |
| `+` in a loop | O(n²). Use `StringBuilder` |
| Text blocks | `"""` multi-line, strips incidental indentation |
| `strip` / `isBlank` / `lines` / `repeat` | Java 11 additions worth knowing |
