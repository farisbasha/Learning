# 8.5 — Garbage collection: the theory

> **What this is:** **Learn the ideas before the collector names**, or the tuning advice
> you read will be cargo cult. This page has no flags in it. 8.6 has the flags.

---

## ⭐ Reachability, not reference counting

**Java does not count references.** It asks a different question:

> **Can this object still be reached from a GC root?**

**GC roots** are the starting points:

- Local variables and parameters on every thread's **stack** (8.3)
- **Static** fields of loaded classes (2.2)
- JNI/FFM native references
- Live **threads** themselves
- Class objects of loaded classes (via their loader, 8.2)
- Objects held by the JVM internally (string pool entries, etc.)

The collector walks the object graph from the roots. **Anything not reached is garbage** —
by definition, because no code could ever refer to it again.

```
   [roots]
      │
      ▼
   A ──► B ──► C          reachable → live
                          
   D ◄──► E               ⚠️ they reference each other, but NOTHING reaches them
                              → both are garbage
```

> ⭐ **This is why Java has no cycle problem.** Python's reference counting needs a
> separate cycle detector; Java's `D ◄──► E` above is simply unreachable and collected.
> It's also why *reachability* is the only thing that matters — and why a "memory leak"
> in Java means **unintentional reachability** (below).

## ⭐ The weak generational hypothesis

> **Most objects die young.**

This is an empirical observation, and it's overwhelmingly true — the vast majority of
allocations are short-lived temporaries (a `StringBuilder` in a method, a stream's
intermediate objects, a DTO for one request).

A secondary observation: **few references point from old objects to young ones.**

**Every mainstream collector is built around this**, which is why the heap is split into
generations (8.3):

| Generation | Behaviour |
|---|---|
| **Young** | Most objects die here. Collect **often**, and it's **cheap** — because only the few survivors are touched |
| **Old** | Objects that proved long-lived. Collect **rarely**, and it's **expensive** |

**The key insight about young-generation cost:** a copying collector's work is proportional
to the **surviving** objects, not the dead ones. If 98% of eden is garbage, a minor GC
copies 2% and declares the rest free in one step. **Dead objects cost nothing to collect.**

---

## The algorithm families

| Family | How | Pro | Con |
|---|---|---|---|
| **Mark-sweep** | Mark reachable, free the rest in place | Simple; no copying | **Fragmentation** |
| **Mark-compact** | Mark, then slide survivors together | No fragmentation; fast allocation after | Slow — moves everything |
| **Copying** | Copy survivors to a fresh space; declare the old one empty | **Cost ∝ survivors**; compacts for free | Needs 2× the space |

**In practice collectors combine them:** copying for the young generation (few survivors,
so copying is cheap), mark-sweep or mark-compact for the old generation (many survivors,
so copying would be expensive).

That's exactly what eden/S0/S1 is (8.3) — a copying collector using survivor spaces
instead of a full second heap.

## Minor, major, full — and promotion

| Collection | Covers | Cost |
|---|---|---|
| **Minor** (young) | Eden + survivors | **Milliseconds** |
| **Major** (old) | Old generation | 100s of ms to seconds |
| **Full** | Everything, usually stop-the-world | Worst case |

**Promotion:** an object surviving enough minor GCs (tracked by the **age** in its mark
word, 8.4) is moved to the old generation.

### ⭐ Premature promotion — the pathology worth recognising

If the young generation is **too small**, objects that would have died get promoted
because there's no room for them.

```
young gen too small
   → survivor space fills
   → objects promoted early
   → old generation fills with short-lived garbage
   → frequent expensive major GCs
```

**Symptom:** frequent major GCs on an application that allocates a lot of short-lived
objects. **Fix:** a *larger* young generation — which is counterintuitive, because the
instinct is to give the old generation more room.

> This is the single best example of why you need the theory before the flags.

## ⭐ Safepoints

**A safepoint is a point in execution where a thread can be paused** — where the JVM knows
exactly what's in every register and stack slot, so it can walk the object graph.

The JVM inserts safepoint polls at:
- Method entry and exit
- **Loop back-edges** — but see below
- Allocation sites

To start a collection, the JVM requests a safepoint and **waits for every thread to
reach one**. That wait is called *time to safepoint*.

### ⭐ Why a counted loop can delay the entire JVM

**The JIT omits safepoint polls from "counted" loops** — loops with an `int` counter and
a known bound — because the poll costs more than the loop body and the loop is assumed
short.

```java
for (int i = 0; i < Integer.MAX_VALUE; i++) {
    // no safepoint poll inside this loop
}
```

**One thread in this loop blocks every other thread in the JVM**, because GC cannot start
until all threads reach a safepoint. Your application freezes and the GC log shows a
long pause the collector didn't cause.

**The fix:** use a `long` counter — the JIT keeps safepoint polls in those.

```java
for (long i = 0; i < Integer.MAX_VALUE; i++) { }    // ✅ polls preserved
```

```bash
-XX:+PrintSafepointStatistics                 # older JVMs
-Xlog:safepoint                                # unified logging
```

> Diagnostic signature: pause times in the GC log much larger than the reported GC work,
> with a high "time to safepoint".

## The three-way trade

You cannot have all three. **Every collector picks two:**

```
              THROUGHPUT
             (total work done)
                  ▲
                 ╱ ╲
                ╱   ╲
               ╱     ╲
      LATENCY ◄───────► FOOTPRINT
   (pause times)      (memory used)
```

| Want | Cost |
|---|---|
| **Throughput** | Longer pauses — batch everything into rare big collections |
| **Low latency** | More CPU and memory — do work concurrently with the application |
| **Small footprint** | More frequent collections, worse throughput |

**Stop-the-world** pauses freeze every application thread. **Concurrent phases** run
alongside the application — which costs CPU and needs headroom, because the application
keeps allocating while the collector works.

> This trade is the entire content of 8.6. Parallel picks throughput. ZGC picks latency.
> G1 picks a balance.

## ⭐ Allocation is a pointer bump

The most useful counterintuitive fact on this page.

**Allocating in Java is usually cheaper than `malloc`.**

Because a copying collector compacts eden, free space is always one contiguous block.
Allocation is:

```
1. read the "next free" pointer
2. add the object size
3. write it back
```

Two or three machine instructions.

**TLABs (Thread-Local Allocation Buffers)** remove even the synchronisation: each thread
gets its own chunk of eden and bump-allocates within it with **no locking at all**. Only
when a TLAB is exhausted does the thread take a slow path to claim another.

```bash
-XX:+PrintTLAB   (with -XX:+UnlockDiagnosticVMOptions)
```

**Combined with escape analysis** (8.3, 8.8), which can delete the allocation entirely:

> **"Don't allocate in a loop" is dated advice.** Short-lived objects are close to free —
> cheap to allocate (pointer bump), cheap to collect (dead objects cost nothing), and
> sometimes not allocated at all. Optimise allocation only when a profiler says so.

## ⭐ What a "memory leak" means in a garbage-collected language

You cannot leak by forgetting to free. **You leak by accidentally keeping a reference.**

> **A Java memory leak is unintentional reachability.**

The object is garbage in every sense that matters — your code will never use it again —
but something still points at it, so the collector must keep it.

```java
// the classic
public class Cache {
    private static final Map<String, Object> CACHE = new HashMap<>();   // static = GC root

    public static void put(String k, Object v) { CACHE.put(k, v); }
    // nothing ever removes. This grows until OOM.
}
```

The full catalogue of leak shapes is in 8.7. The point here is the **definition**: to find
a leak, you don't look for missing `free()` calls — you take a heap dump and ask *"what is
still referencing this?"* (8.9).

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Java uses reference counting | **Reachability.** Which is why cycles are collected fine |
| More old-gen space fixes frequent major GCs | Often the opposite — **premature promotion** needs a bigger *young* gen |
| Allocation is expensive | It's a **pointer bump**, often free after escape analysis |
| Long GC pauses are always the collector's fault | Could be **time to safepoint** — check for counted loops |
| You can get low pauses, high throughput and low memory | Pick two |
| `System.gc()` helps | See 8.7 — don't |

---

## Recap

| Concept | One line |
|---|---|
| **Reachability** | Not reference counting. Cycles are collected |
| GC roots | Stacks, statics, native refs, live threads |
| **Weak generational hypothesis** | Most objects die young — every collector assumes it |
| Cost of a minor GC | ∝ **survivors**, not garbage. Dead objects are free |
| Families | Mark-sweep (fragments) · mark-compact (slow) · copying (needs 2× space) |
| **Premature promotion** | Young gen too small → short-lived garbage fills old gen |
| **Safepoints** | All threads must reach one; a **counted `int` loop** can block the JVM |
| Three-way trade | Throughput / latency / footprint — pick two |
| Allocation | A **pointer bump** in a TLAB |
| **Leak** | **Unintentional reachability** |
