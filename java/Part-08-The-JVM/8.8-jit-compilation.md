# 8.8 — JIT compilation

> **What this is:** **The most under-appreciated part of the platform**, and the reason
> naive benchmarks lie. This is the right-hand side of the diagram from 8.1.

---

## ⭐ Tiered compilation

```
                    hot?              hotter?
 interpreter ──────► C1 ────────────► C2 ──────────► optimised machine code
 starts instantly    fast compile,    slow compile,
 runs slowly         collects profile aggressively optimised
      ▲                                     │
      └───────────── deoptimisation ────────┘
              a speculative assumption turned out false
```

**Five tiers**, though you mostly care about three:

| Tier | What |
|---|---|
| 0 | Interpreter |
| 1 | C1, no profiling (for trivial methods) |
| 2, 3 | C1 **with** profiling |
| 4 | **C2** — fully optimised |

**The thresholds** (approximately, and adaptive):

```bash
-XX:Tier3InvocationThreshold=200      # → C1 with profiling
-XX:Tier4InvocationThreshold=5000     # → C2
-XX:CompileThreshold=10000            # legacy single-tier
```

A method gets promoted based on **invocation count + loop back-edge count**. A method
called 10,000 times and a method with one loop running 10,000 iterations both qualify —
the latter via **on-stack replacement (OSR)**, which swaps compiled code in *while the
loop is still running*.

> **This is why a Java service is slow for its first few thousand requests and then
> several times faster.** It's not warming caches — it's the JIT reaching C2.

```bash
-XX:+PrintCompilation           # watch it happen
-Xint                           # interpreter only — see how slow that is
-XX:-TieredCompilation          # C2 only
```

---

## ⭐ Inlining — the optimisation that makes the rest possible

**Inlining replaces a call with the callee's body.** It matters far more than the saved
call overhead, because it **creates the context for every other optimisation**:

```java
int getX() { return x; }

// before inlining — opaque call
int sum = p.getX() + p.getY();

// after inlining — the optimiser can now see everything
int sum = p.x + p.y;
// → and now constant folding, escape analysis, dead code elimination all become possible
```

**The size limits:**

```bash
-XX:MaxInlineSize=35            # bytecodes — always inlined if hot
-XX:FreqInlineSize=325          # bytecodes — inlined if very hot
-XX:MaxInlineLevel=15           # recursion depth
```

> ⭐ **This is why tiny methods are free.** A getter is ~5 bytecodes — always inlined,
> zero cost. "Getters are slow" has been false for 25 years.
>
> And the corollary: **a large method may not be inlined**, which blocks optimisation of
> everything around it. Small methods are genuinely faster, which is the opposite of the
> naive intuition.

```bash
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
```

## ⭐ Escape analysis and scalar replacement

Can the JIT prove an object **never escapes** the method — never stored in a field, never
returned, never passed somewhere that might keep it?

If so, **the object need not exist at all**:

```java
double distance(int x1, int y1, int x2, int y2) {
    var p1 = new Point(x1, y1);       // does this allocate?
    var p2 = new Point(x2, y2);
    return Math.hypot(p2.x() - p1.x(), p2.y() - p1.y());
}
```

After inlining, C2 sees that `p1` and `p2` never leave. **Scalar replacement** deletes the
objects and keeps `x1, y1, x2, y2` in registers.

**No allocation. No object. No GC work.** (This is the "useful lie" from 8.3.)

Escape analysis also enables:
- **Lock elision** — a lock on a non-escaping object can't be contended, so it's removed
- **Stack allocation** — in some cases

```bash
-XX:+PrintEscapeAnalysis  (with -XX:+UnlockDiagnosticVMOptions)
-XX:-DoEscapeAnalysis     # turn it off to see the difference
```

> ⚠️ **Escape analysis is fragile.** It works method-locally after inlining, so a method
> too big to inline, or a value stored anywhere, defeats it. Don't *rely* on it — but do
> stop pre-optimising short-lived allocations (8.5).

## ⭐ Monomorphic, bimorphic, megamorphic call sites

**The most practically surprising part of this page.**

A virtual call (2.3) needs to find the right implementation. The JIT profiles what it
actually sees:

| Call site | Implementations seen | What the JIT does |
|---|---|---|
| **Monomorphic** | **1** | **Inline it directly**, guarded by a class check. As fast as a static call |
| **Bimorphic** | 2 | Inline both, with an if/else |
| **Megamorphic** | 3+ | Give up — a real vtable lookup every call |

```java
interface Shape { double area(); }
// only Circle is ever loaded
```

```java
for (Shape s : shapes) total += s.area();
```

If every element is a `Circle`, C2 emits roughly:

```
if (s.class == Circle) { total += PI * s.r * s.r; }    // inlined!
else                   { deoptimise(); }                // the guard
```

> ⭐ **An interface with one implementation is as fast as a direct call.** Which means
> "don't add interfaces, they're slow" is wrong — the JIT erases the cost entirely.

**And what happens when a second appears:** the guard fails, the method **deoptimises**,
and it gets recompiled as bimorphic. Performance changes at runtime based on which classes
have been loaded — which is why a benchmark that only ever uses one implementation
**measures a scenario that doesn't exist in production**.

---

## The other optimisations worth naming

| Optimisation | What |
|---|---|
| **Loop unrolling** | Do 4 iterations per pass, fewer branch checks |
| **Range-check elimination** | Prove `i` is always in bounds, delete the array check |
| **Lock elision** | Remove locks on non-escaping objects |
| **Lock coarsening** | Merge repeated lock/unlock on the same object into one region |
| **Dead code elimination** | Delete code whose result is never used — ⚠️ **this is what destroys naive benchmarks** |
| **Constant folding** | Evaluate compile-time-constant expressions once |

## ⭐ Deoptimisation

C2 optimises **speculatively**, based on what has happened so far, and backs each
assumption with a **guard**:

| Assumption | Guard |
|---|---|
| "This call site only ever sees `Circle`" | Class check |
| "This branch is never taken" | An uncommon trap |
| "This class is never subclassed" | Invalidated when a subclass loads |
| "This value is never null" | Null check |

When a guard fails, the JVM **deoptimises**: discards the compiled code, rebuilds the
interpreter frame mid-execution, continues in the interpreter, and re-profiles.

> **This is the whole reason the JIT can be more aggressive than a static compiler.** A
> C++ compiler must assume any subclass might exist. The JVM knows what's *actually
> loaded*, optimises for that, and can undo it if a class loads later.

Practical consequence: **loading a new class can slow down code that was already fast.**
A plugin, a lazily-initialised implementation, or a mock in a test can all trigger
deoptimisation of production code paths.

## ⭐ JMH — why you cannot benchmark Java with `System.nanoTime()`

```java
// ❌ this measures nothing
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    doWork(i);
}
IO.println(System.nanoTime() - start);
```

**Everything that's wrong with it:**

| Problem | Effect |
|---|---|
| **No warmup** | You measured the interpreter and C1, not C2 |
| **Dead code elimination** | `doWork`'s result is unused → **the JIT deletes the call entirely.** You timed an empty loop |
| **Constant folding** | Constant inputs → the result is computed once at compile time |
| **On-stack replacement** | OSR-compiled loops optimise differently from normal method calls |
| **GC interference** | One collection in the middle skews everything |
| **Loop unrolling** | The loop you wrote isn't the loop that ran |

**JMH (Java Microbenchmark Harness)** is the OpenJDK tool that handles all of it:

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(3)
@State(Scope.Benchmark)
public class MyBenchmark {

    private int input = 42;

    @Benchmark
    public int measure() {
        return doWork(input);          // returning it prevents dead-code elimination
    }

    @Benchmark
    public void measureWithBlackhole(Blackhole bh) {
        bh.consume(doWork(input));     // explicit, for multiple results
    }
}
```

**What JMH does for you:** warms up properly, forks fresh JVMs (so profiles don't leak
between benchmarks), uses `Blackhole` to defeat dead-code elimination, uses `@State` to
defeat constant folding, and reports error bars.

> **If you are comparing two implementations without JMH, your numbers are wrong.** Not
> "slightly off" — often measuring an empty loop. This is the most common mistake in Java
> performance discussions.

## GraalVM's JIT as an alternative compiler

**Graal** is a JIT compiler written **in Java**, usable in place of C2:

```bash
-XX:+UnlockExperimentalVMOptions -XX:+UseJVMCICompiler
```

Better at some things (aggressive inlining, escape analysis on lambda- and stream-heavy
code), worse at others (longer warmup, some numeric workloads).

> Distinct from **GraalVM native image** (8.10), which is ahead-of-time compilation with no
> JIT at all. Same project, opposite ends.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Benchmarking with `System.nanoTime()` | Measures the interpreter, or an empty loop. **Use JMH** |
| "Interfaces are slow" | Monomorphic call sites are inlined — as fast as direct |
| "Getters cost a method call" | ~5 bytecodes, always inlined. Free |
| "Small methods are slower" | The opposite — **they're the ones that get inlined** |
| Java is slow because it's interpreted | Only until C2 compiles it |
| Performance is stable at runtime | Loading a class can **deoptimise** hot code |

## Recap

| Concept | One line |
|---|---|
| **Tiered** | interpreter → C1 (+profile) → C2. Thresholds ~200 / ~5,000 |
| **Inlining** | The enabler for everything else. Tiny methods are free |
| **Escape analysis** | Non-escaping objects may **never be allocated** |
| **Monomorphic** | One implementation → inlined → **as fast as a static call** |
| Megamorphic | 3+ implementations → real vtable lookup |
| **Deoptimisation** | Speculate + guard; undo when the guard fails |
| **JMH** | The only correct way to benchmark Java |
| Graal | An alternative JIT written in Java |
