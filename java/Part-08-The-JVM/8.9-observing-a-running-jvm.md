# 8.9 — Observing a running JVM

> **What this is:** A practical skill set. **This is what makes you the person who can
> answer "why is production slow".** Everything here works on a live process with no code
> changes and no restart.

---

## ⭐ The command-line tools

All ship with the JDK. Learn `jcmd` first — it subsumes most of the others.

```bash
jps -l                         # list running JVMs with their main classes
jps -lvm                       # + JVM args and full command line
```

```bash
jcmd <pid> help                # ⭐ list every available command for that process
jcmd <pid> Thread.print        # thread dump
jcmd <pid> GC.heap_info        # heap usage by region
jcmd <pid> GC.class_histogram  # ⭐ object counts by class — the fastest leak triage
jcmd <pid> VM.flags            # flags actually in effect
jcmd <pid> VM.system_properties
jcmd <pid> VM.native_memory summary   # requires -XX:NativeMemoryTracking=summary
jcmd <pid> GC.heap_dump /tmp/heap.hprof
jcmd <pid> JFR.start name=rec settings=profile
```

**The others, and what they do:**

| Tool | Does | Prefer |
|---|---|---|
| `jstack <pid>` | Thread dump | `jcmd <pid> Thread.print` |
| `jmap -histo <pid>` | Class histogram | `jcmd <pid> GC.class_histogram` |
| `jmap -dump:live,file=h.hprof <pid>` | Heap dump | `jcmd <pid> GC.heap_dump` |
| `jstat -gcutil <pid> 1s` | **GC stats every second** — still genuinely useful | — |
| `jinfo <pid>` | Flags and properties | `jcmd <pid> VM.flags` |

```bash
jstat -gcutil <pid> 1000       # S0 S1 E O M CCS YGC YGCT FGC FGCT GCT
```

That one line tells you, live: survivor/eden/old occupancy percentages, and young/full GC
counts and times. **If old (`O`) climbs and never drops after a full GC, you have a leak.**

## ⭐ Reading a thread dump

```bash
jcmd <pid> Thread.print > threads.txt
```

```
"http-nio-8080-exec-3" #42 daemon prio=5 tid=0x00007f8 nid=0x1e03 BLOCKED
   java.lang.Thread.State: BLOCKED (on object monitor)
    at com.example.Service.process(Service.java:45)
    - waiting to lock <0x000000076ab62208> (a java.lang.Object)
    - locked <0x000000076ab62218> (a java.lang.Object)
    at com.example.Handler.handle(Handler.java:22)
```

**The thread states:**

| State | Means |
|---|---|
| `RUNNABLE` | Executing, or in native/blocking I/O (⚠️ the JVM can't tell the difference) |
| `BLOCKED` | **Waiting for a monitor** — someone else holds a `synchronized` lock |
| `WAITING` | In `wait()`, `join()`, `park()` — indefinitely |
| `TIMED_WAITING` | Same, with a timeout |

**The two lines that matter:**

- `- locked <0x...>` — **this thread holds** that monitor
- `- waiting to lock <0x...>` — this thread **wants** it

### ⭐ Spotting a deadlock by eye

```
"Thread-1"  BLOCKED
    - waiting to lock <0xAAA>
    - locked <0xBBB>

"Thread-2"  BLOCKED
    - waiting to lock <0xBBB>          ← Thread-1 holds this
    - locked <0xAAA>                   ← Thread-1 wants this
```

**A cycle in the wait-for graph.** Thread-1 wants what Thread-2 holds, and vice versa.
Neither will ever proceed.

> **The JVM finds these for you** — a thread dump ends with an explicit
> `Found one Java-level deadlock:` section when it detects a monitor cycle. Scroll to the
> bottom first.
>
> ⚠️ It detects `synchronized` monitor deadlocks. It does **not** detect deadlocks on
> `ReentrantLock`, semaphores, or database locks. Full treatment in 9.2, 9.5.

**Triage pattern:** take **three** dumps ten seconds apart. Threads stuck in the same frame
across all three are stuck; threads that move are just busy.

## ⭐ Heap dumps

```bash
jcmd <pid> GC.heap_dump /tmp/heap.hprof          # `live` only by default — runs a full GC first
```

```bash
# ⭐ set this in every production JVM, before you need it
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app/
```

That flag costs nothing until an OOM, and gives you the one artifact that actually
explains it. **Add it now.**

**Analysing:** Eclipse MAT, VisualVM, or IntelliJ's profiler.

**The three concepts that make analysis work:**

| Concept | Means |
|---|---|
| **Shallow size** | The object itself (8.4) |
| **Retained size** | ⭐ Everything that would be freed if this object went away |
| **Dominator tree** | Who *exclusively* keeps what alive |

> **Retained size is the number you want.** A `HashMap` has a shallow size of ~48 bytes and
> a retained size of 2 GB. Sort by retained size, and the leak is usually row 1 or 2.

**The workflow:**

1. Sort by **retained size** → find the big object
2. **Path to GC roots** → find what's keeping it alive (8.5)
3. That path names the bug — usually a static collection, a `ThreadLocal`, or a listener
   (8.7)

**Fast triage without a full dump:**

```bash
jcmd <pid> GC.class_histogram | head -20
```

```
 num     #instances         #bytes  class name
   1:       8234567      395258016  com.example.Session      ← 8 million sessions?
   2:       8234567      263506144  java.util.HashMap$Node
```

Run it twice a minute apart. **What's growing is the leak.**

## ⭐ JDK Flight Recorder (JFR)

**Always-on, low-overhead (~1%) profiling built into the JVM.** Free since Java 11. This
is the most valuable tool on the page and the least used.

```bash
# start at launch
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr,settings=profile -jar app.jar

# or attach to a running process — no restart
jcmd <pid> JFR.start name=rec settings=profile
jcmd <pid> JFR.dump name=rec filename=/tmp/rec.jfr
jcmd <pid> JFR.stop name=rec
```

| Settings profile | Overhead |
|---|---|
| `default` | **< 1%** — safe to run continuously in production |
| `profile` | ~2% — more detail, for investigation |

**What it records:** allocation by call site, CPU by method, GC pauses, lock contention,
thread states, I/O, exceptions thrown, class loading, JIT compilation, safepoint time.

**Reading it:** JDK Mission Control (JMC), or IntelliJ opens `.jfr` files directly.

```bash
jfr summary rec.jfr                          # CLI, quick look
jfr print --events GCPhasePause rec.jfr
```

**Recent additions:**

| Version | Feature |
|---|---|
| `Java 25` | **CPU-time profiling** — real CPU time per method, not just wall-clock samples |
| `Java 27` | **Automatic redaction of secrets** in recordings |

That last one matters operationally — recordings previously could capture sensitive values
in strings, which made sharing them with vendors awkward.

> **The practical advice: run JFR with `default` settings continuously in production.**
> When something goes wrong at 3am you'll have the recording, instead of trying to
> reproduce it.

## Sampling vs instrumenting profilers

| | **Sampling** | **Instrumenting** |
|---|---|---|
| How | Periodically capture stacks | Inject timing code into every method |
| Overhead | **Low** (~1%) | **High** (2–10×) |
| Accuracy | Statistical | Exact counts |
| Distorts the program | Minimally | ⚠️ Yes — prevents inlining (8.8) |
| Use | **Production** | Narrow, local investigation |

> ⚠️ **Instrumenting profilers change what they measure.** By adding code to every method,
> they defeat inlining — so tiny methods that were free (8.8) now look expensive. This
> misleads people into "optimising" getters.

### ⭐ `async-profiler` and flame graphs

Most JVM sampling profilers only sample **at safepoints** (8.5), which biases results
toward methods that happen to contain safepoint polls — the "safepoint bias" problem.

**async-profiler** uses OS-level signals (`perf_events`) instead, so it samples anywhere
and sees native frames too:

```bash
./profiler.sh -d 30 -f flame.html <pid>
```

**Reading a flame graph:**

```
        ┌──────────────────────────────────────┐
        │             main                     │   ← width = % of samples
        ├──────────────┬───────────────────────┤
        │  handle()    │      render()         │
        ├──────┬───────┼──────────┬────────────┤
        │parse │ query │ toString │  format    │   ← wide box = hot
        └──────┴───────┴──────────┴────────────┘
```

- **Width = time.** Height is just stack depth
- **Look for wide boxes**, not tall ones
- A wide box with nothing above it is where the time is actually spent

## `-XX:+PrintFlagsFinal` — every flag and its real value

```bash
java -XX:+PrintFlagsFinal -version | grep -i heapsize
```
```
   size_t MaxHeapSize   = 8589934592    {product} {ergonomic}
```

The last column is the **source**:

| Source | Means |
|---|---|
| `{default}` | Built-in default |
| `{ergonomic}` | ⭐ **The JVM chose this** based on the machine |
| `{command line}` | You set it |

> **This is how you answer "what heap size is it actually using?"** in a container — where
> the ergonomic default is ~25% of the limit (8.3) and rarely what anyone expects.

```bash
java -XX:+PrintFlagsFinal -version | grep -E "UseG1GC|UseCompressedOops|MaxHeapSize"
```

## JMX and MBeans

The JVM exposes itself over **JMX**, and so do most frameworks:

```java
var mem = ManagementFactory.getMemoryMXBean();
mem.getHeapMemoryUsage();                     // init, used, committed, max

ManagementFactory.getThreadMXBean().findDeadlockedThreads();     // programmatic detection
ManagementFactory.getGarbageCollectorMXBeans();
ManagementFactory.getRuntimeMXBean().getInputArguments();        // the JVM's own args
```

```bash
-Dcom.sun.management.jmxremote.port=9010     # expose it (⚠️ secure this properly)
```

Tools: JConsole, VisualVM, Mission Control. In practice, most teams scrape JMX into
Prometheus/Micrometer rather than connecting interactively.

## Native memory tracking

For **the memory the heap doesn't explain** — when RSS is 4 GB and the heap is 1 GB.

```bash
-XX:NativeMemoryTracking=summary
jcmd <pid> VM.native_memory summary
```

```
Total: reserved=5GB, committed=2GB
-   Java Heap (reserved=1GB, committed=1GB)
-      Metaspace (reserved=1GB, committed=256MB)      ← 8.3
-         Thread (reserved=1GB, committed=100MB)      ← ⭐ 1MB per thread!
-           Code (reserved=250MB, committed=80MB)     ← JIT output, 8.8
-            GC (reserved=200MB, committed=180MB)
```

**Common answers this gives:**
- **Thread stacks** — 1,000 threads × 1 MB = 1 GB (8.3, and why virtual threads exist)
- **Metaspace** — a classloader leak (8.2)
- **Direct buffers** — Netty, NIO (10.4)
- **Code cache** — lots of JIT-compiled code

## ⭐ A triage playbook

| Symptom | First move |
|---|---|
| **Slow, high CPU** | JFR or async-profiler → flame graph |
| **Slow, low CPU** | Three thread dumps 10s apart → find the blocked/waiting threads |
| **Memory grows steadily** | `GC.class_histogram` twice → see what grows → heap dump |
| **OOM** | The dump from `-XX:+HeapDumpOnOutOfMemoryError` → sort by retained size |
| **Long pauses** | `-Xlog:gc*` → if pause ≫ GC work, it's **safepoints** (8.5) |
| **Frozen** | Thread dump → scroll to the bottom for `Found one Java-level deadlock` |
| **RSS ≫ heap** | Native memory tracking |
| **"What settings is it using?"** | `jcmd <pid> VM.flags`, `-XX:+PrintFlagsFinal` |

> **The habit worth building: `jps` → `jcmd <pid> help` → pick the command.** You can
> diagnose most of a production incident from those two commands and a thread dump, with
> no agent, no restart and no code change.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| One thread dump | Take **three**. One is a snapshot, three show what's stuck |
| `RUNNABLE` means using CPU | Blocking I/O also shows as `RUNNABLE` |
| Shallow size in a heap dump | Sort by **retained** size |
| Instrumenting profiler in production | 2–10× overhead, and it defeats inlining |
| Adding `-XX:+HeapDumpOnOutOfMemoryError` after the OOM | Too late. **Add it now** |
| JFR is a paid feature | Free and open-source since Java 11 |

## Recap

| Tool | For |
|---|---|
| `jps` / `jcmd <pid> help` | **Start here** |
| `jcmd Thread.print` | Thread dump — states, locks, deadlocks |
| `jcmd GC.class_histogram` | Fastest leak triage. Run it twice |
| `jstat -gcutil <pid> 1s` | Live GC stats |
| Heap dump + MAT | **Retained size** → path to GC roots |
| **JFR** | Always-on, <1%. Run it in production |
| async-profiler | Flame graphs, no safepoint bias |
| `-XX:+PrintFlagsFinal` | What the JVM actually chose |
| `VM.native_memory` | Memory the heap doesn't explain |
