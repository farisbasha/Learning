# 8.10 — Startup, packaging and AOT

> **What this is:** **The active frontier**, driven entirely by containers and serverless.
> This is the one part of the JVM story that is genuinely changing right now.

---

## ⭐ Why JVM startup is slow

Three costs, in order:

| Cost | What happens |
|---|---|
| **Class loading** | Find, read, parse thousands of class files (8.2). A Spring Boot app loads **10,000–20,000** classes before serving a request |
| **Verification** | Every method's bytecode is proved safe (8.2) — a real cost, paid every start |
| **An interpreter that has learned nothing** | The JIT profile is empty. The first requests run interpreted, ~20× slower than C2 (8.8) |

```
JVM start ──► load+verify 15,000 classes ──► interpret ──► C1 ──► C2
   0ms              ~800ms                    slow      faster   fast
                                              └─── first few thousand requests ───┘
```

**Why it suddenly matters:** for a service that runs for weeks, none of this is relevant —
you pay it once. For a **serverless function** invoked for 200ms, or a **container** that
autoscales dozens of times an hour, or a **CLI tool**, startup *is* the workload.

This is where Java loses to Go and Node, and it's what Project Leyden exists to fix.

---

## Class Data Sharing (CDS) and AppCDS

**The idea:** parse the classes once, dump the result to an archive, and `mmap` it on every
subsequent start.

```bash
# 1. record which classes your app loads
java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar

# 2. use the archive
java -XX:SharedArchiveFile=app.jsa -jar app.jar
```

Or the one-step form since Java 19:

```bash
java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=app.jsa -jar app.jar
```

**Typical gain: 10–30% faster startup**, plus lower memory when multiple JVMs share the
same archive (the mapped pages are shared by the OS).

> The JDK's own classes are archived by default since Java 12 — you already get some of
> this for free. **AppCDS** extends it to your application's classes.

## ⭐ Project Leyden

**Goal:** shift work from runtime to build time, incrementally, **without giving up the
JIT**.

| Version | What landed |
|---|---|
| `Java 24` | **AOT class loading and linking** — classes arrive pre-loaded and pre-linked |
| `Java 25` | **AOT method profiling** — the JIT starts with a profile instead of learning from zero; simpler command-line ergonomics |
| `Java 26` | **AOT caching that works with any collector** (previously G1-only) |

```bash
# Java 24+ — a two-step training run
java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -jar app.jar
java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf -XX:AOTCache=app.aot -jar app.jar

# then use it
java -XX:AOTCache=app.aot -jar app.jar
```

**Reported gains: roughly 40% faster startup on Spring Boot-class applications**, with
**no code changes and no loss of peak performance** — the JIT still runs and still
optimises.

> **This is the important distinction from native image (below).** Leyden makes the JVM
> start faster while remaining a JVM. Native image makes something that is no longer a JVM.

## `jlink` — a trimmed runtime

Build a custom JRE containing **only the modules you use** (11.10):

```bash
jlink --add-modules java.base,java.logging,java.sql \
      --strip-debug --no-header-files --no-man-pages \
      --compress=zip-6 \
      --output myruntime

./myruntime/bin/java -m myapp/com.example.Main
```

| | Size |
|---|---|
| Full JDK | ~300 MB |
| `jlink` runtime for a small service | **~40 MB** |

**Why it matters: container image size.** A 40 MB base layer instead of 300 MB changes pull
times and registry costs across a fleet.

> ⚠️ Requires your dependencies to be modular or at least automatic modules. Many older
> libraries aren't, which is the usual reason teams skip this.

---

## `jpackage` — a native installer

```bash
jpackage --name MyApp --input target/ --main-jar app.jar \
         --type dmg          # or msi, deb, rpm, pkg, exe
```

Produces a platform-native installer that **bundles a runtime**, so the user doesn't need
Java installed. For desktop applications (JavaFX, Swing) and CLI tools.

## ⭐ GraalVM native image

**Ahead-of-time compilation to a standalone native binary. No JVM at all.**

```bash
native-image -jar app.jar
./app                      # a real executable
```

| | JVM | Native image |
|---|---|---|
| **Startup** | 500–2000 ms | **1–50 ms** ⭐ |
| **Memory** | 200–500 MB | **20–60 MB** ⭐ |
| **Peak throughput** | **Higher** (C2 optimises with runtime profiles, 8.8) | ~10–30% lower |
| **Build time** | Seconds | **Minutes** |
| Binary size | — | 30–100 MB |
| GC | Full choice (8.6) | Serial, or G1 in paid Oracle GraalVM |

### ⭐ The real costs

**1. The closed-world assumption.**

Everything reachable must be known **at build time**. The compiler walks the call graph
from `main` and includes only what it can prove is used. Anything it can't see is **not in
the binary**.

**2. Reflection configuration.**

Reflection (11.6), dynamic proxies, JNI and resource loading are all invisible to static
analysis:

```java
Class.forName(System.getenv("HANDLER_CLASS"));    // ❌ the compiler cannot see this
```

You must declare them:

```json
// reflect-config.json
[ { "name": "com.example.User",
    "allDeclaredFields": true,
    "allDeclaredMethods": true } ]
```

> **This is the actual pain.** A library using reflection without native-image metadata
> fails at **runtime**, in the binary, with a `ClassNotFoundException` that worked fine on
> the JVM.
>
> **The ecosystem has largely solved it:** Spring Boot 3+, Quarkus and Micronaut generate
> this metadata at build time, and the GraalVM **Reachability Metadata Repository** ships
> configs for common libraries. A greenfield Spring Boot native build mostly just works.
> A ten-year-old codebase with four reflection-heavy libraries does not.

**3. No JIT.**

Peak throughput is lower, because there's no runtime profile to optimise with. **Profile-
guided optimisation** (a training run, Oracle GraalVM only) recovers much of it.

## ⭐ When each is the right answer

| Workload | Use |
|---|---|
| **Long-running server** (weeks of uptime) | **Plain JVM.** Startup is amortised to nothing; you want peak JIT throughput |
| Long-running server, faster deploys | JVM + **AppCDS / Leyden AOT cache** |
| Container image size matters | + **`jlink`** |
| **Serverless function** (short-lived, cold starts billed) | **Native image** |
| **CLI tool** (runs for 200ms) | **Native image** |
| **Desktop application** | `jpackage` |
| Autoscaling microservice, scales often | Native image **or** JVM + Leyden — measure both |

> ⭐ **The honest default: for a normal server application, use the plain JVM and add the
> Leyden AOT cache when you upgrade to Java 24+.** It's a flag, not an architecture change.
>
> **Native image is a real commitment** — a different build pipeline, minutes-long builds,
> reflection configuration, a different debugging story, and different runtime
> characteristics. Take it when **cold start is the actual product requirement**, not
> because the startup number looks good.

---

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Native image is strictly better | **10–30% lower peak throughput.** Wrong for long-running servers |
| Native image "just works" | Reflection, proxies and resources need metadata |
| A benchmark on a fresh JVM | You measured the interpreter, not C2 (8.8) |
| `jlink` works with any dependency | Needs modular or automatic modules |
| AOT means no JIT | **Leyden keeps the JIT.** Only native image removes it |
| Optimising startup for a service that runs for weeks | Optimise throughput instead |

---

## Recap

| Technique | Gains | Costs |
|---|---|---|
| **AppCDS** | 10–30% startup | A training run |
| **Leyden AOT** `Java 24`–`26` | **~40% startup, keeps the JIT** | A training run |
| **`jlink`** | ~300 MB → ~40 MB runtime | Needs modules |
| **`jpackage`** | Native installer | Desktop only |
| **GraalVM native image** | **1–50 ms start, 20–60 MB** | No JIT, closed world, reflection config, slow builds |

| Why startup is slow | Class loading · verification · a cold JIT profile |
|---|---|
| **Default advice** | Plain JVM + Leyden AOT cache. Native image only when cold start *is* the requirement |
