# 8.4 — How an object is laid out

> **What this is:** **Concrete byte counts.** This is what makes performance intuition
> real rather than superstitious.

---

## ⭐ The object header

Every object on the heap carries a header before its fields:

```
┌────────────────┬───────────────┬──────────────┬─────────┐
│   mark word    │ class pointer │    fields    │ padding │
│    8 bytes     │   4 bytes*    │      …       │  0–7    │
└────────────────┴───────────────┴──────────────┴─────────┘
  * 4 with compressed class pointers (the default), 8 without
```

**12 bytes of header**, then your fields, then padding to an 8-byte boundary.

### What the mark word stores

The mark word is **reused for different purposes depending on state** — this is why it's a
"word" and not named fields:

| State | Contents |
|---|---|
| Unlocked | **Identity hash code** (once computed), GC age, biased-lock bits |
| Locked | Pointer to the lock record / monitor (Part 09) |
| GC in progress | Forwarding pointer to the object's new location |

> ⭐ **This is why `System.identityHashCode()` costs something the first time** — the hash
> isn't stored until you ask, because the space is shared with the lock state. And it's
> why the `[I@1b6d3586` in `Object.toString()` (1.4, 2.5) is that stored value.

### The class pointer

Points to the class metadata in metaspace (8.3). This is what `getClass()` returns and
what `invokevirtual` reads to find the vtable (2.3).

## ⭐ Compact object headers `Java 24` (experimental) · **default in 27**

Headers shrink from **96 bits (12 bytes) to 64 bits (8 bytes)** — the mark word and class
pointer are packed together.

```bash
-XX:+UnlockExperimentalVMOptions -XX:+UseCompactObjectHeaders    # Java 24–26
```

**Effect: roughly 10–20% less heap** on typical object-heavy applications, plus better
cache utilisation because more objects fit per cache line.

It's one of the largest free wins in recent JVM history, and it's the reason a Java 27
application may use noticeably less memory than the same code on 21 with no changes.

## Field alignment and padding

```java
class Example {
    boolean flag;   // 1 byte
    int count;      // 4 bytes
    long id;        // 8 bytes
    Object ref;     // 4 bytes (compressed)
}
```

**Declaration order is not memory order.** The JVM reorders fields to minimise padding —
typically largest first:

```
offset  0: header      (12 bytes)
offset 12: int count   (4)          ← fills the gap to 16
offset 16: long id     (8)
offset 24: Object ref  (4)
offset 28: boolean flag(1)
offset 29: padding     (3)
───────────────────────────
total: 32 bytes
```

Had it followed declaration order, `boolean` then `int` then `long` would need padding
after the boolean to align the long — wasting bytes.

> **Consequence:** you cannot infer an object's layout from its source. Measure it.

### Measuring it yourself with JOL

**JOL (Java Object Layout)** is the OpenJDK tool for this:

```bash
java -jar jol-cli.jar internals java.lang.Integer
```

```
java.lang.Integer object internals:
OFF  SZ   TYPE DESCRIPTION               VALUE
  0   8        (object header: mark)     0x...
  8   4        (object header: class)    0x...
 12   4    int Integer.value             5
Instance size: 16 bytes
Space losses: 0 bytes internal + 0 bytes external = 0 bytes total
```

Or as a dependency:

```java
System.out.println(ClassLayout.parseClass(Example.class).toPrintable());
System.out.println(GraphLayout.parseInstance(obj).totalSize());   // deep size
```

> This is the tool that turns "I think this is big" into a number.

## ⭐ Compressed ordinary object pointers (compressed oops)

On a 64-bit JVM, a reference *should* be 8 bytes. **It's 4** — because the JVM stores a
shifted offset from the heap base rather than a full address.

```
real address = heapBase + (compressedOop << 3)
```

Since objects are 8-byte aligned, the low 3 bits are always zero, so a 32-bit value can
address **2³² × 8 = 32 GB**.

**The cliff:**

**Measured on OpenJDK 17** — the boundary is exact, not approximate:

| Flag | `UseCompressedOops` | Reference size |
|---|---|---|
| `-Xmx4g` | `true` | 4 bytes |
| `-Xmx31g` | **`true`** | 4 bytes |
| `-Xmx32g` | **`false`** ← the cliff | **8 bytes** |
| `-Xmx33g` | `false` | 8 bytes |

```bash
java -Xmx31g -XX:+PrintFlagsFinal -version | grep -w UseCompressedOops   # true
java -Xmx32g -XX:+PrintFlagsFinal -version | grep -w UseCompressedOops   # false
```

> ⭐ **Going from a 31 GB to a 32 GB heap can leave you with *less* usable memory**,
> because every reference in every object doubles. This is a real and commonly-hit
> production trap.
>
> **Rule: stay at or below 31 GB, or jump well past 32.** The dead zone between ~32 and
> ~40 GB gives you strictly less usable space than 31 GB does.

## ⭐ Why `Integer` costs roughly four times `int`

```
int                4 bytes

Integer object:
  header          12 bytes
  int value        4 bytes
  ───────────────────────
                  16 bytes   ← 4× the data

plus a reference   4 bytes
  ───────────────────────
  total           20 bytes   ← 5× per element in a collection
```

**For a million values** (5.8):

| | Total | Ratio |
|---|---|---|
| `int[]` | **~4 MB** | 1× |
| `Integer[]` / `ArrayList<Integer>` | ~20 MB | **5×** |
| `HashMap<Integer,Integer>` | ~80 MB | **20×** |

The `HashMap` figure adds a `Node` object per entry (~32 bytes: header + hash + key ref +
value ref + next ref) plus two `Integer` objects.

> **The `Integer` cache mitigates this only for −128..127** (1.1). Real data outside that
> range allocates.

## ⭐ Arrays of objects are arrays of *references*

```java
int[] ints = new int[1000];          // ONE object: header + 1000 × 4 bytes, contiguous
Integer[] boxed = new Integer[1000]; // 1001 objects: the array + 1000 separate Integers
```

```
int[1000]:      [hdr][1][2][3][4][5]…            one contiguous block
                       ↑ scanning this is a linear memory read

Integer[1000]:  [hdr][ref][ref][ref]…            the array
                       │    │    │
                       ▼    ▼    ▼
                     [obj][obj][obj]              scattered across the heap
                       ↑ each access is a pointer chase, possibly a cache miss
```

**A cache miss costs ~100× a cache hit.** So scanning an `Integer[1000]` isn't 5× slower
than `int[1000]` because of the memory — it's slower because the CPU's prefetcher can
follow a contiguous array and cannot follow scattered pointers.

> This one fact explains, across the whole roadmap:
> - Why `ArrayList` beats `LinkedList` (5.2)
> - Why `ArrayDeque` beats `LinkedList` (5.4)
> - Why `IntStream` beats `Stream<Integer>` (6.4)
> - Why `int[]` beats `List<Integer>` by more than the byte counts suggest (5.8)
> - Why `ArrayList` splits well for parallel streams (6.8)

**2D arrays have the same problem** (1.4): `int[1000][1000]` is 1,001 separate objects,
not one block.

## What Project Valhalla would change `not yet`

```java
value record Point(int x, int y) { }
```

A **value class** has no identity — so no header, no reference. It can be **flattened**
directly into its container:

```
today:        Point[3] = [ref][ref][ref] → three separate 16-byte objects
with Valhalla: Point[3] = [x][y][x][y][x][y]    ← inline, contiguous, 24 bytes total
```

Plus specialised generics — `List<int>` with no boxing (3.5).

**Status:** a decade in development, not here. Compact headers (above) are the piece that
*has* landed. **Don't design around Valhalla** — use `int[]` and `IntStream` today.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Field order in source = memory order | The JVM reorders to minimise padding |
| A 33 GB heap gives more usable memory than 31 GB | Compressed oops switch off; may give **less** |
| `Integer` is "a bit bigger" than `int` | **5× per collection element** |
| `Integer[]` is contiguous | It's an array of references to scattered objects |
| Estimating object size by adding field sizes | Forgetting 12 bytes of header and padding |
| Guessing at layout | Use **JOL** |

## Recap

| Concept | Number |
|---|---|
| Object header | **12 bytes** (8 mark + 4 class) → **8 bytes** with compact headers `Java 24`, default `27` |
| Alignment | 8 bytes; fields reordered by the JVM |
| Compressed oops | 4-byte references **up to `-Xmx31g`**; off at `32g` — a measured cliff |
| `Integer` | **16 bytes** + 4-byte reference = 20, vs 4 for `int` |
| 1M ints | `int[]` 4 MB · `List<Integer>` 20 MB · `HashMap` 80 MB |
| Object arrays | Arrays of **references** — pointer chase, cache misses |
| Measure with | **JOL** |
