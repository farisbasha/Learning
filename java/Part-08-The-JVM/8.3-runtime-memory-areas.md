# 8.3 — Runtime memory areas

> **What this is:** Where your objects, your variables and your classes actually live.
> **Four areas, four different failure modes** — and knowing which region ran out tells
> you what kind of bug you have before you open a profiler.

---

## ⭐ The map

```
SHARED BY EVERY THREAD                                    ONE PER THREAD
──────────────────────────────────────────────────        ──────────────────

 HEAP — every object you ever create                       STACKS
┌──────────────────────────┬────────────────────┐        ┌──────────────────┐
│    YOUNG GENERATION      │  OLD GENERATION    │        │ frame: locals +  │
│  ┌──────┬────┬────┐      │                    │        │   operand stack  │
│  │ eden │ S0 │ S1 │ ───► │  survivors get     │        │ frame            │
│  └──────┴────┴────┘      │  promoted here     │        │ frame            │
│  new objects land here   │                    │        └──────────────────┘
│  most die here           │  collected rarely, │         StackOverflowError
│  collected often, cheaply│  expensively       │
└──────────────────────────┴────────────────────┘        METASPACE
 OutOfMemoryError: Java heap space                       ┌──────────────────┐
                                                          │ class metadata   │
                                                          │ NATIVE memory    │
                                                          └──────────────────┘
                                                           OOME: Metaspace
```

> **Objects live on the shared heap. Variables that point at them live on a private
> stack.**
>
> That split is the entire explanation of **pass-by-value** (1.5), of why **two threads
> can see the same object** (Part 09), and of **which `OutOfMemoryError`** you're looking
> at.

## The heap

**Shared by all threads. Every object lives here.** Garbage collected (8.5).

### Young generation

```
┌─────────────────┬──────┬──────┐
│      eden       │  S0  │  S1  │
└─────────────────┴──────┴──────┘
```

- **Eden** — every new object is allocated here
- **S0 / S1 (survivor spaces)** — one is always empty; objects alive after a collection
  are copied into the other

**A minor GC:** copy the live objects out of eden and the occupied survivor space into the
empty one, increment each survivor's **age**, then declare eden empty. Because most
objects die young (8.5), almost nothing gets copied — which is why minor GCs are cheap.

### Old generation

Objects that survive enough young collections (`-XX:MaxTenuringThreshold`, default ~15)
get **promoted** here. Collected rarely and expensively.

> Objects too large for eden are allocated **directly** in the old generation.

### Sizing flags

```bash
-Xmx4g                 # maximum heap
-Xms4g                 # initial heap — set equal to -Xmx in servers to avoid resize pauses
-XX:NewRatio=2         # old:young ratio
-XX:SurvivorRatio=8    # eden:survivor ratio
```

> **In a container**, the JVM reads cgroup limits and defaults `-Xmx` to ~25% of the
> container's memory. That's often surprisingly small — set it explicitly.

## The stack

**One per thread.** Not garbage collected — frames pop automatically.

Each method call pushes a **frame** containing:
- **Local variable slots** — parameters and locals (8.1)
- The **operand stack** for that method
- A reference to the constant pool, and the return address

```java
void a() { b(); }
void b() { c(); }
void c() { }
```

```
│ frame: c()  │  ← top
│ frame: b()  │
│ frame: a()  │
│ frame: main │
└─────────────┘
```

```bash
-Xss1m        # stack size per thread (default ~512KB–1MB)
```

> ⭐ **A platform thread reserves ~1 MB of stack.** This is **exactly** why you cannot have
> a million of them — 1 million × 1 MB = 1 TB of reserved address space — **and why
> virtual threads exist** (9.11). Virtual threads keep their stack on the *heap* and grow
> it as needed.

**`StackOverflowError`** comes from here — deep or infinite recursion (1.5).

---

## Metaspace `Java 8`

**Class metadata** — the loaded `Class` objects, method bytecode, field descriptors,
the runtime constant pool (8.1).

**It's native memory, not heap, and has no fixed limit by default** — it grows until the
machine runs out.

```bash
-XX:MaxMetaspaceSize=256m      # worth setting, to fail fast instead of consuming the box
```

> **It replaced PermGen**, removed in Java 8. PermGen was a fixed-size *heap* region, and
> `OutOfMemoryError: PermGen space` was a rite of passage — especially on app servers,
> where redeploying an app 20 times filled it (the classloader leak from 8.2). Metaspace
> made it a native-memory problem instead of a heap-sizing problem.

**`OutOfMemoryError: Metaspace` almost always means a classloader leak** (8.2), not that
you have too many classes.

## The other regions

| Region | Holds | Failure |
|---|---|---|
| **Code cache** | JIT-compiled machine code (8.8) | `CodeCache is full. Compiler has been disabled` — performance silently collapses |
| **Thread native stacks** | Native frames for JNI/FFM calls | `unable to create native thread` |
| **Direct byte buffers** | `ByteBuffer.allocateDirect` — off-heap, used by NIO and Netty (10.4) | `OutOfMemoryError: Direct buffer memory` |

```bash
-XX:ReservedCodeCacheSize=256m
-XX:MaxDirectMemorySize=1g
```

## ⭐ Which error comes from which area

**This table is the practical payoff of the page.**

| Error | Area | Usual cause |
|---|---|---|
| `StackOverflowError` | **Stack** | Infinite/deep recursion (1.5) |
| `OutOfMemoryError: Java heap space` | **Heap** | A genuine leak (8.7), or `-Xmx` too small |
| `OutOfMemoryError: GC overhead limit exceeded` | **Heap** | >98% of time in GC, <2% reclaimed — a leak, about to OOM |
| `OutOfMemoryError: Metaspace` | **Metaspace** | **Classloader leak** (8.2) |
| `OutOfMemoryError: Direct buffer memory` | **Direct** | Unreleased NIO buffers |
| `OutOfMemoryError: unable to create native thread` | **Native** | Too many threads, or OS limits |
| `OutOfMemoryError: Requested array size exceeds VM limit` | **Heap** | Array > ~2³¹ elements |

> **Read the message, not just the class name.** Each variant points at a different
> region, a different cause, and a different fix. "We got an OOM" is not a diagnosis.

## ⭐ Why "everything is on the heap" is a useful lie

The standard teaching is: *primitives and references on the stack, objects on the heap.*

**Mostly true, and useful for pass-by-value (1.5). But the JIT breaks it.**

```java
void f() {
    var p = new Point(1, 2);        // does this allocate?
    IO.println(p.x() + p.y());
}
```

If **escape analysis** (8.8) proves `p` never leaves the method — never stored in a field,
never returned, never passed to something that might keep it — the JIT can apply **scalar
replacement**: delete the object entirely and keep `x` and `y` in registers.

**No heap allocation. No object. Nothing for the GC to collect.**

This is why:
- Micro-benchmarks that "prove allocation is expensive" often measure nothing (8.8)
- Small short-lived objects can be genuinely free
- "Avoid creating objects in a loop" is dated advice, applied without measurement

> The lie is useful because it's the right model for **reasoning about semantics**
> (pass-by-value, sharing between threads). It's the wrong model for reasoning about
> **performance**. Keep both.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| "We got an OOM" | Which one? Six different causes, six different fixes |
| `OutOfMemoryError: Metaspace` = too many classes | Almost always a **classloader leak** |
| Default `-Xmx` in a container is the container's memory | It's ~25%. Set it explicitly |
| The stack is garbage collected | It isn't — frames pop |
| Every `new` allocates | Escape analysis may delete it entirely |
| Catching `OutOfMemoryError` to recover | Your handler needs memory (4.1) |

## Recap

| Area | Shared? | Holds | Error |
|---|---|---|---|
| **Heap** | ✅ all threads | **Every object**; young (eden+survivors) → old | `Java heap space` |
| **Stack** | ❌ one per thread | Frames: locals + operand stack | `StackOverflowError` |
| **Metaspace** | ✅ | Class metadata, **native memory**, no default limit | `Metaspace` |
| **Code cache** | ✅ | JIT output | `CodeCache is full` |
| **Direct** | ✅ | Off-heap NIO buffers | `Direct buffer memory` |

| Fact | |
|---|---|
| ~1 MB stack per platform thread | Why virtual threads exist |
| Objects on heap, references on stack | Explains pass-by-value and thread sharing |
| Escape analysis | Can delete the allocation entirely |
