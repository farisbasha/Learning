# 8.2 — Class loading

> **What this is:** How code gets into a running JVM. **This is the layer frameworks live
> in, and the layer that produces the most baffling errors.**

---

## The three phases

```
LOADING  →  LINKING (verify → prepare → resolve)  →  INITIALISATION
```

| Phase | Does |
|---|---|
| **Loading** | Find the `.class` bytes, parse them, create the `Class` object |
| **Linking: verify** | Check the bytecode is well-formed and safe |
| **Linking: prepare** | Allocate static fields, set them to **default** values (`0`, `null`) |
| **Linking: resolve** | Turn symbolic references into direct ones (lazy — often deferred) |
| **Initialisation** | Run static initialisers and static field assignments (2.2) |

> Note **prepare** vs **initialisation**: `static int x = 5;` gets `0` in prepare and `5`
> in initialisation. That gap is real and observable in circular-initialisation bugs.

---

## ⭐ Bytecode verification — a security boundary

Before running anything, the JVM proves the bytecode can't break the machine:

- The operand stack never underflows or overflows
- Types match — no treating an `int` as a reference (8.1)
- `final` classes aren't subclassed; `final` fields aren't reassigned outside `<init>`
- Jumps land on real instruction boundaries
- Every local is assigned before use

```
java.lang.VerifyError: Bad type on operand stack
```

**Why it matters:** this is what makes the JVM a **sandbox**. Handcrafted or corrupted
bytecode cannot forge a reference, read arbitrary memory, or escape the type system. Java
applets — untrusted code from the internet — were only conceivable because of the
verifier.

> `-Xverify:none` disabled it. It was **deprecated in 13 and removed** — the JVM now
> ignores it, because "skip the security boundary to start 200ms faster" was never a
> good trade.

## ⭐ Exactly when a class is initialised

The rules matter, because static initialisers running "later than you expect" is a real
bug class (2.2).

**A class initialises on the first of:**

1. An instance is created — `new Foo()`
2. A static **method** is invoked
3. A static field is read or written — **unless it's a compile-time constant**
4. A **subclass** is initialised (the superclass goes first)
5. It's the main class
6. Reflective access — `Class.forName("Foo")`

**It does NOT initialise on:**

| Action | Why not |
|---|---|
| Declaring a variable of that type | No use yet |
| **Reading a `static final` compile-time constant** | **Inlined at compile time** (2.2) |
| Accessing a static field declared in a **superclass** | Only the declaring class initialises |
| `Class.forName(name, false, loader)` | The `false` means "don't initialise" |
| Array creation — `new Foo[10]` | No `Foo` instance exists |

```java
class Loud {
    static { IO.println("initialised"); }
    static final String NAME = "x";              // compile-time constant
    static final List<String> ITEMS = List.of(); // NOT a constant
}

Loud[] arr = new Loud[10];     // nothing printed
IO.println(Loud.NAME);         // nothing printed! — inlined
IO.println(Loud.ITEMS);        // "initialised"  ← now
```

**Initialisation is thread-safe and happens exactly once** — the JVM holds a lock per
class. That guarantee is what makes the enum singleton (2.7) and the holder idiom correct
with no synchronisation of your own:

```java
class Lazy {
    private static class Holder {                 // not initialised until first use
        static final Expensive INSTANCE = new Expensive();
    }
    static Expensive get() { return Holder.INSTANCE; }   // thread-safe, lazy, no locks
}
```

> ⚠️ If a static initialiser **throws**, the class is marked **erroneous permanently**.
> The first access throws `ExceptionInInitializerError`; every subsequent one throws
> `NoClassDefFoundError: Could not initialize class Foo` — which looks like a missing
> class and isn't. **Always look for the first occurrence in the log.**

## ⭐ The loader hierarchy and parent delegation

```
   Bootstrap  (native, no Java object — getClassLoader() returns null)
       │        loads java.*, the core JDK
       ▼
   Platform    loads JDK modules outside java.base (java.sql, java.xml…)
       │
       ▼
   Application loads your classpath  ←  this is the one you usually mean
       │
       ▼
   (custom loaders: web apps, plugins, OSGi…)
```

**Parent delegation** — the rule every loader follows:

```
load(name):
    1. already loaded?  → return it
    2. ask the PARENT first
    3. only if the parent fails, look yourself
```

**Why it exists — security and consistency.** You cannot ship a class called
`java.lang.String` and have it used: the application loader asks the platform loader, which
asks bootstrap, which finds the real one. Your fake is never reached.

(Belt and braces: the JVM *also* rejects any user-defined package starting with `java.`,
1.6.)

## ⭐ Class identity is name **plus** loader

> **Two classes with the same fully-qualified name, loaded by different loaders, are
> different types.**

```java
ClassCastException: com.example.User cannot be cast to com.example.User
```

That error looks impossible. It isn't — those are two distinct `Class` objects from two
loaders.

**Where it happens:**
- Application servers (Tomcat, WebLogic) — one loader per deployed app
- OSGi, plugin systems, hot reloading
- A jar present on **both** the app classpath and a plugin's classpath

**How to diagnose:**

```java
IO.println(a.getClass().getClassLoader());
IO.println(b.getClass().getClassLoader());     // different? that's your answer
```

## ⭐ `ClassNotFoundException` vs `NoClassDefFoundError`

**Different causes.** Distinguishing them saves hours.

| | `ClassNotFoundException` | `NoClassDefFoundError` |
|---|---|---|
| Type | Checked **Exception** (4.1) | **Error** |
| Trigger | **Explicit** lookup — `Class.forName`, `loadClass` | **Implicit** — the JVM needed it while linking |
| Means | "You asked for a class by name and it isn't there" | "It was there at compile time, not now — **or it failed to initialise**" |
| Usual cause | A typo, or a genuinely missing optional dependency | **Classpath mismatch**, or ⭐ **a static initialiser threw earlier** |

```java
Class.forName("com.example.Missing");        // → ClassNotFoundException
```

```java
new SomeClass();      // compiled fine; jar absent at runtime → NoClassDefFoundError
```

> ⭐ **The trap worth remembering:** `NoClassDefFoundError: Could not initialize class X`
> almost never means X is missing. It means X's static initialiser threw, probably much
> earlier in the log. Search backwards for `ExceptionInInitializerError`.

## Writing a custom classloader, once

Do this once to understand hot reloading and plugin systems:

```java
public class SimpleLoader extends ClassLoader {
    private final Path dir;

    public SimpleLoader(Path dir, ClassLoader parent) {
        super(parent);                                   // ← preserve delegation
        this.dir = dir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] bytes = Files.readAllBytes(dir.resolve(name.replace('.', '/') + ".class"));
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

> **Override `findClass`, not `loadClass`.** `loadClass` implements parent delegation;
> overriding it breaks the security model. `findClass` is the hook it calls when the
> parent fails.

**Hot reloading works by throwing the loader away**, not by reloading a class:

```java
var loader = new SimpleLoader(dir, parent);
var clazz = loader.loadClass("com.example.Plugin");
// ... later, to "reload":
loader = new SimpleLoader(dir, parent);      // a NEW loader → a NEW class identity
```

Which is exactly why hot reload produces the `X cannot be cast to X` error above — the old
and new versions are genuinely different types.

## Unloading, and why classes usually aren't unloaded

A class can be unloaded **only when its entire loader is unreachable** — the loader, every
class it defined, and every instance of those classes (8.7).

```
Class → ClassLoader → all its other Classes → their static fields → ...
```

One live reference anywhere keeps the whole graph alive. In practice:

- **Bootstrap/platform/application loaders are never unloaded** — they live for the JVM
- Custom loaders *can* be, if you're careful
- A **classloader leak** is the classic app-server bug: redeploy an app 20 times, and 20
  copies of every class stay in metaspace (8.3) → `OutOfMemoryError: Metaspace`

Common causes of classloader leaks: a `ThreadLocal` on a pooled thread, a JDBC driver
registered in a static registry, a shutdown hook, a logging framework holding the context
classloader.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `NoClassDefFoundError` = missing jar | Often a **static initialiser that threw** earlier |
| `X cannot be cast to X` is impossible | Two loaders. Print `getClassLoader()` |
| Overriding `loadClass` | Breaks parent delegation. Override `findClass` |
| Expecting a static block on declaration | Initialisation is **lazy**, and constants are inlined |
| Expecting classes to be unloaded | Only when the whole loader is unreachable |

---

## Recap

| Concept | One line |
|---|---|
| Phases | load → verify, prepare, resolve → initialise |
| Verification | A real **security boundary**; `-Xverify:none` is removed |
| Initialisation | Lazy, **exactly once, thread-safe**; constants don't trigger it |
| Failed init | Erroneous **permanently**; then reports as `NoClassDefFoundError` |
| Delegation | Ask the parent first — you can't override `java.lang.String` |
| **Identity** | **Name + loader.** Explains `X cannot be cast to X` |
| `CNFE` vs `NCDFE` | Explicit lookup vs implicit linking-or-init failure |
| Unloading | Only when the entire loader graph is unreachable |
