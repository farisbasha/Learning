# 8.7 — References and reachability

> **What this is:** The four strengths of reference, and **the only correct way to interact
> with the collector**. Plus the catalogue of leak shapes — which is the practically
> useful half of the page.

---

## ⭐ The four strengths

```java
import java.lang.ref.*;

Object strong  = new Object();                        // ordinary reference
SoftReference<Object>    soft    = new SoftReference<>(obj);
WeakReference<Object>    weak    = new WeakReference<>(obj);
PhantomReference<Object> phantom = new PhantomReference<>(obj, queue);
```

| Strength | Collected when | `get()` | Use for |
|---|---|---|---|
| **Strong** | Never, while reachable | n/a | Everything normal |
| **Soft** | Only under **memory pressure** | Returns or `null` | Memory-sensitive caches |
| **Weak** | At the **next GC** once no strong refs remain | Returns or `null` | Canonicalising maps, metadata |
| **Phantom** | Already finalised; **enqueued** after collection | **Always `null`** | Post-mortem cleanup |

```java
var weak = new WeakReference<>(new Object());
System.gc();
weak.get();       // likely null — nothing else referred to it
```

> **The ordering:** strong > soft > weak > phantom. The collector clears them in that
> order when it needs memory.

### Soft vs weak — the practical difference

```java
// soft: "keep this until memory is tight"
Map<Key, SoftReference<BigThing>> cache = new HashMap<>();

// weak: "drop this as soon as nobody else wants it"
Map<Key, WeakReference<Metadata>> meta = new HashMap<>();
```

> ⚠️ **`SoftReference` is a worse cache than it looks.** The JVM's clearing policy is
> opaque and heuristic — it tends to clear everything at once under pressure, giving you
> a cache that's full or empty with nothing in between. **Use a real cache library
> (Caffeine) with a size bound instead.**

## `WeakHashMap` and the patterns it enables

```java
Map<Config, ExpensiveResult> cache = new WeakHashMap<>();
```

**Keys are weakly referenced** — an entry disappears automatically once nothing else holds
its key (5.3).

```java
var key = new Config("x");
cache.put(key, compute(key));
cache.size();        // 1
key = null;          // drop the last strong reference
System.gc();
cache.size();        // 0 — the entry vanished
```

**The listener-registry pattern:**

```java
// ❌ the classic leak — the registry holds listeners forever
private final List<Listener> listeners = new ArrayList<>();

// ✅ listeners disappear when their owner is collected
private final Map<Listener, Boolean> listeners = new WeakHashMap<>();
```

> ⚠️ **Two traps:**
> 1. **Values are strongly referenced.** If a value refers to its own key, the entry never
>    clears. (Use `new WeakReference<>(value)` for the value too, or restructure.)
> 2. **Entries vanish nondeterministically**, whenever GC runs. Never use it where you
>    need the entry to still be there.

## `ReferenceQueue` and post-mortem cleanup

A `ReferenceQueue` is how you find out that something **was** collected:

```java
var queue = new ReferenceQueue<Connection>();
var ref = new PhantomReference<>(connection, queue);

// later, on a cleanup thread
Reference<?> dead = queue.remove();      // blocks until something is enqueued
releaseNativeHandle(dead);               // note: you can't touch the object — get() is null
```

`PhantomReference.get()` **always returns null** — deliberately. You cannot resurrect the
object, which is exactly the flaw that made finalizers dangerous.

## 💀 `finalize()` — a two-decade mistake

```java
@Override protected void finalize() { }      // 💀 deprecated 9, REMOVED
```

**Every one of these is a real, fundamental problem:**

| Problem | |
|---|---|
| **May never run** | No guarantee the JVM ever calls it. Not at exit either |
| **Unpredictable timing** | Runs on an unspecified thread, at an unspecified time |
| **Slows collection** | A finalizable object survives **at least two** GC cycles |
| **Can resurrect the object** | `finalize()` can store `this` somewhere — the object comes back from the dead |
| **Exceptions are swallowed** | A throw inside `finalize()` is ignored, leaving a half-cleaned object |
| **A security hole** | The finalizer attack: subclass, let the constructor throw validation, and `finalize()` still runs on the partially-built object |

### `Cleaner` — the supported replacement

```java
public class Resource implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    private final Cleaner.Cleanable cleanable;

    public Resource() {
        long handle = allocateNative();
        // ⭐ the state must NOT reference `this`, or it's never collected
        this.cleanable = CLEANER.register(this, new CleanupTask(handle));
    }

    // a STATIC class — capturing the outer instance would defeat the whole thing (2.9)
    private record CleanupTask(long handle) implements Runnable {
        public void run() { freeNative(handle); }
    }

    @Override public void close() { cleanable.clean(); }
}
```

> ⭐ **The critical rule:** the cleanup action must not reference the object being
> registered. If it does, the object is permanently reachable and never collected — the cleaner
> never fires. This is the same hidden-`this` problem as inner classes (2.9).

### But try-with-resources is still better

| | try-with-resources | `Cleaner` |
|---|---|---|
| When it runs | **Deterministically**, at the end of the block | Whenever GC gets around to it, or never |
| Visible in the code | ✅ | ❌ |
| Correct choice | **Almost always** | A safety net for native memory |

```java
try (var r = new Resource()) { ... }      // ✅ the right answer (4.3)
```

> **Use `Cleaner` only as a backstop** for when a caller forgets `close()`, and only when
> you hold native memory. If you think you need it, you probably need try-with-resources.

## ⭐ Common leak shapes

**A Java leak is unintentional reachability** (8.5). These are the shapes it takes — worth
knowing by sight, because they're most of what you'll actually meet.

### 1. Static collections

```java
private static final Map<String, Session> SESSIONS = new HashMap<>();   // a GC root (2.2)
// nothing ever removes
```

**The single most common leak.** A `static` field is a GC root, so everything it reaches
lives forever. Fix: bound it, evict it, or don't make it static.

### 2. Unremoved listeners and callbacks

```java
button.addActionListener(listener);
// the dialog closes... but the button still holds the listener,
// which holds the dialog, which holds everything on it
```

Fix: `removeActionListener` on teardown, or a `WeakHashMap` registry.

### 3. ⭐ `ThreadLocal` in a pooled thread

```java
private static final ThreadLocal<UserContext> CONTEXT = new ThreadLocal<>();

void handleRequest(Request r) {
    CONTEXT.set(new UserContext(r.user()));
    // ... handle it
    // ❌ never removed
}
```

**Why this is nasty:** in a thread pool the thread is **reused**, not destroyed. The
`ThreadLocal` value stays attached to that thread indefinitely — leaking the context, and
potentially leaking one request's user data into another's.

```java
try {
    CONTEXT.set(new UserContext(r.user()));
    handle(r);
} finally {
    CONTEXT.remove();                     // ✅ mandatory in pooled threads
}
```

It's also a classic **classloader leak** (8.2): a `ThreadLocal` holding an
application-classloader object on a container-owned pooled thread keeps the entire
application's classes alive after redeploy.

### 4. Inner class references

```java
private static class Task implements Runnable { }    // ✅
private class Task implements Runnable { }           // ❌ holds the outer instance
```

The hidden `this$0` field (2.9). A long-lived task holds its whole enclosing object alive.

### 5. Unclosed resources

Streams, connections, file handles — each holds buffers and native memory. Fix:
try-with-resources (4.3).

### 6. Mutated map keys

Not strictly a leak, but the same shape — an entry unreachable by lookup yet still
occupying memory (5.3, 2.5).

### 7. Growing caches with no eviction

```java
private final Map<Key, Value> cache = new HashMap<>();     // unbounded
```

Fix: a bounded `LinkedHashMap` LRU (5.3), or Caffeine.

## ⭐ Why `System.gc()` is not something you call

```java
System.gc();      // ❌
```

| | |
|---|---|
| **It's a hint** | The JVM may ignore it entirely — `-XX:+DisableExplicitGC` makes that official |
| **It usually triggers a FULL GC** | The most expensive kind (8.6), stopping the world |
| **It destroys the collector's tuning** | The generational heuristics are adaptive; a forced full GC discards what they learned |
| **It fixes nothing** | If memory is genuinely leaking, the objects are **reachable** — GC cannot collect them by definition |

> **If `System.gc()` appears to help, you have a leak** (things are reachable that
> shouldn't be) **or a sizing problem** (8.3). Fix the actual cause.

**The only legitimate uses:** benchmarking setup between measured runs, and forcing
reference clearing in a test — both outside production code.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `SoftReference` is a good cache | Opaque clearing policy. Use Caffeine |
| `WeakHashMap` values are weak | **Keys** are weak; values are strong |
| `Cleaner` replaces try-with-resources | It's a **backstop**. TWR is deterministic |
| A `Cleaner` action referencing `this` | The object is never collected; cleanup never runs |
| `ThreadLocal` is fine without `remove()` | In a **pooled** thread it leaks — and can leak data across requests |
| `System.gc()` before a memory-heavy operation | A full GC, discarded tuning, no benefit |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `finalize()` | try-with-resources; `Cleaner` as a backstop |
| `System.gc()` | Nothing. Find the real cause |
| `SoftReference`-based hand-rolled caches | Caffeine, or a bounded `LinkedHashMap` |
| Non-static inner classes for long-lived tasks | `static` nested classes |

---

## Recap

| Concept | One line |
|---|---|
| **Strong** | Normal. Never collected while reachable |
| **Soft** | Cleared under memory pressure. Poor cache semantics |
| **Weak** | Cleared at the next GC. `WeakHashMap`, listener registries |
| **Phantom** | `get()` always null; enqueued after collection, for cleanup |
| 💀 `finalize()` | Removed. May never run, can resurrect, a security hole |
| `Cleaner` | Backstop only; **the action must not reference the object** |
| **Leak shapes** | Static collections · listeners · **`ThreadLocal` in pools** · inner classes · unclosed resources · unbounded caches |
| `System.gc()` | Don't. If it helps, you have a different bug |

## Self-check

1. Why does a `ThreadLocal` leak in a thread pool but not in a thread you create and discard?
2. Why must a `Cleaner` cleanup action never reference the object it cleans up?
3. Someone adds `System.gc()` and memory usage improves. What have they actually discovered?
