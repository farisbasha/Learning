# 7.2 — Pattern matching for `switch`

> **What this is:** `switch` stops being a **jump table over constants** and becomes a
> **dispatch over shapes**. `Java 21`

---

## Coming from JS/Python/Dart

Python 3.10's `match`/`case` is the direct equivalent — same idea, same syntax family.
Rust's `match` is the model both were built from.

JS has nothing like this; you'd write an if-else chain on `typeof` or a discriminant field.

---

## The concepts

### Type patterns as case labels

```java
String describe(Object o) {
    return switch (o) {
        case Integer i  -> "int " + i;
        case String s   -> "string of length " + s.length();
        case int[] arr  -> "int array of " + arr.length;
        case null       -> "nothing";
        default         -> "unknown: " + o.getClass().getSimpleName();
    };
}
```

Compare with what it replaces:

```java
// ❌ the if-else chain
String describe(Object o) {
    if (o == null)             return "nothing";
    if (o instanceof Integer)  return "int " + (Integer) o;
    if (o instanceof String)   return "string of length " + ((String) o).length();
    if (o instanceof int[])    return "int array of " + ((int[]) o).length;
    return "unknown";
}
```

The switch version is an **expression** (1.2), so it returns a value and the compiler can
check it for completeness.

### ⭐ `case null` — explicit null handling

**This is a genuine change in behaviour.** Historically:

```java
switch (someString) {          // old-style switch on a String
    case "a" -> ...;
    default  -> ...;
}
// if someString is null → 💥 NullPointerException, before any case is considered
```

A `switch` has always thrown NPE on a null selector. With patterns you can opt in to
handling it:

```java
switch (o) {
    case null      -> "nothing";       // ✅ explicit
    case String s  -> "string: " + s;
    default        -> "other";
}
```

**The rules:**

| Written | Behaviour on null |
|---|---|
| No `case null` | 💥 `NullPointerException` (backwards compatible) |
| `case null ->` | Matches |
| `case null, default ->` | Matches, combined with default |

```java
case null, default -> "nothing or unknown";     // the common combined form
```

> **Important:** `default` alone does **not** catch null. You must write `case null`
> explicitly. This was deliberate — silently changing null behaviour would have broken
> existing code.

### ⭐ Exhaustiveness with a sealed hierarchy

This is the payoff, and it connects 2.8 and 1.2.

```java
sealed interface Shape permits Circle, Rectangle, Triangle { }
record Circle(double radius)        implements Shape { }
record Rectangle(double w, double h) implements Shape { }
record Triangle(double b, double h)  implements Shape { }

double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
        case Triangle t  -> 0.5 * t.b() * t.h();
    };                                        // ← NO default needed
}
```

The compiler knows `Shape` has exactly three subtypes (2.8), sees all three covered, and
accepts the switch as exhaustive.

**Now add a fourth:**

```java
sealed interface Shape permits Circle, Rectangle, Triangle, Square { }
record Square(double side) implements Shape { }
```

```
error: the switch expression does not cover all possible input values
```

**Every switch over `Shape` in the codebase stops compiling** until someone handles
`Square`. The compiler is your migration checklist.

> ⚠️ **Do not add a `default`.** It makes the switch trivially exhaustive and you lose
> exactly this benefit. Same rule as enums (2.7).
>
> ```java
> case Triangle t -> ...;
> default -> throw new IllegalStateException();   // ❌ now adding Square compiles silently
> ```

**Note:** exhaustive switches over sealed types get an implicit `MatchException` if a
subtype appears at runtime that wasn't there at compile time (possible with separate
compilation). You don't write it; it exists so the switch can't silently fall through.

### ⭐ Guarded patterns — `when`

A pattern plus a boolean condition:

```java
String classify(Object o) {
    return switch (o) {
        case Integer i when i < 0    -> "negative";
        case Integer i when i == 0   -> "zero";
        case Integer i when i > 100  -> "large";
        case Integer i               -> "small positive";
        case String s when s.isBlank()-> "blank string";
        case String s                -> "string: " + s;
        default                      -> "other";
    };
}
```

`when` is a **contextual keyword** — it only means this here, so existing variables named
`when` still work.

**Order matters:** guarded cases must come **before** the unguarded version of the same
type, or the unguarded one catches everything first.

```java
case Integer i              -> "any int";
case Integer i when i > 100 -> "large";     // ❌ unreachable — dominated
```

> A guarded pattern **never** makes a switch exhaustive on its own — the compiler can't
> prove `when i > 0` covers everything. You always need an unguarded fallback.

### ⭐ Dominance ordering

**A broader pattern before a narrower one is a compile error.**

```java
switch (o) {
    case Object obj -> "anything";      // ❌
    case String s   -> "string";        // error: this case label is dominated
}
```

`Object` matches everything, so `String` could never be reached. The compiler rejects it
rather than letting you ship dead code.

Same for a class hierarchy:

```java
switch (shape) {
    case Shape s  -> ...;      // ❌ dominates everything below
    case Circle c -> ...;      // unreachable
}
```

**The rule: order from most specific to most general** — the same discipline as `catch`
blocks (4.3). Unlike `catch`, the compiler enforces it in both directions.

> `case null` is never dominated and can go anywhere, but conventionally goes first or is
> combined with `default`.

### ⭐ Switch over sealed interfaces as the replacement for the visitor pattern

**The classic visitor:**

```java
// the 1994 way — an interface, a method per type, and a double dispatch
interface ShapeVisitor<R> {
    R visitCircle(Circle c);
    R visitRectangle(Rectangle r);
    R visitTriangle(Triangle t);
}

interface Shape {
    <R> R accept(ShapeVisitor<R> visitor);       // every shape must implement this
}

class Circle implements Shape {
    public <R> R accept(ShapeVisitor<R> v) { return v.visitCircle(this); }
}
// ... and the same boilerplate in Rectangle and Triangle

class AreaVisitor implements ShapeVisitor<Double> {
    public Double visitCircle(Circle c)    { return Math.PI * c.radius() * c.radius(); }
    public Double visitRectangle(Rectangle r) { return r.w() * r.h(); }
    public Double visitTriangle(Triangle t)   { return 0.5 * t.b() * t.h(); }
}

double area = shape.accept(new AreaVisitor());
```

**The modern version:**

```java
double area = switch (shape) {
    case Circle c    -> Math.PI * c.radius() * c.radius();
    case Rectangle r -> r.w() * r.h();
    case Triangle t  -> 0.5 * t.b() * t.h();
};
```

| | Visitor | Sealed + switch |
|---|---|---|
| Boilerplate | An interface + `accept` in every type | **None** |
| Adding an operation | A new visitor class | A new switch, anywhere |
| Adding a type | Change the visitor interface → **every visitor breaks** (that's the point) | Every switch fails to compile (same point) |
| Exhaustiveness | By interface definition | **By the compiler** |
| Readability | The logic is scattered across classes | One place |

> **The visitor pattern existed to get compile-checked exhaustive dispatch in a language
> without pattern matching.** Java has pattern matching now. The pattern is obsolete for
> this purpose.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `default` in a sealed switch | Kills exhaustiveness checking. Omit it |
| Expecting `default` to catch null | It doesn't. Write `case null` |
| Broad pattern first | Compile error — dominance |
| Unguarded before guarded, same type | The guarded one is unreachable |
| Guarded patterns making a switch exhaustive | They never do |
| `case String s` on a null selector without `case null` | NPE |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| The visitor pattern for closed hierarchies | Sealed interface + switch |
| A long `if (o instanceof X)` chain | `switch` with type patterns |
| `default -> throw new IllegalStateException()` over a sealed type | Omit `default` entirely |

---

## Recap

| Concept | One line |
|---|---|
| Type patterns as cases | `case String s ->` `Java 21` |
| `case null` | Explicit. Without it, null still throws NPE |
| **Exhaustiveness** | Sealed hierarchy + no `default` = compiler-enforced completeness |
| `when` guards | Pattern + condition; must precede the unguarded case |
| **Dominance** | Specific before general, or compile error |
| Visitor pattern | Replaced entirely |
