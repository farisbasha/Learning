# 7.4 — The combined idiom

> **What this is:** **The single most valuable step in this part.** Everything above —
> records (2.6), sealed types (2.8), switch expressions (1.2), patterns (7.1–7.3) — was
> built to combine *here*. Eight years of language design, one idiom.

---

## ⭐ The idiom

> **Sealed interface + record implementations + exhaustive switch.**
>
> Model your domain as a **closed set of shapes**, and let the compiler enforce
> completeness.

```java
sealed interface PaymentResult
    permits Approved, Declined, Pending { }

record Approved(String transactionId, BigDecimal amount) implements PaymentResult { }
record Declined(String reason, boolean retryable)        implements PaymentResult { }
record Pending(Instant retryAfter)                       implements PaymentResult { }
```

```java
String message(PaymentResult r) {
    return switch (r) {
        case Approved(String id, BigDecimal amt) -> "Paid %s (ref %s)".formatted(amt, id);
        case Declined(String reason, boolean retry) when retry -> "Failed: " + reason + " — try again";
        case Declined(String reason, _)          -> "Failed permanently: " + reason;
        case Pending(Instant after)              -> "Pending until " + after;
    };
}
```

**What the compiler guarantees here:**

1. `r` cannot be any type other than those three (sealed).
2. Every case is handled — **no `default`**.
3. The components are typed and bound — no casts, no accessor calls.
4. Add a fourth result type, and **this method stops compiling** until you handle it.

## ⭐ Data-oriented programming in Java

The idiom has a name and a philosophy behind it:

> **Data is immutable and transparent. Behaviour lives outside it.**

| Classical OO | Data-oriented |
|---|---|
| Data and behaviour bundled in a class | **Data is plain records** |
| State is encapsulated and hidden | **State is transparent** (records expose components) |
| Behaviour is a method on the object | **Behaviour is a function over the data** |
| Extensibility: add new **types** | Extensibility: add new **operations** |
| Dispatch: virtual method (2.3) | Dispatch: exhaustive `switch` |

```java
// classical — behaviour inside
interface Shape { double area(); }
record Circle(double r) implements Shape {
    public double area() { return Math.PI * r * r; }
}

// data-oriented — behaviour outside
sealed interface Shape permits Circle, Rectangle { }
record Circle(double r) implements Shape { }              // just data

final class Shapes {                                       // behaviour lives here
    static double area(Shape s) { return switch (s) { ... }; }
    static double perimeter(Shape s) { return switch (s) { ... }; }
    static String render(Shape s) { return switch (s) { ... }; }
}
```

> This is not a rejection of OO — it's a recognition that **some things are data, not
> objects** (2.5's value-vs-identity distinction). A `PaymentResult` has no identity, no
> lifecycle and no behaviour of its own. Forcing it into an object with methods was
> always a bit of a lie.

## ⭐ When this beats polymorphism, and when polymorphism wins

### The expression problem, stated honestly

You have **types** (Circle, Rectangle) and **operations** (area, render, serialise).
You want to add both without modifying existing code. **You can have one, not both.**

| | Add a new **type** | Add a new **operation** |
|---|---|---|
| **Polymorphism** (interface + methods) | ✅ Easy — write a new class | ❌ **Change the interface → every implementation breaks** |
| **Sealed + switch** | ❌ **Change `permits` → every switch breaks** | ✅ Easy — write a new function anywhere |

This is a genuine, proven trade-off. Neither approach is better; they fail in opposite
directions.

### So which do you choose?

**Ask: which axis changes more often?**

| Situation | Use |
|---|---|
| **Open set of types**, stable operations | **Polymorphism** |
| **Closed set of types**, growing operations | **Sealed + switch** |
| Plugins, extensions, third parties implement your interface | **Polymorphism** — you *can't* seal it |
| Results, states, AST nodes, commands, protocol messages | **Sealed + switch** |
| The behaviour genuinely belongs to the data | **Polymorphism** |
| The behaviour depends on the caller's context | **Sealed + switch** |

**Concrete examples:**

```java
// ✅ polymorphism — the set of implementations is open by design
interface PaymentProvider { Result charge(Card c, Money m); }
// Stripe, PayPal, and whoever else — you don't control the list

// ✅ sealed + switch — the set of results is closed by definition
sealed interface Result permits Success, Failure { }
// there are exactly two outcomes; new *operations* on them appear constantly
```

> ⚠️ **Don't seal something that should be open.** If third parties need to implement it —
> a plugin API, an extension point, a strategy — an open interface is correct, and
> sealing it is a design error you can't undo without a breaking change.

## Modelling with the idiom

### Results

```java
sealed interface Result<T> permits Ok, Err { }
record Ok<T>(T value)              implements Result<T> { }
record Err<T>(String code, String message) implements Result<T> { }
```

Failure as a value rather than an exception (4.2) — works in streams, no stack-capture
cost (4.1), exhaustively checked.

### State machines

```java
sealed interface OrderState permits Draft, Placed, Shipped, Delivered, Cancelled { }
record Draft()                                implements OrderState { }
record Placed(Instant at, PaymentRef payment) implements OrderState { }
record Shipped(String tracking, Instant at)   implements OrderState { }
record Delivered(Instant at, String signedBy) implements OrderState { }
record Cancelled(String reason, Instant at)   implements OrderState { }
```

**Each state carries exactly the data that state has.** `Shipped` has a tracking number;
`Draft` doesn't. A single class with nullable `trackingNumber`/`cancelReason`/`signedBy`
fields can represent nonsense (2.10 — make illegal states unrepresentable). This cannot.

Transitions become total functions:

```java
OrderState cancel(OrderState current, String reason) {
    return switch (current) {
        case Draft _, Placed _ -> new Cancelled(reason, Instant.now());
        case Shipped _         -> throw new IllegalStateException("already shipped");
        case Delivered _       -> throw new IllegalStateException("already delivered");
        case Cancelled c       -> c;                      // idempotent
    };
}
```

### Parsed structures (ASTs)

```java
sealed interface Json permits JNull, JBool, JNumber, JString, JArray, JObject { }
record JNull()                             implements Json { }
record JBool(boolean value)                implements Json { }
record JNumber(double value)               implements Json { }
record JString(String value)               implements Json { }
record JArray(List<Json> items)            implements Json { }
record JObject(Map<String, Json> fields)   implements Json { }

String render(Json j) {
    return switch (j) {
        case JNull()            -> "null";
        case JBool(boolean b)   -> String.valueOf(b);
        case JNumber(double d)  -> String.valueOf(d);
        case JString(String s)  -> "\"" + s + "\"";
        case JArray(List<Json> items) ->
            items.stream().map(this::render).collect(joining(",", "[", "]"));
        case JObject(Map<String, Json> f) ->
            f.entrySet().stream()
             .map(e -> "\"" + e.getKey() + "\":" + render(e.getValue()))
             .collect(joining(",", "{", "}"));
    };
}
```

> Note `case JNull()` — an empty record pattern. It matches the type and destructures
> zero components.

### API responses and commands

```java
sealed interface Command permits Create, Update, Delete { }
record Create(String name, Map<String,String> attrs) implements Command { }
record Update(String id, Map<String,String> changes) implements Command { }
record Delete(String id)                             implements Command { }
```

## ⭐ The comparison that makes it click

```typescript
// TypeScript — discriminated union
type Shape =
  | { kind: "circle";    radius: number }
  | { kind: "rectangle"; w: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":    return Math.PI * s.radius ** 2;
    case "rectangle": return s.w * s.h;
  }                                    // TS checks exhaustiveness
}
```

```rust
// Rust — enum + match
enum Shape { Circle(f64), Rectangle(f64, f64) }

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle(r)       => PI * r * r,
        Shape::Rectangle(w, h) => w * h,
    }                                  // rustc checks exhaustiveness
}
```

```java
// Java — sealed + records + switch
sealed interface Shape permits Circle, Rectangle { }
record Circle(double r)            implements Shape { }
record Rectangle(double w, double h) implements Shape { }

double area(Shape s) {
    return switch (s) {
        case Circle(double r)              -> Math.PI * r * r;
        case Rectangle(double w, double h) -> w * h;
    };                                 // javac checks exhaustiveness
}
```

**Same idea, three languages.** Java took the longest to get here and arrived with the
most verbose declaration syntax — but the *use site* is just as good, and unlike TypeScript
it's enforced at runtime too (the types are real, not erased structural shapes).

## ⭐ How much shorter modern Java is

Take the shape hierarchy as a 2014-era Java developer would have written it:

```java
// ===== 2014 =====  (~70 lines for three shapes and one operation)
public abstract class Shape {
    public abstract double area();
}

public final class Circle extends Shape {
    private final double radius;
    public Circle(double radius) {
        if (radius < 0) throw new IllegalArgumentException("radius must be >= 0");
        this.radius = radius;
    }
    public double getRadius() { return radius; }
    @Override public double area() { return Math.PI * radius * radius; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Circle circle = (Circle) o;
        return Double.compare(circle.radius, radius) == 0;
    }
    @Override public int hashCode() { return Objects.hash(radius); }
    @Override public String toString() { return "Circle{radius=" + radius + '}'; }
}
// ... Rectangle: another 20 lines
// ... Triangle:  another 20 lines
```

```java
// ===== 2025 =====  (9 lines, same behaviour, plus exhaustiveness checking)
sealed interface Shape permits Circle, Rectangle, Triangle { }

record Circle(double radius) implements Shape {
    Circle { if (radius < 0) throw new IllegalArgumentException("radius must be >= 0"); }
}
record Rectangle(double w, double h) implements Shape { }
record Triangle(double b, double h)  implements Shape { }

static double area(Shape s) {
    return switch (s) {
        case Circle(double r)              -> Math.PI * r * r;
        case Rectangle(double w, double h) -> w * h;
        case Triangle(double b, double h)  -> 0.5 * b * h;
    };
}
```

**~70 lines → ~15**, and the new version has something the old one didn't: **the compiler
proves you handled every shape.**

> **Try this yourself on real code.** Find a 2014-era hierarchy in a codebase you know and
> rewrite it. It's the exercise that makes this part land.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Sealing an extension point | Third parties can't implement it. Unfixable without a breaking change |
| `default` in the switch | Loses the exhaustiveness guarantee entirely |
| Using it for types with identity/lifecycle | Records are for values (2.5). An entity isn't one |
| Believing it replaces OO | It replaces OO **for closed data**. Open type sets still need polymorphism |
| Deep nesting in the switch | Two levels max; bind and re-destructure |

---

## Recap

| Concept | One line |
|---|---|
| **The idiom** | Sealed interface + record implementations + exhaustive switch |
| Data-oriented | Data is **immutable and transparent**; behaviour lives outside |
| **Expression problem** | Polymorphism: easy new **types**. Sealed+switch: easy new **operations** |
| Choose by | Which axis changes more often. Open type set → polymorphism |
| Models | Results, state machines, ASTs, commands, API responses |
| Equivalent to | TS discriminated unions, Rust `enum` + `match` |
| Payoff | ~70 lines → ~15, **plus compiler-checked completeness** |
