# 7.3 — Record patterns

> **What this is:** **Destructuring** — which you already know from JavaScript — arriving
> in Java **with types attached**. `Java 21`

---

## Coming from JS/Python/Dart

```javascript
const { x, y } = point;                      // JS object destructuring
const [first, ...rest] = array;
```
```python
match shape:
    case Circle(radius=r): ...               # Python 3.10 structural matching
```

Java's version is **positional** (by component order, not by name) and **type-checked**.

---

## The concepts

### `case Point(int x, int y)` — match and decompose in one step

```java
record Point(int x, int y) { }

// ❌ match, then pull the pieces out by hand
if (o instanceof Point p) {
    int x = p.x();
    int y = p.y();
    IO.println(x + y);
}

// ✅ record pattern
if (o instanceof Point(int x, int y)) {
    IO.println(x + y);                       // x and y already bound
}
```

In a switch:

```java
double area(Shape s) {
    return switch (s) {
        case Circle(double r)              -> Math.PI * r * r;
        case Rectangle(double w, double h) -> w * h;
        case Triangle(double b, double h)  -> 0.5 * b * h;
    };
}
```

Compare with 7.2's version (`case Circle c -> ... c.radius() ...`) — the accessor calls
disappear.

**Positional, not named.** The components bind in **declaration order**:

```java
record Point(int x, int y) { }
case Point(int a, int b)        // a = x, b = y — the NAMES here are yours to choose
```

You can't skip or reorder. That's the trade for it being type-checked.

### Nested record patterns

They compose to any depth:

```java
record Point(int x, int y) { }
record Line(Point start, Point end) { }
record Path(Line first, Line second) { }

switch (obj) {
    case Line(Point(int x1, int y1), Point(int x2, int y2)) ->
        Math.hypot(x2 - x1, y2 - y1);

    case Path(Line(Point p1, var p2), Line l2) ->
        ...;                                  // mix depths freely
}
```

**How deep can they go?** No limit in the language. In practice, **two levels is
readable, three is pushing it**:

```java
// ⚠️ technically legal, practically unreadable
case Order(Customer(Address(String street, String city, _), _), List<Item> items) -> ...
```

Past two levels, bind the intermediate object and destructure in a second step.

### Nesting is also a *test*

This is the powerful bit. A nested pattern matches only if the **inner** pattern matches
too:

```java
sealed interface Expr permits Num, Add { }
record Num(int value)             implements Expr { }
record Add(Expr left, Expr right) implements Expr { }

int simplify(Expr e) {
    return switch (e) {
        case Add(Num(int a), Num(int b)) -> a + b;    // ← only matches Add of TWO Nums
        case Add(Expr l, Expr r)         -> simplify(l) + simplify(r);
        case Num(int n)                  -> n;
    };
}
```

The first case is a **structural test**: "an `Add` whose both sides are `Num`". Writing
that with `instanceof` takes five lines and two nested `if`s.

### `var` inside patterns

```java
case Point(var x, var y)              -> x + y;         // inferred as int
case Line(var start, var end)         -> ...;           // inferred as Point
case Add(var left, Num(int n))        -> ...;           // mix
```

`var` infers the component's declared type (1.1). Use it when the type is obvious from the
record name, spell it out when it isn't.

> ⚠️ `var` in a pattern is **not** a wildcard — it still binds a variable and still
> requires the component to be present. For "I don't care", use `_`.

### ⭐ Unnamed patterns and variables `_` `Java 22`

```java
case Point(int x, _)                  -> x;             // ignore y
case Order(Customer c, _, _)          -> c;             // ignore the rest
case Add(_, _)                        -> "some addition";
```

`_` discards the component — **no variable is created**, so there's no unused-variable
warning and no name to invent.

It works outside patterns too:

```java
// unused loop variable
for (var _ : items) count++;

// unused catch binding
try { ... } catch (NumberFormatException _) { return 0; }

// unused lambda parameter
map.forEach((_, v) -> IO.println(v));

// unused local from a method you call for its side effect
var _ = queue.poll();
```

> `_` stopped being a legal identifier in Java 9 precisely to reserve it for this. If you
> see `int _ = 5` in very old code, that's why it no longer compiles.

### ⭐ Why this only works on records

```java
class Point {                          // a regular class
    private final int x, y;
    public int x() { return x; }
    public int y() { return y; }
}

case Point(int x, int y) -> ...        // ❌ compile error — Point is not a record
```

**The reason:** a record's **canonical constructor defines a reliable deconstruction.**

```java
record Point(int x, int y) { }
//            ↑ this header is BOTH the construction and the destruction contract
```

The language knows, with certainty, that `new Point(a, b)` produces a `Point` whose `x()`
is `a` and `y()` is `b`. That guarantee — construction and deconstruction are exact
inverses — is what makes the pattern sound.

A regular class has no such guarantee. Its constructor might transform, validate, ignore
or derive its arguments, and its getters might compute values that were never passed in.
There's nothing to invert.

> This is the clearest example of why records aren't "just less typing" — the
> transparency they guarantee is what makes a whole language feature possible.
> **Records and record patterns were designed as one feature** (2.6).

Future Java may add **deconstruction patterns** for ordinary classes (an explicit
`pattern Point(int x, int y)` declaration). Not yet.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `case Point(int y, int x)` to reorder | **Positional.** The names are yours, the order is the record's |
| Destructuring a non-record | Compile error. Records only |
| `var` as a wildcard | It still binds. Use `_` |
| Three-plus levels of nesting | Legal, unreadable. Bind and re-destructure |
| Expecting a nested pattern to always match | It's also a **test** — the inner pattern must match |
| Type mismatch in the pattern | `case Point(String s, int y)` won't compile — components are typed |

---

## Recap

| Concept | One line |
|---|---|
| `case Point(int x, int y)` | Match **and** decompose. `Java 21` |
| Positional | Binds in component declaration order; names are yours |
| Nested | Composes to any depth — and each level is also a **test** |
| `var` | Infers the component type; still binds |
| **`_`** | `Java 22`. Discards — no variable, no warning. Works in loops, catch, lambdas |
| **Records only** | The canonical constructor guarantees construction and deconstruction are inverses |
