# 10.2 — Character encoding

> **What this is:** Short step, **disproportionate payoff**. Encoding bugs are among the
> most annoying to diagnose — they appear as mojibake in production and nowhere else.

---

## ⭐ Bytes versus characters

> **A file, a socket and a terminal contain *bytes*. Your program thinks in *characters*.
> An *encoding* is the mapping between them.**

```
"héllo"  ──encode(UTF-8)──►  68 C3 A9 6C 6C 6F        (6 bytes for 5 characters)
"héllo"  ──encode(Latin-1)─►  68 E9 6C 6C 6F           (5 bytes)
```

Decode with the wrong one and you get **mojibake**:

```
UTF-8 bytes read as Latin-1:  "hÃ©llo"
```

| Encoding | Notes |
|---|---|
| **UTF-8** | 1–4 bytes per character. ASCII-compatible. **The answer, always** |
| UTF-16 | 2 or 4 bytes. **What Java uses internally** |
| Latin-1 (ISO-8859-1) | 1 byte, 256 characters only |
| ASCII | 7-bit, 128 characters |

---

## Java strings are UTF-16 internally

```java
"héllo".length()      // 5 — chars (UTF-16 code units, 1.1)
```

A `char` is a **UTF-16 code unit**, not a character (1.1). Since `Java 9`, the JVM stores
Latin-1-only strings as one byte per char internally (**compact strings**, 1.3) — but the
API still presents UTF-16.

> **The boundary is where the bug lives:** every time bytes become a `String` or a `String`
> becomes bytes, an encoding is chosen. If you didn't choose it, something else did.

---

## ⭐ UTF-8 is now the default `Java 18`

**Before Java 18**, the default charset came from the **operating system**:

| Platform | Default was |
|---|---|
| Linux/macOS | Usually UTF-8 |
| **Windows** | **windows-1252** or a regional codepage |
| A Docker container with no locale set | **US-ASCII** ⚠️ |

```java
new String(bytes);                  // ⚠️ used the platform default
"x".getBytes();                     // ⚠️ same
new FileReader("f.txt");            // ⚠️ same
```

**This caused a decade of bugs of exactly one shape:** works on the developer's Mac, breaks
on the Linux CI server, breaks differently on a Windows machine, and breaks in a container
that has no `LANG` set.

`Java 18` (JEP 400) made **UTF-8 the default on every platform**. That single change quietly
fixed a whole bug class.

```bash
-Dfile.encoding=UTF-8            # no longer needed on 18+
java -XshowSettings:properties -version 2>&1 | grep encoding
```

> ⚠️ **But don't rely on it.** Code that must outlive its default — a library, anything
> reading a format you didn't create — should **always be explicit**.

---

## ⭐ Always specify a charset

```java
// ❌ implicit — depends on the JVM version and platform
new String(bytes);
"text".getBytes();
new FileReader("f.txt");
new InputStreamReader(in);
Files.readAllLines(path);          // (this one actually defaults to UTF-8, always)

// ✅ explicit — behaves identically everywhere, forever
new String(bytes, StandardCharsets.UTF_8);
"text".getBytes(StandardCharsets.UTF_8);
new InputStreamReader(in, StandardCharsets.UTF_8);
Files.readString(path, StandardCharsets.UTF_8);
```

### `StandardCharsets`, never the string-named overloads

```java
// ❌ throws a CHECKED UnsupportedEncodingException you must catch
new String(bytes, "UTF-8");

// ✅ a constant — no exception, no typo possible
new String(bytes, StandardCharsets.UTF_8);
```

`StandardCharsets.UTF_8`, `US_ASCII`, `ISO_8859_1`, `UTF_16`. The string-named versions
exist from 1996 and force you to handle an exception for a charset that is guaranteed to
exist.

> **`java.nio.file.Files` methods default to UTF-8 regardless of the platform**, always
> have, and are another reason to prefer them (10.3).

## ⭐ Normalisation and why `length()` isn't what a user sees

**The same visible character can have multiple byte representations:**

```java
String a = "é";              // U+00E9          — a single precomposed code point
String b = "é";        // U+0065 U+0301   — "e" + combining acute accent

a.equals(b);                 // false! 😱
a.length();                  // 1
b.length();                  // 2
```

They look **identical** on screen and are different strings. This breaks equality, map
keys (2.5), searching and sorting.

**The fix — normalise:**

```java
import java.text.Normalizer;

String na = Normalizer.normalize(a, Normalizer.Form.NFC);
String nb = Normalizer.normalize(b, Normalizer.Form.NFC);
na.equals(nb);               // ✅ true
```

| Form | Does |
|---|---|
| **NFC** | **Compose** — combine into precomposed forms. **The usual choice** |
| NFD | Decompose into base + combining marks |
| NFKC / NFKD | Also fold compatibility characters (`ﬁ` → `fi`, `①` → `1`) |

> **Normalise to NFC at your input boundary** — usernames, search terms, anything compared
> or stored. macOS filesystems hand you NFD; most of the web hands you NFC. That mismatch
> is a real and confusing source of "the same name doesn't match".

### Three different "lengths"

```java
String s = "👨‍👩‍👧‍👦";           // family emoji — ONE thing a user sees

s.length();                     // 11 — UTF-16 code units
s.codePointCount(0, s.length()); //  7 — code points
// grapheme clusters:            //  1 — what a user calls "a character"
```

```java
// code points (1.1)
s.codePoints().forEach(cp -> ...);

// grapheme clusters — needs BreakIterator
var it = BreakIterator.getCharacterInstance();
it.setText(s);
```

> ⭐ **`length()` is a count of UTF-16 code units. It is not a count of characters, and
> it is definitely not what a user sees.** Any "max 20 characters" validation written with
> `length()` is wrong for emoji and many scripts.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `getBytes()` with no charset | Platform-dependent before Java 18 |
| `new String(bytes, "UTF-8")` | Forces a pointless checked exception. Use `StandardCharsets` |
| `"é".equals("é")` failing | Different normalisation forms |
| `length()` as a character count | UTF-16 **code units** |
| Assuming the container has a locale | A bare container often defaults to ASCII pre-18 |
| Setting `-Dfile.encoding` at runtime | Unreliable — many places cache the charset at startup |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `new String(bytes, "UTF-8")` | `StandardCharsets.UTF_8` |
| `new FileReader(f)` / `new FileWriter(f)` | `Files.newBufferedReader(path, UTF_8)` |
| Relying on the platform default | Be explicit |

---

## Recap

| Concept | One line |
|---|---|
| Encoding | The mapping between **bytes** and **characters** |
| Java strings | **UTF-16 internally**; files and sockets are bytes |
| `Java 18` | **UTF-8 is the default everywhere** — a decade of bugs fixed |
| Always | Pass `StandardCharsets.UTF_8` explicitly anyway |
| Normalisation | `"é"` has two forms. **Normalise to NFC at the boundary** |
| `length()` | UTF-16 code units — not characters, not graphemes |
