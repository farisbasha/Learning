# 10.5 — Serialization

> **What this is:** **Learn it to recognise it and remove it.** This is a step about *why
> something is dangerous*, not how to use it.

---

## How it works

```java
class User implements Serializable {          // a marker interface — no methods
    private static final long serialVersionUID = 1L;
    private String name;
    private transient String password;         // transient = NOT serialized
}
```

```java
try (var out = new ObjectOutputStream(Files.newOutputStream(path))) {
    out.writeObject(user);                     // writes the whole OBJECT GRAPH
}

try (var in = new ObjectInputStream(Files.newInputStream(path))) {
    User u = (User) in.readObject();
}
```

**It serialises the entire reachable object graph** — every referenced object, transitively,
must also be `Serializable`. One non-serialisable field anywhere in the graph throws
`NotSerializableException`.

**`serialVersionUID`** is a version stamp. If you don't declare one, the compiler computes
it from the class's shape — so **adding a field silently breaks deserialisation of old
data** with `InvalidClassException`.

---

## ⭐ Why it's considered one of Java's worst mistakes

Brian Goetz has called it a "horrible mistake" and there is an active JDK effort to
deprecate and remove it. Four reasons:

### 1. It bypasses constructors — no invariant you wrote is enforced

**This is the fundamental flaw.**

```java
record Range(int low, int high) { }              // (2.6)
class RangeBean implements Serializable {
    private final int low, high;
    RangeBean(int low, int high) {
        if (low > high) throw new IllegalArgumentException();   // ⭐ the invariant
        this.low = low; this.high = high;
    }
}
```

Deserialisation **does not call your constructor**. It allocates the object and writes the
fields directly from the stream. So an attacker — or a corrupted file — can hand you a
`RangeBean` with `low = 100, high = 0`.

> ⭐ **Every validation from 2.10 and 4.4 — validate at the boundary, make illegal states
> unrepresentable — is simply bypassed.** Serialization is an invisible second constructor
> for every serialisable class, one you didn't write and can't see.

### 2. It's an extended, invisible public API

Every `private` field becomes part of your published format. Rename a field and you break
every consumer of old data. **Encapsulation (2.1) does not apply.**

### 3. ⭐ The security record

**Deserialising untrusted data is a remote-code-execution class of vulnerability.**

The mechanism: the stream doesn't just contain data — it names **classes to instantiate**.
An attacker crafts a stream referencing classes that are on your classpath and whose
deserialisation logic (`readObject`, or `finalize`, 8.7) has side effects. Chain enough of
them together — a **gadget chain** — and you get arbitrary code execution.

The attacker does not need your code to be buggy. They need a vulnerable class *anywhere*
on your classpath. Commons-Collections, Spring and Groovy have all provided famous ones.

> **This is not theoretical.** It is behind a long list of critical CVEs across the Java
> ecosystem — including some of the largest breaches of the last decade.

**The rule: never deserialise data you did not produce and cannot authenticate.**

### 4. It's slow and produces a bloated format

Reflection-heavy (11.6), and the output embeds full class metadata.

## Serialization filters — mitigation `Java 9`

```java
var filter = ObjectInputFilter.Config.createFilter(
    "com.example.**;java.base/*;!*");     // allow-list, reject everything else
ois.setObjectInputFilter(filter);
```

```bash
-Djdk.serialFilter=com.example.**;!*
```

`Java 17` added filter factories for per-context filters.

> ⚠️ **A filter is a mitigation, not a fix.** It narrows the gadget surface; it doesn't
> restore constructor invariants or make the format safe. **The fix is not to use it.**

---

## ⭐ Records serialize differently — and correctly

```java
record Point(int x, int y) implements Serializable { }
```

**A record deserialises through its canonical constructor** (2.6) — so:

| | Regular class | **Record** |
|---|---|---|
| Deserialisation path | Direct field writes, **no constructor** | ⭐ **The canonical constructor** |
| Compact-constructor validation | Bypassed | ✅ **Enforced** |
| `readObject`/`writeObject` hooks | Honoured | **Ignored** — cannot be customised |
| Gadget-chain surface | Large | Much smaller |

```java
record Range(int low, int high) implements Serializable {
    Range {
        if (low > high) throw new IllegalArgumentException();   // ⭐ RUNS on deserialisation
    }
}
```

> **This is a deliberate design decision**, and a good illustration of records being more
> than syntax (2.6): because a record's canonical constructor is a guaranteed
> deconstruction/reconstruction contract (7.3), serialisation can safely route through it.
>
> It doesn't make serialisation *safe* — the RCE risk comes from other classes on the
> classpath — but it removes the invariant-bypass flaw for your own types.

## ⭐ What to use instead

| Instead | For |
|---|---|
| **JSON** — Jackson, Gson | APIs, config, anything human-inspectable |
| **Protocol Buffers / Avro** | High-volume, schema-evolved, cross-language |
| **CBOR / MessagePack** | Compact binary, JSON-like model |
| **An explicit format you control** | When you want no surprises at all |

```java
// Jackson — constructors ARE called, validation runs, the format is explicit
var mapper = new ObjectMapper();
String json = mapper.writeValueAsString(user);
User u = mapper.readValue(json, User.class);
```

**What you gain:** a schema you control, cross-language readability, versioning you can
reason about, no gadget chains, and **your constructors actually run**.

> Jackson deserialises records through the canonical constructor natively (since 2.12), so
> compact-constructor validation works there too.

## Where you'll still meet it

| Place | Why |
|---|---|
| **Old RMI** | Built entirely on it |
| **Some caches** | Ehcache, Hazelcast, Coherence default to it |
| **Session stores** | Servlet session replication |
| `java.lang.Exception` and friends | The JDK's own classes are `Serializable` |
| Android `Parcelable` | A different, better mechanism — but you'll see `Serializable` too |

**And one to recognise:** `Optional` is deliberately **not** `Serializable` (6.7) — the JDK
team's way of saying it isn't meant to be stored or sent.

> **If you inherit a codebase using it:** add a serialization filter immediately as
> mitigation, then plan to migrate to JSON. Don't leave an unfiltered `ObjectInputStream`
> reading anything that crosses a trust boundary.

---

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Deserialising untrusted data | **Remote code execution** |
| Expecting constructors to run | They don't — except for records |
| Omitting `serialVersionUID` | Any shape change breaks old data |
| `transient` protects a secret | It's excluded from the stream, but the class is still a gadget surface |
| A filter makes it safe | Mitigation only |
| `Serializable` is a small annotation | It's a permanent public API commitment |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Serializable` in new code | JSON, protobuf, or an explicit format |
| `ObjectInputStream` on untrusted input | **Never.** No exceptions |
| RMI | HTTP, gRPC |

---

## Recap

| Point | |
|---|---|
| How | Marker interface; writes the whole object graph; `serialVersionUID`; `transient` |
| ⭐ **Fatal flaw** | **Bypasses constructors** — no invariant is enforced |
| ⭐ **Security** | Untrusted deserialisation = **RCE**, via gadget chains on your classpath |
| Also | An invisible public API; slow; bloated |
| Filters `Java 9` | Mitigation, not a fix |
| ⭐ **Records** | Deserialise **through the canonical constructor** — validation runs |
| Instead | **JSON / protobuf / your own format** |
