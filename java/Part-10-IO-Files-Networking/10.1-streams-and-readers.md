# 10.1 — Streams and readers

> ⚠️ **Note: these "streams" have nothing to do with Part 06.** Unfortunate naming,
> permanent confusion. `java.io.InputStream` is a pipe of bytes; `java.util.stream.Stream`
> is a lazy pipeline (6.4). They are unrelated.

---

## ⭐ The byte/character split

**The single most important structural fact about `java.io`:**

| | Bytes | Characters |
|---|---|---|
| Read | `InputStream` | `Reader` |
| Write | `OutputStream` | `Writer` |

```java
InputStream  in  = Files.newInputStream(path);      // raw bytes
Reader       rdr = Files.newBufferedReader(path);   // decoded text
```

> **Bytes are what's actually on disk or the wire. Characters are what your program
> thinks in.** Converting between them requires a **charset** (10.2), and that conversion
> is where encoding bugs live.

**The bridge classes:**

```java
new InputStreamReader(inputStream, UTF_8)    // bytes → chars
new OutputStreamWriter(outputStream, UTF_8)  // chars → bytes
```

---

## ⭐ The decorator pattern in action

`java.io` is the JDK's clearest example of the decorator pattern (2.10):

```java
var reader = new BufferedReader(          // adds buffering
    new InputStreamReader(                 // adds byte→char decoding
        new FileInputStream("data.txt"),   // reads raw bytes
        StandardCharsets.UTF_8));
```

```
FileInputStream    → gives you bytes, one syscall at a time
InputStreamReader  → wraps it, decodes bytes to chars
BufferedReader     → wraps that, reads in chunks and adds readLine()
```

Each wrapper **implements the same interface as what it wraps**, so they compose freely.
That's the whole pattern.

The common decorators:

| Decorator | Adds |
|---|---|
| `BufferedInputStream` / `BufferedReader` | **Buffering** + `readLine()` |
| `DataInputStream` | `readInt()`, `readUTF()` — typed binary reads |
| `InputStreamReader` | Byte→char decoding |
| `GZIPInputStream` | Decompression |
| `ObjectInputStream` | 💀 Serialization (10.5) |

> ⚠️ **Close the outermost wrapper.** Closing it closes the whole chain — and closing an
> inner one directly leaves the outer one holding a dead stream. Reverse order is handled
> for you by try-with-resources (4.3).

## ⭐ Why buffering matters

**Every unbuffered `read()`/`write()` is potentially a syscall.**

```java
// ❌ one syscall per byte
try (var out = new FileOutputStream("f.txt")) {
    for (int i = 0; i < 1_000_000; i++) out.write(data[i]);
}

// ✅ one syscall per 8KB
try (var out = new BufferedOutputStream(new FileOutputStream("f.txt"))) {
    for (int i = 0; i < 1_000_000; i++) out.write(data[i]);
}
```

**The difference is typically 10–100×.** A syscall costs ~1µs (a user→kernel transition);
a buffered write is a few nanoseconds into an array, flushed every 8KB.

> **Rule: always buffer**, unless you're writing one large array in one call (in which case
> the buffer just adds a copy).

⚠️ **Buffered output must be flushed** — `close()` flushes, which is another reason
try-with-resources matters.

## The modern conveniences `Java 9`

Most of the old boilerplate is gone:

```java
in.transferTo(out);            // ⭐ copy everything — replaces the read/write loop
in.readAllBytes();             // → byte[]
in.readNBytes(1024);           // → byte[] of at most n
out.write(bytes);
```

```java
// ❌ the loop everyone used to write
byte[] buf = new byte[8192];
int n;
while ((n = in.read(buf)) != -1) out.write(buf, 0, n);

// ✅
in.transferTo(out);
```

And for files specifically, **10.3's `Files` class is almost always better** — you rarely
need to touch `InputStream` directly any more:

```java
String content = Files.readString(path);          // one line
List<String> lines = Files.readAllLines(path);
Files.copy(source, target);
```

## `System.in`, `System.out`, `System.err`

```java
System.in     // InputStream  — stdin
System.out    // PrintStream  — stdout, line-buffered to a terminal
System.err    // PrintStream  — stderr, unbuffered
```

`IO.println` (0.4) `Java 25` is the modern shorthand for `System.out.println`.

> ⚠️ **`System.out` is not logging** (12.5). It has no levels, no timestamps, no
> structure, no way to turn off, and it's synchronised — a hot loop printing to stdout
> serialises your whole application.

### ⚠️ `Scanner` — fine for learning, wrong for production

```java
var scanner = new Scanner(System.in);
String line = scanner.nextLine();
int n = scanner.nextInt();
```

**Why it's wrong for real use:**

| Problem | |
|---|---|
| **Slow** | Regex-based; ~10× slower than `BufferedReader` |
| **Swallows exceptions** | I/O errors set an internal flag you must check with `ioException()` |
| **The `nextInt()`/`nextLine()` trap** | `nextInt()` leaves the newline; the next `nextLine()` returns `""` |
| **Uses the default charset** unless you specify one | (10.2) |

```java
// ✅ for real input
try (var br = new BufferedReader(new InputStreamReader(System.in, UTF_8))) {
    String line = br.readLine();
}
```

> **Use `Scanner` in a tutorial. Never in a service.**

---

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Confusing these with Part 06 streams | Completely unrelated APIs |
| Unbuffered I/O | 10–100× slower |
| Not closing | File handle leak (8.7). Use try-with-resources |
| Forgetting to flush | `close()` flushes — another reason for try-with-resources |
| `Scanner` in production | Slow, swallows errors, the newline trap |
| `System.out` as logging | No levels, no structure, synchronised |
| No charset | Platform-dependent (10.2) |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| The manual `read(buf)`/`write` copy loop | `in.transferTo(out)` |
| `Scanner` for real input | `BufferedReader` |
| `System.out.println` for diagnostics | SLF4J (12.5) |
| Raw `FileInputStream` for text files | `Files.readString` (10.3) |
