# 10.4 — Buffers and channels

> **What this is:** The lower level. **You will not need it often, but when you do,
> nothing else will work.**

---

## ⭐ `ByteBuffer` — the mental model everyone gets wrong once

A `ByteBuffer` is an array plus **three cursors**:

```
           position          limit              capacity
              │                │                    │
              ▼                ▼                    ▼
  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
  │ a │ b │ c │   │   │   │   │                   │
  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
   ◄── written ──►
```

| Cursor | Means |
|---|---|
| **`capacity`** | Total size. Fixed at creation |
| **`limit`** | The first index you may **not** touch |
| **`position`** | Where the next read/write happens |

**The invariant: `0 ≤ position ≤ limit ≤ capacity`.**

### The one thing to memorise: `flip()`

```java
var buf = ByteBuffer.allocate(1024);

channel.read(buf);          // WRITE MODE: position advances as data arrives

buf.flip();                 // ⭐ limit = position; position = 0
                            //    "I've finished writing. Now read what I wrote."

while (buf.hasRemaining()) {
    process(buf.get());     // READ MODE: position advances as you consume
}

buf.clear();                // position = 0; limit = capacity — ready to write again
```

> ⭐ **`flip()` switches the buffer from write mode to read mode.** Forgetting it is *the*
> `ByteBuffer` bug — you read from position 0 to the capacity and get a buffer full of
> zeros, or you read nothing at all because position already equals limit.

**The four state methods:**

| Method | Does |
|---|---|
| **`flip()`** | Write → read. `limit = position`, `position = 0` |
| `clear()` | Read → write. `position = 0`, `limit = capacity`. **Doesn't erase anything** |
| `rewind()` | `position = 0`, limit unchanged — re-read the same data |
| `compact()` | Move unread bytes to the front, then switch to write mode |

> ⚠️ **`clear()` does not clear.** It resets the cursors. The old bytes are still there —
> they'll just be overwritten.

## Heap buffers versus direct buffers

```java
ByteBuffer.allocate(1024);          // HEAP — a byte[] on the Java heap (8.3)
ByteBuffer.allocateDirect(1024);    // DIRECT — off-heap native memory
```

| | Heap | Direct |
|---|---|---|
| Lives | Java heap | **Native memory** |
| I/O | The JVM must **copy** to a temp native buffer first | The OS reads/writes **directly** |
| Allocation | Cheap | **Expensive** |
| Freed by | GC | GC, **eventually** — via a `Cleaner` (8.7) |
| Counted in | `-Xmx` | **`-XX:MaxDirectMemorySize`** |

> ⭐ **Use direct buffers for long-lived, frequently-reused I/O buffers.** Allocating one
> per request is worse than a heap buffer, because allocation is slow and reclamation is
> nondeterministic.

**Where direct buffer memory is accounted:** *not* in the heap. This is why a process can
show 6 GB RSS with a 1 GB heap (8.9) — Netty and NIO allocate direct buffers, and
`OutOfMemoryError: Direct buffer memory` is its own failure mode (8.3).

```bash
-XX:MaxDirectMemorySize=1g
jcmd <pid> VM.native_memory summary        # see it (8.9)
```

## Channels

A channel is a bidirectional connection to a file, socket or pipe.

```java
try (var ch = FileChannel.open(path, READ)) {
    var buf = ByteBuffer.allocate(8192);
    while (ch.read(buf) != -1) {
        buf.flip();
        process(buf);
        buf.clear();
    }
}
```

### Scatter/gather

```java
ByteBuffer header = ByteBuffer.allocate(16);
ByteBuffer body   = ByteBuffer.allocate(1024);

channel.read(new ByteBuffer[]{header, body});     // SCATTER — fill header, then body
channel.write(new ByteBuffer[]{header, body});    // GATHER  — write both in one syscall
```

Useful for protocols with a fixed header and variable body — one syscall instead of two,
and no need to concatenate.

### ⭐ `transferTo` — zero-copy

```java
sourceChannel.transferTo(0, size, destChannel);
```

**The kernel copies the data directly**, without it ever entering the JVM's address space.

```
ordinary copy:  disk → kernel buffer → JVM heap → kernel buffer → socket
transferTo:     disk → kernel buffer → socket          ⭐ two copies eliminated
```

On Linux this uses `sendfile(2)`. It's how a file server ships static files at line rate,
and it's a genuine order-of-magnitude difference for large files.

## Memory-mapped files

```java
try (var ch = FileChannel.open(path, READ, WRITE)) {
    MappedByteBuffer buf = ch.map(FileChannel.MapMode.READ_WRITE, 0, ch.size());
    buf.putInt(0, 42);              // writes to the FILE, through the page cache
    buf.force();                    // flush to disk
}
```

**The file becomes memory.** The OS pages it in on demand and writes it back lazily.

**When it wins:**
- **Random access** to a large file — no `seek` + `read` syscall per access
- A file **shared between processes**
- Large read-mostly data (indexes, databases)

**When it doesn't:**
- Sequential reads — a buffered stream is simpler and just as fast
- Small files — mapping has fixed overhead
- ⚠️ **Unmapping is not deterministic** — the mapping persists until GC collects the
  buffer, so on Windows you may not be able to delete the file for a while

## Byte order

```java
buf.order(ByteOrder.BIG_ENDIAN);       // ⭐ the Java/network default
buf.order(ByteOrder.LITTLE_ENDIAN);    // x86, ARM, most file formats
buf.order(ByteOrder.nativeOrder());
```

> ⚠️ **`ByteBuffer` defaults to BIG_ENDIAN** — network byte order — while your CPU is
> almost certainly little-endian. Reading a binary format written by C code without
> setting the order gives you byte-swapped garbage. **Always set it explicitly** when
> parsing a binary format.

```java
buf.putInt(1);
// BIG_ENDIAN:    00 00 00 01
// LITTLE_ENDIAN: 01 00 00 00
```

## ⭐ Selectors and non-blocking I/O

```java
var selector = Selector.open();
channel.configureBlocking(false);
channel.register(selector, SelectionKey.OP_READ);

while (true) {
    selector.select();                          // blocks until SOME channel is ready
    for (var key : selector.selectedKeys()) {
        if (key.isReadable()) { ... }
    }
}
```

**One thread monitors thousands of connections.** It's `epoll`/`kqueue` exposed to Java,
and it's what **Netty** is built on.

**Why it existed:** a platform thread per connection costs ~1MB (9.1), so 100,000
connections was impossible. Selectors let ~8 threads handle all of them — at the cost of
writing your logic as **callbacks and state machines** rather than straight-line code.

### ⭐ Why virtual threads reduce the need for it

> **Virtual threads (9.11) make thread-per-connection viable again.**

```java
// ❌ the NIO way — one thread, callbacks, explicit state machine, hard to debug
selector.select(); /* dispatch, track per-connection state, resume... */

// ✅ with virtual threads — plain blocking code, one thread per connection
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    while (true) {
        var socket = serverSocket.accept();
        exec.submit(() -> handle(socket));      // blocks. A million of these is fine.
    }
}
```

The virtual thread **unmounts** when it blocks (9.11), so the JVM does exactly what the
selector loop did — multiplexing many connections onto few OS threads — **without you
writing the state machine.**

> **This is the same argument as 9.9 made about `CompletableFuture`:** a whole category of
> complexity existed to avoid blocking a thread, and it is no longer necessary.
>
> Non-blocking NIO is still right for **the lowest layers** (Netty itself) and for
> maximum-throughput proxies. For application code on Java 21+, thread-per-connection with
> virtual threads is simpler and fast enough.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| **Forgetting `flip()`** | *The* `ByteBuffer` bug. You read zeros |
| `clear()` erases data | It resets cursors only |
| Direct buffers per request | Slow to allocate, nondeterministic to free |
| Direct memory counted in `-Xmx` | It isn't — separate limit, separate OOM |
| Default byte order | **BIG_ENDIAN**, unlike your CPU |
| Expecting deterministic unmapping | It waits for GC |
| Reaching for NIO selectors in app code | On Java 21+, virtual threads are simpler |

## Recap

| Concept | One line |
|---|---|
| `ByteBuffer` | position ≤ limit ≤ capacity |
| **`flip()`** | **Write → read.** The one to memorise |
| `clear()` | Resets cursors; erases nothing |
| Direct buffers | Off-heap, no copy for I/O, **own OOM** |
| `transferTo` | **Zero-copy** — kernel to kernel |
| Memory-mapped | The file becomes memory. Random access to large files |
| Byte order | Defaults to **BIG_ENDIAN**. Set it for binary formats |
| Selectors | One thread, thousands of connections. **Largely superseded by virtual threads** |
