# 11.1 — Dates and times

> **What this is:** Java 8 replaced a famously broken API with an excellent one.
> **Learn only the new one.**

---

## 💀 The old API — never use

```java
Date, Calendar, SimpleDateFormat        // 💀 all of them
```

| Problem | |
|---|---|
| **Mutable** | `Date` can be changed under you — unsafe as a map key (2.5), unsafe to share |
| **Not thread-safe** | ⭐ `SimpleDateFormat` corrupts silently under concurrency (0.3, 9.2) |
| **Months count from zero** | `Calendar.JANUARY == 0`. December is 11 |
| **Years from 1900** | `new Date(2024, ...)` means 3924 |
| **No separation** | `Date` is an instant, a date and a time, badly |

```java
// 💀 the classic production bug — a shared SimpleDateFormat in a web handler
private static final SimpleDateFormat FMT = new SimpleDateFormat("yyyy-MM-dd");
// two threads formatting concurrently produce garbage dates, no exception
```

> **`java.time` types are all immutable and thread-safe.** That single change removes an
> entire bug class.

---

## ⭐ The core types — and which question each answers

| Type | Answers | Example |
|---|---|---|
| **`Instant`** | *"When, absolutely?"* — a point on the UTC timeline | `2026-09-20T14:30:00Z` |
| **`LocalDate`** | *"What date?"* — no time, no zone | `2026-09-20` (a birthday) |
| **`LocalTime`** | *"What time of day?"* — no date, no zone | `09:00` (shop opens) |
| **`LocalDateTime`** | *"What date and time?"* — ⚠️ **no zone, so not a real instant** | `2026-09-20T09:00` |
| **`ZonedDateTime`** | *"When, in this place?"* — full zone rules | `2026-09-20T09:00+01:00[Europe/London]` |
| **`OffsetDateTime`** | *"When, at this offset?"* — fixed offset, no DST rules | `2026-09-20T09:00+01:00` |

```java
Instant.now();                             // machine timestamp
LocalDate.of(2026, 9, 20);                 // ⭐ months are 1-based. Finally.
LocalDate.of(2026, Month.SEPTEMBER, 20);
LocalTime.of(9, 30);
ZonedDateTime.now(ZoneId.of("Asia/Kolkata"));
```

> ⭐ **The choice that matters: `LocalDateTime` is not an instant.** "2026-03-29 01:30" is
> a *description*, and in some zones that moment doesn't exist (DST gap) or happens twice
> (DST overlap). **If you mean a real moment, use `Instant` or `ZonedDateTime`.**

### Everything is immutable

```java
LocalDate d = LocalDate.of(2026, 9, 20);
d.plusDays(1);                   // ⚠️ returns a NEW object — d is unchanged
d = d.plusDays(1);               // ✅
```

Same shape as `String` (1.3). Every `plus*`/`minus*`/`with*` returns a new object.

```java
d.plusDays(1).minusMonths(2).withDayOfMonth(1);      // chains cleanly
d.with(TemporalAdjusters.lastDayOfMonth());
d.with(TemporalAdjusters.next(DayOfWeek.MONDAY));
```

## ⭐ `Duration` versus `Period`

> **`Duration` is machine time. `Period` is human time.**

```java
Duration.ofHours(24);            // exactly 86,400 seconds
Period.ofDays(1);                // "one day" — which may be 23 or 25 hours across DST
```

```java
var before = ZonedDateTime.of(2026, 3, 28, 12, 0, 0, 0, ZoneId.of("Europe/London"));

before.plus(Duration.ofHours(24));   // 2026-03-29T13:00  ← 24 real hours, clock jumped
before.plus(Period.ofDays(1));       // 2026-03-29T12:00  ← same clock time next day
```

**Both are "one day" and they give different answers.** That's not a bug — they answer
different questions.

| | `Duration` | `Period` |
|---|---|---|
| Unit | Seconds and nanos | Years, months, days |
| Use with | `Instant`, `LocalTime` | `LocalDate` |
| DST | Ignores it — absolute time | **Respects it** — calendar time |
| "One month" | ❌ meaningless | ✅ |

> **Rule: timeouts, elapsed time, rate limits → `Duration`. Birthdays, subscriptions,
> "next month" → `Period`.**

## ⭐ Time zones

```java
ZoneId.of("Europe/London");          // ⭐ IANA name — carries DST rules
ZoneId.of("UTC");
ZoneId.systemDefault();              // ⚠️ machine-dependent
ZoneOffset.ofHours(1);               // a fixed offset — NO rules
```

> **Always use IANA names (`Europe/London`, `Asia/Kolkata`), never three-letter
> abbreviations.** `IST` is ambiguous (Indian, Irish, or Israel Standard Time), and `EST`
> has no DST rules.

The **IANA tz database** ships with the JDK and is updated in JDK releases — which is one
reason to keep your JDK current. Governments change DST rules with months of notice.

### DST gaps and overlaps

```java
var zone = ZoneId.of("Europe/London");

// GAP — the clocks jump forward; 01:30 never happens on this date
LocalDateTime.of(2026, 3, 29, 1, 30).atZone(zone);
// → 02:30+01:00  (silently moved forward)

// OVERLAP — the clocks go back; 01:30 happens TWICE
LocalDateTime.of(2026, 10, 25, 1, 30).atZone(zone);
// → picks the FIRST (summer) occurrence by default
```

```java
zdt.withEarlierOffsetAtOverlap();
zdt.withLaterOffsetAtOverlap();
```

> ⚠️ **`atZone` resolves gaps and overlaps silently.** For scheduling — alarms, cron,
> billing — you must decide explicitly what "01:30 on the day the clocks change" means.
> This is where real scheduling bugs live.

## `DateTimeFormatter`

```java
DateTimeFormatter.ISO_LOCAL_DATE;                       // 2026-09-20
DateTimeFormatter.ISO_INSTANT;                          // 2026-09-20T14:30:00Z
DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm");
DateTimeFormatter.ofPattern("d MMMM yyyy", Locale.FRENCH);   // (11.4)

String s = date.format(fmt);
LocalDate d = LocalDate.parse("2026-09-20");            // ISO by default
LocalDate d = LocalDate.parse("20/09/2026", fmt);
```

**`DateTimeFormatter` is immutable and thread-safe** — the direct fix for the
`SimpleDateFormat` bug above. Declare one `static final` and share it.

> ⚠️ **Pattern letters are case-sensitive and easy to get wrong:**
> | | |
> |---|---|
> | `yyyy` | Calendar year ✅ |
> | `YYYY` | **Week-based year** — differs from `yyyy` around New Year 💥 |
> | `MM` | Month |
> | `mm` | **Minute** |
> | `DD` | **Day of year** |
> | `dd` | Day of month |
>
> `YYYY-MM-dd` on 2025-12-29 prints **2026**-12-29. A real, annually-recurring bug.

Parsing failures throw `DateTimeParseException` (4.1) with the index of the problem.

## ⭐ `Clock` — the only sane way to test time-dependent code

```java
// ❌ untestable — you cannot control "now"
class Subscription {
    boolean isExpired() { return LocalDate.now().isAfter(endDate); }
}

// ✅ inject a Clock (2.10, 2.2)
class Subscription {
    private final Clock clock;
    Subscription(Clock clock) { this.clock = clock; }

    boolean isExpired() { return LocalDate.now(clock).isAfter(endDate); }
}
```

```java
// in production
new Subscription(Clock.systemDefaultZone());

// in a test — time is now a value you control
var fixed = Clock.fixed(Instant.parse("2026-09-20T00:00:00Z"), ZoneOffset.UTC);
new Subscription(fixed);

Clock.offset(baseClock, Duration.ofDays(30));     // jump forward
Clock.tick(baseClock, Duration.ofSeconds(1));     // coarser resolution
```

> ⭐ **Every `java.time` `now()` method takes an optional `Clock`.** That's why it exists.
> Injecting a `Clock` is the difference between a test that can verify expiry logic and one
> that has to sleep or mock statics.
>
> This is the same dependency-injection argument as 2.2 and 12.3 — `LocalDate.now()` is a
> static call to a hidden global.

## ⭐ What to store in a database

> **Store instants in UTC. Apply zones at the edges.**

| What you're storing | Type | Column |
|---|---|---|
| A moment something happened | **`Instant`** | `TIMESTAMP WITH TIME ZONE` (or UTC `TIMESTAMP`) |
| A birthday, an invoice date | `LocalDate` | `DATE` |
| Shop opening time | `LocalTime` | `TIME` |
| A **future** scheduled event | ⚠️ `LocalDateTime` **+ the `ZoneId`** | Two columns |

```java
// ✅ persisting an event
Instant occurredAt = Instant.now();

// ✅ displaying it
occurredAt.atZone(user.timeZone()).format(fmt);
```

> ⚠️ **The future-event exception is real.** If someone schedules a meeting for "9am on
> 29 March in London" and the government later changes DST rules, storing a UTC instant
> gives the wrong wall-clock time. For future local events, **store the local time and the
> zone**, and resolve to an instant when you need one.

**The rule of thumb: convert to a zone as late as possible, at the presentation edge, and
never store a zone-less `LocalDateTime` for something that happened.**

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `SimpleDateFormat` as a shared field | **Not thread-safe.** Silent corruption |
| `date.plusDays(1)` without assigning | Immutable — returns a new object |
| `LocalDateTime` for a real moment | It has **no zone**. Not an instant |
| `YYYY` instead of `yyyy` | Week-based year. Breaks around New Year |
| `mm` instead of `MM` | Minutes, not months |
| `EST` / `IST` | Ambiguous. Use IANA names |
| `LocalDate.now()` in business logic | Untestable. Inject a `Clock` |
| Storing a `LocalDateTime` for a past event | Ambiguous forever. Store an `Instant` |

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Date`, `Calendar` | `Instant`, `LocalDate`, `ZonedDateTime` |
| `SimpleDateFormat` | `DateTimeFormatter` |
| `java.sql.Date`/`Time`/`Timestamp` | `java.time` — JDBC 4.2 maps them directly |
| `System.currentTimeMillis()` in logic | `Instant.now(clock)` |
| Joda-Time | `java.time` — it's Joda's successor, by the same author |

## Recap

| Concept | One line |
|---|---|
| All immutable, thread-safe | The fix for the entire old API |
| `Instant` | An absolute moment. **What you store** |
| `LocalDate`/`LocalTime` | A date or time with no zone |
| ⚠️ `LocalDateTime` | **Not an instant** — no zone |
| `ZonedDateTime` | Full zone rules, DST-aware |
| **`Duration` vs `Period`** | **Machine time vs human time.** 24h ≠ 1 day across DST |
| Zones | **IANA names only** |
| `DateTimeFormatter` | Thread-safe. ⚠️ `yyyy` not `YYYY`, `MM` not `mm` |
| ⭐ **`Clock`** | **Inject it.** The only way to test time |
| Storage | **Instants in UTC; zones at the edges** |
