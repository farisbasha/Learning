# 11.3 — Regular expressions

> **What this is:** Familiar syntax, Java-specific API, and **one performance trap that can
> take down a server.**

---

## `Pattern` and `Matcher`

```java
Pattern p = Pattern.compile("\\d{4}-\\d{2}-\\d{2}");   // COMPILE ONCE
Matcher m = p.matcher(input);                           // one per use

if (m.matches()) { ... }        // ⭐ the ENTIRE input must match
if (m.find())    { ... }        // ⭐ find the next match ANYWHERE
```

> ⭐ **`matches()` vs `find()` is the #1 Java regex confusion.** `"abc123".matches("\\d+")`
> is **false** — the whole string must be digits. `find()` would return true.

### ⭐ Compile once, reuse — but not the Matcher

```java
// ❌ recompiles the pattern on every call — often the hidden cost in a hot method
boolean isValid(String s) {
    return s.matches("\\d{4}-\\d{2}-\\d{2}");     // String.matches compiles EVERY time
}

// ✅
private static final Pattern DATE = Pattern.compile("\\d{4}-\\d{2}-\\d{2}");
boolean isValid(String s) {
    return DATE.matcher(s).matches();
}
```

> ⭐ **`Pattern` is immutable and thread-safe — share it. `Matcher` is stateful and NOT
> thread-safe — create one per use.**
>
> A `static final Matcher` is a genuine concurrency bug (9.2), the same shape as the
> `SimpleDateFormat` bug in 11.1.

`String.matches`, `String.split`, `String.replaceAll` all compile the pattern on **every
call**. Fine once; wasteful in a loop.

## Groups

```java
var p = Pattern.compile("(\\d{4})-(\\d{2})-(\\d{2})");
var m = p.matcher("2026-09-20");
if (m.matches()) {
    m.group(0);     // 2026-09-20  ⭐ group 0 is the WHOLE match
    m.group(1);     // 2026
    m.group(2);     // 09
}
```

**Named groups** — much more readable:

```java
var p = Pattern.compile("(?<year>\\d{4})-(?<month>\\d{2})-(?<day>\\d{2})");
var m = p.matcher("2026-09-20");
if (m.matches()) {
    m.group("year");        // 2026
    m.group("month");       // 09
}
```

**Non-capturing groups** `(?:...)` — group for alternation without capturing:

```java
Pattern.compile("(?:https?|ftp)://(\\S+)");    // group(1) is the host, not the scheme
```

**Replacement with references:**

```java
"2026-09-20".replaceAll("(\\d{4})-(\\d{2})-(\\d{2})", "$3/$2/$1");   // 20/09/2026
"a1b2".replaceAll("(?<letter>[a-z])\\d", "${letter}!");              // named

m.replaceAll(mr -> mr.group(1).toUpperCase());   // Java 9 — a function per match
```

⚠️ `$` and `\` are special in the replacement string. Use `Matcher.quoteReplacement(s)`
for a literal replacement.

```java
m.results()                    // Java 9 — Stream<MatchResult> (6.4)
 .map(r -> r.group(1))
 .toList();
```

## ⭐ Java's double-escaping

**A regex lives inside a Java string literal, so backslashes are escaped twice:**

| You want | Regex | **Java string literal** |
|---|---|---|
| A digit | `\d` | `"\\d"` |
| A literal backslash | `\\` | `"\\\\"` |
| A literal dot | `\.` | `"\\."` |
| Word boundary | `\b` | `"\\b"` |

```java
"a.b.c".split(".");         // ⚠️ empty array — "." is "any character" (5.2)
"a.b.c".split("\\.");       // ✅ [a, b, c]
```

### Text blocks help `Java 15`

```java
// ❌ unreadable
Pattern.compile("^(?<user>[\\w.+-]+)@(?<domain>[\\w-]+\\.[\\w.]+)$");

// ✅ a text block (1.3) — still needs \\ but you can comment it
Pattern.compile("""
    ^(?<user>[\\w.+-]+)@(?<domain>[\\w-]+\\.[\\w.]+)$""");
```

**Better — `COMMENTS` mode**, which ignores whitespace and allows `#` comments:

```java
Pattern.compile("""
    ^                       # start
    (?<user>[\\w.+-]+)      # local part
    @
    (?<domain>[\\w-]+\\.[\\w.]+)   # domain
    $
    """, Pattern.COMMENTS);
```

**The flags worth knowing:**

```java
Pattern.CASE_INSENSITIVE | Pattern.UNICODE_CASE
Pattern.MULTILINE        // ^ and $ match at each line
Pattern.DOTALL           // . also matches newline
Pattern.COMMENTS         // ignore whitespace, allow #
Pattern.LITERAL          // treat the pattern as literal text
```

Or inline: `(?i)` case-insensitive, `(?m)` multiline, `(?s)` dotall.

## Quantifiers: greedy, reluctant, possessive

| Kind | Syntax | Behaviour |
|---|---|---|
| **Greedy** | `*` `+` `?` `{n,m}` | Match as much as possible, **then backtrack** |
| **Reluctant** | `*?` `+?` `??` | Match as little as possible, then expand |
| **Possessive** | `*+` `++` `?+` | Match as much as possible, ⭐ **never backtrack** |

```java
"<a><b>".replaceAll("<.*>",  "X");   // X        — greedy: one big match
"<a><b>".replaceAll("<.*?>", "X");   // XX       — reluctant: two matches
```

> ⭐ **Possessive quantifiers are the defence against the next section.** By refusing to
> backtrack they make catastrophic backtracking impossible — at the cost of matching
> fewer things.

## ⭐ Catastrophic backtracking — how a regex becomes an outage

**This is the section that matters.**

**Java's engine is a *backtracking* engine.** A pattern like `(a+)+` can split a run of
`a`s among the inner and outer quantifiers in **exponentially many ways** — so when the
match ultimately fails, every arrangement must be tried.

### ⚠️ Measured on OpenJDK 17 — the textbook examples no longer reproduce

```
pattern            n=20    n=24    n=26    n=28    n=30
(a+)+b              0ms     0ms     0ms     0ms     0ms
(a|a)*b             0ms     0ms     0ms     0ms     0ms
([a-zA-Z]+)*b       0ms     0ms     0ms     0ms     0ms
(\w+\s?)*$          0ms     0ms     0ms     0ms     0ms
```

> ⭐ **Every classic ReDoS example you will find online fails to reproduce on a modern
> JDK.** Java's engine has optimisations that recognise and collapse these ambiguous
> quantifier shapes. This is worth knowing, because it means most of the ReDoS advice
> written for JavaScript or Python **overstates the risk for Java**.

### ⚠️ But it is not fixed — backreferences still blow up

A **backreference** defeats the optimiser, because the engine can no longer reason about
the group independently:

```java
Pattern.compile("(a*)*\\1b").matcher("a".repeat(n)).matches();
```

```
n=24 :   434 ms
n=25 :   838 ms      ← doubling
n=26 :  1635 ms      ← doubling
n=27 :  3447 ms      ← doubling
```

**Clean exponential growth — each additional character doubles the time.** At n=40 that is
years.

> ⭐ **So the accurate rule for Java: nested quantifiers are usually optimised away;
> nested quantifiers *combined with a backreference* are still exponential.** Treat
> `\\1` inside a quantified group as the danger signal, and remember that the engine's
> optimisations are an implementation detail that could change.

### How to recognise a vulnerable pattern

Look for **nested quantifiers** and **overlapping alternation**:

```
(a+)+        (a*)*        (a|a)*        (\w+\s?)*        (.*,)*
   ▲             ▲            ▲              ▲              ▲
   a quantifier applied to something that is itself quantified or ambiguous
```

**And the shape that genuinely still bites** — a backreference inside a quantified group:

```java
"(\\w+)\\s*\\1"        // ⚠️ backreference — the optimiser cannot help here
```

### The defences

```java
// 1. ⭐ possessive quantifiers — no backtracking possible
Pattern.compile("(a++)+$");

// 2. ⭐ atomic groups — same idea, for a whole group
Pattern.compile("(?>a+)+$");

// 3. Make the pattern unambiguous — usually the real fix
Pattern.compile("a+$");

// 4. Bound the input length BEFORE matching
if (input.length() > 1000) throw new IllegalArgumentException();

// 5. Never run a user-supplied regex without a timeout and a sandbox
```

> **Rule: never accept a regex from a user.** And treat any nested quantifier in your own
> patterns as a bug until proven otherwise. ⚠️ Java has **no regex timeout** — once
> `matches()` starts, you cannot interrupt it (9.1), because it doesn't check the
> interrupt flag.

## ⭐ When a regex is the wrong tool

**More often than people think.**

| Don't use a regex for | Use |
|---|---|
| **HTML / XML** | A parser (jsoup, JAXB). HTML is not regular |
| **JSON** | Jackson (10.5) |
| **CSV** | A CSV library — quoting and embedded newlines defeat regex |
| **Email validation** | ⭐ Just check for `@` and send a confirmation. RFC 5322 is ~6,000 characters as a regex and still wrong |
| **URLs** | `URI` (10.6) |
| Simple prefix/suffix/contains | `startsWith`, `endsWith`, `contains` (1.3) — clearer **and** faster |
| Splitting on a fixed string | `split` still compiles a regex; for one character, a manual loop or `StringTokenizer` is faster |

```java
// ❌ slower and less readable
if (s.matches(".*error.*")) { }

// ✅
if (s.contains("error")) { }
```

> **The test: if you can express it with `String` methods, do.** A regex is a small
> programming language embedded in a string literal with no type checking, no syntax
> highlighting and no tests. Use one when the pattern genuinely is a pattern.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `matches()` vs `find()` | `matches` requires the **whole** input |
| `"a.b".split(".")` | `.` is any character. Use `"\\."` |
| Recompiling in a loop | `String.matches` compiles every call |
| `static final Matcher` | **Not thread-safe.** Only `Pattern` is |
| Nested quantifiers alone | Usually **optimised away** on a modern JDK |
| **Nested quantifier + backreference** | ⭐ **Still exponential.** The real ReDoS signal |
| Expecting to interrupt a running match | **You can't.** No timeout exists |
| A regex for email validation | Don't. Check for `@`, send a confirmation |
| `$` in a replacement string | Special. Use `quoteReplacement` |

---

## Recap

| Concept | One line |
|---|---|
| `matches` / `find` | **Whole input** vs anywhere |
| `Pattern` | Immutable, **thread-safe, compile once** |
| `Matcher` | **Stateful, not thread-safe** — one per use |
| Double escaping | `\d` → `"\\d"` |
| Named groups | `(?<name>...)` + `m.group("name")` |
| Quantifiers | Greedy / reluctant `?` / **possessive `+`** |
| ⭐ **Catastrophic backtracking** | Textbook cases are optimised away; **backreferences are still exponential** |
| Defences | Possessive quantifiers, atomic groups, unambiguous patterns, bounded input |
| Wrong tool for | HTML, JSON, CSV, email, URLs, simple `contains` |
