# 11.5 — Randomness and cryptography basics

> **What this is:** **Enough to avoid the two or three mistakes that actually matter.**
> Not a cryptography course — the goal is that you never write the dangerous versions.

---

## ⭐ `Random` is predictable. `SecureRandom` is not.

```java
var r = new Random();            // ⚠️ a linear congruential generator — 48-bit seed
r.nextInt(100);
```

**`Random` is deterministic and predictable.** Given ~2 consecutive outputs, its entire
future and past sequence can be reconstructed. The seed is 48 bits — brute-forceable in
seconds.

```java
new Random(42).nextInt();        // same value, every run, every machine — by design
```

```java
var sr = new SecureRandom();     // ✅ cryptographically secure
byte[] token = new byte[32];
sr.nextBytes(token);
```

> ⭐ **Use `SecureRandom` for anything security-related**: session tokens, password reset
> links, API keys, salts, nonces, CSRF tokens, anything an attacker benefits from guessing.
>
> **Use `Random` only for**: simulations, games, sampling, test data, shuffling a playlist.

```java
// ❌ a guessable password-reset token — a real vulnerability
String token = Long.toHexString(new Random().nextLong());

// ✅
var bytes = new byte[32];
new SecureRandom().nextBytes(bytes);
String token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
```

> ⚠️ **`new SecureRandom()` is correct and non-blocking on modern JDKs.** Don't use
> `SecureRandom.getInstanceStrong()` in a request path — it can block on entropy
> (`/dev/random`) and has caused production hangs on entropy-starved VMs.

## `RandomGenerator` `Java 17`

A modern pluggable interface over all the algorithms:

```java
RandomGenerator g = RandomGenerator.getDefault();
RandomGenerator g = RandomGenerator.of("Xoshiro256PlusPlus");   // fast, good quality

RandomGeneratorFactory.all()
    .map(f -> f.name())
    .forEach(IO::println);
```

Splittable and jumpable generators for parallel work (6.8):

```java
var splittable = RandomGenerator.SplittableGenerator.of("L64X128MixRandom");
```

> `Random` now implements `RandomGenerator`, so old code keeps working. **For new
> non-security randomness, prefer a named modern algorithm** over `Random`'s 1995 LCG.

## `ThreadLocalRandom` for concurrent use

```java
ThreadLocalRandom.current().nextInt(100);
```

> ⚠️ **A shared `Random` is a contention point** — its seed update is a CAS (9.6), so
> every thread fights over one cache line (false sharing, 9.6).
> `ThreadLocalRandom` gives each thread its own generator.
>
> ⚠️ Never `new ThreadLocalRandom()` — always `.current()`.

## ⭐ Hashing — and why SHA-256 is not a password hash

```java
var md = MessageDigest.getInstance("SHA-256");
byte[] hash = md.digest(input.getBytes(StandardCharsets.UTF_8));   // (10.2)
```

**Good for:** file integrity, content addressing, deduplication, HMAC.

### ⚠️ Not for passwords

**Why SHA-256 is wrong for passwords: it's *fast*.** That's a feature for integrity
checking and a catastrophe for password storage — a GPU computes **billions of SHA-256
hashes per second**, so a leaked database of SHA-256 password hashes is cracked offline
in hours.

**A password hash must be deliberately slow and memory-hard:**

| Algorithm | Notes |
|---|---|
| **Argon2id** | ⭐ The current recommendation. Memory-hard |
| **bcrypt** | Well-proven, widely available, adjustable cost |
| **scrypt** | Memory-hard |
| **PBKDF2** | ⭐ **In the JDK** — acceptable when you can't add a dependency |

```java
// ✅ PBKDF2 — available in the JDK with no dependency
var salt = new byte[16];
new SecureRandom().nextBytes(salt);

var spec = new PBEKeySpec(password, salt, 600_000, 256);   // ⭐ high iteration count
var factory = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
byte[] hash = factory.generateSecret(spec).getEncoded();
```

> ⭐ **Better still: don't implement password hashing yourself.** Use Spring Security's
> `PasswordEncoder`, or a maintained Argon2/bcrypt library. The parameters change as
> hardware improves, and a library keeps up.

> ⚠️ 💀 **MD5 and SHA-1 are broken** for anything security-related (collisions are
> practical). Fine for a non-adversarial checksum; never for signatures or integrity
> against an attacker.

## `UUID`

```java
UUID.randomUUID();                       // ⭐ version 4 — random
UUID.nameUUIDFromBytes(bytes);           // version 3 — MD5-based ⚠️
UUID.fromString("...");
uuid.toString();                         // 8-4-4-4-12 hex
```

| Version | Source | Safe to expose? |
|---|---|---|
| **v4** | `SecureRandom` — 122 random bits | ✅ **Yes** — unguessable |
| v3/v5 | Hash of a name | ⚠️ Derivable if the input is guessable |
| v1 | Timestamp + **MAC address** | ❌ **Leaks the machine's MAC and creation time** |
| v7 | Timestamp + random | ⚠️ Leaks creation time — but sorts well, good for DB keys |

```java
UUID.randomUUID();      // uses SecureRandom internally — safe as a public identifier
```

> **`UUID.randomUUID()` is safe to expose** — 122 bits of `SecureRandom` entropy is
> unguessable. **v1 is not** — it embeds the MAC address, which is an information
> disclosure. The JDK only generates v4 and v3, so you're fine unless a library generates
> v1 for you.
>
> ⚠️ A UUID is an **identifier, not an authorisation**. "Unguessable URL" is a weak
> security model; check permissions server-side.

## ⚠️ Base64 is encoding, not encryption `Java 8`

```java
Base64.getEncoder().encodeToString(bytes);
Base64.getDecoder().decode(string);

Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);   // ⭐ URL-safe, no '='
Base64.getMimeEncoder();                                          // line-wrapped
```

> ⚠️ **Base64 provides zero confidentiality.** It's a way to carry binary data through a
> text channel. Anyone can decode it instantly.
>
> Every "we base64 the password" incident is this misunderstanding. **Encoding ≠
> encryption ≠ hashing:**
>
> | | Reversible | Purpose |
> |---|---|---|
> | **Encoding** (Base64) | ✅ by anyone | Transport binary as text |
> | **Encryption** (AES) | ✅ with the key | Confidentiality |
> | **Hashing** (SHA-256) | ❌ never | Integrity, fingerprints |

Use `getUrlEncoder()` for tokens in URLs — standard Base64 contains `+`, `/` and `=`,
which need escaping.

## Where the JDK's crypto is heading — post-quantum `Java 24`

```
ML-KEM  (Kyber)     — key encapsulation  → JEP 496, Java 24
ML-DSA  (Dilithium) — digital signatures → JEP 497, Java 24
```

**Why now:** the "harvest now, decrypt later" threat — an adversary records encrypted
traffic today and decrypts it once quantum computers are capable. Data with a long
confidentiality lifetime is at risk *already*.

`Java 27` negotiates post-quantum key exchange **by default** in TLS (10.6), transparently.

> You will not implement these. You benefit by keeping your JDK current.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `Random` for tokens | **Predictable.** Use `SecureRandom` |
| `SecureRandom.getInstanceStrong()` in a request | Can **block** on entropy |
| SHA-256 for passwords | Far too fast. Use Argon2/bcrypt/PBKDF2 |
| MD5 or SHA-1 for security | 💀 Broken |
| Base64 as protection | Zero confidentiality |
| An unguessable URL as authorisation | Check permissions server-side |
| A shared `Random` across threads | Contention. Use `ThreadLocalRandom` |
| Rolling your own crypto | Don't |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `Random` for anything security-related | `SecureRandom` |
| MD5 / SHA-1 for security | SHA-256 or better |
| Plain SHA-256 for passwords | Argon2id, bcrypt, or PBKDF2 |
| Base64 as "encryption" | Actual encryption |
| Your own crypto primitives | A reviewed library |

## Recap

| Concept | One line |
|---|---|
| ⭐ `Random` vs `SecureRandom` | **Predictable vs secure.** Tokens need `SecureRandom` |
| `RandomGenerator` `Java 17` | Modern pluggable algorithms |

| `MessageDigest` | Integrity and fingerprints |
| ⭐ **Passwords** | **Argon2id / bcrypt / PBKDF2** — deliberately slow |
