# 11.8 — Method handles and `invokedynamic`

> **What this is:** Advanced, and **the mechanism behind lambdas and modern string
> concatenation**. You will rarely write this; you benefit from it constantly.

---

## `MethodHandle` and `MethodType` `Java 7`

**A faster, JIT-friendly alternative to reflection** (11.6).

```java
var lookup = MethodHandles.lookup();

// MethodType describes a signature: (parameter types) → return type
MethodType type = MethodType.methodType(String.class, int.class, int.class);
//                                      ↑ returns      ↑ takes

MethodHandle mh = lookup.findVirtual(String.class, "substring", type);

String result = (String) mh.invokeExact("hello world", 0, 5);   // "hello"
```

```java
lookup.findStatic(Integer.class, "parseInt", methodType(int.class, String.class));
lookup.findConstructor(ArrayList.class, methodType(void.class));
lookup.findGetter(Point.class, "x", int.class);
lookup.findSetter(Point.class, "x", int.class);
lookup.unreflect(someMethod);                    // convert from a reflective Method
```

### ⭐ Why it's faster than reflection

| | `Method.invoke` (11.6) | `MethodHandle` |
|---|---|---|
| Access check | **Every call** | **Once, at lookup** |
| Arguments | Boxed into an `Object[]` | Passed directly |
| JIT | ⭐ **Cannot inline** | ⭐ **Can inline a `static final` handle to a direct call** |
| Type checking | At invoke time | At lookup time |

> ⭐ **A `static final MethodHandle` is treated by the JIT as a constant**, so the call can
> be inlined and optimised exactly like a direct call (8.8). A reflective `Method.invoke`
> never can.
>
> **The catch: it must be `static final`.** A handle in an instance field or a local loses
> that benefit entirely.

**`invokeExact` vs `invoke`:**

```java
mh.invokeExact(...)     // ⭐ signature must match EXACTLY — fastest, throws WrongMethodTypeException
mh.invoke(...)          // applies conversions (boxing, widening) — slightly slower
```

`invokeExact` is strict to the point of pedantry: the cast on the result is part of the
signature. `(String) mh.invokeExact(...)` and `Object o = mh.invokeExact(...)` are
*different* calls.

## `MethodHandles.Lookup` and access control

```java
MethodHandles.lookup();               // ⭐ captures the CALLING class's access rights
MethodHandles.publicLookup();         // public members only
lookup.in(OtherClass.class);          // narrow to another class's context
MethodHandles.privateLookupIn(Target.class, lookup);   // Java 9 — needs module permission
```

> ⭐ **A `Lookup` object *is* a capability.** It carries the access rights of wherever it
> was created — so `lookup()` inside your class can reach your privates, and handing that
> object elsewhere hands over that access. This is a cleaner security model than
> `setAccessible(true)` (11.6), which is a global override.

## Handle combinators

Method handles **compose** — you can build a new handle from existing ones without writing
any bytecode:

```java
MethodHandles.insertArguments(mh, 0, "fixed");     // bind an argument (currying)
MethodHandles.filterArguments(mh, 0, transformer); // transform an argument first
MethodHandles.filterReturnValue(mh, postProcess);  // transform the result
MethodHandles.dropArguments(mh, 0, int.class);     // ignore an argument
MethodHandles.guardWithTest(test, ifTrue, ifFalse);// ⭐ a branch, as a handle
MethodHandles.catchException(mh, Type.class, handler);
mh.bindTo(instance);                                // fix the receiver
mh.asType(newType);                                 // adapt the signature
```

This is how a language runtime on the JVM (JRuby, Kotlin, Groovy) builds a call site that
does dynamic dispatch at full speed.

## ⭐ `invokedynamic` — the instruction that makes modern Java work

You met it in 8.1 as one of the five invoke instructions. Here's the mechanism:

```
FIRST execution of an invokedynamic instruction:
   1. The JVM calls a BOOTSTRAP METHOD named in the constant pool (8.1)
   2. The bootstrap method returns a CallSite holding a MethodHandle
   3. The call site is LINKED to that target

EVERY subsequent execution:
   4. Jumps straight to the target — at full speed, inlinable (8.8)
```

> ⭐ **A call site that decides its own target on first execution, then runs at full
> speed.** The linkage strategy lives in *library* code (the bootstrap method), not in the
> bytecode — so the JDK can change how lambdas are implemented without recompiling a single
> line of your code.

### ⭐ What actually uses it

| Feature | Bootstrap method |
|---|---|
| **Lambdas** (6.1) | `LambdaMetafactory.metafactory` |
| **Method references** (6.2) | Same |
| **String concatenation** (1.3) `Java 9` | `StringConcatFactory.makeConcatWithConstants` |
| **Records' `equals`/`hashCode`/`toString`** (2.6) | `ObjectMethods.bootstrap` |
| **Pattern-matching `switch`** (7.2) `Java 21` | `SwitchBootstraps.typeSwitch` |

**Verify it yourself** (8.1):

```bash
javap -c -p YourClass.class | grep invokedynamic
```

```java
// this line...
String s = "a" + x + "b";

// ...compiles to ONE invokedynamic, not a chain of StringBuilder calls
//    0: invokedynamic #7  // makeConcatWithConstants
```

> **That's why 1.3 said `+` is fine outside a loop**: the JVM picks an optimal strategy at
> link time — often a single exactly-sized allocation — rather than the `StringBuilder`
> chain javac used to emit. And because the strategy is in library code, it improved in
> later JDKs with no recompilation.

**And it's why a lambda produces no class file** (6.1, 2.9): there's no
`Outer$1.class` because the implementing class is spun up at runtime by
`LambdaMetafactory` and cached.

## `VarHandle` — covered in 9.6

```java
VarHandle vh = MethodHandles.lookup().findVarHandle(Counter.class, "value", int.class);
vh.getVolatile(obj);
vh.compareAndSet(obj, expected, newValue);
```

The field-and-array equivalent of `MethodHandle`, with **explicit memory ordering modes**
(9.3) — the supported replacement for `sun.misc.Unsafe`. Full treatment in 9.6.

---

## ⭐ Do you need this?

**Almost certainly not.** You need it if you are:

- Writing a language runtime on the JVM
- Writing a framework that generates call sites
- Replacing hot reflective calls with something the JIT can inline

**You benefit from it constantly**, because lambdas, string concatenation, records and
switch patterns all run on it.

> **The value of this page is recognition**: when you see `invokedynamic` in `javap`
> output, or `LambdaMetafactory` in a stack trace, or `StringConcatFactory` in a profile,
> you now know what they are and why they're there.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `MethodHandle` in an instance field | Loses the constant-folding benefit. Make it `static final` |
| `invokeExact` with a mismatched cast | `WrongMethodTypeException` — the cast is part of the signature |
| Expecting a class file per lambda | `invokedynamic` — none exists (6.1) |
| Using method handles for ordinary code | Reflection is simpler; a direct call is simpler still |
| Passing a `Lookup` around | It **carries access rights** — a capability leak |

## Recap

| Concept | One line |
|---|---|
| `MethodHandle` | **JIT-friendly** reflection. `static final` → inlinable |
| `MethodType` | `(params) → return` |
| `Lookup` | ⭐ **A capability** carrying the creating class's access rights |
| `invokeExact` vs `invoke` | Exact signature vs with conversions |
| Combinators | `bindTo`, `insertArguments`, `filterArguments`, `guardWithTest` |
| ⭐ **`invokedynamic`** | **Decides its target on first call, then runs at full speed** |
| Used by | **Lambdas, method references, string concat, records, switch patterns** |
| `VarHandle` | Fields and arrays with explicit ordering (9.6) |
| Do you need it? | **No.** Recognise it in `javap` and stack traces |
