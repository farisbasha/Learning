# 11.10 — The module system

> **What this is:** **Deliberately last.** It is **important to understand and mostly
> optional to use**, and knowing which is which saves a lot of wasted effort. `Java 9`

---

## ⭐ What the JDK needed it for

**Not for you. For itself.**

Before Java 9 the entire JDK was one jar — `rt.jar`, ~60 MB, ~20,000 classes — and
**everything in it was reachable**:

```java
sun.misc.Unsafe                      // ⚠️ internal, and half the ecosystem used it
com.sun.*, sun.*                     // ⚠️ internal, no compatibility promise, widely used
```

Two consequences the JDK team could not live with:

| Problem | |
|---|---|
| **No encapsulation** | "Internal" was a naming convention, not a boundary. The JDK couldn't change internals without breaking Netty, Hibernate and Spring |
| **Monolithic** | You shipped 60 MB to run "hello world". No way to build a smaller runtime |

**JPMS (Java Platform Module System) fixed both — for the JDK.** `java.base`, `java.sql`,
`java.xml` and ~70 others are now real modules with real boundaries, and `jlink` (8.10) can
assemble just the ones you use.

> ⭐ **That is the part that affects you**, whether or not you ever write a
> `module-info.java`.

---

## `module-info.java`

```java
module com.example.app {
    requires java.sql;                        // I need this module
    requires transitive com.example.api;      // ⭐ and anyone requiring ME gets it too

    exports com.example.app.api;              // ⭐ PUBLIC API — compile + runtime access
    exports com.example.app.internal to com.example.other;   // qualified export

    opens com.example.app.model;              // ⭐ REFLECTIVE access (11.6) — for frameworks

    uses com.example.spi.Plugin;              // I consume this service
    provides com.example.spi.Plugin
        with com.example.app.MyPlugin;        // I provide this implementation
}
```

| Directive | Means |
|---|---|
| `requires` | I depend on this module |
| `requires transitive` | ⭐ …and my consumers get it automatically |
| `exports` | This package is my **public API** |
| `exports … to` | …but only to named modules |
| ⭐ **`opens`** | **Deep reflective access** (11.6) — what Hibernate and Jackson need |
| `uses` / `provides` | `ServiceLoader` wiring |

> ⭐ **`exports` vs `opens` is the distinction that matters.** `exports` grants normal
> compile-and-call access to public members. **`opens` grants reflective access to
> everything, including private members** — which is what a framework calling
> `setAccessible(true)` (11.6) requires.
>
> Forget `opens` and Jackson cannot read your DTO's fields, at runtime, with a confusing
> `InaccessibleObjectException`.

## Module path versus class path

```bash
java -cp lib/*  com.example.Main            # ⭐ CLASS path  — no modules, everything open
java -p mods -m com.example.app/com.example.Main    # MODULE path — modules enforced
```

**Three kinds of module:**

| Kind | What it is | Reads | Exports |
|---|---|---|---|
| **Named** | Has a `module-info.class` | What it `requires` | What it `exports` |
| **Automatic** | A plain jar **on the module path** | ⭐ **Everything** | ⭐ **Everything** |
| **Unnamed** | Anything **on the class path** | Everything | Everything |

> ⭐ **Automatic modules are the migration bridge**: drop a non-modular jar on the module
> path and it becomes a module named after its jar file, reading and exporting everything.
> It lets you modularise your own code before your dependencies do — at the cost of getting
> no encapsulation from them.

**If you do nothing, your application runs on the class path as an unnamed module** — which
is what the overwhelming majority of Java applications do, including most Spring Boot
services.

## ⭐ Strong encapsulation — and `--add-opens`

**This is the part you will actually meet.**

```java
sun.misc.Unsafe.getUnsafe();              // ⚠️ warned in 9, restricted in 16, mostly gone
```

| Version | Behaviour for JDK internals |
|---|---|
| Java 9 | Warning |
| Java 16 | ⭐ **Denied by default** |
| Java 17+ | Enforced; no way to relax without flags |

```
InaccessibleObjectException: Unable to make field private java.lang.String.value
accessible: module java.base does not "opens java.lang" to unnamed module
```

**The escape hatch:**

```bash
--add-opens java.base/java.lang=ALL-UNNAMED      # reflective access
--add-exports java.base/sun.nio.ch=ALL-UNNAMED   # compile/call access
--add-modules java.sql                            # add a module to the graph
```

> ⭐ **If you've seen a block of `--add-opens` flags in a `pom.xml`, a Gradle
> `jvmArgs`, or a `JAVA_OPTS` — this is what they are.** A library is reflecting into JDK
> internals that were sealed, and the flags reopen them. They're a **migration aid, not a
> solution**: each one is a library that needs updating, and they may stop working.

This connects directly to 11.6: `setAccessible(true)` is now subject to module permissions,
and to 9.6: `sun.misc.Unsafe` being closed is why `VarHandle` exists.

## Services and `ServiceLoader`

```java
// in the API module
public interface PaymentProvider { boolean supports(String type); }

// in the provider module's module-info.java
provides com.example.PaymentProvider with com.example.stripe.StripeProvider;

// in the consumer's module-info.java
uses com.example.PaymentProvider;
```

```java
ServiceLoader.load(PaymentProvider.class)
    .stream()
    .map(ServiceLoader.Provider::get)
    .filter(p -> p.supports("card"))
    .findFirst();
```

**Plugin discovery with no reflection configuration and no DI container.** It also works on
the class path via `META-INF/services/` files — that mechanism predates modules (it's how
JDBC drivers and SLF4J bindings are found).

> ⭐ **`ServiceLoader` works in GraalVM native images** (8.10) where reflective discovery
> doesn't, because the provider set is known at build time.

## ⭐ Module import declarations `Java 25`

**A real ergonomic win**, and the one module feature you might use without adopting modules:

```java
import module java.base;          // ⭐ imports EVERY exported package of java.base
```

```java
import module java.base;

void main() {
    List<String> names = new ArrayList<>();      // no java.util import
    var path = Path.of("x");                     // no java.nio.file import
    IO.println(Map.of("a", 1));
}
```

Replaces a stack of `import java.util.*; import java.nio.file.*; import java.util.stream.*;`
with one line. Especially good for scripts and compact source files (0.4).

⚠️ Ambiguity (two modules exporting the same simple name, like `List`) still requires an
explicit single-type import to resolve.

## ⭐ The honest assessment

> **Most applications never declare a module. The JDK itself is fully modularised, and
> that is what affects you.**

**Why adoption stayed low:**

| Reason | |
|---|---|
| **Spring Boot doesn't need it** | Fat jars on the class path work fine |
| **The dependency graph must cooperate** | One non-modular dependency with a split package blocks you |
| **Split packages are fatal** | Two jars contributing the same package cannot both be modules |
| **The benefit is small for applications** | You already control your own code |
| **Automatic module names are unstable** | Derived from the filename unless the jar sets `Automatic-Module-Name` |

**When it IS worth adopting:**

| Case | Why |
|---|---|
| ⭐ **You want `jlink`** | It **requires** modules (8.10). ~300 MB → ~40 MB runtime |
| **You publish a library** | Real API boundaries; consumers can't depend on your internals |
| **A large modular codebase** | Compile-time enforcement of architectural layers |

> **The practical advice:** understand `--add-opens` because you *will* meet it. Set
> `Automatic-Module-Name` in your library's manifest as a courtesy. Otherwise, write
> `module-info.java` only when you want `jlink` or you're publishing a library.

---

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `exports` where `opens` is needed | Frameworks fail reflectively at **runtime** |
| Split packages | Fatal — two modules cannot share a package |
| `--add-opens` as a permanent fix | A migration aid. The library needs updating |
| Expecting modules to solve dependency versioning | They don't. **No version resolution at all** |
| Relying on an automatic module's name | Derived from the filename unless declared |
| Modularising before your dependencies do | One uncooperative jar blocks the whole graph |

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `sun.misc.Unsafe` | `VarHandle` (9.6), `MemorySegment` (11.9) |
| `com.sun.*` / `sun.*` internals | The public API |
| Permanent `--add-opens` in production | Update the library |

## Recap

| Concept | One line |
|---|---|
| **Why it exists** | To break up `rt.jar` and make JDK internals **genuinely inaccessible** |
| `module-info.java` | `requires`, `exports`, **`opens`**, `uses`, `provides` |
| ⭐ **`exports` vs `opens`** | **Public API vs deep reflective access** (11.6) |
| Automatic modules | A plain jar on the module path — the migration bridge |
| **Strong encapsulation** | Denied by default since **Java 16**. `--add-opens` is the escape hatch |
| `ServiceLoader` | Plugin discovery; **works in native images** |
| `import module java.base;` | `Java 25`. A real ergonomic win |
| ⭐ **Honest assessment** | **Most apps never declare one.** Adopt it for `jlink` or a library |
