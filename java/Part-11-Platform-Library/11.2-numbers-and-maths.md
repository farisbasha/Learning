# 11.2 — Numbers and maths

> **What this is:** **Mostly about knowing when the obvious type is the wrong one.**

---

## `Math` and the `*Exact` methods

```java
Math.max, min, abs, pow, sqrt, floor, ceil, round
Math.floorMod(-7, 3);        // 2 — always positive, unlike % (1.2)
Math.floorDiv(-7, 3);        // -3 — rounds toward negative infinity
Math.hypot(x, y);            // √(x²+y²) without intermediate overflow
```

### ⭐ The `*Exact` methods — throw instead of overflowing silently

**Integer overflow is silent** (1.1) — this is the fix:

```java
int big = Integer.MAX_VALUE;
big + 1;                     // ⚠️ -2147483648, silently
Math.addExact(big, 1);       // ✅ ArithmeticException: integer overflow
```

```java
Math.addExact, subtractExact, multiplyExact, negateExact, incrementExact,
     decrementExact, absExact, toIntExact
```

```java
long total = ...;
int count = Math.toIntExact(total);     // ✅ throws if it doesn't fit
int count = (int) total;                // ❌ silently truncates (1.1)
```

> **Use `*Exact` anywhere a wrong answer matters more than a thrown exception** —
> financial calculations, sizes, IDs, anything derived from user input. The cost is
> approximately zero (the JIT compiles it to an add plus an overflow-flag check, 8.8).

## ⭐ `BigDecimal` — money

`double` cannot represent `0.1` (1.1). **Never use it for money.**

```java
0.1 + 0.2 == 0.3;           // false
0.1 + 0.2;                  // 0.30000000000000004
```

### ⚠️ `new BigDecimal(0.1)` is a bug; `BigDecimal.valueOf(0.1)` is not

```java
new BigDecimal(0.1);
// 0.1000000000000000055511151231257827021181583404541015625
//   ⚠️ faithfully represents the double's actual value — including its error

BigDecimal.valueOf(0.1);    // 0.1  ✅ — goes via Double.toString()
new BigDecimal("0.1");      // 0.1  ✅ — best: never involve a double at all
```

> ⭐ **The rule: construct a `BigDecimal` from a `String`, or use `valueOf`. Never pass a
> `double` to the constructor.** Doing so imports the exact error you were trying to avoid.
> ErrorProne and SpotBugs both flag this (12.5).

### Scale and rounding

```java
var price = new BigDecimal("19.99");
var qty   = new BigDecimal("3");

price.multiply(qty);                                    // 59.97 — scale 4 → 59.9700
price.divide(qty, 2, RoundingMode.HALF_UP);             // ⭐ scale + mode REQUIRED
price.divide(new BigDecimal("3"));                      // 💥 ArithmeticException — non-terminating
```

**`divide` without a rounding mode throws** if the result doesn't terminate. That's
deliberate: it forces you to decide.

| Mode | |
|---|---|
| `HALF_UP` | 0.5 → up. **What people mean by "round"** |
| `HALF_EVEN` | **Banker's rounding** — 0.5 → nearest even. The financial default; avoids systematic bias |
| `UP` / `DOWN` | Away from / toward zero |
| `CEILING` / `FLOOR` | Toward +∞ / −∞ |

```java
amount.setScale(2, RoundingMode.HALF_EVEN);
```

### ⭐ `equals` compares scale; `compareTo` does not

**A real source of bugs** — and the JDK's own documented exception to the
`compareTo`/`equals` consistency rule (5.5):

```java
var a = new BigDecimal("1.0");
var b = new BigDecimal("1.00");

a.equals(b);          // ⚠️ FALSE — different scale
a.compareTo(b) == 0;  // ✅ TRUE — same value
```

**The consequences:**

```java
Set<BigDecimal> set = new HashSet<>();      // uses equals (2.5)
set.add(new BigDecimal("1.0"));
set.contains(new BigDecimal("1.00"));       // false 😱

new TreeSet<>(...)                          // uses compareTo (5.5) — treats them as equal
```

> ⭐ **Always compare `BigDecimal` with `compareTo`, never `equals`.** And normalise the
> scale (`setScale`) before storing them in a `HashSet` or using them as map keys.

**The alternative for money:** store integer **minor units** (cents, paise) in a `long`.
Exact, fast, no scale questions. Most payment systems do this.

## `BigInteger`

```java
var big = new BigInteger("123456789012345678901234567890");
big.multiply(big);
big.pow(100);
big.mod(other);
big.isProbablePrime(100);
big.gcd(other);
```

Arbitrary precision integers. Used in cryptography (11.5), and anywhere `long` overflows.
Immutable, and much slower than primitives — don't reach for it by default.

## Parsing and formatting

```java
Integer.parseInt("42");           // throws NumberFormatException (4.1)
Integer.parseInt("ff", 16);       // 255 — radix
Long.parseLong("42");
Double.parseDouble("3.14");
Integer.valueOf("42");            // → Integer (boxed, cached, 1.1)
```

### ⚠️ Locale-dependent decimal separators

```java
NumberFormat.getInstance();                     // ⚠️ uses the DEFAULT locale
NumberFormat.getInstance(Locale.GERMANY).parse("1.234,56");   // 1234.56
NumberFormat.getInstance(Locale.US).parse("1,234.56");        // 1234.56
```

**In Germany `1.234,56` means one thousand two hundred thirty-four point five six.** In the
US it means 1.234 followed by nonsense.

```java
NumberFormat.getCurrencyInstance(Locale.UK).format(1234.56);   // £1,234.56
NumberFormat.getPercentInstance().format(0.75);                // 75%
new DecimalFormat("#,##0.00").format(1234.5);                  // 1,234.50
```

> ⚠️ **`Double.parseDouble` always uses `.` regardless of locale** — which is correct for
> machine-readable data and wrong for user input. Use `NumberFormat` with an explicit
> locale for anything a human typed (11.4).

## Bit manipulation

```java
Integer.bitCount(n);              // population count
Integer.toBinaryString(n);
Integer.toHexString(n);
Integer.highestOneBit(n);
Integer.numberOfLeadingZeros(n);
Integer.reverse(n);
Integer.rotateLeft(n, 4);

Long.bitCount(n);                 // same family on Long
Integer.MAX_VALUE, MIN_VALUE, SIZE, BYTES
```

Most compile to a **single CPU instruction** (8.1) — `bitCount` becomes `POPCNT`. They're
free and clearer than hand-rolled bit twiddling.

## `StrictMath` and floating-point reproducibility

```java
Math.sin(x);            // may use a faster platform-specific intrinsic
StrictMath.sin(x);       // ⭐ bit-for-bit identical on every platform, forever
```

`Math` is allowed to use hardware instructions with up to 1 ULP of difference between
platforms. `StrictMath` uses a fixed software algorithm.

> **Use `StrictMath` when results must be reproducible across machines** — distributed
> computation where nodes must agree, scientific work, anything hashed or compared.
> Otherwise `Math` is faster.

💀 The `strictfp` keyword is **obsolete since Java 17** — all floating-point arithmetic is
now strict by default (JEP 306). If you see `strictfp` in code, it's a no-op.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `double` for money | `0.1 + 0.2 != 0.3`. Use `BigDecimal` or minor units |
| `new BigDecimal(0.1)` | Imports the double's error. Use `valueOf` or a `String` |
| `bigDecimal.equals(other)` | **Compares scale.** Use `compareTo` |
| `BigDecimal` in a `HashSet` | `1.0` and `1.00` are different keys |
| `divide` with no rounding mode | Throws on non-terminating results |
| Silent integer overflow | Use `Math.addExact` |
| `(int) someLong` | Truncates. Use `Math.toIntExact` |
| `NumberFormat.getInstance()` | Default locale — machine-dependent (11.4) |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `double` for currency | `BigDecimal` or `long` minor units |
| `new BigDecimal(double)` | `BigDecimal.valueOf` / `new BigDecimal(String)` |
| `strictfp` | No-op since Java 17 |
