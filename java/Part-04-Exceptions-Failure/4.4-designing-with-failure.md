# 4.4 — Designing with failure

> **What this is:** Judgement, not syntax. The syntax was 4.3; this is where to actually
> put things. **One item on this page — logging *and* throwing — is the most common
> mistake in Java codebases**, and you will see it everywhere.

---

## 1. Writing custom exceptions

### When a new type earns its place

**Only when a caller would `catch` it specifically.** That's the whole test.

```java
// ❌ nobody will ever catch these separately
class UserNotFoundException extends RuntimeException { }
class OrderNotFoundException extends RuntimeException { }
class ProductNotFoundException extends RuntimeException { }
```

Every caller writes `catch (Exception e)` anyway, so the three types bought nothing.
Either use `Optional` for absence (4.2), or one type carrying the detail:

```java
// ✅ one type, the detail as data
public class NotFoundException extends RuntimeException {
    private final String entityType;
    private final String id;
    // ...
}
```

```java
// ✅ these genuinely earn it — a caller WILL branch on them
class InsufficientFundsException extends RuntimeException { }   // → show a top-up prompt
class RateLimitExceededException extends RuntimeException { }   // → back off and retry
```

**Prefer the JDK's types when they fit.** `IllegalArgumentException`,
`IllegalStateException` and `UnsupportedOperationException` cover a surprising amount of
ground (4.1).

### Constructor conventions

Provide all four. This is what every JDK exception does, and tooling expects it:

```java
public class OrderException extends RuntimeException {
    public OrderException() { super(); }
    public OrderException(String message) { super(message); }
    public OrderException(String message, Throwable cause) { super(message, cause); }
    public OrderException(Throwable cause) { super(cause); }
}
```

**The `(String, Throwable)` one is non-negotiable** — without it, callers cannot preserve
the cause chain (4.3).

### Carry the data, not just a message

```java
// ❌ the caller has to parse the message to do anything
throw new InsufficientFundsException("Balance 50.00 but tried to withdraw 100.00");

// ✅ the caller can use the values
public class InsufficientFundsException extends RuntimeException {
    private final BigDecimal balance;
    private final BigDecimal requested;

    public InsufficientFundsException(BigDecimal balance, BigDecimal requested) {
        super("Balance %s but tried to withdraw %s".formatted(balance, requested));
        this.balance = balance;
        this.requested = requested;
    }

    public BigDecimal balance()   { return balance; }
    public BigDecimal shortfall() { return requested.subtract(balance); }
}
```

Now a handler can render `"You need £%s more"` without string-parsing.

## ⭐ 2. Messages that contain the values

This is the cheapest high-value habit on the page.

```java
// ❌ tells you the category, which you already knew from the exception type
throw new IllegalArgumentException("Invalid age");
throw new IllegalStateException("Connection not ready");
throw new IllegalArgumentException("Invalid input");

// ✅ tells you what actually happened
throw new IllegalArgumentException("age must be 0–150, got: " + age);
throw new IllegalStateException("connection is " + state + ", expected OPEN");
throw new IllegalArgumentException(
    "email must contain '@', got: '%s' (length %d)".formatted(email, email.length()));
```

> **The test: could you diagnose the problem from the log line alone, at 3am, without the
> source?** If not, add the values.

Include: **the offending value, the expected range or condition, and the identifier**
(order id, user id) that lets you find the record.

```java
// ⚠️ but never log secrets
throw new IllegalArgumentException("invalid token: " + token);   // ❌ leaks a credential
throw new IllegalArgumentException("invalid token for user " + userId);  // ✅
```

Same rule as `toString()` in 2.5.

## 3. Failing fast at boundaries vs defensive checks everywhere

```java
// ❌ defensive checks scattered through every layer
public void process(Order order) {
    if (order == null) return;                        // silently does nothing?!
    if (order.items() == null) return;
    for (Item item : order.items()) {
        if (item == null) continue;
        if (item.price() == null) continue;
        ...
    }
}
```

This is the "defensive programming" style, and it's a trap:
- It **hides bugs** rather than surfacing them — a `null` order now silently succeeds.
- It **spreads uncertainty**: every method must re-check, because none can trust its input.
- It's **unmaintainable** — you can never delete a check, because you can't prove nothing
  relies on it.

```java
// ✅ validate ONCE, at the boundary; trust everywhere inside
public record Order(Customer customer, List<Item> items) {
    public Order {
        Objects.requireNonNull(customer, "customer");
        items = List.copyOf(items);          // rejects null list AND null elements (2.10)
        if (items.isEmpty())
            throw new IllegalArgumentException("order must have at least one item");
    }
}

public void process(Order order) {
    for (Item item : order.items()) { ... }  // no checks needed — it CANNOT be invalid
}
```

> **Validate at the boundary** — constructors, public API entry points, deserialisation.
> **Trust inside.** This is "make illegal states unrepresentable" (2.10) applied to
> error handling.

**Where the boundary is:**

| Boundary | Validate |
|---|---|
| HTTP handler | Request body, params |
| Constructor / factory | Invariants |
| Public library method | Arguments |
| Deserialisation | Everything |
| **Private method** | **Nothing** — it's already been validated |

## 4. Where to catch

> **As close to where you can actually do something as possible, and nowhere else.**

```java
// ❌ catching at every level, doing nothing useful
public User load(String id) {
    try {
        return repo.find(id);
    } catch (DataAccessException e) {
        log.error("failed to load", e);
        throw e;                         // ← what did this accomplish?
    }
}
```

That block adds a log line and rethrows. Every layer doing this produces the same error
logged six times (see §5).

```java
// ✅ let it propagate to somewhere that can act
public User load(String id) {
    return repo.find(id);                // no try/catch at all
}

// ...and catch where a decision exists
@ExceptionHandler(DataAccessException.class)
public ResponseEntity<Error> handle(DataAccessException e) {
    log.error("database failure", e);              // logged ONCE
    return ResponseEntity.status(503).body(new Error("service unavailable"));
}
```

**The three places catching is legitimate:**

1. **You can genuinely recover** — retry, fall back to a cache, use a default.
2. **You're adding context and rethrowing** — with the cause (4.3).
3. **You're at a top-level boundary** — the HTTP handler, the scheduled-job wrapper, the
   `main` method — where the process must not die and the failure must be reported.

Anywhere else, don't catch.

## ⭐ 5. Logging versus throwing — **the most common mistake**

```java
// ❌ log AND throw
catch (SQLException e) {
    log.error("Failed to load user", e);
    throw new AppException("Failed to load user", e);
}
```

**Why this is wrong:** the exception propagates upward and gets logged again at the next
layer, and again at the top-level handler. One failure produces **three to six identical
stack traces** in your log, at different timestamps, looking like multiple incidents.

Anyone debugging then has to work out whether they're seeing one problem or several.

> **The rule: log **or** throw, never both.**
> - **Throwing?** Don't log. The catcher will.
> - **Handling it here** (swallowing, recovering, returning a default)? **Log it**, because
>   nobody upstream will ever see it.

```java
// ✅ throwing — no log
catch (SQLException e) {
    throw new DataAccessException("query failed: " + sql, e);
}

// ✅ handling — log, because this is where the trail ends
catch (CacheException e) {
    log.warn("cache unavailable, falling back to database", e);
    return database.load(id);
}

// ✅ top-level — log, because there's nowhere left to throw to
catch (Exception e) {
    log.error("request failed: {}", request.id(), e);
    return errorResponse(500);
}
```

**And always pass the exception as the last argument**, never concatenate it:

```java
log.error("failed: " + e.getMessage());     // ❌ no stack trace at all
log.error("failed", e);                     // ✅ full trace
log.error("failed for user {}", userId, e); // ✅ SLF4J — placeholders + trailing throwable
```

## 💀 6. What never to do

### Empty catch blocks

```java
catch (Exception e) { }                    // ❌
catch (Exception e) { /* ignore */ }       // ❌ a comment doesn't make it OK
```

The single worst thing in this part. The failure becomes **invisible** — no log, no
rethrow, no evidence. Debugging a system with swallowed exceptions is genuinely miserable
because the symptom appears arbitrarily far from the cause.

**If you truly must ignore something, prove you thought about it:**

```java
catch (NumberFormatException e) {
    // Expected: this field is optional and free-text. Absence means "use the default".
    return defaultValue;
}
```

### Catching `Throwable` or `Exception` broadly

```java
catch (Throwable t) { }     // ❌ catches Error too — OutOfMemoryError, StackOverflowError
catch (Exception e) { }     // ❌ catches every RuntimeException — i.e. all your bugs
```

`catch (Exception e)` turns a `NullPointerException` in your own code into a handled
condition. The bug stops being visible and starts being "handled".

**The one legitimate use** is a top-level supervisor that must not die:
```java
// a scheduled job wrapper — must survive one bad task
try {
    task.run();
} catch (Exception e) {                    // Exception, NOT Throwable
    log.error("task {} failed", task.id(), e);
}
```

### Exceptions for control flow

```java
// ❌ using an exception as a loop terminator
try {
    int i = 0;
    while (true) { process(list.get(i++)); }
} catch (IndexOutOfBoundsException e) {
    // "done"
}
```

Two problems: it's unreadable, and stack capture is ~1000× a method call (4.1), so this is
catastrophically slow in a hot path.

```java
// ❌ absence as an exception
try {
    User u = findUser(id);
    return u.name();
} catch (UserNotFoundException e) {
    return "Guest";
}

// ✅
return findUser(id).map(User::name).orElse("Guest");   // Optional (6.7)
```

> **The test: is this outcome *exceptional*, or just *one of the normal results*?**
> "Not found" on a lookup is normal. "Disk is on fire" is exceptional.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| Log and throw | One failure, six stack traces |
| `log.error("x: " + e.getMessage())` | No stack trace. Pass `e` as an argument |
| `catch (Exception e)` mid-stack | Catches your own bugs and hides them |
| Null checks in every method | Validate at the boundary, trust inside |
| A new exception class per entity | Only if someone will `catch` it specifically |
| Generic messages | Include the value, the expectation, and an identifier |

---

## Recap

| Principle | One line |
|---|---|
| New exception type | Only if a caller will catch it specifically |
| Constructors | All four; `(String, Throwable)` is mandatory |
| Messages | The offending value + expected range + an id. **No secrets** |
| Validation | **At the boundary, once.** Trust inside |
| Where to catch | Where you can act: recover, add context, or top-level |
| **Log or throw** | **Never both** |
| Never | Empty catch, `catch (Throwable)`, exceptions as control flow |
