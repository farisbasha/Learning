# 4.1 — The hierarchy

> **What this is:** Three categories with three different meanings. **Most bad error
> handling comes from conflating them.**

---

## Coming from JS/Python/Dart

| | JS/Python/Dart | Java |
|---|---|---|
| Categories | One — everything is throwable | **Three**, with different rules |
| Compiler involvement | None | **Checked exceptions are enforced** |
| Stack trace cost | Cheap-ish | **Expensive** — captured at construction |

The genuinely new idea is **checked exceptions**: the compiler refuses to compile code
that ignores certain failures. No other mainstream language kept this.

---

## The concepts

### The tree

```
                    Throwable
                   /         \
              Error           Exception
           (don't catch)     /          \
                    RuntimeException   (everything else)
                    (unchecked)        (CHECKED)
```

| Branch | Checked? | Meaning | You should |
|---|---|---|---|
| `Error` | ❌ No | **The JVM is in trouble** | Do not catch |
| `RuntimeException` | ❌ No | **A programming bug** | Fix the code, don't catch |
| Other `Exception` | ✅ **Yes** | A recoverable condition | Handle or declare |

Everything under `Error` and `RuntimeException` is **unchecked**. Everything else under
`Exception` is **checked**.

### `Error` — the JVM is in trouble

```java
OutOfMemoryError        // heap exhausted
StackOverflowError      // recursion too deep (1.5)
NoClassDefFoundError    // a class was there at compile time, missing at runtime (1.6)
ExceptionInInitializerError  // a static initialiser threw (2.2)
LinkageError            // incompatible class versions
```

```java
// ❌ never
try { ... } catch (OutOfMemoryError e) { ... }
```

**Why not:** if the heap is exhausted, your handler needs memory to run. Your logging call
needs memory. Your recovery allocates. You are very likely to throw another
`OutOfMemoryError` from inside the handler, and now you've lost the original.

> **The only legitimate exception:** a top-level supervisor in a server that logs and
> exits deliberately. Even then, `-XX:+ExitOnOutOfMemoryError` is usually better.

`NoClassDefFoundError` is the one you'll actually *see* most — it almost always means a
classpath problem (1.6), not a code problem.

### Checked exceptions — the compiler forces you to acknowledge

```java
// The compiler will not let you ignore this
public void read() throws IOException {
    Files.readString(Path.of("data.txt"));
}
```

```java
Files.readString(path);      // ❌ error: unreported exception IOException;
                             //    must be caught or declared to be thrown
```

You have exactly two options:

```java
// 1. handle it
try {
    var content = Files.readString(path);
} catch (IOException e) {
    // do something real
}

// 2. declare it and make it the caller's problem
void load() throws IOException {
    var content = Files.readString(path);
}
```

The common ones: `IOException`, `SQLException`, `InterruptedException`,
`ClassNotFoundException`, `ParseException`.

### Unchecked exceptions — programming errors

```java
NullPointerException          // you dereferenced null
IllegalArgumentException      // caller passed nonsense
IllegalStateException         // the object is in the wrong state for this call
ClassCastException            // a bad cast (3.3)
IndexOutOfBoundsException     // bad index
ArithmeticException           // integer divide by zero
ConcurrentModificationException  // modified a collection while iterating (Part 05)
UnsupportedOperationException // e.g. add() on List.of()
```

**These signal bugs.** The correct response is almost never `catch` — it's to fix the code
so the condition cannot arise.

**The two you should throw yourself, constantly:**

```java
// the ARGUMENT is wrong
if (amount <= 0)
    throw new IllegalArgumentException("amount must be positive, got: " + amount);

// the OBJECT is in the wrong state for this call
if (closed)
    throw new IllegalStateException("connection already closed");
```

The distinction: `IllegalArgument` blames the **caller's input**; `IllegalState` blames
the **timing**.

## ⭐ What a stack trace contains, and why capturing it is expensive

```java
throw new IllegalStateException("nope");
```

At the moment the exception object is **constructed** (not thrown — constructed), the JVM
walks the entire call stack and records every frame: class, method, file, line number.

**That's the cost, and it scales with how deep the stack is.** Measured on OpenJDK 17,
after JIT warmup, 200k iterations:

| Stack depth | `new RuntimeException("x")` | Same, stack capture disabled | Plain call |
|---:|---:|---:|---:|
| 1 | **450 ns** | 15 ns | ~2 ns |
| 10 | **624 ns** | 15 ns | ~2 ns |
| 50 | **2,061 ns** | 47 ns | ~2 ns |
| 100 | **3,353 ns** | 344 ns | ~2 ns |

Two things to read off this:

1. **The stack walk is almost the entire cost.** At depth 1 it's 450 ns vs 15 ns without
   capture — a **30×** difference for the same allocation.
2. **It scales with depth.** In a real application (a web request at depth 50–100 through
   a framework), you're paying **2–3 microseconds** per exception constructed.

Against a ~2 ns method call, that's roughly **200× at shallow depth and 1,500× deep in a
framework stack.**

> **This is why "exceptions for control flow" is a real performance problem**, not just a
> style objection (4.4). Throwing one exception per loop iteration in a hot path is
> measurably catastrophic.

**Suppressing capture** — the `false, false` trick from the table above, for a genuinely
hot, pre-allocated exception:

```java
public class FastException extends RuntimeException {
    public FastException(String msg) {
        super(msg, null, false, false);    // enableSuppression=false, writableStackTrace=false
    }
}
```

Rare, and a strong smell. If you need this, you're probably using exceptions for control
flow.

**Reading a trace properly** is covered in 1.5 — top frame is where it threw, the last
`Caused by:` is usually the root cause.

### Helpful NullPointerExceptions `Java 14`

Before Java 14:
```
Exception in thread "main" java.lang.NullPointerException
    at com.example.Main.process(Main.java:12)
```

Line 12 is `order.customer().address().city()`. **Which one was null?** You had to add
print statements or split the line.

Java 14+:
```
Exception in thread "main" java.lang.NullPointerException:
    Cannot invoke "Address.city()" because the return value of
    "Customer.address()" is null
        at com.example.Main.process(Main.java:12)
```

It names the **exact expression**. This is genuinely one of the best quality-of-life
improvements in modern Java, and a strong reason not to run on Java 11.

> Enabled by default since Java 15. If you're on 14, add
> `-XX:+ShowCodeDetailsInExceptionMessages`.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `catch (Exception e)` | Also catches every `RuntimeException` — i.e. your bugs |
| `catch (Throwable e)` | Also catches `Error`. Never do this |
| Catching `NullPointerException` | You're catching a bug. Fix the bug |
| Exceptions are cheap | Stack capture is 200–1,500× a method call, depending on depth |
| Catching `OutOfMemoryError` to recover | Your handler needs memory too |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `catch (Throwable t)` | Catch the specific type you can handle |
| Catching `Error` | Let it kill the JVM |
| `throw new Exception("...")` | A specific type — `IllegalArgumentException`, or your own (4.4) |
| `e.printStackTrace()` | A logger (4.4) |

---

## Recap

| Category | Checked | Means | Response |
|---|---|---|---|
| `Error` | ❌ | JVM in trouble | Don't catch |
| `RuntimeException` | ❌ | **Your bug** | Fix the code |
| Other `Exception` | ✅ | Recoverable condition | Handle or declare |

| Fact | |
|---|---|
| Stack trace captured | At **construction**, not at throw |
| Cost | 450 ns shallow, ~3,400 ns at depth 100. The **stack walk** is ~97% of it |
| Helpful NPEs | `Java 14`, on by default since 15 |
