# 4.3 — The mechanics

> **What this is:** The syntax — including **one construct, try-with-resources, that you
> should reach for automatically** and that most older code doesn't use.

---

## Coming from JS/Python/Dart

- `try`/`catch`/`finally` — identical to JS.
- **try-with-resources** is Python's `with` statement. Same purpose, same automatic
  cleanup, and Java's version handles the "both the body and the close failed" case
  more carefully than Python does.
- **Multi-catch** `catch (A | B e)` is Python's `except (A, B) as e`.

---

## The concepts

### `try` / `catch` / `finally`

```java
try {
    risky();
} catch (FileNotFoundException e) {
    // most specific first
} catch (IOException e) {
    // less specific
} finally {
    // always runs — exception or not, return or not
}
```

**Catch ordering: most specific to least specific.** The compiler enforces it:

```java
try { ... }
catch (IOException e) { }
catch (FileNotFoundException e) { }   // ❌ error: already caught by IOException
```

`FileNotFoundException extends IOException`, so the first block would catch everything and
the second would be unreachable (1.7).

### Multi-catch `Java 7`

When two exceptions get identical handling:

```java
// ❌ before Java 7 — duplicated
try { ... }
catch (IOException e)        { log.error("failed", e); throw new AppException(e); }
catch (SQLException e)       { log.error("failed", e); throw new AppException(e); }

// ✅ Java 7
try { ... }
catch (IOException | SQLException e) {
    log.error("failed", e);
    throw new AppException(e);
}
```

Two rules:
- The types must **not** be in a subtype relationship (`catch (IOException | FileNotFoundException e)` is an error — the second is redundant).
- `e` is **implicitly final** — you cannot reassign it.

The static type of `e` is the **least upper bound** of the listed types, so you can only
call methods common to all of them.

## ⚠️ The `finally` traps

### Trap 1 — `return` inside `finally` swallows the exception

```java
static int broken() {
    try {
        throw new RuntimeException("the real problem");
    } finally {
        return 42;              // 💥 the exception VANISHES. Returns 42.
    }
}
```

The `return` in `finally` completes the method normally, **discarding the in-flight
exception entirely**. No trace, no log, no evidence. This is one of the nastiest silent
bugs in Java.

Same for `break`, `continue`, and throwing a *different* exception from `finally`.

> **Rule: never `return`, `break`, `continue` or `throw` from a `finally` block.**
> `-Xlint:finally` warns about it (1.7).

### Trap 2 — `finally` overwrites the return value

```java
static int weird() {
    int x = 1;
    try {
        return x;               // the value 1 is captured HERE
    } finally {
        x = 2;                  // too late — the return value was already evaluated
    }
}                               // returns 1
```

Confusing enough that you should just not do it.

### Trap 3 — an exception in `finally` masks the original

```java
try {
    throw new IllegalStateException("original");
} finally {
    stream.close();             // if THIS throws, the original is lost
}
```

This is exactly the problem try-with-resources was invented to solve.

## ⭐ try-with-resources `Java 7`

**Reach for this automatically.** Any object implementing `AutoCloseable` can be declared
in the `try` header and is closed for you.

```java
// ❌ the manual version — and this is still subtly wrong
BufferedReader reader = null;
try {
    reader = Files.newBufferedReader(path);
    return reader.readLine();
} finally {
    if (reader != null) reader.close();     // if close() throws, it masks the real error
}
```

```java
// ✅
try (var reader = Files.newBufferedReader(path)) {
    return reader.readLine();
}   // close() called automatically, exception or not
```

**Multiple resources — closed in reverse order:**

```java
try (var in  = Files.newInputStream(src);
     var out = Files.newOutputStream(dst)) {
    in.transferTo(out);
}   // out.close() first, then in.close()  ← reverse of declaration
```

Reverse order matters: an outer wrapper must close before the thing it wraps (the
decorator stack from 2.10 — `BufferedReader` wrapping a `FileReader`).

**Effectively-final resources `Java 9`** — you can use an existing variable:

```java
var reader = Files.newBufferedReader(path);     // declared outside
try (reader) {                                  // ✅ Java 9+, must be effectively final (1.1)
    return reader.readLine();
}
```

### Writing your own `AutoCloseable`

```java
public class Connection implements AutoCloseable {
    @Override public void close() {      // note: narrowing the throws clause is allowed
        // release the resource
    }
}

try (var c = new Connection()) { ... }
```

`AutoCloseable.close()` declares `throws Exception`. **Override it with a narrower
`throws`** (or none), so callers aren't forced to catch `Exception` (4.2).

`Closeable extends AutoCloseable` and narrows to `throws IOException` — that's what
`java.io` uses.

## ⭐ Suppressed exceptions

**The case the manual version gets wrong.** What if the body *and* `close()` both throw?

```java
try (var r = new Resource()) {     // close() will throw "close failed"
    throw new RuntimeException("body failed");
}
```

try-with-resources keeps the **body's** exception as primary and attaches the close
exception as **suppressed**:

```
Exception in thread "main" java.lang.RuntimeException: body failed
    at Main.main(Main.java:5)
    Suppressed: java.lang.IllegalStateException: close failed
        at Resource.close(Resource.java:9)
        at Main.main(Main.java:5)
```

**Both are preserved.** The manual `finally` version loses the body's exception entirely.

Reading them programmatically:

```java
catch (Exception e) {
    for (Throwable s : e.getSuppressed()) {
        log.warn("also failed during cleanup", s);
    }
}
```

> **This alone is a sufficient reason to always use try-with-resources.** Correct
> suppression is genuinely hard to hand-write, and almost nobody does it right.

## Rethrowing, wrapping, and preserving the stack trace

### Always pass the cause

```java
// ❌ the original stack trace is GONE
catch (SQLException e) {
    throw new AppException("could not load user");
}

// ❌ slightly better — the message survives, the trace doesn't
catch (SQLException e) {
    throw new AppException("could not load user: " + e.getMessage());
}

// ✅ the cause chain is preserved
catch (SQLException e) {
    throw new AppException("could not load user " + id, e);
}
```

The third form produces the `Caused by:` chain you read in 1.5. Without it, you know
*something* failed and have no idea where.

**Your custom exceptions must have a `(String, Throwable)` constructor** (4.4).

### Adding context as you go up

Wrapping is most valuable when each layer **adds information the layer below didn't have**:

```java
// repository layer knows the SQL
catch (SQLException e) {
    throw new DataAccessException("query failed: " + sql, e);
}

// service layer knows the business operation
catch (DataAccessException e) {
    throw new OrderException("could not place order for customer " + customerId, e);
}
```

The final trace tells a story: *placing order for customer 42 → query failed → connection
refused.*

> **Don't wrap without adding anything.** `throw new MyException(e)` with no message is
> pure noise in the trace.

### Rethrowing the same exception

```java
catch (IOException e) {
    metrics.increment("io.failure");
    throw e;                        // ✅ rethrow — the original trace is intact
}
```

**Do not** `throw new IOException(e)` here — that adds a frame and gains nothing.

### More precise rethrow `Java 7`

```java
void f() throws IOException, SQLException {      // ✅ not "throws Exception"
    try {
        risky();                                  // declares IOException, SQLException
    } catch (Exception e) {
        log.error("failed", e);
        throw e;                                  // compiler knows it can only be those two
    }
}
```

Before Java 7 this required `throws Exception`. The compiler now analyses what the `try`
block can actually throw.

## ⭐ Why swallowing `InterruptedException` is a bug

```java
// ❌ this is broken
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // ignore
}
```

**What an interrupt means:** another thread is asking yours to stop — a shutdown, a
timeout, a cancelled task.

**The mechanism:** when `InterruptedException` is thrown, the JVM **clears the thread's
interrupted flag**. If you swallow the exception, the request to stop is now gone
completely — nothing upstream can tell it was ever made. Your thread keeps running
through a shutdown.

**Two correct responses:**

```java
// (a) propagate it — best, if your signature allows
void doWork() throws InterruptedException {
    Thread.sleep(1000);
}

// (b) restore the flag, then handle — when you cannot propagate (e.g. in a Runnable)
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();     // ← put the flag back
    return;                                 // and stop doing work
}
```

> Full treatment in Part 09. For now: **`InterruptedException` is never ignorable**, and
> `Thread.currentThread().interrupt()` is the line to remember.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `return` in `finally` | Silently discards the in-flight exception |
| Manual `finally` close | Loses the body's exception if `close()` throws |
| `throw new X(e.getMessage())` | Drops the stack trace. Pass `e` as the cause |
| `catch (Exception e) { throw new RuntimeException(e); }` around everything | Tunnelling (4.2) |
| Swallowing `InterruptedException` | Destroys the cancellation signal |
| Catch order least-specific first | Compile error — unreachable |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| Manual `finally { x.close(); }` | try-with-resources |
| `return` / `break` / `throw` in `finally` | Restructure |
| `throw new AppException(e.getMessage())` | `throw new AppException(msg, e)` |
| Empty `catch (InterruptedException e) { }` | Propagate, or restore the flag |

---

## Recap

| Construct | Key fact |
|---|---|
| Catch order | Most specific first — enforced |
| Multi-catch `A \| B` | `Java 7`. No subtype relation; `e` is implicitly final |
| `finally` | Never `return`/`throw` from it |
| **try-with-resources** | `Java 7`. Reverse close order. **Use it always** |
| Suppressed exceptions | Both body and `close()` failures preserved |
| Wrapping | **Always pass the cause.** Add context each layer |
| `InterruptedException` | Propagate, or `Thread.currentThread().interrupt()` |
