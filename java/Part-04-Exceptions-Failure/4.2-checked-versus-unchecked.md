# 4.2 — Checked versus unchecked

> **What this is:** A design debate you must be able to reason about, **because the whole
> ecosystem has taken a side** — and it's not the side the language designers intended.

---

## Coming from JS/Python/Dart

None of your languages have checked exceptions. **Java is the only mainstream language
that shipped them, and no major language since has repeated the experiment** — not C#,
not Kotlin, not Scala, not Swift (Swift's `throws` is closer, but untyped), not Rust
(which uses `Result` values instead).

That fact is itself the strongest piece of evidence in this debate.

---

## The concepts

### The original intent

The idea was genuinely good: **make failure part of the method signature.**

```java
public String readConfig() throws IOException
```

The signature now tells you: *this can fail because of I/O, and you must decide what to
do about it.* It's documentation the compiler enforces. Compare:

```python
def read_config() -> str:      # can this throw? read the source. And its callees.
```

In principle, checked exceptions give you the same benefit as a `Result` type in Rust —
failure is visible in the type system.

---

## ⭐ What went wrong in practice

Four failure modes, all extremely common in real codebases.

### 1. `catch (Exception e) { }` — the swallow

The compiler demands you handle it. The path of least resistance is to make the error go
away:

```java
try {
    doSomething();
} catch (Exception e) {
    // TODO handle this
}
```

**This is worse than no checked exception at all.** The failure is now completely silent —
no log, no rethrow, no evidence. The compiler forced an acknowledgement and got a lie.

Search any large Java codebase for empty catch blocks. You will find them.

### 2. Exception tunnelling

You're implementing an interface that doesn't declare your exception:

```java
interface Transformer { String apply(String s); }     // no throws clause

new Transformer() {
    public String apply(String s) {
        try {
            return Files.readString(Path.of(s));      // throws IOException
        } catch (IOException e) {
            throw new RuntimeException(e);            // ← tunnelling
        }
    }
};
```

So the checked exception gets wrapped in an unchecked one to get past the compiler. The
type system's guarantee is now gone, and you've added a layer of stack trace noise.

**This is so common it has a name**, and every Java codebase does it.

### 3. Signatures that leak implementation detail

```java
public interface UserRepository {
    User findById(String id) throws SQLException;     // ⚠️
}
```

You've just told every caller that this repository uses **JDBC**. Switch to MongoDB and
every caller breaks — not because the behaviour changed, but because the *implementation
detail* was in the signature.

```java
// ✅ an abstraction that doesn't leak
public interface UserRepository {
    User findById(String id);                         // throws DataAccessException (unchecked)
}
```

This is precisely what Spring did: it wraps every `SQLException` into an unchecked
`DataAccessException` hierarchy. That decision, in 2003, is a large part of why the
ecosystem moved.

### 4. ⭐ Checked exceptions and lambdas do not mix

**This is the one that settled the argument.**

```java
List<Path> paths = ...;

paths.stream()
     .map(p -> Files.readString(p))     // ❌ unhandled exception type IOException
     .toList();
```

**Why:** `Stream.map` takes a `Function<T,R>`, and `Function.apply` is declared as:

```java
R apply(T t);        // no throws clause
```

A lambda cannot throw a checked exception the functional interface didn't declare. And
**none of the JDK's functional interfaces declare any** (6.3).

The workarounds are all ugly:

```java
// (a) wrap inline — noisy, repeated everywhere
.map(p -> {
    try { return Files.readString(p); }
    catch (IOException e) { throw new UncheckedIOException(e); }
})

// (b) a helper that wraps for you — the standard workaround
.map(unchecked(Files::readString))

// (c) give up on streams and use a for loop
```

The JDK itself acknowledged this by adding **`UncheckedIOException`** in Java 8 —
an unchecked wrapper for `IOException`, created specifically because streams couldn't
handle the checked one.

> **That's the tell.** When the language designers ship an unchecked version of their
> flagship checked exception so the new API can work, the experiment has reported its
> result.

## ⭐ Where the ecosystem landed

| Library / framework | Choice |
|---|---|
| **Spring** | All unchecked. `DataAccessException` wraps `SQLException` |
| **Hibernate** | Switched from checked to unchecked in 3.0 |
| **Jackson** | `JsonProcessingException` is checked, but most usage wraps it |
| **Most modern libraries** | Unchecked |
| **New application code** | Overwhelmingly unchecked |
| **The JDK itself** | Still checked (`IOException`, `SQLException`) — it cannot change without breaking everything |

**Read that last row carefully.** The JDK is stuck with checked exceptions for backwards
compatibility (same constraint as erasure, 3.3), not because they're considered correct.

*Effective Java* still defends checked exceptions for genuinely recoverable conditions.
Most practitioners have moved further than that.

---

## ⭐ The defensible rule

If you want one rule you can justify in a code review:

> **Checked if the caller can plausibly recover. Unchecked otherwise.**

Apply it honestly:

```java
// ✅ checked — the caller genuinely might retry, use a cache, or prompt
public Config load(Path p) throws ConfigNotFoundException

// ✅ unchecked — the caller cannot do anything useful; this is a bug or an outage
public User findById(String id)          // throws DataAccessException
```

**The honest test:** *write the `catch` block you expect the caller to write.* If the only
sensible content is `log and rethrow`, or `wrap and rethrow`, the exception should be
unchecked — you're making every caller in the stack pay a syntax tax for nothing.

In practice, **very few conditions pass this test.** Which is why most new code is
unchecked.

## ⭐ Alternatives for *expected* outcomes

The deepest fix is to notice that **many "exceptions" aren't exceptional at all.**
"User not found" is a normal outcome of a lookup, not a failure.

### (a) `Optional` — for "might not be there"

```java
// ❌ absence as an exception
User findById(String id) throws UserNotFoundException

// ✅ absence as a value
Optional<User> findById(String id);
```

Full treatment in 6.7.

### (b) A sealed `Result` type — for "succeeded or failed, with detail"

Combining sealed types (2.8), records (2.6) and generics (3.2):

```java
public sealed interface Result<T> permits Ok, Err { }
public record Ok<T>(T value)             implements Result<T> { }
public record Err<T>(String code, String message) implements Result<T> { }
```

```java
Result<User> result = service.findById(id);

String message = switch (result) {                 // exhaustive — compiler-checked
    case Ok<User>(User u)         -> "Found " + u.name();
    case Err<User>(String c, String m) -> "Failed [" + c + "]: " + m;
};
```

**What you gain:** failure is a value, so it works in streams, it's exhaustively checked,
and there's no stack-capture cost (4.1). This is Rust's `Result` and Go's `(value, err)`,
expressed in Java.

**What you lose:** it doesn't unwind the stack automatically, so every layer must
propagate it explicitly. For deeply nested calls that's verbose.

> **Use it at boundaries** — an API handler, a validation layer, a parser — where the
> failure is expected and the caller must branch on it. Don't rewrite your whole codebase
> in it.

### (c) Error enums — for a closed set of failure reasons

```java
public enum ValidationError {
    EMPTY_NAME("Name is required"),
    INVALID_EMAIL("Email format is invalid"),
    AGE_OUT_OF_RANGE("Age must be 0–150");

    private final String message;
    ValidationError(String m) { this.message = m; }
    public String message() { return message; }
}

List<ValidationError> validate(User u) { ... }     // return ALL the problems at once
```

An exception can only report the **first** failure. A list of errors reports all of them —
which is what a form validation actually needs.

## ⚠️ Traps

| Trap | Reality |
|---|---|
| `throws Exception` on a method signature | Tells the caller nothing; forces them to catch everything |
| Wrapping every checked exception in `RuntimeException` | Tunnelling. At least use a **meaningful** type and keep the cause |
| Checked exceptions in an interface | Leaks implementation detail to every caller |
| Using exceptions for "not found" | That's an `Optional` |
| Assuming checked = safer | It produced empty catch blocks at scale |

---

## 💀 Dead / never use

| Thing | Instead |
|---|---|
| `throws Exception` | The specific type, or unchecked |
| Empty `catch` blocks | Handle, wrap with cause, or let it propagate |
| Checked exceptions in new library APIs | Unchecked, with a meaningful type |
| `UserNotFoundException` for a normal lookup | `Optional<User>` |

---

## Recap

| Point | |
|---|---|
| Intent | Make failure part of the signature |
| Failure 1 | Empty catch blocks — silent swallowing at scale |
| Failure 2 | Tunnelling — wrap in `RuntimeException` to escape |
| Failure 3 | Signatures leak implementation detail |
| Failure 4 | **Lambdas cannot throw them** → `UncheckedIOException` exists |
| Ecosystem | Spring, Hibernate, most new code: **unchecked** |
| The rule | Checked **only** if the caller can plausibly recover |
| Alternatives | `Optional`, sealed `Result`, error enums |
